## Description

## Finding

Found by the SO-31 spec implementer while reconciling spec §3's transfer funnel with the code. The lead confirmed it.

**The defect.** `Process.give` (`kernel/sysapi/src/system.saw`: the `Memory`, `IoMemory` and other overloads) disarms its typed wrapper before the syscall (`handle = …(NO_HANDLE)`) and never re-mints it. Its comment justifies that with "every failure of this syscall is a FAULT, so there is no path on which a disarmed-but-unsent word leaks". **That premise is false.** `process_give` in `kernel/core/dispatch.saw` answers statuses for resource conditions the caller could not have known: `NoResource` (the child's table or boot set is full) and `QuotaExceeded` (the child is at its handle budget). In both cases the kernel leaves the giver's entry untouched, so the capability is still in the giver's table, but **no typed wrapper names it**. It is stranded until teardown.

**The precedent.** `Waiter.give` handles the same shape correctly, per a user ruling recorded in its doc ("a full attachment table is a RESOURCE CONDITION, not a bug, so the caller keeps what it had"). It disarms first, and on a status refusal it builds a fresh wrapper around the word the kernel provably didn't consume and returns it in the error payload.

## Proposed fix

Give `Process.give` `Waiter.give`'s shape. Disarm before the syscall; on `NoResource` or `QuotaExceeded`, re-mint the wrapper and return it in the error payload. That changes the error type of every `Process.give` overload. Callers are in `root/` and `tests/`. The spec (SO-31 r2) states this intended behaviour.

## Acceptance

- [ ] A probe test first: give to a child whose table or quota is full. Today the giver can't name the capability afterwards.
- [ ] After the fix, the refusal returns the object and the giver can use it (for example, give it elsewhere).
- [ ] Every `Process.give` overload is covered; the system.saw comment states the real contract.
- [ ] Targeted give/quota cases pass on all three profiles.

**Lead review, SO-38.p1** (rebased onto current main).

**Probe, on the unfixed tree**
- Root gives masked System siblings to an unstarted child. The 13th give answers `QuotaExceeded` (the child's quota is `DEFAULT_QUOTA_HANDLES`).
- Root's teardown then counts `handles=8`, against the control's 7. The refused sibling is stranded in root's table, and no typed wrapper names it.
- `NoResource` can't be provoked through a give, because the default quota is below `MAX_HANDLES`.

**Fix (lead ruling: copy `Waiter.give` exactly)**
- All seven overloads return `Result<Void, (SosStatus, T)>`, and the catch re-arms on any status.
- The doc states the contract: every status `ProcessOp.Give` answers is a refusal that left the giver's entry in place, and every other failure faults.
- I checked that contract against `process_give`:
  - `boot_handle_room` returns `NoResource` before `move_handle` runs.
  - `move_entry` returns `NO_HANDLE` straight after `mint_handle` refuses, before `ref_object`/`unbind_handle`. `mint_refusal` then answers `NoResource` or `QuotaExceeded`.
  - The only path through `unbind_handle` ends in `op_ok()`.
- Two more false comments are fixed: `start(boot_tag:)`'s "answers with a status alone", and pipe.saw's "the same trade `Process.give` makes".

**Callers (tests/ only)**
- Print sites use `error.0`.
- Bare `try` sites in `Result<_, SosStatus>` functions use the pipe-cq/child-far destructure (`let (why, back) = move error; let _ = move back; return why`).
- As a result, every site now releases the returned object on a refusal instead of stranding it. No existing case reaches a refusal, so no transcript moves.

**spec.md:** the §3 "not yet enforced" sentence and the known-limits bullet are replaced by the behaviour, and §2.7's Give paragraph points at it.

**New case `give_full_returns`:** after the refusal, root uses the returned sibling ("the refused System still speaks"), drops it, and its teardown reads the control count `{seven}`.

**Runs:** 118/118 across three profiles at v0.21.0. They cover every `give_*` case, the quota cases, and the case for every edited package.

**Air: SO-38.p1 (r2 = r1 rebased), approved.** I checked the contract the hand-back rests on myself: every status `ProcessOp.Give` answers must leave the giver's entry bound.
- **The kernel side holds.**
  - `give_faults` has only fault paths: `BadHandle`, `AccessDenied`, `BadArg`, `BadState`, `DuplicateKey`.
  - `boot_handle_room` answers `NoResource` before anything moves.
  - `move_entry` returns `NO_HANDLE` straight after `mint_handle` refuses, before `ref_object` and `unbind_handle`.
  - `mint_refusal` answers only `NoResource` or `QuotaExceeded`, and `queue_boot_handle` is infallible.
  
  So the only path through the unbind ends in `op_ok()`, and a refused word is still the giver's.
- **The wrapper side:** each of the seven overloads disarms before the syscall and rebuilds around the same word on a status. All seven wrappers (`Memory`, `IoMemory`, `System`, `PipeInlet`, `PipeOutlet`, `PipeReply`, `PipeRequest`) hold only their handle, so nothing is lost in the rebuild.
- **The new case pins the contract.** Printing through the returned sibling would fault `BadHandle` if a refusal had consumed the entry, and the teardown count would read 8. `gave 12` is `DEFAULT_QUOTA_HANDLES` (under `MAX_HANDLES = 16`, so only `QuotaExceeded` is reachable, as the case says).
- **Call sites:** the 39 bare-`try` sites destructure, drop the returned object and return the status. The print sites read `error.0`, and the tuple drops with the object.
- **Docs:** the spec §3 rule, §2.7, the dropped known-limits bullet, `pipe.saw`'s stale "same trade" line, and `start(boot_tag:)`'s wording.
