## Description

## Finding

Found by the SO-31 spec implementer while reconciling spec §3's transfer funnel with the code. The lead confirmed it.

**The defect.** `Process.give` (`kernel/sysapi/src/system.saw`: the `Memory`, `IoMemory` and other overloads) disarms its typed wrapper before the syscall (`handle = …(NO_HANDLE)`) and never re-mints it. Its comment justifies that with "every failure of this syscall is a FAULT, so there is no path on which a disarmed-but-unsent word leaks". **That premise is false.** `process_give` in `kernel/core/dispatch.saw` answers statuses for resource conditions the caller could not have known: `NoResource` (the child's table or boot set is full) and `QuotaExceeded` (the child is at its handle budget). In both cases the kernel leaves the giver's entry untouched, so the capability is still in the giver's table, but **no typed wrapper names it**. It is stranded until teardown.

**The precedent.** `Waiter.give` handles the same shape correctly, per a user ruling recorded in its doc ("a full attachment table is a RESOURCE CONDITION, not a bug, so the caller keeps what it had"). It disarms first, and on a status refusal it builds a fresh wrapper around the word the kernel provably didn't consume and returns it in the error payload.

## Proposed fix

Give `Process.give` `Waiter.give`'s shape. Disarm before the syscall; on `NoResource` or `QuotaExceeded`, re-mint the wrapper and return it in the error payload. That changes the error type of every `Process.give` overload. Callers are in `root/` and `tests/`. The spec (SO-31 r2) states this intended behaviour.

## Acceptance

- [ ] A probe test first: give to a child whose table or quota is full. Today the giver can't name the capability afterwards.
- [ ] After the fix, the refusal returns the object and the giver can use it (for example, give it elsewhere).
- [ ] Every `Process.give` overload is covered; the system.saw comment states the real contract.
- [ ] Targeted give/quota cases pass on all three profiles.
