## Description

On the ESP32-C3, `irq_line_valid` (hal/riscv32-esp32c3/kernel/lib.saw) accepts every line up to `INTMATRIX_MAX_SOURCE`, except `IRQ_NONE`. That includes `SYSTIMER_TARGET0_SOURCE` (37), the matrix source the kernel routes to `TIMER_CPU_INT` for its own tick.

The risk: an `InterruptBind` on line 37 may succeed. Depending on how bind programs the matrix, the binder could then re-route or take over the kernel timer's source. The kernel's own timer is reported as `IRQ_TIMER`, which sits above the matrix range, so nothing user-facing needs 37.

Next steps:
- Probe it: bind 37 from root on the C3 and see what happens to the timer smoke.
- If the bind reaches the matrix, refuse kernel-owned sources in `irq_line_valid`.

Found by the SO-27 r2 implementer. The C3 is non-gating, hence low priority.

**Lead review, SO-43.p1.**

**Probe (not a failing one, and I'm saying so).** On the unfixed tree, root binds `SYSTIMER_TARGET0_SOURCE` (37), releases it, and then waits on a timer. The bind and the release both succeed, and the release really does unroute the kernel's tick source: `refs.saw` → `hal.irq_mask` → `IntMatrix().unroute(37)`. The timer wait still returns, but only because the C3 idle path polls SYSTIMER (`irq_poll`, `wait_for_irq`'s spin) instead of trapping. A preempting kernel or a trapping idle would lose its tick.

**Lead ruling:** fix it on that reasoning. It is the same class as `IRQ_TIMER`, which `interrupt_bind` already refuses.

**Fix**
- The C3 `irq_line_valid` refuses `SYSTIMER_TARGET0_SOURCE`, and its doc says why.
- New C3 smoke case `irq_timer_source_refused` asserts the `BadArg` fault ("argument outside its domain").

**Other boards (no change)**
- virt's timer is the CLINT, not a PLIC source.
- arm64's timer PPI is refused by the arch-free `line == hal.IRQ_TIMER` check.

**Runs**
- C3 smoke: 4/4 (flash for the new case: 96856).
- `no_root_image`, `irq_bad_line`, `interrupt_unbind` and `irq_early_ack`: 12/12 on the three gate profiles.

Approved patch SO-43.p1 (revision 1)

**Air: SO-43.p1, approved.**
- **The fix is complete for the board.** `irq_line_valid` has one caller, `interrupt_bind`'s `line == hal.IRQ_TIMER || not hal.irq_line_valid(line)` check. The kernel routes its tick at bring-up (`mtx.route(SYSTIMER_TARGET0_SOURCE, TIMER_CPU_INT)`) without consulting it, so refusing 37 there can't affect the kernel's own route. That route is the only matrix source the kernel claims on the C3: the other `route` call is `irq_unmask` for bound lines.
- **The C3 smoke passes 4/4** in my run at v0.21.0, `irq_timer_source_refused` included (flash 96856). The doc's reason, that masking a bound Interrupt on 37 would unroute the tick, matches `irq_mask` → `IntMatrix().unroute`.

Nit: the case imports `Process` and `Interrupt` but names neither.
