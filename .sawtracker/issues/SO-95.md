## Description

**From the user, Nov 13.** "Can we make the number of processes and memory ranges configurable by image? So use defaults unless overridden by an image's config? ... Is there an image description file somewhere which defines which processes are loaded and their addresses and their memory ranges?"

**Today there is no such file.** What a system image holds is spread over four places:
- a case's entry in `tools/sos_runner.py` (`root_pkg`, `children`, `pool`, `device`, `tick`), which is the only list of what goes in an image;
- the runner's per-board table (`ESP32S3_ARCH` and its siblings): where a child's RAM region, the pool and the device window are, as numbers;
- one linker script per resident image (`hal/*/user/root.ld`, `child.ld`, `child2.ld`, `child3.ld`), each repeating one of those numbers as its `ORIGIN`, because an image is linked for the one address it runs at;
- each package's `Saw.toml` (`[sos]`: the linker script, the native sources, the priority map).

The runner builds each package to a `.sosimg`, appends the children to the kernel, and generates the boot region table (`_region_rows`): a row per child blob, a row per child's RAM, the pool, the device window. The kernel mints one handle per row and interprets nothing; root is written to know which ordinal is which. The limits are constants in `kernel/core/limits.saw`, the same for every image.

**The idea, as a sketch for a design.** One description file per system image, read by the build, that states:
- the board, the root package and each child package with its flash slot and its RAM region;
- the pool, and each device window and interrupt line by name;
- limits, each a default unless stated: slab floors (processes, Waiters, pipes and the rest) and each process's quotas (mappings, device windows).

From it the build would generate the region table, each image's link addresses (so the per-slot linker scripts stop being hand-kept), and the table root reads to know what each row is.

**What a design has to settle.**
- How a limit reaches the kernel. Slab floors can already grow at run time by donation, so root could apply the image's numbers at start with no kernel change; the alternative is a record in the boot table that the kernel applies before root runs. Compiling the kernel per image is the third way.
- Per-process quotas have no door today: §2.9 says there is no per-create quota argument. An override is a spec change, and it is the launcher's authority to grant, not the image's to claim.
- Whether the runner's cases become description files, or build one in memory from the keys they have now.
- The file's place and format, and what `make` target turns one into a flashable image for a board.

**Why now.** The box (SO-78) needs four children on the ESP32-S3, and SO-77's unit U5 would otherwise hand-write three more linker scripts and runner rows. This would be U5's shape.

Design document first, to the user, before anything is built.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":3037,"created":"1794601082","id":"c1"} -->
**The user widened this, Nov 13.** "This is probably a good time to think about images and packaging. Ideally, we should be able to create a new repo which defines one or more images and have those images define the hardware, which drivers it needs from the common drivers in the sawos repo and which new drivers and processes also need to be loaded from the repo itself."

So the design covers packaging as well as the file. What the code says today, for the designer:
- **Packages can already cross repositories.** Blade takes `{ path = ... }` and `{ git = ..., version = ... }` dependencies, so a product's program can depend on `sos` and on a driver's protocol package in sawos.
- **The kernel is not a package.** The runner compiles `kernel/main.saw` with `sawc` directly, naming `kcore`, the board's `hal`, `sosrt` and `sosabi` by module path into this tree (`_build_elf`). Nothing outside this repository can build a kernel.
- **The only image builder is the test runner.** Building, stitching and the boot table are woven into `tools/sos_runner.py`'s cases.
- **A board is three things in three places:** its HAL directory, its user linker scripts, and its table in the runner (addresses, device window, interrupt line).
- **Every root is hand-written** to know its boot rows by ordinal and what to hand each child.
- **A program is linked for the address it runs at,** so a driver from sawos is built per image, from source. Kernel, `sos` and every program then come from one sawos revision, which is what the vDSO discipline (§5.7) wants: no binary compatibility is promised or needed.

The lead's sketch of the parts, for the design to attack:
1. **A board description** in sawos: memory map, flash slots, device windows and interrupt lines by name. An image names a board and names devices, never addresses.
2. **An image description** in the product's repository: the board, limits (defaults unless stated), and each process with its package (from sawos or local), the devices it is given, and which driver it is a client of.
3. **A driver's own statement of what it needs** (windows, lines, quotas), beside its package, so the build can refuse an image that does not supply them.
4. **An image builder** as a tool of its own, which the test runner then uses too, so there is one path.
5. **A root that is generated or table-driven:** it launches each process and hands out windows, lines and connections as the description says. The description is root's policy, fixed at build time; nothing is parsed on the target. A product may still supply its own root.
6. **A pin on sawos** in the product's repository, as `sawlang.pin` is here, and a way for the builder to find the sawos tree.
7. **The product's own test:** boot its image under the emulator and diff the console, with the runner's harness as a library.

Questions the design brings to the user: whether a new board can live outside sawos or boards stay here; whether root is generic by default; what is in for the box's first run on the part and what follows it.

**Lead, Nov 13: the design is written and published as the tracker doc `SO:images-and-packaging`** (a copy is at `.claude/lead/so95-design.md`). It changes nothing in the repository. The user and the reviewer read it before anything is built.

**Its verdict.** The seven-part shape holds, with three changes:
- **Limits reach the kernel by compiling it per image.** The runner already compiles a kernel per case; `kcore.limits` would read a generated `kconfig` module. Donation stays for growth at run time. (Checked by compiling the split with the pinned compiler.)
- **A per-process quota door:** `ProcessOp.QuotaSet` and `QuotaGet` under a new right. A launcher sets a quota only on a child it has created and not started, never above its own. This replaces §2.9's "no per-create quota argument".
- **A driver's pins arrive as a build-time module the image supplies,** not as a message from root.

**The parts.** `hal/<board>/board.toml` in sawos; a `process.toml` beside each package saying what it needs at boot (tags, windows, lines, endpoints, quotas, build inputs), which the builder checks an image against; `images/*.toml` and a `sawos.pin` in a product's repository; one builder, `tools/sosimage/`, that the test runner uses too; a stock root driven by a generated Saw module, replaceable. Root's interfaces are written in three layers (kernel contract, generated per image, userspace convention) with proposed spec text for §2.7, §2.9, §11 and §12, including the boot set's drain order, which the kernel implements and the spec does not state.

**Where it meets text or code that says otherwise (its §0.1).**
- §5.5 and §5b.1 call the hand-kept per-child linker scripts deliberate; those sentences change.
- SO-77's design has root route the servo pads and turn on LEDC's clock; a generic root cannot carry device code, so the PWM driver is given four windows through the quota door. Four is exactly the mapping budget.
- Blade's git dependencies cannot reach a package in a subdirectory of sawos, so a product uses path dependencies through a `.sawos` link the resolver writes.
- **One sawlang change:** three `blade build` flags (`--linker-script`, `--out-dir`, `--module-path`), so a release and a pin bump sit on the box's path.

**Its nine questions for the user, each with the designer's recommendation** (§13): how a product finds sawos (a pin and a copied resolver); how a driver gets its pins (a build-time module); who routes the servo pads (the PWM driver); what the stock root does when a child ends (report; stop the machine when a child marked `shutdown` ends or all have; no restart yet); per-image limits by compiling the kernel per image (yes); the quota door only before `start` and capped by the launcher's own (both); the three Blade flags ahead of the box (yes); where the box lives (its own repository, plus a gate case here that builds a small product copied out of the tree); root's region per image (not yet).

**Its order of work** (§12): U1 the builder library and `board.toml`, every transcript and image size unchanged; U3 the Blade flags (sawlang); U2 the description format and an existing case built from a file, byte-identical; U5 per-image limits; U6 the quota door (spec first); U4 generated link addresses, several children on the ESP32-S3; U7 `process.toml`, the stock root, the UART drivers finding their registers through `Mapping.base()`; U8 product support. SO-77's unit U5 is replaced; its drivers come after U4, U6 and U3; SO-78 is last, as the first product.

**Not verified by the designer:** no emulator run; Espressif's `ld.lld` with `INCLUDE`; builds through the link for Xtensa and arm64; the generated plan's exact Saw shape; whether the box's processes fit 24 to 32 KiB regions.

**User, Nov 13, on the design's question 5 (limits by compiling the kernel per image):** "Can we define a board info symbol which is defined per board that every kernel references? Then the kernel can stay the same, we just link in a config table. Would that work?"

The lead's reading: yes, on two conditions the designer is now checking by trying. The kernel is compiled once per board; an image's limits are a small table in an object the builder generates and links in, as the boot region table already is. (1) At boot the kernel gives each slab kind an extent sized from the table, through the code a donation already runs, from kernel-owned RAM. (2) The kernel exports each slot's size so the builder can size that RAM and refuse an image that does not fit. What a table cannot reach are arrays inside every process body (the handle table, the grant record) and what a HAL sizes; those stay per-board constants, and the box needs none of them. The compile-time asserts in `limits.saw` become checks in the builder, with a boot refusal as the backstop. Revision 2 of the design reworks its section 6 around this and recommends one way.

**Lead, Nov 13: revision 2 of the design is published** (tracker doc `SO:images-and-packaging`, revision 2; copy at `.claude/lead/so95-design.md`). It takes in the user's two rulings since revision 1: tools in Saw where possible, and limits as a linked-in table under a kernel compiled once per board.

**What changed.**
- **The kernel is compiled once per board, and an image's limits are a table linked in beside the boot region table.** At boot the kernel grows each slab by one extent from a reserve the builder assigns, through the code `SlabDonate` already runs. The designer built it into a scratch copy of the kernel (about 70 lines): on riscv32 and arm64 `process_donate`'s root found a fourth process before any donation, and the unchanged case passed. The per-image `kconfig` compile moves to the rejected alternatives.
  - The table reaches all thirteen slab kinds and the children's quota defaults. Per board, not per image: the handle table and boot set, the grant record, arm64's domain pool, root's region and the stack length. The box needs none of them raised.
  - An image can raise a limit and not lower it: extent 0 stays the board's floor.
  - The kernel exports each slot's size for the builder. Saw cannot yet export a struct's size as a constant, so until it can the number is a literal per board, checked against the slab's own geometry at every boot.
  - Wrong numbers are refused by the builder, by name, before the link; the kernel's boot check is the backstop.
  - The design says the boot table "goes to version 4"; it was written against main before SO-92.p2 merged, which took version 4. The limits block makes it version 5.
- **The builder is a Saw program,** `tools/sosimage`, a hosted Blade package. The runner builds it after Blade and calls it per case with a JSON description; its first unit takes over the runner's stitching with every transcript unchanged.
- **What stays Python, each with its reason:** the two resolvers (they run before any Saw compiler exists, and building that compiler needs Python); the emulator harness until `std.process` can run an interactive child; the runner's case table until both of those and a complete TOML reader exist. The runner moves in four steps, not one.

**Saw gaps, filed in sawlang's tracker** as the user asked, each with its program, the error text and how badly sawos needs it: SL-1092 (`libs/toml` misreads the description formats; blocks hand-written descriptions), SL-1098 (`blade build` flags, and unknown flags ignored silently; blocks generated link addresses), SL-1093 (`std.process`: no working directory, stdin, streamed stdout, kill or deadline; blocks a Saw harness), SL-1095 (a struct's size as a constant), SL-1099 (a git dependency on a package in a subdirectory), SL-1094 (no `is_dir`), SL-1096 (no hex formatting), SL-1097 (`Map.get` needs `Copy` values), SL-1100 (no portable dependency on a toolchain library), SL-1101 (no SHA-256).

**Its questions for the user are now eleven** (section 15), each with a recommendation. New or changed: accept the linked table's terms (yes); the kernel's reserve as a RAM range the builder assigns (recommended) or a linker-sized section; TOML through a completed `libs/toml`, with JSON for the machine-written path (recommended); sawlang takes the Blade flags and the TOML work ahead of the box (yes; `std.process` can follow); the runner moves stepwise (yes); the resolvers stay Python (yes).

**Order of work** (section 14): the Blade flags (sawlang) beside U1, the Saw builder, transcript-identical; `libs/toml` (sawlang) beside U2, the per-board kernel and the linked table, and U5, the quota door (spec first); U3 the description formats; U4 generated link addresses; U6 `process.toml` and the stock root; U7 product support; U8 judging and then booting in Saw; SO-78 as the box's repository. SO-77's drivers sit beside U4 and U6.

**Not verified by the designer:** the prototype on the flat profile or the ESP32-S3 (its slot sizes are unmeasured, so the box's reserve is not computed); the full gate; Espressif's `ld.lld` with `INCLUDE`; hosted Saw on Linux; whether the box's processes fit their regions.
