## Description

**From the user, Nov 13.** "Can we make the number of processes and memory ranges configurable by image? So use defaults unless overridden by an image's config? ... Is there an image description file somewhere which defines which processes are loaded and their addresses and their memory ranges?"

**Today there is no such file.** What a system image holds is spread over four places:
- a case's entry in `tools/sos_runner.py` (`root_pkg`, `children`, `pool`, `device`, `tick`), which is the only list of what goes in an image;
- the runner's per-board table (`ESP32S3_ARCH` and its siblings): where a child's RAM region, the pool and the device window are, as numbers;
- one linker script per resident image (`hal/*/user/root.ld`, `child.ld`, `child2.ld`, `child3.ld`), each repeating one of those numbers as its `ORIGIN`, because an image is linked for the one address it runs at;
- each package's `Saw.toml` (`[sos]`: the linker script, the native sources, the priority map).

The runner builds each package to a `.sosimg`, appends the children to the kernel, and generates the boot region table (`_region_rows`): a row per child blob, a row per child's RAM, the pool, the device window. The kernel mints one handle per row and interprets nothing; root is written to know which ordinal is which. The limits are constants in `kernel/core/limits.saw`, the same for every image.

**The idea, as a sketch for a design.** One description file per system image, read by the build, that states:
- the board, the root package and each child package with its flash slot and its RAM region;
- the pool, and each device window and interrupt line by name;
- limits, each a default unless stated: slab floors (processes, Waiters, pipes and the rest) and each process's quotas (mappings, device windows).

From it the build would generate the region table, each image's link addresses (so the per-slot linker scripts stop being hand-kept), and the table root reads to know what each row is.

**What a design has to settle.**
- How a limit reaches the kernel. Slab floors can already grow at run time by donation, so root could apply the image's numbers at start with no kernel change; the alternative is a record in the boot table that the kernel applies before root runs. Compiling the kernel per image is the third way.
- Per-process quotas have no door today: §2.9 says there is no per-create quota argument. An override is a spec change, and it is the launcher's authority to grant, not the image's to claim.
- Whether the runner's cases become description files, or build one in memory from the keys they have now.
- The file's place and format, and what `make` target turns one into a flashable image for a board.

**Why now.** The box (SO-78) needs four children on the ESP32-S3, and SO-77's unit U5 would otherwise hand-write three more linker scripts and runner rows. This would be U5's shape.

Design document first, to the user, before anything is built.

**The user widened this, Nov 13.** "This is probably a good time to think about images and packaging. Ideally, we should be able to create a new repo which defines one or more images and have those images define the hardware, which drivers it needs from the common drivers in the sawos repo and which new drivers and processes also need to be loaded from the repo itself."

So the design covers packaging as well as the file. What the code says today, for the designer:
- **Packages can already cross repositories.** Blade takes `{ path = ... }` and `{ git = ..., version = ... }` dependencies, so a product's program can depend on `sos` and on a driver's protocol package in sawos.
- **The kernel is not a package.** The runner compiles `kernel/main.saw` with `sawc` directly, naming `kcore`, the board's `hal`, `sosrt` and `sosabi` by module path into this tree (`_build_elf`). Nothing outside this repository can build a kernel.
- **The only image builder is the test runner.** Building, stitching and the boot table are woven into `tools/sos_runner.py`'s cases.
- **A board is three things in three places:** its HAL directory, its user linker scripts, and its table in the runner (addresses, device window, interrupt line).
- **Every root is hand-written** to know its boot rows by ordinal and what to hand each child.
- **A program is linked for the address it runs at,** so a driver from sawos is built per image, from source. Kernel, `sos` and every program then come from one sawos revision, which is what the vDSO discipline (§5.7) wants: no binary compatibility is promised or needed.

The lead's sketch of the parts, for the design to attack:
1. **A board description** in sawos: memory map, flash slots, device windows and interrupt lines by name. An image names a board and names devices, never addresses.
2. **An image description** in the product's repository: the board, limits (defaults unless stated), and each process with its package (from sawos or local), the devices it is given, and which driver it is a client of.
3. **A driver's own statement of what it needs** (windows, lines, quotas), beside its package, so the build can refuse an image that does not supply them.
4. **An image builder** as a tool of its own, which the test runner then uses too, so there is one path.
5. **A root that is generated or table-driven:** it launches each process and hands out windows, lines and connections as the description says. The description is root's policy, fixed at build time; nothing is parsed on the target. A product may still supply its own root.
6. **A pin on sawos** in the product's repository, as `sawlang.pin` is here, and a way for the builder to find the sawos tree.
7. **The product's own test:** boot its image under the emulator and diff the console, with the runner's harness as a library.

Questions the design brings to the user: whether a new board can live outside sawos or boards stay here; whether root is generic by default; what is in for the box's first run on the part and what follows it.

**Lead, Nov 13: the reviewer checked revision 3; t2 to t12 are resolved, t1 stays open, and the lead changes its recommendation on question 2.**

Revision 3's answer to t1 gives root one peripheral row to carve windows from. The reviewer's reply: on the ESP32-S3 that row is the megabyte from 0x6000_0000, which also holds the console UART, both flash controllers, **the eFuse controller**, the RTC, the system timer, the permission registers and the interrupt matrix. The stock root carves by name and gives only what the image lists, but a root a product brings would hold the whole range, and on a protected board the same rule would put the interrupt controller in root's hands. Narrower rows cannot join GPIO and the IO MUX without the eFuse block between them, so rows held to the devices an image lists put the box back at twelve rows.

**Lead's recommendation for question 2 is now (b): rows name only the devices an image uses, and `MAX_HANDLES` is raised for the board** (the reviewer's view too). A root should not be handed registers no process of the image asked for, least of all the eFuse controller on a part whose owner has ruled that nothing may write eFuses. The cost is a larger handle table in every process body on that board, which the design must price (the table is an array in the body, so it multiplies by the process count). Option (c), minting a boot row's handle only when it is drained, stays the alternative that needs a kernel and spec change.

**User, Nov 14, on the linked-in limits table:** "Can we also provide rw slab areas sized to the limits? That would remove the need for the donation at boot."

**Lead's reading: yes, and it is simpler than revision 3's reserve.** The builder already reads each slab's slot size from the kernel's symbol table. So beside the numbers it can emit the storage: one zero-filled, writable section per slab kind, as long as that kind's limit times its slot size, linked into the kernel's own RAM by a rule in the board's link script (the sawlang lead's note on SO-95 says a section placed by name needs such a rule on the ESP32-S3). The kernel finds each area by its section's start and stop symbols.

What it removes from revision 3:
- the reserve: a RAM range the builder assigns from the board's process memory;
- the kernel's three checks on it (that every extent fits, that it is RAM the board can give, that it misses root's region). The linker places the areas inside the kernel's region, so they cannot meet a process, and one that does not fit is a link error that names the section;
- most of the limits block: a section's length is the limit (length over slot size is the slot count, and a remainder is a boot refusal, which also catches a builder and a kernel that disagree about a slot's size). The children's quota defaults remain numbers.

What it does not remove, to be said plainly:
- **A pass at boot.** A free slot is not all zeros (a `Memory` slot's pool is `NO_MEMORY`, for one), so the kernel still writes each area's slots vacant before use, through the code that installs a donated extent. It is an initialisation, not a donation: no `Memory` object, nothing taken from a pool.
- **Where the bytes come from.** They come out of the kernel's RAM region as the board's link script draws it, not out of process memory. An image can raise limits only as far as that region has slack, unless the board's split between kernel and process memory moves, which is a board matter.

Two depths, for the design to weigh:
- **(a) Beside the compiled floor.** Each slab keeps its inline extent 0 at the board's floor and takes its linked area as one more extent. The smallest change; limits stay raise-only and each raised kind still spends one of its four extents.
- **(b) In place of it.** The linked area is the slab's only storage and nothing is compiled in. An image can then lower a limit as well as raise it, and the kernel's `.bss` is exactly what the image asks for, with the kernel's code still built once per board. The cost is in the kernel: every slab access goes through a base and a count (as slots above the floor already do through `Slab.locate`), and every compile-time assert that relates a floor to another number becomes a builder check with a boot refusal behind it.

Not verified: nothing here has been built. The designer is asked to prototype it in scratch, as it did the limits table, and to rework section 6 in a revision 4 that also takes the open thread t1 (rows that name only an image's devices, and `MAX_HANDLES` raised for the board, with what the megabyte at 0x6000_0000 holds shown to the user and the cost of a larger handle table priced).

**User, Nov 14, a general rule:** "Generally where a design is constrained by a limit, e.g. the process handle table size, I think we should use the simpler design and increase the limit to handle it."

It goes into revision 4 as one of the fixed points. The designer is asked to list every place the design bends to fit under a number, say for each whether the number is hardware or policy, take the simpler design with the number raised wherever it is policy, and give what raising it costs (bytes per process body, the kernel loop it lengthens with interrupts masked, the cases that reach it on purpose), with a table of limits.

The lead's caveats, told to the user and not ruled on: a hardware wall (the PMP boards' eight protection rows, a board's RAM, arm64's static domain pool) is not ours to raise; a number that is the same everywhere only because the smallest board set it can be set per board or per image; and what a driver may reach is a question of authority, not of a limit, so the PWM driver's windows are weighed on their own.

**User ruling, Nov 14:** "I definitely think we should set the limits per board: more hardware protection rows based on the hardware limits, more RAM means more potential processes, etc."

So limits are per board, a fixed point for revision 4 and not a question in it. Each limit gets a value where the board is described, derived from the hardware where a hardware fact stands behind it (the protection-row budget from what the board can hold, the slab floors from its RAM, the handle table from what a root there must hold), and an image raises or sets its own within what its board allows. The designer lists every number that is one value everywhere today only because the smallest board set it (`MAX_GRANT_ROWS`, `MIN_GRANT_ROW_BUDGET`, the mapping quota default tied to them, `MAX_HANDLES`, the slab floors, the stack length, the child region), who owns each, the per-board values with reasons, which asserts stay compile-time, and what it means for the suite, whose cases run on three profiles with one set of numbers and often reach a limit on purpose. A process states what it needs, and the builder refuses an image on a board that cannot give it.
