## Description

**Two lines of `tools/sosimage` that no test holds, from the approval of SO-104.p1.** Tests only; the builder's behaviour does not change.

1. **`flash_image`'s refusal of a flash image whose first byte is 0xE9** (the header byte of an esptool-format image, which the ROM would take as a second-stage loader), and its sibling in the same routine, the check of the direct-boot magic at its offset. With the 0xE9 test removed from the source, `blade test` passes, and the ESP32-S3 smoke is outside `make sos-test`. The tests in `tests/flash_check.saw` are `check_in_place`'s. Add tests of `flash_image` on small hand-made inputs: an image that would begin with 0xE9 is refused with its message; a wrong or missing magic is refused with its message; a good one is written, with the bytes and the "used" and "end" figures as expected.

2. **The page a pool blob is placed on and padded to** (`POOL_BLOB_ALIGN`). With 16 in place of 4096, `blade test` passes and so do the gate's cases that carry a pool blob, on riscv32. Hold it in the builder's tests by the stub's text (the `.balign` before and after a blob that a pool row names, against one an ordinary row names), and say in the hand-back whether a gate case could hold it too (one that needs the whole blob as a single run of whole pages on arm64, where the grain is a page).

For each: remove or change the line alone, see the new test red, restore it, see it green. Run `blade test` in `tools/sosimage` the way the runner does (read how `tools/sos_runner.py` builds and tests the package, including the `.sawlang` link and the `SAWC` it sets), then a full `make sos-test` once, since that is where the builder's tests run in the gate.

Not here: refusing a number the target's word cannot hold (the formats' unit), and a repeated key in a description (sawlang's JSON reader, filed there).

**Lead: SO-107.p1 is up.** Two test files in `tools/sosimage/tests/`; no source changed. `blade test` is 7 of 7, and a full `make sos-test` is 789.

- **`flash_image.saw`** calls `flash_image` on a hand-built ELF with a small flash and the magic at its offset: a good image is written with the size, the "used" and "end" figures, the segment bytes in place, erased bytes between and after, and both magic words; no magic and a wrong magic are each refused with their messages; a first byte of 0xE9 with the magic present is refused with its message. With the 0xE9 test removed from `flash.saw` alone, this file fails (the refusal's message is absent); restored, it passes.
- **`stub_alignment.saw`** calls `regions_stub` for an image of two children: the blob a pool row names has `.balign 4096` before its start label and before its end label; the blob an ordinary row names has none between its labels; exactly two such lines in all, and the same with the rows the other way round. With `POOL_BLOB_ALIGN` as 16 alone, this file fails; restored, it passes.

**Could a gate case hold the alignment too?** By reading, `pool_boot` on arm64 should: it takes the blob pool's whole run and runs the child from it, and arm64 rounds a pool's base up to a page, so a blob aligned to 16 would lose its first page. Not run with the mutant; the builder's test holds the line either way.

**Changes requested (reviewer, Nov 14), revision 1: one case the file's own comment promises and does not make.** Both tests are otherwise right and hold what SO-107 asked for. Probe and log: `.build/scratch/air-review/so107_p1/` on the Air.

**The gap.** `flash_image.saw`'s third case is headed "A magic that is not the board's, in either of its two words", and `magic_seg` writes the one word twice, so both words are wrong together. `flash_image` refuses when either differs (`m0 != magic || m1 != magic`), and the message says "twice". With the test changed to read one word alone, the file passes:

```
only the first magic word checked            exit 0  SURVIVES
only the second magic word checked           exit 0  SURVIVES
```

Two cases close it: the right word then a wrong one, and a wrong one then the right, each with its message (`read 0xaedb041d 0xaedb041e` and the reverse). `magic_seg` needs a second word for that.

**While the file is open, the routine's third refusal.** "a segment loads at ..., outside the flash window" has no case either: with that test removed from `flash.saw` the seven tests pass. What it guards is a panic in place of a message: a segment past the window would index the image out of range, and one below it would underflow the offset. A segment that starts inside and runs past the end (`IBUS + 0x7FE`, four bytes, in this layout) and one below `IBUS` hold it. This is outside what SO-107 named, so say if you would rather it were its own issue.

**Checked: `blade test` is 7 of 7 on the patch, and twelve one-line changes to the source, the tests after each.** Nine fail a test:

- in `flash_image`: the 0xE9 refusal removed, the magic refusal removed, erased bytes as 0x00, `used` counting one per segment, `end` never moving;
- in `stub_alignment`: `POOL_BLOB_ALIGN` as 16, no padding after a pool blob, every blob treated as a pool's, no blob treated as a pool's.

So the two lines my SO-104 verdict named are held, both ways round for the alignment (the page before and the page after, and only on the pool's blob). The three that pass are the two magic words above and the window.

**Not run:** `pool_boot` on arm64 with the alignment mutant, which the note says should hold it too; the builder's test holds the line either way, as the note says.
