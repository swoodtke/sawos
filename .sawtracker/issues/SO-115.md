## Description

**ESP32-S3: save a thread's windowed registers and its FP state lazily, as one unit.**

**User ruling, Nov 14:** "If/when we do the lazy saving, we should do both the FP and windowed registers."

**What lazy means here.** A trap from a thread saves only what the kernel itself will use (the current window's sixteen registers), and the rest of the thread's register state (the other 48 physical registers of the window file with `WINDOWBASE` and `WINDOWSTART`; the FP registers `f0`-`f15`, `FCR`, `FSR` and `BR`) is saved only when the thread is moved off the processor, and loaded only when a different thread is moved on. A trap that returns to the same thread touches none of it.

**What exists today.**
- **arm64 already does this for FP/SIMD** (spec §7, Profile B's contract; `hal/arm64/kernel/lib.saw`, `fp_trap`): EL0 access traps until a thread's first use, the kernel executes no FP instruction and saves nothing on kernel entry, and a switch saves the outgoing thread's state only if it has used FP. That scheme is the model.
- **The ESP32-S3 has no FP state handling yet.** The networking design's unit K2 (FP and `BR` per S3 thread, lazily, on the coprocessor-disabled trap) is the FP half and has not been built.
- **Windowed threads (SO-112)** are being designed. Its revision 1 saves all 64 registers on every trap (87 to 213 instructions a round trip; estimated at 0.1 to 0.35% of `kill_churn`). The designer is evaluating the lazy variant of the windowed half (an owner of the live 48; every event that must update it; the ROM stub, which rotates the register file and so may run only when no thread's state is live), and its findings go on this issue.

**What this unit is.** One owner bookkeeping for a thread's off-processor state on the S3, used by both halves: the windowed registers and the FP state. Whichever half is built first, the other joins the same mechanism; they are not two schemes.

**To decide (the user):** whether the windowed half is built lazily now, in SO-112, with the FP half joining it when K2 is built, or whether SO-112 ships the eager save and both halves become lazy together later under this issue. The lead's first answer to the user said FP state is not saved lazily today; that is true of the S3 and false of arm64, and the user's ruling above was given on that answer.

**Acceptance**
- [ ] the user's decision on when the windowed half goes lazy
- [ ] a design for the shared owner bookkeeping, with its attack (a stale owner; a freed frame slot reused; kill and exit of the owner; the idle path)
- [ ] cases and mutants in the S3 smoke for each event that updates the owner, for both halves

**User ruling, Nov 15:** "do the full save/restore for all 64 registers for now." Given after the lead corrected its earlier answer (arm64 already saves FP state lazily; the ESP32-S3 has no FP handling yet). So SO-112 builds the eager save of all 64 registers on every trap, as `SO:windowed-threads` revision 1 designs it, and the lazy variant of the windowed registers is deferred to SO-115, to be built together with lazy FP state on the S3. The designer's evaluation of the lazy variant (sound by reading, not run; 93 instructions for a trap that returns to the same thread and 221 for one that switches, against 213 eager) is kept in the design as the alternative considered, for SO-115 to start from.
