## Description

**Legs for lines the review of SO-92.p5 found unheld. All are older than that patch; none is a known fault.** Tests only, unless a leg turns up a fault, which stops the unit.

Each line below survives a one-operator mutant on all three whole suites (the reviewer's runs, listed on SO-92):

1. **First fit from a free range longer than the request** (`kernel/core/objects.saw`, the branch of `pool_cut` that serves from the free list). Seven mutants survive, the worst being the remainder's base left where it was, which **hands two live allocations the same bytes**. The others: the remainder a grain too far, the test for an exact fit (`!= 0` and `false`), the list link, the node not freed on an exact fit, and a grain more recorded as on loan. A case that frees a range, allocates less than it from it, and then checks the ledger (`available`), that the remainder is still served and that no two live allocations share a byte (a mark written through each mapping, as `pool_ops`' neighbours do).
2. **A donated pool's free-list nodes return to their slab** (§2.8; `memory_retire_donated`), and **a freed pool's nodes** (`pool_drop_nodes`). Both need a pool that holds nodes with nothing out, then the node slab's room read before and after.
3. **`Memory.map`'s own right** (`dispatch.saw`, the check that the handle carries `Map`): `if false` survives. A handle minted without `Map` is refused.
4. **The stack row's hold on its destination** (`loader.saw`, the stack grant recorded with its region): recorded with no region, nothing notices. A destination whose only row is the stack is still held until the child's death.

**How.** The reviewer's ledger probe (a random sequence of allocate and release against two pools, checked against a model) already tells five of the seven first-fit mutants from the kernel on riscv32; it arrives in chat as a diff and is the construction to read. Prefer a deterministic case to a random one: a fixed sequence that reaches each branch, with the model's numbers as expected lines. Every leg is shown red under its mutant alone on each profile it runs on, and the one-operator hunt is run over the whole of `pool_cut`, `pool_return`, `pool_insert_range` and `pool_fold_frontier` afterwards, survivors closed or argued. No host-time value.

Depends on SO-92.p5 (the pool code's final shape). SO-94 changes `pool_return`; if the user rules on it first, do it in the same unit.

**Lead: SO-101.p1 is up.** Tests, a rename and one dead function removed; no kernel behaviour changed and no fault turned up. Gate on the lead's machine: 789 / 6 / 39 (main's 779 and ten new rows); 305 named cases, none repeats a key.

**Cases.**
- `pool_first_fit` (three profiles): holes of 1, 2, 3 and 4 pages with a live page between them and the frontier spent. Each page carries its own number in its first word, so a new allocation's mapping says where it landed, and after every step each live allocation still reads its own mark. It takes an exact fit from the middle of the list, two pages off a range of three, an exact fit at the head, the page the range of three kept (at the address the model says), and a page off a range of four; then the releases: a remainder rejoining what it was cut from, new nodes at the head and in the middle, a join below, above and both, a fold into the frontier with and without a node before it; forty exact fits and forty three-into-one merges, more than the node slab holds; and at the end the whole pool, nothing out, is accepted as a donation.
- `pool_nodes_home` (riscv32 and the flat profile, as `slab_donate_free_nodes`): two pools left with nothing out and two nodes each; one is released and one donated, and the node slab's room, read as how many holes a pool's list takes before a release is dropped, grows by two each time.
- `map_needs_map` (three profiles): a sibling minted with every right but `Map` is refused, an `AccessDenied` fault.
- `stack_row_held` (riscv32 and flat; a child run in place, so its destination's only row is the stack grant): the destination is held while the child lives and comes home at its death.
- `memory_split` is `pool_allocate` (package, manifest, console lines, the runner, three comments). `pool_free_bytes` is gone.

**Mutants.** The review's seven first-fit mutants, the two node paths, the `Map` right and the stack row's region are each red under the mutant alone on every profile the leg runs on (table in the implementer's hand-back; logs in the lead's scratchpad). One note: the exact-fit test forced `false` survives `pool_first_fit` and is red in `pool_nodes_home` (it leaks a node, which only the node count sees).

**The hunt:** 108 one-operator mutants over `pool_can_serve`, `pool_cut`, `pool_return`, `pool_insert_range`, `pool_fold_frontier`, `pool_drop_nodes`, `memory_retire_donated` and the release's call, each against the 54 pool cases on riscv32. Three survivors got legs (the list test taking a range a grain short; the three-into-one merge's link and its middle node). **Ten are argued equivalent, for the reviewer to break:**
- `pool_cut`'s "bytes its pool does not have" check forced false: it runs only after `pool_can_serve` said yes;
- `base > base` as `>=` in the insert walk: a range being returned is out, so no free range starts at its base;
- `dropped` not counted, or doubled: **nothing in the kernel reads the field**, so no leg can exist without a reader (see SO-94);
- the fold's `return` dropped: the walk reads a `next` that is 0 either way;
- the two invariant stops in `pool_return` removed: a correct kernel never trips them;
- `free_head = 0` dropped in `pool_drop_nodes`: both callers overwrite the slot at once;
- `memory_retire_donated`'s test forced true: an allocation's list is never written.
None was set aside for SO-94: `pool_nodes_home` never releases beside the frontier with the slab full.
