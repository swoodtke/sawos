## Description

**Unit U2a of the image and packaging design (SO-95): linked slab areas and the boot table at version 5.** The user approved the spec (SO-106) on Nov 14. This unit builds the part of it marked `(not yet enforced: limits)` that concerns slab areas, and changes no limit's value: every board keeps today's floors and quota defaults, so no existing case's numbers move. The per-board values are the next unit (U2b).

**What is built.** `spec.md` is authoritative: §12 "After the rows, the image's slab areas" (the block, and every reason the boot stops), §2.8 "The machine's limits" (an image raises what a machine boots with; an image's totals keep the floors' relations), §2.9's child rows as far as an image's quota defaults go, and the transition note's `limits` paragraph, which shrinks to what is still not built after this unit (the per-board values). The design's section 6.1 (`.claude/lead/so95-design.md` in the lead's checkout) describes a prototype of the kernel half that ran on riscv32, arm64 and the ESP32-S3 smoke; its code was not kept.

- **Kernel.** The region table at version 5. After its rows: nothing, or one whole block (a magic word, the number of areas, a quota default for each quota kind, an entry per area naming a slab kind, a base and a length). Read before the first process exists. Each stop of §12 is a `fatal_image` naming what it found. Each area is zeroed and installed as one extent of its slab through the path a donation uses (`slab_geometry`, `slab_install`). The areas must lie inside the kernel's own zeroed memory, between the board script's `_bss_start` and `_arena_start`, and not meet (a HAL accessor for the two bounds).
- **Capacities, not floors.** Wherever the kernel reads a slab's compiled floor to bound something that an area can now raise, it reads the capacity at boot instead: the bound on boot rows (`mint_boot_regions`), root's mapping clamp (`install_quota_limits`), the bound on bodies, and any other reader of a `MAX_*` floor that means "how many there are" (find them all and list them). The spec's unmarked sentences about these are true today only because capacity at boot is the floor.
- **The children's quota defaults** come from the block when an image carries one, and are the compiled defaults otherwise.
- **The builder (`tools/sosimage`).** The image description gains the limits an image asks for (slab kinds to raise and by how many slots; quota defaults). `sosimage link` reads each slot's size from the kernel object's slab symbols, emits one zero-filled section per raised kind inside the kernel's `.bss` (so the boards' scripts need no new rule) and the block after the table's rows, and refuses by name, before the link, an image whose numbers break a relation of §2.8 or a bound of §12. The rule that the Mapping slab holds four per process is the builder's alone: it is how the builder sizes a default, not something the kernel checks.
- **The runner** gives a case a way to state limits (a key on the case), writes them into the image description, and keeps every case that states none byte for byte as it is.
- **riscv32's `virt.ld`** gains the check arm64's has, that the kernel ends below root: today a kernel that is too large links, boots and goes silent.

**Cases.**
- A case on every profile, and in the ESP32-S3 smoke, whose image raises several kinds (processes, Waiters, Memories at least): the root sees the raised capacity before any donation (it creates one process more than the floor holds), and a donation after that still works and takes one extent fewer.
- An image's quota defaults reach a child: a child created under raised defaults can make more of a kind than the compiled default, and is refused one past the new default.
- Every stop of §12, each with its message: a partial block and bytes after the block; an unknown kind and a repeated kind; a length that is not whole slots, a zero length, a misaligned base; an area outside the kernel's zeroed memory and two that meet; a capacity past the slab's ceiling; each broken relation; each quota default out of bounds. Where the builder would refuse the image first, the case feeds the kernel a hand-made block, as the hand-assembled payload cases do.
- The builder's refusals, in its own tests: each relation and bound, by name.
- The boot-row bound and root's mapping clamp reading capacity: an image that raises Memories boots with more rows than the floor holds; root's mapping row reaches the raised Mapping capacity.
- Each new check and each changed reader is shown to hold its line by a one-operator mutant (the walk, each comparison, each bound, the order of the stops). The reviews of the last units each found survivors: run the hunt yourself over every line this unit adds or changes, in the kernel and in the builder, and close or argue each.

**Not in this unit:** any limit's value (U2b); the quota door (U5); the description formats (U3); removing the Python image path (after U2b). The Python path does not learn about limits: a case that states limits is built by the builder only, and the runner says so if asked to build it the other way.
