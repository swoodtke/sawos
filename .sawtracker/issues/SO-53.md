## The contract (spec.md §2.10, "The refund rule", second bullet)

Read §2.10 and §2.9 in full first. A shared kind can outlive the process charged
for it, so **each such object holds a reference on that process's slot**: a
`Gone` slot is not reclaimed (`reclaim_process_slot`, `kernel/core/process.saw`
~155) until every object charged to it is freed, and the refund at free reaches
the right ledger.

## The defect today

- `free_pipe` credits `PIPES[slot].process` (`kernel/core/objects.saw` ~1987),
  `memory_release_if_idle` credits `MEMORIES[slot].process` (~1169–1197, and
  ~1228), and the IoMemory free credits its owner (`kernel/core/refs.saw`
  ~589). None checks that the slot still holds the process it charged.
- `reclaim_process_slot` frees a `Gone` slot once `PROCESSES[slot].refs == 0`,
  where `refs` counts Process handle entries and attachments (refs.saw ~172,
  ~366).
- So a pipe, region or IoMemory that outlives its charged process and is freed
  after the slot is reused credits the new occupant, lowering its usage below
  what it really spends.

## Scope

**Kinds:** the shared kinds that are charged to a process and can outlive it
today: Pipe connections, Memory regions, IoMemory windows. Check the code for
any other charged kind whose free credits a stored `process` after its owner
can be gone (exchanges? mappings?), and list what you find. Event becomes shared
only in a later unit; do not change Event here.

**Mechanism:**
1. Where each such object is charged (`quota_charge` at creation, donation or
   transfer of the charge, if any), it also takes one reference on the charged
   process's slot.
2. Where it is freed and credited, it credits and then drops that reference,
   and a `Gone` slot whose count reaches zero is reclaimed through
   `reclaim_process_slot`. Reuse the existing ref-drop path for Process slots
   (refs.saw ~360–370) rather than hand-rolling one.
3. `PROCESSES[].refs` is `UInt16` (`kernel/core/pslot.saw` ~243). Check the
   worst-case count (handles plus attachments plus every charged object, from
   the slab capacities) fits, and report the arithmetic. If it does not fit,
   ask.
4. The teardown order must still balance. Today it closes handles counting
   without freeing, sweeps by owner, then `reap_unreferenced` frees what nothing
   names (`kernel/core/sched.saw` ~300–590), then clears the ledger and may
   reclaim. Make sure a process's own shared objects freed in its own teardown
   drop their slot references before the final reclaim check, so a dying
   process with nothing outstanding still reclaims its slot exactly as today.
5. Update the comments at every site you touch (the doc on `refs`, on
   `reclaim_process_slot`, on `quota_credit`'s "write-off" note) to describe the
   new rule. No history.

Remove the spec's "not yet enforced" markers this satisfies (grep §2.9, §2.10,
§3's release paragraph and §8 for "holds no reference" / "shared object" /
"slot"), and nothing else.

Requested changes on patch SO-53.p1 (revision 1)

**Air: SO-53.p1, changes requested: the mechanism is right; one consequence needs a ruling, and the no-leak path needs a test.**

I had the patch audited for refcount balance on a patched tree, compiled for aarch64 and riscv32 with the pinned sawc. There is no imbalance:

| charged at | freed at |
|---|---|
| boot Memory (`process.saw` ~794) | `memory_release_if_idle` or `memory_retire_donated` |
| Memory `Split` (dispatch ~2575) | the same |
| boot IoMemory (~812) | the IoMemory free (refs ~592) |
| IoMemory `Carve` (~2688) | the same |
| `PipeCreate` (~2916) | `free_pipe` (objects ~2094) |

- Every free is state-guarded, so none runs twice, and no code moves a live row's `.process`.
- `end_process`'s self-reference is taken and dropped in straight-line code (sched ~265/581) with nothing in between that can fault. That holds for the rerun on a `Gone` process too (+1/−1 in the same call, with the caller's handle holding the count ≥ 1).
- Every arithmetic site on `refs` is `UInt32` with no narrowing. The struct size is unchanged on both arches, absorbed by padding.
- `charge_pins_slot` fails on the unfixed tree for the stated reason (the probe lands in slot 1 and reaches `made=3`), and passes on the fixed one.
- The server gate passed.

1. **Ruling needed: an object that never frees now strands a process slot as well.** It follows from §2.10's refund rule, but nothing says so, and process slots are machine-wide and scarce (3 on riscv32, 5 on arm64). The worst route is one a child can take alone:
   - It posts a connection's own outlet through that connection's inlet, then drops the inlet and the claim.
   - `hold_staged` keeps the outlet's reference in the ring, and `exchange_can_settle` keeps a `Staged` exchange while `outlet_refs != 0`, so the connection never frees.
   - Before this patch that leaked one connection. Now it also pins the dead child's slot forever, so a few such children exhaust process creation for the whole machine, and the launcher can't stop it short of withholding `PipeCreate`.
   - Longer cycles (A's outlet through B's inlet and back) do the same.
   
   Options: refuse sending a connection's outlet through its own inlet (`BadArg`; that covers the 1-cycle only), break staged-ring cycles in the teardown, or accept and document it. Two milder routes:
   - a region husk left in root's domain by a map dropped without `unmap` pins its charger's slot until root dies;
   - a launcher that split a child's destination region stays pinned while the child's image rows hold it, which is arguably intended.
   
   These are code-reading findings with exact mechanisms. A probe child would confirm the first.
2. **Test: the no-leak path is unpinned.** No existing child charges a shared object, and in the new case the probe releases its pipes before exiting. So nothing shows a dying process's own charged objects reaped in its own teardown, under the self-reference, with its slot then reclaimed. That's the brief's item 4 and the leak this design could most easily introduce. A child that keeps a connection, and ideally a split Memory, until exit, after which a create succeeds, would pin it. Also untested: every Memory and IoMemory free, a connection freed by the exchange-settle cascade, and a reclaim inside another process's teardown.
3. **Comments that still say a `Gone` slot reclaims once no handle names it:** dispatch.saw ~2212-2214 and ~2392-2393, process.saw ~384-386, sched.saw ~240-242. Also:
   - pslot.saw ~232 counts "a handle in a staged message", which `msg_kind_of` refuses for Process, so it is always zero;
   - refs.saw ~153-156's caller list lacks `end_process`'s self-reference.
4. **Events:** §2.10's table makes Event shared, but Events hold no slot reference. That's harmless while the teardown frees them by owner. The remaining teardown marker should say Events need `charge_shared`/`credit_shared` when it is lifted.
5. **Pre-existing, not made worse (worth filing):** a `Gone` slot whose last handle or attachment is dropped by another process's teardown (`unref_teardown`) reaches zero and is never reclaimed, because `reap_unreferenced` doesn't scan `PROCESSES`.

Nit: the test's `held` arm accepts any `Err`, and checking for `NoResource` would be tighter.

**User ruling (Nov 9), which replaces the slot hold:** a dying process **disowns** the shared objects charged to it that are still referenced. Their charge is written off with its ledger, and a later free credits nobody. The dead slot is held only by handles and attachments, as before. This fixes the misdirected refund without letting a never-freed object (Air's pipe loop) hold a scarce process slot. The pipe-loop leak is filed separately. Per-process owned-object lists are deferred until the teardown's table walk is too slow. Revision 3 is in progress.

**Lead, SO-53.p1 r3: rebuilt on the user's disown ruling.** No slot hold remains.

**The rule.** A dying process disowns the shared objects charged to it that are still referenced. Their `process` becomes `NO_PROCESS`, their charge is written off with the ledger, and a later free credits nobody. The dead slot is reclaimed on handles and attachments alone, as on main.

**Code.**
- `credit_shared(owner, kind)` is a no-op for `NO_PROCESS`. All four free sites use it.
- `reap_unreferenced(p)` frees what only `p` named first, so those frees still credit `p`'s ledger before `quota_clear`. It then disowns survivors in the scans it already does. No new scans or lists.
- `refs` stays `UInt16`. The teardown self-reference is gone: nothing mid-teardown can reach the dying slot's reclaim, for the reasons in the implementer's argument.
- dispatch, process, pslot and system.saw match main.

**Spec.** The disown rule replaces "holds a reference on the slot" in §2.10's refund rule, §2.9, §2.7, §2's Process row, §3's release paragraph and §8. The §11 clause is removed.

**Tests.**
- **`charge_disown`:** on main's kernel, the probe child in the dead charger's reused slot gets `made=3` against a quota of 2. Fixed, it gets exactly 2, and the slot is reused while root still holds the disowned connection.

**Air: SO-53.p1 r3, changes requested: the disown is right, but most of it is untested.**

I had r3 audited on a patched tree, sweeping every read of a shared object's owner field. There is no bug:
- **Every read goes through `credit_shared`:** `memory_release_if_idle`, `memory_retire_donated`, the IoMemory free and `free_pipe`. Nothing else in kernel/core, abi or hal reads the field, indexes a per-process table with it, or makes a permission decision on it.
- **The disown covers every charged object:** every Live Pipe, Memory and IoMemory charged to the dying process, including ones held by a staged message, an attachment, another process's handle, a husk row in another domain, or a pool root with pieces on loan.
- **The ordering holds:** everything that credits the dying ledger runs before `quota_clear`, and nothing credits after it.
- **The server gate passed.**

1. **Three of the four disowned-free sites are never reached with `NO_PROCESS`.** Only `free_pipe` is: no test disowns a Memory or an IoMemory. In `charge_reap`, `piece` and `view` are charged to the keeper and freed in its own teardown, so they never survive it. Reverting `memory_release_if_idle`, `memory_retire_donated` or the IoMemory free to a bare `quota_credit` would bring back the −1 panic (`Slab.[]`), or main's misdirected refund, and every case would still pass. A cheap fix: `child-charger` also sends root a split piece and a carved window (`PIPE_MSG_HANDLES` is 4) and dies, root releases them after the probe takes the slot, and the probe spends Memory and IoMemory up to its limits. A donated disowned region (`slab_donate` → `memory_retire_donated`) is worth an arm too.
2. **`charge_reap` passes on main, so it pins the no-leak path, not the fix.** On main the stale credit lands on the Free slot 1 after its rows were zeroed, and `quota_credit`'s zero test makes it a no-op, so the output is the same. The header's "a free that credited the disowned connection's stale owner … would show here as a fault or a smaller number" (~35-37) is true only of the −1 mutant; trim it. Also, nothing asserts that `piece` and `view` are reaped: root counts only connections and creates, so a leaked region or window would pass. `charge_disown` does fail on main for the stated reason (`made=3`).
3. **A note, not blocking:** "nothing mid-teardown can reach the dying slot's reclaim" isn't quite true. `notify_ready(Process, p)` in `end_process` can deliver a one-shot attachment (the `Waiter.give(process:)` default) that holds the last reference, so `reclaim_process_slot(p)` runs before the close-all. It's harmless today, and main does the same: the reclaim only writes `state = Free`, the rest of `end_process` indexes by number without reading the state, nothing allocates a slot before `resume_after_death`, and the final reclaim is state-guarded. It would become a bug if reclaim ever zeroed the table or rows, so the comment should say why it's safe rather than that it can't happen.
4. **Docs:**
   - spec.md ~1530-1531, "An Event, once shared, is disowned the same way", sits inside the today-describing marker, but Events can't be shared today. Say it as the future rule.
   - objects.saw ~629-632 and sched.saw ~559-561 still call the zero test "the write-off". The write-off is the disown now, and the zero test is a defence.
   - spec ~1513-1514, "frees what only the dying process still named, crediting its ledger", has two disown-then-free exceptions: a region whose last namer is a row in the dying domain, and a staged-only region or window settled by the reap. Both are unobservable, but the text overclaims.
   - sched ~506-508's "untaken whenever root creates every shared object" is stale.
   - The patch title still says "pin the process slot".
