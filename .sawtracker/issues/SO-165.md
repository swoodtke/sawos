**Interrupt-driven UART transmit, and a real ESP32-S3 UART driver.**

Today every console driver is one thread with one loop.
- **The emulators' UART drivers** (`svc-uart-ns16550`, `svc-uart-pl011`) read through interrupts, but write synchronously inside the request.
- **The S3's console** is `svc-console`, which makes one kernel `debug_print` per byte. When UART0's FIFO is full, that print stalls with interrupts masked. That stall is the console share measured in the flash-speed runs.

**The owner's direction (Nov 25):**
- **Serving.** A serving thread at a high band takes a `Write`, copies its bytes into the driver's own ring, and answers once they are queued.
- **Transmit is interrupt-driven.** The driver fills the hardware FIFO, then sleeps until the TX-empty interrupt and tops it up. Nothing spins, and no background thread is needed.
- **A full ring holds the `Write`** (the protocol already allows a held request), so the writer slows down and nothing is lost.
- **The kernel's own console** (boot lines, panics) stays synchronous.
- **Bands.** Once this exists, the console driver declares `bands = "full"` and serves at High or Rt0.

**Scope:**
- A new S3 UART driver for UART0, with its interrupt line, as the console's server on the S3.
- The same transmit path in the ns16550 and pl011 drivers.
- Cases for back-pressure, for the hold when the ring is full, and for no lost bytes.
- A board run of the stress profile with the new driver.

It needs a design first; I will brief one.

Requested changes on patch SO-165.p2 (revision 1)

**Held for a revision.** Every register fact checks out against ESP-IDF v5.4.1:
- the base 0x6000_0000 and source 27;
- the seven offsets;
- the interrupt bits, with `INT_RX = 0x19D` being bits 0, 2, 3, 4, 7 and 8, all receiver-side;
- STATUS's two 10-bit counts, CONF1's and MEM_CONF's fields, the 128-byte FIFO and the threshold bounds;
- the hosted tests pin the offsets, bits and sequences.

An agent read the code against `uart_reg.h`, `uart_struct.h`, `uart_ll.h` and `uart.c`, citing each fact, and I rechecked the access orders below in the code. Two access orders, and the unchecked inputs, need changing before U4 builds on them.

**1. `service_rx` clears too late** (lib: the `port.write_word(uart_int_clr(), status)` after the drain loop).
- It reads `S = INT_ST & INT_RX`, drains until STATUS reads 0, and only then writes `S` to `INT_CLR`.
- Suppose a second damaged byte arrives between the last count read and that store, while FRM_ERR, PARITY_ERR or BRK_DET is already in `S`. Its error re-sets a bit that is already set, and the store erases it. The byte is popped later with no error bit, so it's delivered with no mark.
- That breaks the docstring's own promise ("a bit that rises after the `INT_ST` read stays raised and fires again", also ABI §4b), which holds only for bits not in `S`. It also breaks the design's "the bytes after a mark arrived whole".
- The same window can erase a timeout raised by a single byte, if the part raises the timeout once rather than holding it, which is UNVERIFIED. The driver is a preemptible thread, so the window has no bound.
- **Fix:** drain to 0, store `S` to `INT_CLR`, then read the count once more and drain into the same batch. A byte that arrived before the clear is taken and flagged with this batch; one after it raises fresh bits. The fake can show it: deliver a byte and an error bit at the clear's store.

**2. `start_uart` configures and then clears; IDF clears and then configures.**
- The patch writes CONF1 (with `RX_TOUT_EN`), then MEM_CONF, then `INT_CLR` of the receive set, then `INT_ENA`. IDF clears first and sets the timeout threshold before its enable.
- A timeout raised by the configuration is erased by the clear. Bytes left from before the start, which the doc and ABI promise to deliver, may then wait for another byte.
- **Fix:** clear before configuring and set MEM_CONF before CONF1, or drain once after `INT_ENA`.

**3. The word builders don't mask their inputs, and two public paths are unchecked.**
- `start_uart` doesn't call `check_uart_thresholds`, and `uart_set_tx_threshold` has no check at all, yet U4 passes it a computed Sync value.
- Out of range, the values spill into bits the driver doesn't own:
  - a transmit threshold of 1024 or more sets CONF1 bit 20 and up (`DIS_RX_DAT_OVF`);
  - a timeout of 1024 sets MEM_CONF bit 27, `MEM_FORCE_PD`, which powers the UART memory down;
  - a receive threshold over 0x3FF spills into the transmit field.
- **Fix:** mask each value to its field, or refuse values outside 1..max where they enter.

**4. The transmit interrupt's clear after a refill.** TXFIFO_EMPTY's raw bit stays set until cleared. `fill_tx` doesn't clear it and `service_rx` masks it out, so the caller must re-arm with `uart_set_tx_interrupt` after every refill, or the line storms. Design §3 says so; `fill_tx`'s doc and ABI §4b don't, and no hosted test holds fill-then-clear. Say it at `fill_tx`, and pin it.

**5. Docs:**
- **The `INT_RXFIFO_TOUT` docstring** says the bit rises "with bytes in the FIFO below the full threshold". IDF gives no such condition, and `service_rx`'s doc and ABI say it can rise with the FIFO empty.
- **`check_uart_thresholds`' reasons.** A receive threshold of 0 does raise, at any count above 0; refusing it is right, but for the stated reason it's wrong. "A timeout of 0 turns it off" is IDF's API convention; in the register, `RX_TOUT_EN` is the switch.
- **ABI §4b's "relies on no reset value"** overclaims. The 128-byte FIFO, which `fill_tx` and `RX_FULL_MAX` use, depends on MEM_CONF's `RX_SIZE`/`TX_SIZE` keeping their reset value of 1, which the driver neither writes nor checks. Name it.
- **`INT_ENA` is written whole** (`start_uart`, `uart_set_tx_interrupt`), where IDF reads, modifies and writes it. The design allows it (§2), but then the note's "each word keeps every bit of its register it doesn't own" needs "except `INT_ENA`, which the driver owns whole". Which UART0 enables the ROM leaves set is UNVERIFIED.

**6. Hosted-test gaps:**
- MEM_CONF bits 1–16, and CONF1 bits 20 and 22, are 0 in every starting word the tests use. So a mask mutant such as `MEM_CONF_RX_TOUT_MASK = 0x07FF_FFFE` passes. Start a test from all-ones words.
- The `& 0xFF` on the FIFO read isn't covered (the fake never returns bits above 7).
- `UART0_SOURCE` isn't checked anywhere.

**The implementer's note for SO-165.p3 (U2, `drivers/uartcore`).**

**Base.** Built against `uartproto` as it is on main, because U1 (p1) hadn't merged.
- U1's values sit behind one seam, `src/wire.saw`: `OP_STATS = 6`, `STATUS_LOST = 4`, `STATUS_GARBLED = 5`, and the mark and Stats builders. They have the same numbers and byte layout as p1.
- Once p1 lands, the seam switches to `UartBody`'s methods. That's a small follow-up in U4's or U5's patch.

**The trait, `UartDevice`:** `rx_count`, `rx_pop`, `tx_count`, `tx_capacity`, `tx_push`, `events()` and `clear_events(bits)`, `tx_interrupt(on)` and `set_tx_threshold(level)`. The event bits are the core's own (`EV_RX`, `EV_TX`, `EV_OVERRUN`, `EV_PARITY`, `EV_FRAME`, `EV_BREAK`); a device maps its status register onto them.

**The core:**
- `Core<TX, RX>` with `Rx<N>` and `Tx<N>`, whose ring sizes are const generics, and a `Config` (`tx_empty`, `fill_cap`, `max_syncs`, `held_reads`).
- **Entry points:**
  - `request` answers `Served::Now(Answered)` or `Served::Held(kind, slot)`;
  - `service(dev)` makes every device access, and the driver acknowledges the line after it;
  - `next_answer`;
  - `undeliver(answer)`, called straight after a reply that doesn't land;
  - `abandon(slot)`, `intake_open()` and `begin_drain`/`drained`.
- The driver owns the PipeRequests; the core names each obligation by kind and slot.
- `uartcore.fake` holds `FakeUart`, with `hardware()` and `emulator()`. `uartcore.bench` is a model driver loop.

**States:**
- **Receive:** at most one standing mark, at the tail, so nothing is accepted behind it. It's Lost if any byte was lost, else Garbled.
- **Held reads:** 4, answered by arrival order, with Busy past the limit.
- **Transmit:**
  - Idle, or Busy (the transmit cause enabled);
  - one held Write, answered once it's wholly queued;
  - up to 4 held Syncs, each marked with `queued`;
  - a drain mark.
- **Intake** is open unless a Write is held or unanswered, or the Sync set is full.
- **The transmit level** is `tx_empty` while the ring or the hold has bytes, `pushed − oldest_mark + 1` only with the ring empty, and off when nothing waits.

**Tests:** 12 hosted test files, with every mutant red by hand.

| test | mutants |
|---|---|
| `tx_stream` | drop byte, double store, ring room off by one, reversed hold copy |
| `tx_hold` | answered at take, intake ignores the hold, early release |
| `tx_sync` / `tx_level` | answered at take, ready at ring-empty, mark from `pushed`, level ±1, `>` for `>=`, level kept low with bytes |
| `rx_marks` / `rx_second_loss` / `rx_garbled` | drop uncounted, mark before bytes, `received` uncounted, mark not set, standing mark ignored, slot not freed, error kinds ignored, swapped or fixed, cause not cleared |
| `rx_held` | slot order, newest first, Busy off by one, Busy never, abandon a no-op, put-back a no-op or at the tail, mark put-back lost |
| `serve_requests` | Stats with payload accepted, Pending ignoring the mark or unsaturated, Stats fields swapped, writes_held uncounted, Stats length, Mark refused |
| `intake` | Sync limit ignored or hardcoded, Syncs newest first, drain ready early or never clearing, sync slot kept, Write taken while closed |
| `emulator` / `fake_device` | fill ignores the cap, no overrun, inclusive level, timeout always on, clear a no-op, enable ignored, count ignored, and a lagging transmit count |

"Hold released early" is red only in `tx_stream`.

**Where the code differs from the design:**
- `Stats` is op 6.
- `Pending` counts what a Read would answer at once, buffered bytes plus a standing mark, saturating at 255.
- The transmitter isn't enabled when a start leaves nothing to send.
- The interrupt's transmit half is fill, admit, fill, clear, settle.
- The defensive Write refusal answers Busy whenever intake is closed.
- The drain is a pseudo-Sync with no obligation.
- `Answered`/`Served`/`undeliver` are the core-to-driver seam.

Requested changes on patch SO-165.p3 (revision 1)

**Held for a revision.** The core is carefully built. These hold:
- the transmit interrupt path (fill, admit, fill, clear, settle) can't stall or storm under the level contract;
- the level rule;
- the receive, held-read, Pending and Stats rules;
- the wire seam carries exactly p1's numbers and layout (op 6, `Lost` 4, `Garbled` 5, the counts at words 1–13, Stats at 1–29).

Two ordering bugs need fixing, and three smaller ones go with them. An agent read the core against design §2–§3 and §9. I rechecked the first three below in the code.

**1. A `Sync` can be held with its answer ready and nothing enabled (a stall).**
- `sync()` reads the transmit count once and finds the mark unpassed, so it takes a slot and answers `Waits`.
- `sync_request` then calls `start`. With nothing busy and the ring empty, `fill` touches no register, and `settle` → `pass_syncs` reads the count a second time.
- If the last byte before the mark left between the two reads, `pass_syncs` flags the slot ready. `waiting_mark()` is then `None`, so `want` is false and the cause is never enabled.
- Yet `sync_request` returns `Held(KIND_SYNC, slot)`, and the documented loop (serve.saw's module doc) calls `next_answer` only on an interrupt. So the `Sync` waits for an unrelated interrupt, which on an idle console, such as the runtime's `Sync` at exit, may never come.
- The window is small but real: the tick can land between the two reads.
- The tests can't see it, because `Bench.pump` calls `next_answer` after every request, which the documented loop doesn't.
- **Fix:** have `sync_request` answer `Now` when its slot is already ready after `start`, or put `next_answer` after requests in the documented loop, and make the bench run the loop as documented.
- `begin_drain` ends in the same `settle`, so a drain mark that has already passed never enables the cause. Say how a driver learns it's drained in that case.

**2. ✓ The receive clear comes after the drain** (`service`: `dev.clear_events(ev & EV_RECEIVE)` after the loop). This is p2's finding again, at the device-independent layer. A second damaged byte arriving between the last count read and the clear re-sets an error bit already in `ev`, and the clear erases it, so the byte is delivered unmarked. The clear covers `EV_RX` too, so if the part's receive timeout is a latched event, a byte that arrives just after the last count read can lose its only wakeup: a receive stall. **Fix:** the same as p2's, clear, then recount and drain into the same batch.

**3. ✓ An overrun's mark lands after bytes that arrived after the loss** (`service`, then `rx.overrun()`).
- `ev` is read once and the drain pops in passes. A FIFO that overran was full, so the first pass's bytes are older than the dropped one, but bytes popped on later passes arrived after it. All are accepted before `overrun()` puts the mark at the tail.
- So the reader sees `b1..b128, b130, b131, Lost`, where the gap is at b129. That breaks §2's "after the last byte accepted before a loss" and §9's red condition.
- **Fix:** apply an overrun seen in `ev` after the first batch, so the bytes after it are dropped behind the mark as the one-mark rule intends.
- A variant: OVF rising after `events()` isn't in `ev`, so it survives the clear and is marked an interrupt late. Recounting after the clear (item 2) should read `events()` again too.

**Smaller:**
4. **A newer `Sync` answered ahead of an older held one.** `sync()` answers `Reached` without first flagging older Syncs whose marks have passed, which a `settle` would do. The agent traced it through the bench: `order(s2) < order(s1)`. Run `pass_syncs` before the new one's check.
5. **`drained()` answers true with a held Write's remainder still waiting** (`drain_mark = queued` leaves out the hold), so "the ring and the FIFO are empty" is false then. Include the hold, or refuse `begin_drain` while a Write is held.
6. **The defensive Busy covers `Write` but not `Sync`.** A `Sync` taken while a Write is held is marked at `queued`, before the held bytes, and can be answered before them. Refuse it while intake is closed, as `Write` is.
