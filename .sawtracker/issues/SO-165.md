**Interrupt-driven UART transmit, and a real ESP32-S3 UART driver.**

Today every console driver is one thread with one loop.
- **The emulators' UART drivers** (`svc-uart-ns16550`, `svc-uart-pl011`) read through interrupts, but write synchronously inside the request.
- **The S3's console** is `svc-console`, which makes one kernel `debug_print` per byte. When UART0's FIFO is full, that print stalls with interrupts masked. That stall is the console share measured in the flash-speed runs.

**The owner's direction (Nov 25):**
- **Serving.** A serving thread at a high band takes a `Write`, copies its bytes into the driver's own ring, and answers once they are queued.
- **Transmit is interrupt-driven.** The driver fills the hardware FIFO, then sleeps until the TX-empty interrupt and tops it up. Nothing spins, and no background thread is needed.
- **A full ring holds the `Write`** (the protocol already allows a held request), so the writer slows down and nothing is lost.
- **The kernel's own console** (boot lines, panics) stays synchronous.
- **Bands.** Once this exists, the console driver declares `bands = "full"` and serves at High or Rt0.

**Scope:**
- A new S3 UART driver for UART0, with its interrupt line, as the console's server on the S3.
- The same transmit path in the ns16550 and pl011 drivers.
- Cases for back-pressure, for the hold when the ring is full, and for no lost bytes.
- A board run of the stress profile with the new driver.

It needs a design first; I will brief one.

**The owner's answers on design revision 1 (Nov 26):**
- Q1: a loss is reported at the gap (`Lost`) plus the counter.
- Q3: instead of a builder refusal, the kernel does not write UART0 while a userspace driver owns it. It prints directly only before the driver claims the UART, after the driver dies, and on a panic, when it takes the UART back.
- The kernel's routine messages move to root: root already watches each death, and the kernel may keep a death record root can read for the detail.
- Q5: ns16550 and pl011 come later.
- Q6: root prints through the console driver; this now folds into this work.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":366,"created":"1795731310","id":"c5"} -->
**Owner ruling (Nov 26):** the kernel learns that a userspace driver owns UART0 through an **explicit claim**. It's an op on the UART0 `IoMemory` handle behind its own right, made once the driver's interrupt path runs. A death or a release ends it, and a panic overrides it. The kernel does not infer ownership from the driver mapping the window or binding the line.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":428,"created":"1795731388","id":"c6"} -->
**Owner refinement (Nov 26):** the claim is a **generic device claim** on any `IoMemory` handle, not a UART-specific op. Proposed semantics, for the design to settle:
- on a device the kernel itself uses (`kernel = true`, today the console), the kernel hands it over while the claim holds, and a panic overrides it for the console;
- on any other device, the claim is exclusive ownership: an overlapping second claim is refused.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":306,"created":"1795731576","id":"c7"} -->
**Owner (Nov 26):** while UART0 is claimed, the kernel's debug print returns an error, never a silent drop. Lead's follow-on for the design: a process's panic text must never vanish. The runtime falls back to the console inlet, and the kernel keeps the panic text in the death record root reads and prints.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":221,"created":"1795731666","id":"c8"} -->
**Owner ruling (Nov 26):** a process's panic message goes to the kernel, which saves it with the death record and returns it to root. Root prints it with the exit status. There is no runtime fallback to the console inlet.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":191,"created":"1795731728","id":"c9"} -->
**Owner ruling (Nov 26):** a panic in root panics the kernel, as a system fault. The kernel's panic path takes UART0 back and prints root's panic text. Root's clean exit stays as it is today.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":433,"created":"1795732058","id":"c10"} -->
**Owner's answers on design revision 2 (Nov 26):**
1. The death record keeps the panic text up to 256 bytes.
2. In a claimed image, root prints the teardown counts only for faults and panics.
3. Root's faults and a kill of root are kernel panics too, with today's lines and statuses; root's clean exit is unchanged.
4. `svc-console` meeting a claim ends with `EXIT_CLAIMED`.
Revision 2 stands with these, pending the reviewer's read.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":495,"created":"1795733795","id":"c11"} -->
**Owner ruling (Nov 26), replacing the generic device claim:** the console claim is an interim, console-specific `SystemOp` behind its own `SystemRight`. Root's plan grants it only to the image's console driver, and the builder refuses it elsewhere. A release or the claimant's death ends it, and a panic overrides it. The real mechanism is device objects, a separate design. Design revision 3 is under way: it also answers the reviewer's t5 (root parking behind a stalled claimant) and t1–t4.
