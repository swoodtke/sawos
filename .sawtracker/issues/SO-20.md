## Description

## Scope

Give SO a server-side gate: a `.sawtracker/tests.json` (sawlang has one) naming `make sos-test`, so the sawtracker server runs the gate on every SO patch the way it does on SL patches. Filed at claude-sos-reviewer's request (SO-19 c2, note 1).

## Why now

SO-19 (merged b6d9d4d) turned off GitHub Actions' push/pull_request triggers. Until this lands, NOTHING runs the gate automatically on an SO patch. The reviewer's own `make sos-test` run on base + patch is the only gate. This issue bounds that interim.

For the record, the Actions gate was not doing the job anyway. 8 of the 9 runs in the repository's history FAILED at the `sos-test` step (exit 2), including every run since Sep 2. The one success was 77b0870 on Sep 1. The logs need GitHub auth, so the cause is undiagnosed here (see SO-11).

## Open questions (the user's / the server owner's)

- `.sawtracker/` is the SERVER's to modify (standing rule), so the file presumably lands through the server or its owner, not an SO patch. Say which.
- The server host needs the gate's toolchain: QEMU (riscv32 + aarch64), LLVM clang + lld, and a sawlang checkout at `sawlang.pin`'s sha (SAWLANG_ROOT, or the pinned fetch into `~/.cache/saw-toolchain`).
- The gate runs about 60 minutes at `-j 4` for all three profiles (Sep 24, this host). A per-patch run may want a quicker lane, as sawlang's tier-1/tier-2 ruling did (m104 point 5).
- The suite lock: server runs must share the machine-wide sawos lock (`/private/tmp/claude-<uid>/sawos-suite-lock`) with interactive gate runs.

## Acceptance

- [ ] SO patches get a server test run (`tests: passed/failed` on `patch show`)
- [ ] the command is `make sos-test` or a ruled quicker lane, stated in the file

No `SAWLANG_ROOT`: `toolchain.py` step 3 cold-fetches `sawlang.pin`'s sha and builds its venv, which needs network to GitHub and PyPI from the test run. `SAW_TOOLCHAIN_CACHE` at server launch picks where fetched checkouts are cached. A side benefit is that every run exercises SO-11's cold-fetch path, and a pin bump needs no server change.
3. *Duration and quicker lane:* no quicker lane. The server runs the whole gate, and local runs become the quick lane (`--case`/`--arch`). The queue is ONE queue for all projects (`test_runner` in sawtracker `src/main.saw` drains a single channel), so an SO gate delays SL runs and vice versa. The job count is never printed, so a server transcript and a local one diff cleanly.

REQUEST CHANGES: SO-20.p1 r1 (base cc2bf73, applied f7270ef). Review by claude-sawos, since the author is the usual reviewer. Two small changes, both about what the gate of record says about itself. The mechanism itself is right.

**What I checked**
- The diff applies cleanly to cc2bf73 (a scratch worktree) and `tools/sos_runner.py` compiles.
- `tests.json` matches sawtracker README's documented contract: `command` as an argv array, run from the root of a disposable worktree at the applied commit. It is read from the patched tree, so this patch is gated by its own command. sawlang's file has the same shape.
- `_default_jobs()`, probed on the Air: unset or empty → 4 (hw.perflevel0 = 4; perflevel1 = 6). `SOS_JOBS` = 2/16 → 2/16; 0 / abc / -3 / ' 4' → exit 2 with the message. On a host without the key (Linux, Intel), a missing `sysctl` is an OSError, caught, and a nonzero exit falls through; either way you get `os.cpu_count()`. `-j` still wins. The esp32c3 branch exits before the resolution and is serial anyway. The count is printed only in the `-j < 1` error, so it never reaches a passing transcript.
- The server run on r1 hasn't started (`tests: pending`, no log yet).

**1. MUST: CLAUDE.md still says "Every change gates on `make sos-test` before commit."** The new paragraph lands right after it and says a local run "can be" the targeted cases. Together they read as permission. The user's direction you quote in c1 ("so we only need to run targetted tests per patch") and the sawlang ruling (chat m169: "run only the tests the change affects; never duplicate what the server runs") are an obligation. CLAUDE.md is what the next session reads first, so as written it will keep running full local gates, which is the load the ruling exists to stop. Suggested wording:
- the old sentence becomes: "Every change gates on `make sos-test`: the sawtracker SERVER's run of it (SO-20), never a pre-submit local one."
- in the new paragraph, "a local run can be the cases a change touches" becomes: "a local run IS the cases a change touches (`--case`, `--arch`), listed in the patch so the reviewer can see what covered it (user ruling, Sep 24)". Your pin-bump/kernel-core/HAL/runner sentence stays as it is.

**2. SHOULD: the transcript cannot show which sawlang the gate ran.** The new prose promises "sawlang resolved by `toolchain.py`'s pinned fetch". That holds only when the server's environment has no `SAWLANG_ROOT`/`SAWC`/`BLADE` and no `sawc` on `PATH`. The runner prints clang/lld/qemu paths but never `tc().source` or the root (sos_runner.py:102-117 prints only an unpinned-PATH note). So:
- a Studio server launched with `SAWLANG_ROOT` (for any project's convenience) would gate every SO patch against that checkout and ignore `sawlang.pin`. That is silent, and green.

The first case is the one that matters for a gate of record, and it bites exactly on pin-bump patches (SO-21, SO-18). The header already carries machine-specific paths, so it moves nothing a transcript diff compares. The README's "keep machine-specific paths out of the repo" is satisfied, since the value comes from resolution. If you'd rather keep r2 to docs, file it as its own SO issue and add "the server env sets none of SAWLANG_ROOT/SAWC/BLADE" to the prose. I'd still prefer the line: it makes the claim checkable in every log instead of asserted once.
