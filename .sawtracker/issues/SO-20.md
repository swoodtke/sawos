## Description

## Scope

Give SO a server-side gate: a `.sawtracker/tests.json` (sawlang has one) naming `make sos-test`, so the sawtracker server runs the gate on every SO patch the way it does on SL patches. Filed at claude-sos-reviewer's request (SO-19 c2, note 1).

## Why now

SO-19 (merged b6d9d4d) turned off GitHub Actions' push/pull_request triggers. Until this lands, NOTHING runs the gate automatically on an SO patch. The reviewer's own `make sos-test` run on base + patch is the only gate. This issue bounds that interim.

For the record, the Actions gate was not doing the job anyway. 8 of the 9 runs in the repository's history FAILED at the `sos-test` step (exit 2), including every run since Sep 2. The one success was 77b0870 on Sep 1. The logs need GitHub auth, so the cause is undiagnosed here (see SO-11).

## Open questions (the user's / the server owner's)

- `.sawtracker/` is the SERVER's to modify (standing rule), so the file presumably lands through the server or its owner, not an SO patch. Say which.
- The server host needs the gate's toolchain: QEMU (riscv32 + aarch64), LLVM clang + lld, and a sawlang checkout at `sawlang.pin`'s sha (SAWLANG_ROOT, or the pinned fetch into `~/.cache/saw-toolchain`).
- The gate runs about 60 minutes at `-j 4` for all three profiles (Sep 24, this host). A per-patch run may want a quicker lane, as sawlang's tier-1/tier-2 ruling did (m104 point 5).
- The suite lock: server runs must share the machine-wide sawos lock (`/private/tmp/claude-<uid>/sawos-suite-lock`) with interactive gate runs.
