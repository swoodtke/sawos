**Unit U2 of the GPIO/PWM drivers design (SO-77): the GPIO driver.** U1 (SO-131) has merged. The owner accepted every recommendation of the design's §11 (Nov 16); the useless box (SO-78) reads its switch through this driver.

**Build what §12's U2 lists, as U1 left the ground** (read scratchpad `SO-77/u1-as-built.md` first: where it and the design differ, it wins): `drivers/gpioproto/` (§4's protocol), the GPIO driver package and its `process.toml`, its configurations, the smoke cases `gpio_service` (a described S3 image: the stock root, the driver, a test client child) and `gpio_bad_config` (runner cases on the stock root with `root_plan`, `devices`, `inputs`), and the board cases G1 (nothing wired) and G2 (a switch from GPIO 21 to ground, flipped ten times by the owner). **Red cases:** each of §8.4's GPIO rows, as amended by `u1-as-built.md`; the patch note lists the mutants run, one per row and more where a check has several bounds. The review standard (the owner's ruling, Nov 15): every check, refusal and stop has a case or test that goes red when it is removed or inverted.

**Board:** the lead requests G1 and G2 through the reviewer under the owner's standing approval; build the images (`--emit-flash`) with expected text and device-write lists. G2 needs the owner's switch wired; G1 needs nothing.

**Not in this unit:** the PWM driver (U3), the box (SO-78).

Requested changes on patch SO-134.p1 (revision 1)

**Changes requested: any client can end the driver. Sent now so the fix can start; the gate, the image comparison and 137 mutants are still running here and I will post what they show.** The G1 board run is on this issue: the driver answered ten edges by interrupt on the part and its three start words read back right.

**1. A request that carries handles ends the driver** (chat f263, `probe_handles.py`; found by an Opus agent's read, run by me). With one `WaitLevel` held, one `Status` call carrying four Events:

```
SOS gpioclient probe: held=1
SOS gpiosvc drv: failed: no room for what was asked
SOS gpioclient probe: the call with four handles came back the other end of this connection is gone
root: driver ended status=65537
```

The same with four held; with none held the call is answered and the driver goes on. `process.toml` counts 13: the eight the driver holds, the request being served, and `MAX_HELD` held requests. A delivery needs room for the obligation and for every handle the message carries before it mints any (`kernel/core/refs.saw`, `table_room(p, staged_count(x) + 1)`), a message may carry `PIPE_MSG_HANDLES` (4), and `serve` treats a refused `wait` as the driver's end. So 8 + 1 held + 1 + 4 is 14, and the driver exits; every other client's connection is then gone, and the comment above `answer` ("a driver one client could end would be no driver") is the bar this misses. The declaration wants the carried handles in its count, with the comment saying so, and a case that sends a handle-carrying request with four waits held.

**2. Two counters panic when they wrap** (read, not run). `served` is an `Int`, 32 bits here, and `fires` a `UInt32`; `self.served = self.served + 1` and `self.fires = self.fires + 1` are checked arithmetic, which panics on overflow in every build. `served` counts refusals too, so a client's loop of bad requests reaches it; `fires` counts every edge of an input left floating. `abandoned` and `dropped` saturate. A driver meant to stay up wants these two to saturate or wrap as well.

**3. `Read` on a plain output answers 0 on a part, whatever was written** (read, not run). It reads `IN`, and an `Output`'s IO MUX word (`0x1800`) has the input enable off; ESP-IDF says of `gpio_get_level`, "If the pad is not configured for input (or input and output) the returned value is always 0" (`esp_driver_gpio/include/driver/gpio.h:148`). So `Write(2, 1)` then `Read(2)` answers Ok and 0. The emulator's `IN` reads 0 everywhere and G1 and G2 read only pads with the input on, so nothing shows it. The note's decision ("Read on a plain output reads `IN`") stands or falls with whether that answer is meant: `BadMode`, or the `OUT` bit, would both say something true.
