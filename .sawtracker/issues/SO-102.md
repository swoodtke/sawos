## Description

**From the user, Nov 14:** "For the S3 specifically, we can also move the userspace processes into the 8 MB PSRAM instead of keeping it all in 512 KB SRAM too."

**Today.** The kernel and every process share the part's internal SRAM. The layout in `hal/xtensa-esp32s3/kernel/lib.saw` leaves processes 256 KiB of DRAM from 0x3FCB_0000: root's region (96 KiB), one child's region (96 KiB) and a 64 KiB pool. That is why the board has one child slot. Nothing in the HAL, the link scripts or the runner touches the PSRAM; the part's ROM does not set it up, and the kernel direct-boots with no second-stage loader that would.

**What it would give.** Process regions and pools out of 8 MB: room for the box's four children with no squeezing, per-board limits sized by it (the user's ruling on SO-95), and the internal SRAM left to the kernel, its slabs and its stacks.

**What it takes, as far as the lead knows without having built anything.**
- **A PSRAM bring-up in the HAL, at boot.** The module's PSRAM is an octal SPI RAM on the same memory-SPI controller as the flash, on its own chip select (the pin plan already keeps GPIO 35 to 37 clear for it). Bringing it up means configuring that controller for the second chip select, putting the RAM chip in its mode (mode-register commands), and mapping its 64 KiB pages into the data address space through the cache's MMU table (the range the flash's read-only data shares, from 0x3C00_0000). Espressif's own driver (`esp_psram`, Apache-2.0) is the reference for the sequence and the timing.
- **Code stays in flash.** Processes already run in place from flash (SO-84); their writable data, stacks and the pools are what move. Executing from PSRAM is possible on this part and not needed.
- **The kernel reaches process memory by its data address**, so the copy doors, `row.pa` and the buffer rule need no change in kind; `map_source_ok` and the memory map gain a second RAM range.
- **A fallback.** A part with no PSRAM, or one whose bring-up fails its own read-back test, must still boot: processes stay in SRAM as today, and the kernel says which it chose.

**Risks and unknowns, to settle before any brief.**
- **The controller is the flash's.** A wrong write there is a command to the flash chip, not to the RAM. Nothing in this touches eFuses, and the ROM's download mode still talks to the flash, but a stray status-register write is the kind of mistake that makes a part awkward to recover. So the register sequence gets written down and checked against Espressif's driver and the headers before it runs on the user's part, and its first run is under the usual limit with the reviewer watching the console.
- **Speed.** PSRAM is reached through the cache, so a miss costs a serial transfer. Fine for processes; the kernel's own data and anything touched with interrupts masked stays in SRAM. A board stage should measure it.
- **The emulator.** The installed Espressif QEMU (9.2.2, esp_develop_20250817) carries an octal PSRAM model and an `esp32s3.cache.psram_as` address space, by its strings; whether the `esp32s3` machine wires it and how it is switched on is not checked. If the gate's emulator models it, the smoke can run with processes in PSRAM; if not, that layout is tested only on the part and the smoke keeps the SRAM layout.
- **Timing at the bus speed the ROM leaves**, and whether the module needs the tuning Espressif's driver does at higher speeds.
- **Which module the user's board carries** (the R8 in N8R8/N16R8 is the octal 8 MB RAM): the read-only board probe (SO-77's U0) should print what it finds.

**Further out, noted and not proposed:** the cache's MMU maps pages at run time, so a per-process mapping at one fixed address is conceivable on this part, which would end one link address per slot there. It costs a table rewrite and a cache flush at every switch between processes and is a different tier of port.

**Next step.** A short design (Opus): the bring-up sequence with its sources, the memory map with PSRAM in it, what the emulator does, the fallback, and the board stages; it feeds SO-95's board description. Nothing is built before the user has read it.

**User ruling, Nov 14:** "I don't think we need to handle the automatic fallback. If the board is specified to have PSRAM and it can't be configured, the board should loudly panic to the console and halt. The board should match the config exactly or fault."

So:
- **No fallback and no second layout.** A board described with PSRAM either brings it up or stops, with a console line that names the step that failed and what was read against what was expected. It never continues with processes in SRAM and never guesses a size.
- **The rule is general: the part matches its description exactly, or the boot stops.** The same holds for a described RAM range of the wrong size, and it is the rule the image and packaging design already applies to a limits block or a device row the machine cannot honour (`fatal_image`).
- A part with the RAM and a part without are two board descriptions (or one with a stated variant); a description with no PSRAM never touches its controller.

This settles question 5's fallback clause in SO-95's revision 4 (it recommended one image per description and a stop at boot, which is this) and replaces the fallback section asked of SO-102's design; its designer has been told.

**Lead, Nov 14: the design is written and published as the tracker doc `SO:s3-psram`** (a copy is at `.claude/lead/so102-design.md`). It changes nothing in the repository. The user and the reviewer read it before anything is built, and nothing runs on the part without the user's word.

**Its verdict.**
- **The bring-up is about forty register writes and six commands to the RAM chip, all volatile.** Each value is cited from ESP-IDF v5.4.1's octal driver or from the ROM's own code. Nothing in it writes an eFuse or a non-volatile register of either chip; it reads one eFuse word (the part's PSRAM capacity and vendor) to compare with the description.
- **How it stays off the flash.** Every command goes out on SPI1 with chip select 0 disabled, and that is read back before each command starts, as the ROM's own routine does. It writes none of SPI0's flash-side registers, never changes the shared core clock and never touches the flash's pads. ESP-IDF's speed modes and tuning are left out because they write registers the flash shares; the RAM runs at the core clock divided by four, aiming at 20 MHz, below the speed ESP-IDF tunes at.
- **The map.** PSRAM at 0x3D00_0000 for 8 MiB through the cache MMU. The part has one MMU table for both buses, so the same pages also appear on the instruction bus at 0x4300_0000 and the flash window shrinks to 16 MiB. Process data, stacks and pools go in PSRAM; code stays in flash; the kernel stays in SRAM.
- **No fallback, as ruled.** The checks run in order (the eFuse word, pad hold, SPI1 idle, ECC, the chip-select gate, the chip's vendor, good-die bit and size, the mode write, the MMU map, a full 8 MiB read-back). The first that differs prints one line naming what was read against what the board says, and halts. A halted part keeps nothing across a reset that anything reads; the flash was never selected, so download mode and `write-flash 0x0` work as on a fresh part. Identity is checked before anything is written to the chip, which is stricter than ESP-IDF.
- **Two boards on one HAL** are recommended: `esp32s3`, which never touches the PSRAM's chip select and runs on any S3, and `esp32s3-r8`, a facade over it (as the flat profile is over riscv32) whose description names the PSRAM and which brings it up or stops.

**The emulator models it, when asked** (run, under the suite lock): `-m 8M -global ssi_psram.is_octal=true` behaves as the octal part (the mode registers read as the real chip's, a mode write takes, mapped pages serve loads and stores, the instruction-bus alias reads the same bytes); an eFuse file sets the capacity and vendor word. With the flash model's trace on, the flash is selected once per boot, by the ROM, when the chip-select gate is in place, and a mutant with the gate removed sends a byte to the flash: the smoke can hold the guard that protects the flash. Not modelled: SPI0, the IO MUX, line modes, timing, the cache; those are the board stages'.

**The riskiest steps for the part,** by the designer's own account: the chip-select gate and command start (the one place a chip select is driven; guarded twice, and no write-enable is ever sent, which a non-volatile change to the flash would need), and the IO MUX and MMU index writes (a wrong index takes a pad or a page from the flash; the kernel would crash at once and a reset recovers).

**Board stages** P0 to P7, the first of which only reads and changes nothing; every one under the user's limit for the part and only on their word.

**Pins.** Octal PSRAM uses GPIO 26 (its chip select) and 33 to 37, not only 35 to 37 as the pin plan had it; the plan's proposed pins (41, 42, 21) are clear. GPIO 45 must read low at reset (it selects the flash supply).

**Its questions for the user,** each with its recommendation: two boards with the second a facade (yes); the plain board does not refuse a part that has PSRAM (it claims nothing about it); identity is the eFuse capacity and vendor plus the chip's vendor, good-die and size fields; 20 MHz; the full read-back at every boot; root's region stays in SRAM by default; the read-only stage folded into SO-77's board probe if that is not yet built.

**Not verified:** every register value on silicon; the RAM chip's datasheet limits (the maximum chip-select-low time matters at low clock rates); how SPI0 and SPI1 share the bus, taken from header descriptions and not the reference manual; atomics, halfword and unaligned access on cached PSRAM; whether GPIO 33 and 34 are brought out on the board.

Units: A the read-only probe; B the command layer with its emulator cases and stops; C the map, the read-back, the `esp32s3-r8` facade; D a child linked into PSRAM. Against SO-95: its generated link addresses come after C.

**Lead, Nov 14: revision 2 of the design is published** (tracker doc `SO:s3-psram`, revision 2; copy at `.claude/lead/so102-design.md`). All six of the reviewer's threads and the networking design's clock thread are accepted; nothing is disputed. No repository file changed.

**What changed.**
- **SPI1's clock (t1).** The sequence now saves SPI1's clock register, sets it to the PSRAM divider for the commands, and restores it. What the ROM leaves there is now cited from the ROM's own code: on the direct-boot path it writes a divide by 4 to both SPI0's and SPI1's clock.
- **Every write ESP-IDF makes on the way to PSRAM is listed** (section 2.1), each kept, dropped with its reason, or not applicable. Dropped on purpose: everything that touches the flash's pads, the flash's clock, the cache's shape, and the speed raises; kept: the PSRAM's pads and chip select, the chip-select timing, ECC off, the dividers, the commands, SPI0's PSRAM-phase registers, the MMU entries, the memory test. Added beyond ESP-IDF: the checks before anything is sent, the chip-select gate re-checked before each command, a bound on every wait, read-back of every MMU entry, save and restore of every SPI1 register touched.
- **Nothing on the command path may be fetched from flash (t2).** The command layer is one C file whose every function is placed in IRAM, with no constant tables, no dense switch, no string, no call out of the file. A build check, `check_iram`, fails on any section of that object outside IRAM code or RAM data, any symbol it uses and does not define, and any of its symbols linked outside IRAM and DRAM. Run against a stand-in in scratch: the good build passes, and five mutants (a constant table, a jump table, a 64-bit division, a zeroed struct, a function without the attribute) each fail.
- **Order (t3).** One C call from IRAM makes every comparison and returns at the first failure with a record; Saw only prints. The chip's identity is checked before the mode register is written.
- **Bounded waits (t4).** Every wait ends at 100,000 reads with its own stop. If a command never finishes, the C side prints its own short line from IRAM and leaves the flash's chip select disabled.
- **The stops, in order** (section 5.2): the record's place; the eFuse word; pads held; the system clock not the one the divider was chosen for; SPI1 busy; ECC; the gate's read-back; SPI1 busy before a command; the gate lost; a command not finishing; the chip's vendor, good-die bit and density; the mode register after its write; an MMU entry's read-back; the data bus; the read-back test.
- **Board stages (t5, t6).** The first stage no longer touches the system timer or the interrupt controller: it writes nothing beyond what every image's start-up writes, and section 9 lists exactly what that is. The stage that expects a size mismatch now expects the eFuse stop.

**The clock contract (from the networking review).** What the memory-SPI clock derives from is known on the PLL and not on the crystal: the sources allow two readings (the core at the crystal's 40 MHz, or at a PLL-derived 80 MHz), and the ROM appears to leave the part on the crystal. A later switch to the PLL with the sequence unchanged would double both bus speeds, the PSRAM to its untuned limit or past it. So: **any clock switch runs first**, in a `hal.clock_init()` before `memory_init`; the board description gains a `[clock]` section naming the three registers; the sequence compares them and stops if they are not what the divider was chosen for; nothing writes them afterwards. The first board stage reads all the clock registers, and the second times one command to settle which reading of the crystal clock is true.

**Still not verified:** every register value on silicon (the first stage's job); writes the ROM might make through computed addresses; the RAM chip's datasheet (its chip-select-low limit, its warm-boot read); the reference manual on how SPI0 and SPI1 share the bus and whether a stuck SPI1 command stalls SPI0; `check_iram` on the real file and script; GPIO 33 and 34 on the board.

**The user's seven questions** stand as in revision 1, with one addition this revision makes necessary: a `[clock]` section in the board description, checked at boot (recommended).

**Lead, Nov 14: revision 3 of the design is published** (tracker doc `SO:s3-psram`, revision 3; copy at `.claude/lead/so102-design.md`). Both new threads are accepted; nothing is disputed. No repository file changed.

- **t7, the clock.** The check before anything is sent now compares every field that can change the system clock: the source select, the pre-divider and its enable bit, the PLL frequency select and the CPU period select, and the memory-SPI core clock select. Each is a field of the board description's `[clock]` section, with the PSRAM divider beside them, and the stop line prints the three register words against what the board says. The three readings of the memory-SPI clock on the crystal are tabled against each divider (the crystal's 40 MHz; a PLL-derived 80 MHz; 20 MHz after the pre-divider), before and after a later clock change. **The early stages run at a divide by 4**, which is 5 to 20 MHz under every reading, never above ESP-IDF's untuned limit, and is also the divider the ROM left and the register's reset value, so the write changes nothing. Those stages send only mode-register commands. The reading is then settled by a measurement in the third stage (timing reads of two and of sixty-four bytes against the system timer, which runs from the crystal whatever the CPU does), and the divider fixed for 20 MHz from there on.
- **t8, the stops.** The smoke's wait harness is replaced by a fault-injecting build of the real call: every register read goes through one accessor, and a harness build makes one read at one step return an injected value, while writes always reach the real register. The runner refuses a fault record in any image that is not a harness, and the IRAM check covers the fault build. Six stops are reached with no injection (a record not in RAM, the eFuse word, the clock, the chip's vendor, its size, the read-back test); eleven by one injected read each. Each case asserts whether SPI1 was left untouched or restored, and for the gate stops that the flash model saw no select after the ROM's. The exit that leaves the flash's chip select disabled has its own case and its own mutant ("restore on that exit" turns it red).

**Still not verified:** which reading of the clock is true (the third stage settles it); that the ROM leaves every clock field at reset (inferred from its code; the first stage prints them); whether a mode-register command a few microseconds long at 5 MHz is within the RAM chip's chip-select-low limit (its datasheet is still unread); and what revision 2 listed.

**For the user:** the seven questions of revision 1 and the `[clock]` section, which now carries six fields.
