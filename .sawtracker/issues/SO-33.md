- **The rest:** the `scalars()` migration, the GIC shift's `UInt32` operands, thread-preempt's statement split, and Blade's `--module-path blade=…` are all as expected.

**The `Slab.[]` doc comment (`kernel/core/slab.saw`) is wrong.** "Declared `&var`, so … a read of the same place (`EVENTS[i].state`) is still a shared borrow: the compiler opens a shared window for a read and an exclusive one only for a write, out of this one declaration."

Probed on v0.21.0's sawc with a `&var self … borrows -> &var Int` accessor and no shared twin (`var_only_read.saw`):
- **A read through a `let` root is refused.** The compiler says "`S.[]` takes `&var self` and declares no shared twin, so every use borrows its receiver exclusively, a read included … `s` is a `let` binding".
- **Two reads held at once conflict.** `both(&s[0], &s[1])` gives "`s` is borrowed exclusively here while the window of `[]` opened at … holds `s` exclusively".
- **Sequential reads of a `var` root are fine.**

This is the language rule (SL:borrowing §3/§4, conformance row K125): the use site can narrow within the declared mode, but a read shares the root only through a `&self` accessor, written or `@synthesize(shared)`. The kernel builds because every slab is a `var` static and no code holds two windows on one slab at once.

Suggested wording: "Declared `&var` with no shared twin, so every use borrows the slab exclusively, a read included: a read through a `let` binding is refused, and two windows on one slab can't be open at once. Every slab is a `var` static and no kernel code needs two at once; `@synthesize(shared)` would add shared reads."

The rest stands, and r2 needs only this comment.
