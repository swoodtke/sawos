## Description

## Ruled design (user, Nov 11)

**A universal `INFO_OP`.** It is a third universal op beside `RELEASE_OP` and `MINT_OP`, valid on any handle kind. It answers the handle's **kind and rights word** for a word in the caller's own table.

- **No right gates it.** The answer describes the caller's own handle, not the object behind it, and the kernel still checks every op on use. It spends none of the reserved universal bits.
- **A word that names nothing** is the usual `BadHandle` fault.
- **The kind** is answered as the published kind number. Say how the C floor spells it, and keep op numbers out of the typed tier, which has no use for the kind.
- **Choose how two values come back** (the kind and the rights): two result registers if the ABI has them, or one packed word if both fit. Say which.
- **Typed tier:** `rights()` on every handle wrapper answers its rights word, to test against the kind's exported rights enum (all fifteen are public since SO-60), for example `event.rights() & EventRight.Signal`.
- **Why:** it makes "a missing right is a caller-checkable fault" true for received handles, whose rights the sender chose, and it serves generic code, debuggers and tracing.

**An invalid object:** whether `INFO_OP` answers normally on a handle to an invalid object (the handle and its rights still exist) or answers `Revoked` is to be settled in the brief. The lead's lean: it answers normally, because it describes the handle, not the object.
