## Description

**A debug process that introspects a crashed process.** The owner (Nov 17): "eventually, we probably want a debug process which can introspect a process when it crashes so i can print its state even when the state is corrupt." A process's own panic report goes through its console connection (SO-124's ruling), which a corrupt process may not manage; a separate process, holding the authority to read another's state, can report it whatever the crashed process's state.

**To design (later; not scheduled):** how the debug process learns of a fault (a Waiter attached to the Process, which already reports its death and status word; or a fault that stops a process in place for inspection instead of tearing it down); what it may read (the trap frame and registers at the fault, the faulting address and cause, the process's stats, its memory through a mapping of its regions) and the right that grants it (a new `ProcessRight`, held only by root and handed to the debug process by an image's declaration); keeping the body alive until the debugger releases it, and the teardown after; what it prints (registers, a stack walk from the frame, the fault, the last lines of the process's console). Spec changes (§2.7's death and teardown, the Process rights) go to the owner first.
