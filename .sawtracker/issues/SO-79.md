## Description

## Finding (lead, Nov 12)

`rt/common_c/support.c` supplies the word atomics (`__atomic_load_4`,
`__atomic_fetch_add_4`, `__atomic_compare_exchange_4` and the rest) as plain
read-modify-write. Its own comment states the condition: correct only while
no involuntary switch can land between the read and the write.

A target with atomic instructions never calls them: riscv32 `virt` has the A
extension and arm64 lowers atomics inline. The ESP32-C3 has no A extension,
so every `Atomic` operation there is one of these libcalls.

In the kernel the condition holds, because the kernel runs with interrupts
masked. In a user process it holds only while nothing preempts. Once the
shipping kernel arms a tick (SO-71), two threads of one C3 process that share
an `Atomic`, the sosrt arena cursor included (SO-42), can each be preempted
inside the libcall.

## Options, for a ruling when a C3 program needs it

- A restartable sequence: the kernel, on a preempting trap, rewinds a thread
  interrupted inside the libcalls' address range to the range's start.
- A syscall that performs the operation with interrupts masked.
- Leave the C3 without a tick.

No in-tree C3 program runs two threads that share an `Atomic`, and the board
this week is the ESP32-S3, so this is recorded and not scheduled.
