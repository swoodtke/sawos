## Description

## Finding

From claude-air-reviewer's review of SO-27.p1 (SO-27 c5 §1). Not probed.

`rt/common/src/lib.saw`'s bump allocator (`ARENA_NEXT`, the `__saw_rt_alloc` seam) takes no lock. Its comment justifies that with "the kernel runs with interrupts masked, so no other agent can observe the window". But `sosrt` is also **every user process's runtime**: `root/Saw.toml` and the user linker scripts reserve the arena. User mode takes interrupts and is preempted, and `thread_preempt` runs two preemptive threads in one process. Two threads of one process that both allocate can race the bound check against the cursor store, and hand out overlapping memory or overrun the arena.

## Acceptance

- [ ] A probe: two threads of one user process allocating in a loop under preemption; check for overlap.
- [ ] The fix, chosen by the probe: an atomic compare-and-swap cursor (the Saw `Atomic` machinery, or the `__atomic_*` libcalls `support.c` provides), or a documented single-allocating-thread rule that the runtime enforces.
- [ ] The comment states the real condition (SO-27's revision states it already).

## Implementation notes (lead, Nov 12)

**Model:** Sonnet. **Rules:** `.sawtracker/docs/implementer-rules.md`.
**Depends on:** nothing. SO-71 depends on this.

### The defect

`rt_alloc` in `rt/common/src/lib.saw` (the `__saw_rt_alloc` seam) reads
`ARENA_NEXT`, rounds it, checks the bound and stores `offset + size`. Nothing
makes the read and the store one step. Two threads of one process preempted
between them receive overlapping blocks.

### The fix

1. Make the cursor an `Atomic<UInt>` and advance it with a compare-and-swap
   loop: load the cursor, compute the aligned offset and the new cursor, check
   the bound exactly as today, then `compare_exchange(old, new)`; on failure
   reload and repeat. Only the winner returns its block.
2. `tests/c3-cas/src/main.saw` shows the API in this tree (`Atomic<Int>`,
   `compare_exchange`). Check the saw-lang skill for `Atomic<UInt>`, the
   static's spelling and what `compare_exchange` returns. The kernel links
   sosrt and builds with `--no-hidden-alloc`, so the change must allocate
   nothing.
3. Keep the out-of-memory path as it is: the message, then
   `sos_rt_abort(AbortCode.NoMemory …)`.
4. Don't touch `rt/common_c/support.c`. On a target with atomic instructions
   (riscv32 `virt`, arm64) the compare-and-swap lowers inline. On the
   ESP32-C3 it becomes the `__atomic_compare_exchange_4` libcall, which is a
   plain read-modify-write; that limit is SO-79 and stays.

### The probe and the case

1. New root package `tests/arena-race/`, modelled on the root package of the
   `thread_preempt` case (`THREAD_PREEMPT_PKG` in `tools/sos_runner.py`): two
   worker threads in one process under the preemption harness kernel
   `tests/threads_timer.saw`, which arms a 1 ms tick.
2. Each worker allocates many small blocks in a loop through whatever in the
   package reaches `__saw_rt_alloc` (say which construct you used), writes its
   own marker byte across each block and records the block's address and size
   in a static table of its own.
3. After both are joined, the initial thread checks that no block of one
   worker overlaps a block of the other and that every block still holds its
   marker. It prints one line for success and a different line naming the
   first overlap.
4. Size the loop to fit the arena: nothing is reclaimed. The linker scripts'
   `ARENA_SIZE` is the budget; `tests/arena-small/` shows a package choosing
   its own.
5. **Before the fix,** run the case at least 20 times on riscv32 and report
   how often it shows an overlap. If it never does, try to widen the window
   (more allocations, both workers started before either allocates) and
   report what you saw. Don't claim a reproduction you didn't get.
6. **After the fix** the case passes on all three profiles, 20 runs on
   riscv32 included. It strips kernel lines like `thread_preempt`
   (`strip_kernel_lines`), since tick narration lands in the stream.

### Docs

- The cursor's doc comment: state the new rule and the C3 limit.
- Spec §11's known limit on the arena, and the §5c sentence it points at:
  the arena is safe under preemption on a target with atomic instructions;
  on a part without them, word atomics in a user process are safe only while
  nothing preempts.

### Runs

The new case, `thread_preempt`, `thread_basics`, `arena_small` and three other
cases of your choice that allocate or panic, on three profiles; then
`--board esp32c3`.
