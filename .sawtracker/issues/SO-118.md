## Description

**arm64: a lazy FP save can run after the outgoing thread's process has ended.**

Found by the windowed-threads designer (SO-112, revision 2, section 12a), by reading; not run. In the arm-free scheduler, `pick_next` calls the HAL's `fp_switch_out` for the outgoing thread **after** `idle_until_runnable`. During the idle wait, `drain_deaths` can end the outgoing thread's process, so the FP save then writes into a thread slot whose process is gone and whose slot may be on its way to reuse. It is harmless today only because slab donation is permanent and a frame slot is reused only through `frame_init`, which overwrites the save area.

**The fix:** call `fp_switch_out` for the outgoing thread before the idle wait (one line in the core), so the save is made while the thread is still its process's, and never into a slot an idle-time teardown has released. Any lazy scheme on the S3 (SO-115) depends on the same ordering.

**Acceptance**
- [ ] a case on arm64 that ends a thread's process during the idle wait after that thread used FP, with a later thread reusing the slot, and checks that neither the new thread's FP state nor its frame is disturbed; red with the call where it is today, if a red can be made by construction (say how, or argue why not)
- [ ] the spec's Profile B FP sentence (§7) still true, or corrected

**Lead: SO-118.p1 is up.** `pick_next` calls `hal.fp_switch_out(current_frame)` once, before `ready_pop()` and the idle wait, instead of after them. Gate on the implementer's machine: 1035 / 6 / 43 and 1 board-only.

**The hazard the issue describes cannot be reached today**, by reading, so the new case is a liveness check, not red and green: while the processor idles the outgoing thread is still `CURRENT_THREAD`, and a death of its own process during the idle wait is paid through the running-process fault path, which ends in `resume_after_death` and never returns into `pick_next`'s tail; a death of another process leaves the outgoing slot alone; and a reused slot's FP area is zeroed by `frame_init` anyway. The implementer checked this with two temporary probes (a stop if the outgoing slot were `Invalid` or `Free` after the wait, never fired; and that the case does reach the idle wait with the FP-using thread outgoing). The move is still the right order, and it is what a lazy scheme on the S3 (SO-115) needs.

**Case `fp_idle_teardown`** (arm64): a child's thread fills FP state and is the last to block, so the kernel idles with it outgoing; a Timer's fire then ends the child (its wait record was unmapped); root then starts a thread whose first FP use reads zeros and whose own pattern survives a yield. Its source and runner entry say it is a liveness check, and why. **§7** now says the save comes "before the processor idles and before the slot of an exited thread is released". `hal/arm64/kernel/lib.saw` and `ABI.md` follow.

Approved patch SO-118.p1 (revision 1)

**Approved (reviewer, Nov 15), revision 1.** The save is in the right place, the note's account of why the old place could not be caught holds over the whole arm64 profile, and the new case is steady under load.

- **The move:** `hal.fp_switch_out(current_frame)` now comes after the outgoing thread is put back on the ready list and before `ready_pop()` and the idle wait; it ran after them, just ahead of the deferred free. It is still called once for every thread that leaves the processor, and the kernel uses no FP register in between, so what is saved is the same; only when it is saved changes. On riscv32 and the S3 the call is empty.
- **The note's premise, probed** (chat f168, `old_order_stop.py`): the old order put back, with a stop if the outgoing slot is `Free` or `Invalid` after the idle wait. All 340 arm64 cases pass, the new one among them, and the stop never fires. So no case can tell the two orders apart today, as the note says, and the case is the liveness check it calls itself.
- **The case does hold the save itself:** with the call removed, `fp_idle_teardown` is red ("new thread nonzero=0" is not printed) and so is `fp_threads`.
- **Under load:** `fp_idle_teardown`, 15 of 15 on arm64 with six cores kept busy. Its Timer is the event that ends the child, not a park for ordering.
- **The text:** spec §7's sentence, the comment in `pick_next`, and `fp_switch_out`'s doc in the arm64 HAL say what the code does.

Smaller: the second changed line of `hal/arm64/kernel/ABI.md` is 105 columns where its neighbours wrap near 80.

**Not run by me:** the suite on the other profiles and the smokes (the server's gate passed).
