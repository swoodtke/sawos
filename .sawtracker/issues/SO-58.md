## The change

2. **Boot record kinds** (`kernel/abi/src/boot.saw` `BootHandleKind`): add
   `Thread`, `Event`, `Waiter`, `Timer`, numbered after `PipeRequest`. Update
   `boot_kind_of` and `msg_kind_of` (`kernel/core/objects.saw`) so all four can
   be given and carried in a message. Check the kernel's give, stage and mint

   Thread that is running or joined), find out what the code does today and
   report it. **If moving one would break an invariant, stop and ask.**
3. **Typed tier** (`kernel/sysapi/src/`):
   - `PipeHandle` gains a case for each, and `decode_handle` decodes them.

   - `BootHandle` accessors for the four kinds, matching the existing ones

   The modules for these kinds sit below `sos.pipe` (no import cycle); confirm

**Lead review, SO-58.p1, rescoped to Event only.** An Event is givable and shared.

**Kernel.**
- `event_rights()` gains `Transfer`, and `BootHandleKind.Event = 8` is added. `boot_kind_of` gets an Event arm, which `msg_kind_of` inherits.
- `free_object(Event)` credits through `credit_shared`.
- `reap_unreferenced(p)` gets a first scan over the Event slab. It frees what nothing names, and those frees credit `p`'s ledger before `quota_clear`. It disowns `p`'s still-named Events.
- The by-owner Event sweep is gone, and `events=` now counts the reap's frees of `p`'s own Events.
- No existing `events=` assertion changed.

**Typed tier.**
- `PipeHandle.Event`, `PipeHandles.put(event:)`, `decode_handle`, `Process.give(event:)` (with the status hand-back), `BootHandle.event` and `take_event()`.
- No import cycle: `sos.event` sits below `sos.pipe` through `sos.waiter`.

**Attachments.** An attachment on another process's Waiter keeps a living Event's ref, so a disowned Event stays attached.

**Tests.**
- `event_give`: a boot give and a message round trip.
- `give_event_returns`: a refused give hands the Event back.
- `event_outlive`: the owner dies holding three Events. Two are freed (`events={two}`, capacity back), the sent one keeps working, and capacity returns once it is released.
- **Not built:** the reused-record over-credit probe. Without `credit_shared`, `event_outlive` would stop the machine at the final release, so the no-owner test is still exercised.

**Runs.** The full suite passes locally, 421 runs, plus the C3 smoke.

**Lead edit:** I reflowed one 86-column comment line in sched.saw.

**Scope.** Thread, Waiter and Timer stay non-givable until their own invalidation; their markers are untouched.

Requested changes on patch SO-58.p1 (revision 1)

**Air: SO-58.p1, changes requested: one contract break that needs a user ruling, an untested disown, and stale docs. The kernel paths themselves are right.** It also needs a rebase onto SO-54.p2 (merged 8102f46), which rewrote `reap_unreferenced` and `end_process`.

**1. A process can now be killed because a different process attached the same Event. This needs a ruling.**
- `waiter_add` faults the caller with `BadState` when the target is already attached (dispatch.saw:2057-2060). The attachment is recorded on the Event slot (`EventSlot.attachment`, waitables.saw:115), not on the handle.
- With this patch an Event travels with `Wait`: `event_rights()` mints it, `give`'s default keep is all rights, and messages pass rights unchanged.
- So if process A attaches its handle, process B attaching ITS handle to the same Event is terminated. B can't check for this first, and no op lets it ask.
- That breaks the faults ruling (spec §6: "a caller error the process could have checked … terminates", and "a condition the caller could not have known answers with a status"). It also makes these false for Events:
  - dispatch.saw:2024-2026 ("caller-checkable: the process is the only thing that attaches anything, so it knows");
  - waiter.saw:74-76;
  - spec §2.2/§2.4's "a handle attaches to at most one Waiter" (the kernel enforces one Waiter per OBJECT, not per handle).
- The same flaw already exists for pipe-end siblings given to two processes; this patch extends it to Events, unmarked.
- The fixes I can see:
  - (a) answer a status (not a fault) when the object is attached through ANOTHER process's handle;
  - (b) move the one-Waiter rule to the handle, with a list on the object;
  - (c) withhold `Wait` from a given Event by default (keep the producer-narrowed-to-`Signal` pattern).
- Which one is the user's call; meanwhile the spec should mark the gap.

**2. No test fails if the disown is deleted** (`disown_event`, refs.saw:748, 819-826).
- In `event_outlive`, root's final release would then credit slot 1, which is reclaimed with its ledger already zeroed, and `quota_credit`'s zero test makes that a no-op. Nothing reuses slot 1.
- The real hazard, a refund reaching the slot's next occupant, is untested. This is the over-credit probe you noted as not built.
- Under SO-54's split it needs record reuse: hold nothing on the dead owner's record so a new create takes it, then release the Event and check the new process's capacity didn't grow.
- `event-outlive`'s header (main.saw:13-17) implies the test shows "charged to nobody"; it doesn't.

**3. `give-event-returns` claims a teardown-line proof the runner never checks.** main.saw:11-14 says "Root's teardown line is the second half of the proof, as in give-full-returns", but the runner case (sos_runner.py ~4339-4357) asserts no teardown line. "The Event is dropped at the end" is also inaccurate: root exits holding `back`, and the close-all releases it.

**4. The "own Events" filter isn't pinned.** Dropping `if EVENTS[e].process == p` (refs.saw:745) changes no test, since no test has a dying process hold the last name to another process's Event.

**5. Stale or unmarked docs:**
- boot.saw:66-74 (published `///`): "A Thread, Event, Waiter … cannot be given at all", and its list of sets minting `Transfer` omits `event_rights()`.
- system.saw:743-750: "Thread, Event, … handles therefore cannot be given at all", directly above the new `give(event:)`.
- objects.saw:646: `credit_shared`'s shared-kind list omits Event.
- sched.saw:229-232: the `end_process` docstring still says "every Event … it held goes back to its slab".
- waitables.saw:110: `EventSlot.process` lacks the "or `NO_PROCESS` once disowned" note the Memory/IoMemory slots carry (the warning against using it as an index); the `refs` doc (:117) omits staged-message references.
- spec ~1633-1635: the `events=` sentence over-claims. An own Event staged on the dying process's own pipe is freed inside the close-all (the outlet's zero arm), and one named only by a message in an exchange the reap settles is freed by the exchange scan; neither is counted. The reap docstring (refs.saw:719-722) says a staged-only Event is "freed later by the exchange scan's release", which is false when the message is owed to a live outlet, `event_outlive`'s own case.

**Checked and fine:**
- Every reader of `EventSlot.process` is `free_object` (through `credit_shared`), the count and the disown, so no index of −1 is possible. Signal, wait and delivery faults use the acting thread's process.
- Every way a reference is held and dropped keeps an exact count and one free: a handle elsewhere, a staged message delivered or released later, a pending boot give, an attachment on another process's Waiter (keeps the disowned Event live), an attachment on the dying process's own Waiter (detached before the scan), a consuming attach, a refused give (minted before unbind).
- **The teardown order:** every free crediting `p` precedes `quota_clear`, and later ones see `NO_PROCESS`.
- **The mutants:**
  - replacing `credit_shared` with a direct credit IS caught: `event_outlive` stops on `PROCESSES[-1]`, as you said;
  - keeping the old by-owner sweep is caught (`events=` reads three);
  - removing `Transfer` is caught;
  - moving the Event scan after `quota_clear` is an equivalent mutant.
- Runner assertions are additions only. Spec lines are ≤ 80, with no IDs or history.

**User ruling (Nov 9) on Air's SO-58.p1 item 1, relayed by Air: keep the fault.** In the user's words: "the reason we choose to fault instead of returning errors because the fault indicates a program error - which this is: only 1 waiter per Event - enforce that however you want in your code".

So `waiter_add` keeps faulting `BadState` on an already-attached Event, whichever process's handle attached it. No status answer and no per-handle attachment list. The one-Waiter rule is a contract on the **Event**, binding every holder, and keeping it is the programs' job: for example, a giver withholds `Wait` with the keep mask, or the processes agree which one attaches.

**What this leaves for the revision:** the text that states the rule per handle, or calls it something only the attaching process can get wrong, should state it per Event:
- spec §2.2 ("a handle attaches to at most one Waiter") and §2.4 ("a handle attaches to at most one Waiter, so no second watcher …"): an Event, whichever handle names it;
- dispatch.saw:2024-2026 ("caller-checkable: the process is the only thing that attaches anything, so it knows") and waiter.saw:74-76;
- optionally, a sentence beside `give(event:)` (or the `Process.give` docs) saying a full-rights give hands over the right to attach, so a giver that attaches itself should withhold `Wait`.

Items 2-5 of the review stand.
