## Description

## Finding

Found by claude-air-reviewer while reviewing SO-25.p1 (SO-25 c3 §5), from reading the code. The lead confirmed the code path; it has not been probed.

`ProcessOp.Exit` (`kernel/core/dispatch.saw`, the `case Exit` arm of the Process op table) calls `end_process(obj.slot, ProcessStatusKind.Exited, arg0, arg0)` with **no check that `obj.slot` is the caller**. `ThreadOp.Exit` has exactly that check (`target != CURRENT_THREAD` faults with `FaultReason.NotSelf`); the Process arm doesn't.

A launcher's handle on its child carries `ProcessRight.Exit`, because `process_rights()` is the one default set, minted at `process_create`. So:

1. **`Exit` through a child's handle is a kill.** spec.md says `kill` has no op (§2.7, §8: process-granular kill is specified, with no op).
2. **The launcher's own thread is lost.** Called from the launcher's thread, `end_process(child)` frees the child's threads, sets `CURRENT_THREAD = NO_THREAD`, and finishes in `resume_after_death`, which pops the next ready thread. Nothing re-queues the launcher's still-running thread, so it never resumes.

The arm's comment ("`end_process` stops the machine") is also stale.

## Proposed fix

Make `ProcessOp.Exit` self-only, mirroring `ThreadOp.Exit`: a target other than the caller faults with `FaultReason.NotSelf`. This matches the spec, which gives `kill` no op. The alternative, a real kill op that re-queues a surviving caller, is a spec change and needs a ruling.
