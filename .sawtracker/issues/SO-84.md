## Description

## Decision (user, Nov 12)

"If the current location == link location just leave it there? And just
allocate and copy for the data sections?" ... "OK. Let's do it this way."

**A segment that is already where it is linked is used in place.** On the
ESP32-S3 a process's code and read-only data stay in flash, and only its
writable memory is copied into RAM. The earlier design on this issue (code
copied into IRAM a word at a time; the "design" comment below) is
superseded and kept for the record: its word mover may return as a unit of
its own if a program ever has to be loaded into RAM at run time.

## Why this unit exists

On the user's board the kernel boots, enters user mode and takes timer
interrupts, but loading a process fails: the loader's first byte store to
an IRAM address is refused (SO-76). The part serves each kind of access
only at some addresses:

| Addresses | Fetch | Word access | Byte and halfword |
|---|---|---|---|
| flash instruction window (0x4200_0000) | yes | load only | refused |
| flash data window (0x3C00_0000) | no | load only | load only |
| IRAM (0x4037_8000) | yes | yes | refused |
| DRAM (0x3FC8_8000) | refused | yes | yes |

All of it probed on the board (SO-76's tables), except that fetch from the
flash data window was not tried. The two flash windows are one flash, and
IRAM and DRAM are one SRAM.

## The rule

- A segment whose bytes already sit at the address it is linked for is used
  in place. Nothing is copied; the process's grant names the image's own
  bytes. It must be read-only and have no zero-filled tail.
- Every other segment is copied into the destination region, as now.
- The kernel allocates nothing, as now: the launcher supplies the
  destination, which needs room only for what is copied, plus the stack.
- The rule is the loader's and holds on every board. On the ESP32-S3 an
  executable segment that is not in place is refused.

## On the ESP32-S3

- Code and literal pools: linked at the flash instruction window, in place.
- Read-only data: linked at the flash data window, in place.
- `.data`, `.bss`, the arena, the stack: at DRAM addresses, copied or
  zero-filled.
- Nothing of a process sits at an IRAM address.

## Who does what

- **The build** gives each resident image a fixed place in flash, links its
  code for that place, and fails if the two do not agree.
- **The kernel's loader** recognises and validates the in-place case and
  skips the copy. One loader, as now (spec §12): no second code path.
- **Elsewhere in the kernel:** the image is kept alive while a process runs
  out of it; a system call accepts a buffer that lies in an in-place
  read-only segment (a string literal).
- **The HAL** says whether two addresses name the same byte (the two flash
  windows on this board; the identity elsewhere).

## For the design pass to settle

- How the build makes the link address and the flash position agree: the
  linker script computing it from the format's header size with the runner
  checking, or a Blade option to place a segment's bytes at a chosen file
  offset (a sawlang change, to raise with the sawlang lead if chosen).
- The copy-in window when read-only data is outside the destination.
- The image's lifetime: the grant rows hold its `Memory`.
- Alignment of an in-place segment where the protection grain is coarse
  (arm64's pages), and whether the isolated profiles get a case.
- What a region-table row and a `Memory` over flash may be used for.
- What the emulator shows and what only the board shows.

## Acceptance

- [ ] design and spec text reviewed by the user
- [ ] the gate's profiles pass with the in-place rule in the loader
- [ ] the S3 smoke passes under QEMU with processes running from flash
- [ ] `root_server_boot` prints root's lines on the user's board

## The design (Opus design pass, Nov 12; awaiting the user's review)

Nothing is built. The spec text is one commit touching `spec.md` only, held
by the lead (`.claude/lead/so84-spec.diff`).

### No sawlang change is needed

A sosimg can already carry segments at two disjoint address ranges with the
entry in either: every segment's `load_addr` and the header's `entry` are
absolute, and Blade's emitter takes each `PT_LOAD` as it finds it, with no
base, span or ordering rule.

One hazard on our side: left to itself `ld.lld` loads the ELF's own headers
into the page below the lowest section, which here is the DRAM twin of
root's code, so the loader would write header bytes over the code. The S3's
user linker scripts must name their `PHDRS`. Shown with a trial link of
root's objects: three loads and no header load once `PHDRS` is explicit.

### The image

- **Instruction (IRAM) addresses:** literal pools and code, one R+X segment
  at the bottom of the region. Literals stay beside the code: `l32r` is a
  word load.
- **Data (DRAM) addresses:** `.rodata` as its own R segment (Saw reads
  strings a byte at a time, and a copy-out into it stays refused); `.data`,
  `.bss` and the arena as one RW segment; the stack at the region's top.
- The linker starts `.rodata` at the DRAM twin of the code's end, so no byte
  is reached through both names, and overflow is a link error.
- Regions, `Memory` capabilities, stack tops and both copy windows are all
  in data addresses. Root: code from 0x403A_0000, data in DRAM
  0x3FCB_0000 to 0x3FCC_8000.

### The kernel

- **Two HAL seams,** the identity on every other board:
  `data_name(addr)` maps an instruction address to the data address of the
  same byte; `segment_name_ok(addr, len, flags)` says whether a segment is
  linked where the board's buses serve its permissions (S3: executable and
  not writable at IRAM, everything else at DRAM).
- **The loader** checks each segment with the second seam and runs its
  region tests on `data_name(load_addr)`; refuses two segments that share
  storage (the linker sees two numbers, the loader sees one byte); checks
  the entry by the storage it names; and **stores an executable segment
  with aligned word stores through its linked address**, the last word
  padded with zeros. Other segments are copied by bytes as now.
- **Word placement and the overlap refusal are arch-free,** so the gate's
  three profiles run them. Only the bus rule is the S3's.
- **Copy doors need no change:** both windows are data addresses, so an
  instruction address handed to the kernel is outside the process and
  answers `BadBuffer`. The kernel never makes a byte access at an IRAM
  address, so a process cannot stop the machine that way.
- `thread_create` checks its entry through `data_name`. A region-table RAM
  row at an instruction address stops the boot.

### Why not otherwise

- Storing code through its DRAM twin: the emulator keeps IRAM and DRAM as
  separate arrays, so its IRAM would stay empty and no process would run
  under the smoke.
- Everything at DRAM: the data bus is not expected to fetch instructions.
- Everything at IRAM with word-only stores: compiled code makes byte and
  halfword accesses to its data.
- Regions in IRAM addresses: every data path would need translating.

### What silicon must show first (the next probe image)

The design depends on six facts not yet seen on the part: word stores at
process IRAM addresses; instruction fetch from code stored that way, in
kernel and user mode; `l32r` there from user mode; every access width at
process DRAM addresses; `s32c1i` at a DRAM address with the ROM's
`ATOMCTL`; and the alias itself (a word stored at a DRAM address read back
at its IRAM name). The probe names each step before making it and recovers
from a refusal.

**What the emulator can never show:** that the two names are one byte, that
a sub-word access at IRAM is refused, and that code was placed by words (a
byte-store mutant passes there). Only the board shows those.

### Decisions for the user

1. **A code address handed to a system call as a buffer on the S3:**
   refuse it (`BadBuffer`, the process ends; recommended), or have the
   kernel read it by words. Refusing is one answer that differs from
   riscv32, where a code-segment source is accepted; no program does it now
   that read-only data is at data addresses.
2. **Mapping a region executable on the S3:** record as a known limit that
   mapped code cannot run there (recommended); or place such rows at
   instruction addresses, which the emulator cannot check; or refuse the
   request. Nothing runs mapped code on any board today.
3. **The overlap refusal and word placement on every board** (recommended)
   or the S3 alone. Every board gains one `BadImage` reason; S3-only would
   hide the word mover from the gate.

### Found on the way, not part of this unit

- `process_create` with a destination that is a flash blob row, and an
  image linked at the blob's addresses, passes validation, and the loader
  then stores into flash: a kernel fault on a part. The new bus rule closes
  it on the S3; it stays open on the C3. To be filed.
- No instruction barrier after the loader writes code on the RISC-V boards
  (the S3 has `isync` on its restore path). Not verified. To be filed.

## Direction from the user (Nov 12): leave a segment where it is

After asking how a process is loaded and what the image format holds, the
user proposed: "if the current location == link location just leave it
there? and just allocate and copy for the data sections?"

That changes this unit's shape. The design above (code copied into IRAM by
words) is to be redone on this basis before any spec goes for review.

### The rule, as the lead reads it

A segment whose bytes already sit at the address it is linked for is used in
place: nothing is copied, and the process's grant names the image's own
bytes. It must be read-only and have no zero-filled tail. Every other
segment is copied into the destination region as now.

### What it does for the ESP32-S3

- A process's code runs from the flash instruction window and its
  read-only data is read through the flash data window. Only `.data`,
  `.bss`, the arena and the stack take RAM, at DRAM addresses.
- No process code goes into IRAM, so the word mover and the IRAM/DRAM
  overlap check in the design above are not needed for the box. An
  executable segment that is not in place is refused on this board.
- Everything it rests on has been seen on the user's board: user-mode
  execution from the flash instruction window (`umode_syscall`,
  `timer_tick`), word loads there, byte loads through the data window, and
  every access width at DRAM from user mode (probe v2).
- The emulator models the two flash windows as one memory, so the smoke can
  show this faithfully, which it could not for the IRAM/DRAM alias.

### What the redone design has to settle

- **"The same location" is judged by storage.** On the S3 the image is
  known to the kernel by its data-window address and its code is linked at
  the instruction-window address of the same flash bytes. The HAL seam that
  maps one name to the other is still needed, for the flash windows now.
- **The build must make the two addresses agree.** Each resident image
  needs a fixed place in flash, and its link address is that place plus the
  segment's offset inside the image file. Either the linker script computes
  it from the format's known header size and the runner checks it, or Blade
  gains a way to place a segment's bytes at a chosen file offset (a sawlang
  change; to raise with the sawlang lead if wanted).
- **The image must outlive the process,** since the process now runs out
  of it. The grant rows hold the image's `Memory`, as they hold the
  destination's today.
- **The copy-in window.** A string literal is now at a flash data-window
  address, outside the destination region, and a system call must still
  accept it as a source.
- **The isolated tiers:** the grant for an in-place segment must cover
  exactly the segment, so its alignment in the image matters where the
  protection grain is coarse (arm64's pages).
- **Whether loading code into RAM stays possible on the S3** (the word
  mover, for a program that arrives at run time) or is left out until
  something needs it. The lead recommends leaving it out.

The three decisions listed above change with it; they are restated with the
redone design.

## The redone design (Opus, Nov 12; awaiting the user's review)

Nothing is built. The spec text is one commit touching `spec.md` only, held
by the lead (`.claude/lead/so84-spec-inplace.diff`, 66 added lines).

### The build: no sawlang change

Each S3 user linker script computes its own addresses from the format's
fixed sizes, and three things check the result:
- the image's header is 24 bytes and each segment record 24, pinned by
  `static_assert` in `imgformat`; Blade writes one segment per `PT_LOAD` in
  program-header order, packed at 4 bytes. With three segments the code's
  bytes start at offset 0x60;
- the script declares its `PHDRS`, links code at the slot's
  instruction-window address plus 0x60, links read-only data at the
  data-window address of the byte after the code, and `ASSERT`s both;
- **the runner reads each staged image back and fails the build** when a
  segment's link address is not where its bytes sit in flash;
- **the loader refuses** a mismatch that slips through. It can never run.

Shown with a trial link of root's objects: code at 0x4210_0060, read-only
data at 0x3C10_1500, which is exactly where Blade's packing puts its bytes.

If the scripts' dependence on Blade's packing becomes a burden, the
alternative is a Blade key giving the image's base address, with Blade
placing each segment's bytes at its load address minus that base. Not
needed now.

### The kernel

- **Two HAL seams.** `same_bytes(link, at, len)`: does this user address
  name the bytes the kernel reads at `at`? The same number on the riscv32
  boards; also an instruction-window address and the data-window address of
  the same flash byte on the S3; never on arm64, which copies everything.
  `segment_bus_ok(addr, len, flags, in_place)`: can the board serve the
  segment there? Always, except on the S3: executable only in place in the
  instruction window; read-only in place in the data window or copied to
  DRAM; writable copied to DRAM.
- **The loader:** an in-place segment must be read-only, with no
  zero-filled tail and its grant inside the image; it is not copied, and
  its grant row names the image's bytes and holds the image's `Memory`.
  Other segments are copied and judged against the destination as now.
- **The image's lifetime:** in-place rows count as references on the
  image, so a launcher may release its handle; the bytes stay until the
  child's teardown.
- **Copy-in** also accepts a source in the process's in-place read-only
  segments (a string literal in flash). **Copy-out** is unchanged.
- **A destination must be memory the board can give a process,** so a
  `Memory` over flash is an image source only. That closes a hole found in
  the first pass (`process_create` into a flash row). Donating a flash
  region to the kernel's slabs becomes a fault for the same reason.
- **A thread's entry** must lie in a row that permits execute, since code
  may now be outside the process's region.
- Dropped from the first design: the word mover, the IRAM/DRAM overlap
  refusal, `data_name`.

### The S3's layout

| Flash offset | Holds |
|---|---|
| 0x00_0000 | the kernel's code (up to 1 MiB) |
| 0x10_0000 | root's image slot (512 KiB) |
| 0x18_0000 | a child image's slot (512 KiB) |
| 0x20_0000 | the kernel's read-only data, as now |

RAM, all at DRAM addresses: root 0x3FCB_0000 to 0x3FCC_8000 (the top 16 KiB
its stack), a child 0x3FCC_8000 to 0x3FCE_0000, the pool to 0x3FCF_0000. A
process's region now holds only its writable data, arena and stack.

### The gate runs the in-place branch

A hand-assembled riscv32 image states its own code's address as its load
address, so it is in place wherever the linker puts it: three cases on
riscv32 and riscv32-flat (in place and running; refused when writable;
refused with a zero-filled tail). The S3 smoke runs every process case from
flash, since the emulator maps both flash windows onto one memory.

### Still inferred, not seen

`l32r` and byte loads through the data window from user mode. The core has
no privilege, the kernel does both on the board, and user payloads ran in
place there, but those used no literal. `root_server_boot` on the board
settles it.

**Only the board shows** that a byte load in the instruction window faults;
the emulator serves it.

### Decisions for the user

1. **A code address handed to a system call as a buffer on the S3** is
   `BadBuffer` and the process ends (recommended). It is the one answer
   that differs from riscv32, where a source in the code segment is
   accepted. The alternative is a word-at-a-time read path in the kernel.
2. **A thread's entry must lie in executable memory, on every board**
   (recommended). An entry pointing at data becomes `BadEntry` at create,
   where today it is a fault at the first instruction. The alternative
   keeps today's region check and adds a code window per process.

### Sequencing

SO-76's pending patch moves the root image out of the instruction window
(main today reads root's header there, which a part refuses) and this
design moves it again, to a fixed slot. So this is built after SO-76
merges.

### To file separately

- No instruction barrier after the loader writes code on the RISC-V boards
  (unverified).

## Rulings (user, Nov 13)

1. "We should refuse to send any data which is marked as executable - even
   strings embedded in the code probably shouldn't be sent."
2. "Yes - only executable memory can be provided as the entry points."

### What the lead takes them to mean

- **Ruling 1 is a rule about permissions, so it holds on every board,** not
  only where the bus forces it: a system call's buffer may not lie in
  memory the process may execute. This is stronger than the design above,
  which refused only the ESP32-S3's instruction window.
  - On riscv32, arm64 and the ESP32-C3 a program's read-only data shares a
    segment with its code today, so a string literal handed to a system
    call lies in executable memory. Under this ruling every board's user
    linker script gives read-only data a segment of its own (readable, not
    executable), as the S3's already must.
  - Hand-written payloads that print a string kept beside their code need
    the string in a segment that is not executable.
  - The design pass states what that costs each board (a grant row and, on
    riscv32, a protection entry per process; a page boundary on arm64) and
    stops if a board cannot afford it.
- **Ruling 2 is the design's recommendation,** unchanged: a thread's entry
  must lie in memory its process may execute, on every board.

The spec is revised to these and then uploaded for review.

**Lead, Nov 13: the design is revised to the rulings and split in two.**

- **SO-85 (new, first):** on every board, executable memory is not a
  buffer, a thread's entry must be executable, and read-only data gets a
  segment of its own. It needs no board.
- **This issue (second):** segments used in place, the ESP32-S3's flash
  layout and the run on the user's board, built on SO-85's linker scripts.

The spec patch on this issue covers both.

### What a third segment costs each board

| Board | Cost |
|---|---|
| riscv32 virt | root's grant rows 3 to 4 of 8; PMP entries in use 6 to 8 of 16; rows free for `map` 5 to 4 |
| riscv32-flat | the same rows, no hardware |
| ESP32-C3 | the same rows and entries; at most 15 bytes of padding |
| arm64 | rows 3 to 4 of 9; up to one page of padding per image |
| ESP32-S3 | none: read-only data is in place in flash |

Every board can afford it, so no board uses the fallback of read-only
data in the writable segment.

### Why the ruling is the right one, from built images

On riscv32 a `switch`'s jump table is in `.rodata` and holds absolute code
addresses. In the writable segment those would be code pointers a process
could overwrite; in a read-only segment they stay as protected as they are
today beside the code. `.rodata` also holds string literals and constant
pools. No function-pointer or dispatch table was found in the samples.

The spec never promised that read-only data is read-only to its own
process; it is a built property on the isolated profiles, and this keeps
it.

### Checked on the way

- A string literal is never written: Saw's String drop skips its atomic
  when the count reads as a literal's, so a literal in flash or in a
  read-only segment takes no store.
- No hand-written payload or fixture needs a change (the list is in
  SO-85).
- The S3 trial link was redone with literals interleaved with code: code
  at 0x4210_0060, read-only data at 0x3C10_1500, data at 0x3FCB_0000.

### This unit's implementation notes (they replace the earlier ones)

1. `loader.saw`: `check_segment` computes the in-place test
   (`file_len > 0 && hal.same_bytes(load_addr, img_base + file_off,
   file_len)`) and asks `hal.segment_bus_ok`. An in-place segment must be
   readable and not writable, with `mem_len == file_len`, grain-aligned,
   its grant inside the image; it skips the region checks. The entry is
   checked by `entry_is_executable` alone. `place_image` takes the image's
   region and returns the writable floor and the read-only window; an
   in-place row is granted at its link address and holds the image.
2. `pslot.saw`, `process.saw`, `dispatch.saw`: the body's read-only
   window; copy-in accepts the region or that window; `process_create`
   requires a destination that passes `hal.map_source_ok` (`BadImage`
   otherwise) and passes the image's slot; `slab_donate` faults `BadArg`
   on a region that fails it.
3. Seams on every HAL: `same_bytes` (the same number on the riscv32
   boards; never on arm64; the two flash windows on the S3) and
   `segment_bus_ok` (true except on the S3: executable in place in the
   instruction window; read-only in place in the data window or in DRAM;
   writable in DRAM).
4. The S3 build: `esp32s3.ld` (the kernel's code within 1 MiB; root's
