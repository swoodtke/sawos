## Description

## Goal

Processes run on a real ESP32-S3. On the part, internal RAM is one SRAM seen
through two buses, and each bus serves only some accesses:

- **IRAM addresses** (0x4037_8000 and up): instruction fetch and word loads
  and stores. A byte store is refused (`LoadStoreError`, cause 3): seen on
  the user's board in the loader's first store to root's region (SO-76).
- **DRAM addresses** (0x3FC8_8000 and up, the same bytes at IRAM minus
  0x006F_0000): loads and stores of every width. Not expected to execute.

Today every process is linked and loaded wholly at IRAM addresses, which the
emulator forgives. The kernel boots on the board, enters user mode and takes
timer interrupts there; loading a process is the first thing that fails.

## The shape the lead proposes (to be confirmed by the design pass)

1. **A process image has two address ranges for one region:** literal pools
   and code at IRAM addresses in the low part of its region; read-only data,
   data, `.bss`, the arena and the stack at the DRAM addresses of the rest.
   The S3's user linker scripts do this. Literals stay beside the code, since
   `l32r` is a word load.
2. **The loader stores an executable segment with word stores,** through
   the addresses it is linked at. That works on the part (the kernel's
   vectors are already copied into IRAM that way) and on the emulator, whose
   IRAM and DRAM are separate arrays, so storing code through the DRAM name
   would leave the emulator's IRAM empty.
3. **The kernel's region checks compare storage, not names:** a HAL seam
   maps an address to the canonical name of the storage it reaches (the
   identity on every other board), so a segment at an IRAM address and one
   at a DRAM address are both inside the region, and cannot overlap each
   other unseen.
4. **Addresses a process hands the kernel** (buffers, strings, stack tops)
   are data, so DRAM names. What the kernel does with an IRAM-named buffer
   is decided in the design: refuse it, or reach it through its DRAM name.

## Open questions for the design pass

- Does the sosimg format, or Blade's emitter, assume one contiguous link
  span per image? If so this needs a sawlang change, and the sawlang lead
  is told at once.
- Which kernel paths touch process memory by address (the loader, the
  `.bss` fill, copy-in and copy-out, the stack grant, Memory objects and
  their sharing ops), and which name each sees.
- What the Flat tier's spec text promises about addresses, and what the
  board's row has to say.
- How the emulator smoke keeps passing with IRAM and DRAM as separate
  arrays, and which silicon-only property it therefore cannot show.
