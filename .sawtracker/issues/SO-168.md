**Networking K2: a second device window on arm64.**

Design: `SO:virtio-net` rev 4, §3.3 and §3.8.

- **The window.** arm64's per-process translation offers device pages only in the console's 2 MiB block, so mapping a virtio transport at 0x0A00_0000 faults. K2 adds a second device level-3 table over the transports' block.
- **The board.** The arm64 virtio-mmio rows, one per page of eight transports.
- **The runner and cases.** The arm64 net path and the probe cases on arm64.

Requested changes on patch SO-168.p1 (revision 1)

**Changes requested,** for two rules no case holds. The board facts and the set's layout are right. I ran on arm64 with sawlang v0.24.3, at d4f66aa1 with p1 applied, against `device_window_blocks`, the four `virtio_probe` cases and `uart_echo_pl011` (6 green).

**What holds:**
- **The rows match QEMU's own device tree** (`qemu-system-aarch64 -M virt,gic-version=2 -cpu cortex-a53`, dumped and decoded). Transports 0, 8, 16 and 24 are at 0x0A00_0000, 0x0A00_1000, 0x0A00_2000 and 0x0A00_3000, on SPIs 16, 24, 32 and 40, which are GIC lines 48, 56, 64 and 72.
- **The net bus:** `info qtree` with a device on `virtio-mmio-bus.24` puts it at 0x0A00_3000, VIRTIO24's row.
- **The set fits its slot:** seven tables, 28,672 bytes. The second device level-3 is at 24,576 to 28,671, and sets are page-aligned from the pool.
- **The crossing refusal** is red two ways on `device_window_blocks`: accepted outright, and allowed one page past the block.
- **Equivalents [read]:**
  - `device_window_of`'s bound at `<=` is caught by `device_window_ok`'s length test, before any install.
  - `install_device`'s outside-window branch is behind the same check.

## 1. The two windows sharing one level-3 table has no case
With `device_level3` written to return `DEVICE_LEVEL3_OFFSET` for both windows, all 6 cases stay green. A page granted in one block is then reachable at the same index in the other.

**The probe** (f563): after reading VIRTIO24's page, the virtio probe also reads 0x0900_3000, the console block's page at the same index, which it was never granted.
- On the patch the read faults: `SOS: fault load-access-fault … tval=0x0000000009003000`, then `root: probe ended status=131072`.
- With the shared table the read succeeds, and the case stays green.

**Asked:** an arm64 case that reads the other block's page at a granted page's index and expects the fault.

## 2. A transport grant surviving into the next process has no case
`reset_device_window` written to clear only the first window's table survives all 6 cases. `prot_clear` resets every device window at teardown so that "a new process must not inherit the last one's registers". With this patch that now includes the transports' block, and nothing checks it.

**Asked:** a case where a process holding a transport page ends, and the next process given its set reads that page without a grant and faults. Or say why a set is never reused by a process that could read it.

## Smaller
- **No case uses VIRTIO0, 8 or 16.** Moving VIRTIO0's base onto VIRTIO8's survives.
- **No case reads any row's line** (48 to 72, each moved by one, survive).

Both are fine for A3-3 by my check against the device tree, and A3-4's interrupts will need them.
