**The S3 clock keys' CPU measurement reads low on a cold first pass.** `cpu_centi_mhz` in `hal/xtensa-esp32s3/keys/clock-common` reads its interval's two ends differently: a SYSTIMER snapshot, then a CCOUNT read, in one cold pass. Flash fetches and the first slow snapshot land at the start, which is then counted late. On the part, the ROM's clock reads 19.65 to 19.92 MHz where it is 20.000 MHz exactly (the 40 MHz crystal divided by two). The PSRAM's P2 measurement had the same flaw and was fixed in SO-102.p2: both ends read by the same sampler, a warm-up pass, the second pass used. Apply the same fix to the keys' `mhz=` measurement. Hold it with a case on the counted clock (`-icount`), with mutants. The fix changes every clock line's `mhz=` text on the part, so update §14h's notes on how it is read.

**Lead: SO-152.p1 is up.** The clock keys measure the CPU the way P2 does, with both ends warm. One commit, 60423999, on main bd033a6f.

**The fix.** `cpu_centi_mhz` (`keys/clock-common`) now runs `cpu_pass` twice and uses the second pass. Both ends of a pass go through `cpu_sample` (the SYSTIMER snapshot, then CCOUNT), over at least `MEASURE_TICKS`. The `mhz=A->B` format is unchanged. The sampler mirrors P2's rather than sharing it, because the keys module names nothing in `kernel/lib.saw`, and the PSRAM sampler takes the kernel's `Systimer`.

**The case.** `clock_mhz_icount` boots `xtal40` on the counted clock. It holds both whole-MHz figures of the `mhz=` line to 36–44; the good build prints `mhz=40.53->40.53`. `expect_number` now takes a list, and each entry takes an optional `past` regex.

**Mutants:**
- **Units wrong** (`TICKS_PER_US` 1000): red, `mhz=2533.76->2533.76`.
- **One end only:** red, `mhz=3318.32->3398.60`.
- **The window constant for the measured ticks:** green. It is equivalent within the measurement: the loop overshoots 80000 ticks by a few counts, about 0.01%. You recorded the same equivalence for P2's K2.
- **No warm-up pass:** green. The emulator models no cold flash fetch, which is the part's flaw, so only the board can show it.

**§14h** says the earlier rows were read by the one-sided measurement, which reads low. They aren't remeasured.

**The S3 smoke:** 222, 5 board-only, the product phase included; main is 221.

**Board check of the warm-up**, if you'd like it: ff435, `kill_churn.pll80.bin`, sha256 552afd18944407f95b6e92ee416ec5e58926c8ecf7a93026d7ec5fd9ceff52fc. Its clock line should read `mhz=20.00->80.00` or within a few hundredths, where main's images read 19.6–19.9. The usual limit applies.
