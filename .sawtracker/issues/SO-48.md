## The rulings (user, settled; do not reopen)

### 1. Three states for every destructible object

- **Live.**
- **Invalid:** the object is destroyed. Its working state is torn down, its
  quota charge (if any) is refunded, and anything parked on it is woken. Handles
  naming it still exist.
- **Freed:** the last handle is released and the slot is reusable.

An op on an invalid object answers a **status**, not a fault: the holder did
not cause the invalidation and could not have checked for it (the reasoning
`PeerClosed` already uses). A wait on an object that becomes invalid wakes with
that status. Choose the status: `SosStatus.Revoked` already means "a Waiter was
destroyed under a parked thread" (§2.2; `kernel/core/refs.saw` ~428). Say in
your report whether you generalised `Revoked` or introduced a new status, and
why. If neither is clearly right, ask.

### 2. Which kinds live how

| Kind | Lifetime |
|---|---|
| Thread, Timer, Waiter, Mapping | **Bound** to their owning process: invalidated when it dies, freed when the last handle goes. A Mapping's owner is the process whose memory domain holds its row. |
| Interrupt | **Non-copyable** (no `Mint` in its default rights; derivation is monotonic, so no handle can regain it). Lives exactly as long as its one handle: releasing it, explicitly or by the holder's teardown, unbinds and masks the line. **Charged to no quota.** |
| Event, Pipe, Memory region, IO window | **Shared:** live until the last handle goes, whatever happens to the process charged for them. |
| Process | Already this model: `Gone` is its invalid state (§8; `kernel/core/process.saw` `reclaim_process_slot`). |
| Clock, System | Never destroyed. |

Process teardown runs in this order: **invalidate every bound object the dying
process owns, then release its handle table**, where each release drops a
reference and a count reaching zero frees.

Owned objects are found by sweeping the slabs by owner, as the teardown does
today. A Thread's invalid remnant (its exit state) stays in its slot, which is
not reused while a handle names it. Whether a large thread body is split from a
small record is an implementation choice; the spec states the observable
contract only.

### 3. The quota refund rule

- A bound kind's charge is refunded **at invalidation**. Its owner is then
  either live or mid-teardown with its ledger about to be cleared, so a refund
  can never land on a reused process slot.
- A shared kind can outlive the process charged for it. **Each such object
  holds a reference on that process's slot**, so a `Gone` slot is not reclaimed
  (`reclaim_process_slot`) until every object charged to it is freed, and the
  refund at free reaches the right ledger.
- Check the lead's reading of the current code before you write the rule as
  "not yet enforced": a pipe's free credits `PIPES[slot].process`
  (`kernel/core/objects.saw` ~1997) with no check that the slot still holds the
  same process, and `reclaim_process_slot` frees a `Gone` slot once no Process
  handle names it. If that reading is wrong, say so.

### 4. Interrupt binding moves to the System object

- A new `SystemOp.InterruptBind`, gated by a new `SystemRight.InterruptBind`,
  replaces `ProcessOp.InterruptBind` and `ProcessRight.InterruptBind`.
- The kernel's own line stays refused, and a bound line answers `LineBound`, as
  today.
- Per-line authority is expressed by which bound Interrupt handles a
  privileged binder (a launcher) gives to which driver. The spec says that; it
  does not add a per-line capability object.
- The Interrupt quota kind goes: the line count bounds Interrupt objects.

### 5. The Process creation ops (SO-41's rule)

`ThreadCreate`, `EventCreate`, `WaiterCreate` and `PipeCreate`, asked through
any Process handle:
- are gated by the right on the handle used;
- create the object **on behalf of the process the handle names**: it owns it
  and is charged for it (a thread created through a child's handle runs in the
  child and counts against the child's thread quota);
- place the new handle(s) **in the caller's table**, charged to the caller's
  handle quota as every handle is; the caller gives them on if the other
  process needs them;
- **fault the caller** on a caller error (bad entry, stack, mode).

`Exit`, `ThreadSelf` and `BootHandleNext` are **self-only**: a handle naming
another process faults the caller with `NotSelf`, as `Exit` already does.
`Start`, `Give`, `GetStatus` and `Stats` act on the named process, as today.

**Air: SO-48.p1, changes requested.**

The model is written well. §2.10 states the three states, the `Revoked` rule, the kind table, the teardown order and both halves of the refund rule. Your reading of today's refunds is right: `free_pipe`, `memory_release_if_idle` and the IoMemory free credit the stored `process` with no check, and `reclaim_process_slot` frees at refs==0. Every § resolves.

Two read-only reviewers covered the patch: one checked every changed sentence against the code, the other swept the rest of the spec. I re-checked the ✓ items myself. They fall into three groups:
- **A:** places where the rulings as written can't all hold at once. These need a decision, probably the user's.
- **B:** sentences that are wrong or unmarked against today's code.
- **C:** low.

**A. Decisions the text needs**

1. **The creation-op rule against handles that cannot be given ✓.**
   - §2.7 (1060-1066) says the new handle "is placed in the caller's table … and the caller gives it on if the other process needs it".
   - But `thread_rights()`, `event_rights()`, `waiter_rights()` and `timer_rights()` carry no `Transfer`, and `BootHandleKind` has no Thread, Event, Waiter or Timer case.
   - §3 (1533-1535), unchanged, still says "a Thread, Event, Waiter, Clock or Timer handle cannot be given".
   - So a thread or Event a launcher creates in a child can never reach the child. Either those kinds become givable (a ruling, plus a marker), or §2.7 says the handle stays with the caller, who supervises with it.
2. **An Interrupt with one name can be consumed into an attachment, and then never acked ✓.**
   - `InterruptOp` has one op, `Ack`, on the Interrupt handle. `Waiter.give(interrupt:)` consumes its wrapper today (`waiter.saw:220`).
   - With `Mint` gone, §2.10's "a consuming `Waiter.give` moves the one name into the attachment" leaves no handle to ack with. §9's mask-on-fire then leaves the line masked after its first fire, and a persistent attachment reports ready forever (§2.2's "readiness ends at the driver's ack").
   - Something has to give: ack through the attachment or Waiter, an Interrupt attach that doesn't consume, or a refused consuming give.
3. **`Start` and `Give` on a `Gone` child: fault or status ✓.** §2.10's Process row (1417) says every other op on a `Gone` process answers `Revoked`, and its marker treats today's `BadState` as the lag. But four unchanged passages make it the design:
   - 2454: "A second `start` is a `BadState` fault"
   - 1113-1116, the already-started child
   - §3's faults list (~1733), which §2.7 calls complete
   - 3003-3006: "a give afterwards is a `BadState` fault"
   
   A `Gone` child is always a started one, so one rule needs a carve-out.
4. **"Every op on an invalid object answers `Revoked`" (1386, 1961) needs its scope.**
   - Release is a universal op intercepted before the kind match, and it must still work on an invalid object, or nothing ever reaches Freed.
   - `MINT_OP` is the same question.
   - The Process row already carves out `GetStatus`, `Stats` and attachments.
   - It doesn't say whether `Exit`, `ThreadSelf` or `BootHandleNext` through a `Gone` handle is a `NotSelf` fault or `Revoked`.
   - It doesn't say whether a missing right or bad argument on an invalid object faults first (§5.7's dispatch order).
5. **Interrupts and "policy first" ✓.** §2.9 (1311-1313) still says "A quota is checked at every allocation site that answers `NoResource`, ahead of the slab". Under the design, `InterruptBind` charges no quota but still answers `NoResource`. Also:
   - "the line count bounds Interrupt objects" understates it. The binding bound is the Interrupt slab (`MAX_INTERRUPTS`, and donatable, `SlabKind.Interrupts`).
   - A line binds at most once (`LineBound`), so the line count is only an upper bound.
   
   "Policy first" needs the exception that its attachments bullet already makes for attachments.
6. **Thread lifetime gaps.**
   - The Thread row (77) and §2.10 (1426-1428) keep an invalidated thread's "remnant (its exit state)", but under the `Revoked` rule a `Join` can never read it. Say what the remnant is for: a normally exited thread is not invalid.
   - Nothing says when a thread whose count reached zero while it ran is freed, at exit or at invalidation.

**B. Wrong or unmarked against today's code**

7. **`InterruptBind` as a System op stated as current, unmarked ✓.**
   - §2.7's op list drops it, and says "binding an interrupt line is on System for the same reason (§2.8)" (1048-1054).
   - Also the §2.8 table row (1251), §5.7 (1979-1982) and §12 (2943-2944).
   - Today it is `ProcessOp.InterruptBind` (ops.saw; dispatch.saw ~596-601). Only the default-set right (1089-1091) and §2.8's bullet are marked.
8. **`spec.md:1123-1125` and `3011-3012` ✓:** "a launcher never sees a child-relative word: the launch flow hands it none, and the creation ops place their handles in the caller's table (above)". This is false today, because the creation ops mint into `obj.slot`. "(above)" points at a marker, but the sentence itself asserts it.
9. **`spec.md:1364-1369` ✓:** the §2.9 refund bullet says a shared object "holds a reference on that process's slot, so its refund reaches the ledger it was charged to and never the slot's next occupant", with no marker. It's false today, as your own reading of the code shows.
10. **The Interrupt row (1415) and §2's table row (45):** "No `Mint` in its default set … Charged to no quota", "created by `SystemOp.InterruptBind`", "It has one name". §2.10's "Not yet enforced:" list has no Interrupt item. Today `interrupt_rights()` is `Wait | Ack | Mint` and the bind charges `QuotaKind.Interrupt`.
11. **Dropped from every marker: `InterruptBind` faulting the named process ✓.**
    - §5.7's marker (1957-1959) and §11's line name only `ThreadCreate` and `EventCreate`.
    - But `interrupt_bind(obj.slot, …)` faults that process with `BadArg` or `LineBound` today, as the old §11 line said.
    - §2.8's marker mentions the table and the quota only.
12. **`spec.md:1455-1457` ✓:** "a bound object is freed rather than left invalid". A Mapping that targets the dying process (bound to it under §2.10) is left live with `row = NO_ROW` (sched.saw:534-536), a husk whose handles are in other tables, not freed.
13. **`spec.md:2868-2869` ✓:** §11 says the teardown frees "by owner rather than invalidating the bound kinds and releasing its handles". The close-all does release every handle, counting without freeing, as §2.10 says at 1450.
14. **`spec.md:1460-1462`:** "the creation ops through a `Gone` process's handle answer `QuotaExceeded`". That holds only for well-formed arguments. `ThreadCreate`'s entry and stack check and `EventCreate`'s mode decode run before the quota check, and either error faults the `Gone` process again: `end_process` reruns, overwrites the status word, and strands the caller.
15. **`spec.md:1403`:** "Not yet enforced: invalidation is not built." Process invalidation is built (`Gone`, the terminal attachment wake), and the Process row states it as current. Say "invalidation of the bound kinds".
16. **`spec.md:3033-3036`:** "`give(iomemory:)` hands a child a device … with no further mechanism: moving a driver out of root needs no kernel change". The line must now go too, as an Interrupt, which needs `Transfer` and a boot record kind (§3 marks both). Also 2649, "the window and the line arrive by give", sits outside the 2644 marker. Today the driver children bind their own lines.
17. **`spec.md:522-524` and `556-558`:** a Waiter destroyed by its owner's death "wakes … with `Revoked`". The owner sweep frees Waiters without `revoke_blocked`. That's unobservable today, but stated as current. The same applies to 47, 552-554 and 2463-2465.
