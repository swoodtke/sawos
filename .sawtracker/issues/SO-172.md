**`uart_dropped_read` depends on host time.** The case asserts that every read is answered from the driver's buffer: `abandoned=0`, `bytes put back=1`, `answered=7 discarded=7`. For that, all four typed bytes must already be in the driver's buffer when the client's dropped `Read` arrives. The runner's `stdin_at_once` doesn't make that true by construction:
- `_run_qemu` writes the bytes into the pipe from a thread after `Popen`;
- QEMU's chardev then moves them into the UART's FIFO on its own main loop, at whatever time a loaded host allows;
- the guest boots meanwhile.

**Seen on the server:** SO-148.p6's run, arm64, under a full parallel gate. The client still echoed `Zq7#`, so no byte was lost. But the dropped read was held, not answered from the buffer: `served=14 abandoned=1`, `bytes put back=0`, `answered=5 discarded=6 traps=32`. The same tree passed twice locally.

**Wanted:** an ordering by construction. One way is to start QEMU paused (`-S`, QMP on a socketpair, as `_run_net_qemu` does), hand over the bytes, and resume only once the device reports them received. For example, read the UART's flag or line-status register through QMP until its receive-ready bit is set, and the FIFO holds the bytes. Another is for the client to wait on the driver's own count of buffered bytes, if the protocol gains one. Whatever the fix, the case must fail red under a mutant driver that loses the put-back byte.
