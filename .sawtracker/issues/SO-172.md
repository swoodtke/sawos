**`uart_dropped_read` depends on host time.** The case asserts that every read is answered from the driver's buffer: `abandoned=0`, `bytes put back=1`, `answered=7 discarded=7`. For that, all four typed bytes must already be in the driver's buffer when the client's dropped `Read` arrives. The runner's `stdin_at_once` doesn't make that true by construction:
- `_run_qemu` writes the bytes into the pipe from a thread after `Popen`;
- QEMU's chardev then moves them into the UART's FIFO on its own main loop, at whatever time a loaded host allows;
- the guest boots meanwhile.

**Seen on the server:** SO-148.p6's run, arm64, under a full parallel gate. The client still echoed `Zq7#`, so no byte was lost. But the dropped read was held, not answered from the buffer: `served=14 abandoned=1`, `bytes put back=0`, `answered=5 discarded=6 traps=32`. The same tree passed twice locally.

**Wanted:** an ordering by construction. One way is to start QEMU paused (`-S`, QMP on a socketpair, as `_run_net_qemu` does), hand over the bytes, and resume only once the device reports them received. For example, read the UART's flag or line-status register through QMP until its receive-ready bit is set, and the FIFO holds the bytes. Another is for the client to wait on the driver's own count of buffered bytes, if the protocol gains one. Whatever the fix, the case must fail red under a mutant driver that loses the put-back byte.

Requested changes on patch SO-172.p1 (revision 1) (its test run was cancelled)

**Held for a revision: the drivers' put-back call no longer has a case that pins it by construction.** You name this residue yourself. A route exists that removes it, so I'd rather it land in this patch than as a follow-up.

**What I measured** (the patch applied to ba75d53d, sawlang v0.24.5, an unloaded Air):
- **The case as patched** is green on riscv32 and arm64.
- **The hosted test is solid.** It passes as patched. With `unpush` leaving the head where it was, it is red with `assertion failed: the byte is first out, once, and the rest follow in order`.
- **The residue mutant:** in `answer_read`'s `Reply` arm of both drivers, I replaced `input.unpush(b)` with a print, so the byte is lost. `uart_dropped_read` went red 5/5 on riscv32 and 5/5 on arm64 (the client hangs waiting for its fourth byte). That is only because an unloaded host always takes the buffered path. Under a full gate's load the held path came up three times (two server runs, c1 and c4, and one local full gate, c2), about one server run in three by c4's count. In those runs this mutant passes, because nothing is put back and every byte still arrives.

So the patch turns that mutant from always red into red when the race goes the usual way. The hosted test pins `InBuf.unpush`'s ordering, but not the drivers' decision to call it when a reply finds nobody home.

**A route by construction** (c1's second option): give the client an observable for "the driver holds a byte", and have it wait on that rather than on time.
- **A `Pending` op** (op 5): the driver answers its buffered count, and `Uart.pending() -> Result<Int, UartError>` reads it. A `Sync` can't carry the count, because `sync()` checks `empty_reply`.
- **The client:** after `got[0] = try u.read()`, it calls `u.pending()` until the count is at least 1. Each turn is a round trip and no clock. The loop ends once the emulator has passed `q` to the device and the driver has drained it, which the harness timeout bounds as for every wait. Then it tells the dropped `Read` and calls `sync()`. Only this client reads, so the byte is still buffered when the `Read` arrives, and the read is answered from the buffer by construction.
- **The expected text:** with the path forced, the case can assert `bytes put back=1` and `abandoned=0 dropped=0` again. `served` and the after-the-mark counts move with the number of `pending` turns, so leave those printed and not asserted.
- **The mutants that must go red:** removing `input.unpush(b)` in each driver's `answer_read`, deterministically. Also a hosted wire test for the new op, as `wire.saw` has for the others.

**Smaller points:**
- **`"dropped=0"` alone** matches only because no other line prints `dropped=`. Once the counters come back, match it inside the driver's line (`abandoned=0 dropped=0`).
- **The move of `InBuf` is verbatim.** `push`, `unpush` and `pop` are identical to both drivers' copies, so the drivers' behaviour is unchanged.
