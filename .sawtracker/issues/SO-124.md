## Description

**Processes written with an ordinary `main`: sosrt owns `_start` and calls a compiler-synthesized entry.** User ruling, Nov 15: "go ahead and create the issue for the _start / main work and tell sawlang i approve of its plan. for sawos though, i think this should go behind the pll work".

**Today.** Every process package exports `@export("_start") func _start(boot_handle: UInt)`, builds its `System` from the raw boot word, drains its boot handles itself, and must end in an explicit exit or shutdown: falling off `_start` returns into nothing. A program's second thread re-enters `_start` and dispatches on a static.

**The split (the sawlang lead's recommendation, approved by the user for sawlang's half on Nov 15).**
- **sawlang:** under `--freestanding`, a `main` in the entry module gets the hosted treatment without the C ABI: the compiler synthesizes a synchronous, C-ABI function with a reserved name (`__saw_main` in their sketch) that runs `main` (driving a suspending `main` with the entry executor), applies design 221's contract (`Void`, `Int`, `Result<Void, E>`, `Result<Int, E>`; the 0...255 check through `__saw_rt_panic`; an `Err` written as `error: <rendering>` through `__saw_rt_write_error`) and returns the status. Their issue number goes here when filed.
- **sawos (this issue):** `sosrt` owns `_start`: it makes the process's boot context, stores the boot handle where a runtime accessor reads it (`main` takes no parameters), calls the synthesized entry, and exits the process with the status through the process exit op.

**To design (a short design first, for the user's review):**
- the boot-context accessor in `sos` (the `System` handle, the process's own handle, the boot records), and what happens to the existing `System(boot_handle:)` spelling;
- a thread's entry: a real entry function for `ThreadCreate` instead of re-entering the image's entry and dispatching on a static;
- the windowed entry on the ESP32-S3: the bootstrap gives a windowed program a correct entry (the call4 rule of `hal/xtensa-esp32s3/ABI.md` §7d);
- the exit status: design 221 limits `main` to 0...255; a process's exit code is a word; say what a status past 255 means, and whether a program that wants a full word calls the exit op itself;
- migration: a package that exports its own `_start` keeps working; root, the drivers and new code move to `main`; old tests convert over time, not in one patch;
- a suspending `main` freestanding (needs sawlang's half).

**Order (user, Nov 15):** after the PLL (SO-113), which follows windowed threads (SO-112).

The design goes to the owner before building; it waits on sawlang v0.24.3's tag for `__saw_main`.

**Correction to the note above (sawlang, chat m1258):** lending a static is refused even through a `&self` method (`lend.root`, "not rooted in the receiver", at borrowck and at build); the spec allows only receiver-rooted lends. **Lead: SO-124.p1 is unit 1 of the design (`SO:sosmain-startup`): `PANIC_OP`, a process ending itself as a panic.** One commit, gated on b09eb0bc and rebased by the lead onto main e5622999 without conflict. Gate against a baseline at b09eb0bc: sos-test 1154 → 1157, S3 149 → 150 (5 board-only); in the report only `panic_op`'s rows, its image lines and the totals moved. Images 3999 → 4017: 3905 moved (every image that links the runtime's abort hook), 94 identical, 18 new.

**ABI:** `PANIC_OP = 0xFFFC`, `PANIC_TEXT_BYTES = 256` (`sosabi` `ops.saw`; every table asserts `< PANIC_OP`, and `PANIC_OP < INFO_OP`); `FaultReason.Panic = 14` ("the program panicked"). **Kernel:** `dispatch` takes `handle == NO_HANDLE && op == PANIC_OP` before the lookup, so it needs no handle and no right. `panic_process` checks the whole read range through `copy_in_check` (a zero length skips it), copies in 8-word chunks to a stack buffer, prints bytes outside 0x20–0x7E as `?` and drops a final line break when the text was not cut; a buffer the door refuses prints `text unreadable: <the door's reason>` and is still a panic. The end is `end_process(Faulted, Panic, ExitCode.Panic)`, with `ExitCode.Panic = 64` held equal to sosrt's `AbortCode.Panic` by a `static_assert`, so root's machine status stays 64. Each kernel HAL's `rt_abort(ptr, len, code)` writes the text and stops. **Process side:** the floor's `sos_panic(text, len) -> Never`; `sos.rt`'s abort hook copies the text into a 256-byte word-aligned stack buffer, cuts it with `...` and calls `sos_panic`, reading no handle (disassembled at `-Oz` on riscv32, arm64 and xtensa: `memset` and `sos_panic`, no trap). Every runtime panic, `_start` packages' included, now ends `Faulted (Panic)` with its text in the kernel's line; `debug_print` is out of the panic path.

**The allocator's failure answers NULL** (sawlang's allocator ABI, stated by the sawlang lead today): the exhaustion abort, its message and `AbortCode.NoMemory` are gone, and std takes it from there. Where std has an error channel the program gets an `Err` (`arena_small` now holds `16 KiB refused as a STATUS: allocation of 16384 bytes (align 4) failed` and a clean exit); where it has none, std panics, which ends `Faulted (Panic)` through the op. std's wording there depends on the profile: an interpolation that runs out ends `String: allocation of N bytes (align A) failed` on riscv32 and flat but `try! failed: allocation of N bytes (align 1) failed` (`String`'s `Printable`) on arm64 and the S3; `String.replace` gives the first text everywhere.

**spec:** the design's §4.5 text at §8, §5.7 (three places), §3, §2.8 and §5c (which also says the arena answers NULL). **Transcripts that moved, as the design's §4.7 names:** the five `stock_skew_*` (riscv32): the panic line becomes the kernel's fault line carrying it, plus root's teardown line, status 64; `double_free`/`stray_free` (three profiles): the same, the line in the text moving `lib.saw:417` → `411` (the deleted abort lines sat above `rt_dealloc`); `arena_small`: as above. The kernel's own panic cases did not move.

**New case `panic_op`** (three profiles and the S3; `tests/panic-op`, `tests/child-panic-op`): root launches the child 15 times in one region and prints each status word: a Saw panic with a System holding `Debug`, with no tag, on a Memory record's word, with a System lacking `Debug`; an arena refusal the child panics on; an interpolation and a `String.replace` running out; a Saw panic past 256 bytes (the runtime's `...`); a text with a line break, ESC, DEL and `é` ending in a line break; 300 bytes cut by the kernel at 256 with a line break at 256 shown as `?`; a zero length at address 1; a buffer outside the process and a misaligned one; the op on the live System handle (`BadOp`, 131074) and on a released word (`BadHandle`, 131073). The design's hand-assembled payloads are a Saw child calling `sos_panic` and the raw `sos_syscall1`, covering the same rows on every profile.
