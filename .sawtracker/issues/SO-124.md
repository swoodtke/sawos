## Description

**Processes written with an ordinary `main`: sosrt owns `_start` and calls a compiler-synthesized entry.** User ruling, Nov 15: "go ahead and create the issue for the _start / main work and tell sawlang i approve of its plan. for sawos though, i think this should go behind the pll work".

**Today.** Every process package exports `@export("_start") func _start(boot_handle: UInt)`, builds its `System` from the raw boot word, drains its boot handles itself, and must end in an explicit exit or shutdown: falling off `_start` returns into nothing. A program's second thread re-enters `_start` and dispatches on a static.

**The split (the sawlang lead's recommendation, approved by the user for sawlang's half on Nov 15).**
- **sawlang:** under `--freestanding`, a `main` in the entry module gets the hosted treatment without the C ABI: the compiler synthesizes a synchronous, C-ABI function with a reserved name (`__saw_main` in their sketch) that runs `main` (driving a suspending `main` with the entry executor), applies design 221's contract (`Void`, `Int`, `Result<Void, E>`, `Result<Int, E>`; the 0...255 check through `__saw_rt_panic`; an `Err` written as `error: <rendering>` through `__saw_rt_write_error`) and returns the status. Their issue number goes here when filed.
- **sawos (this issue):** `sosrt` owns `_start`: it makes the process's boot context, stores the boot handle where a runtime accessor reads it (`main` takes no parameters), calls the synthesized entry, and exits the process with the status through the process exit op.

**To design (a short design first, for the user's review):**
- the boot-context accessor in `sos` (the `System` handle, the process's own handle, the boot records), and what happens to the existing `System(boot_handle:)` spelling;
- a thread's entry: a real entry function for `ThreadCreate` instead of re-entering the image's entry and dispatching on a static;
- the windowed entry on the ESP32-S3: the bootstrap gives a windowed program a correct entry (the call4 rule of `hal/xtensa-esp32s3/ABI.md` §7d);
- the exit status: design 221 limits `main` to 0...255; a process's exit code is a word; say what a status past 255 means, and whether a program that wants a full word calls the exit op itself;
- migration: a package that exports its own `_start` keeps working; root, the drivers and new code move to `main`; old tests convert over time, not in one patch;
- a suspending `main` freestanding (needs sawlang's half).

**Order (user, Nov 15):** after the PLL (SO-113), which follows windowed threads (SO-112).

**From the sawlang lead (chat m1157, Nov 16): SL-1143's design is done, implementation next.** The freestanding entry is `__saw_main() -> i32` (C `int`, no parameters, synchronous), defined in every object whose entry module declares a `main`. It runs `main` (driving a suspending one with the entry executor, its frame on the caller's stack), applies design 221's contract (status 0...255; an `Err` writes `error: ...` and gives 1) and returns the status; it never exits. sosrt's start-up declares `extern "C" { func __saw_main() -> Int32 }` and calls it, with the windowed convention on windowed Xtensa. A `main` with parameters becomes an error freestanding; the lead checked: no `.saw` file in sawos declares one. `Task.spawn` stays refused freestanding until SL-1150 (a runtime-owned background group, designed with us). SO-124 is buildable once SL-1143 lands at a pinned sawlang.

**SL-1143 landed on sawlang main as 6b36fd3be (chat m1198; not yet tagged).** A freestanding object whose entry module declares `main` defines `__saw_main() -> i32` (external, section `.text.__saw_main`); sosrt's `_start` declares `extern "C" { func __saw_main() -> Int32 }` and calls it once (windowed convention on xtensa-windowed) after the stack, the allocation seams and the boot-handle state are set up; another signature is refused (`extern.signature-disagree`). It returns 0...255 and never exits; an out-of-range `Int` panics through `__saw_rt_panic`; an `Err` writes `error: ...` through `__saw_rt_write_error` and gives 1. `main` takes no parameters freestanding (`entry.parameters`). Full text: sawlang runtime/ABI.md "The program entry". SO-124 starts after the tag and sawos's pin bump.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":1291,"created":"1794927017","id":"c4"} -->
**Owner (Nov 17): a crt0-style start-up that takes boot records before the program can, so `print` works as expected.** "i think we need a crt.o type setup where we can steal boot arguments before the process itself can access them - that allows us to get a uart driver and configure it so print works as expected." This joins SO-124's design: sosrt's `_start` drains the boot set before `__saw_main`; takes a reserved console record (a `uartproto` client, by a reserved tag or declaration kind) when the image gives one, and points the runtime's write seam at it (`print` becomes `uartproto` Writes, buffered per line, with `Sync` at exit); keeps the rest for `main` through a runtime-held `BootSet` accessor. To design: the reserved record and how an image names a process's console (by default every process's, to the image's console driver: SO-137 on the S3, the real UART driver elsewhere); the panic path (check-free: the kernel's debug print when the process holds `Debug`, else the console connection only if a send can be made check-free, else the exit status alone), which bears on SO-138's default rights; a process with no console record (writes dropped, as with no `Debug` today). The design goes to the owner before building; it waits on sawlang v0.24.3's tag for `__saw_main`.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":488,"created":"1794927175","id":"c5"} -->
**Owner's ruling (Nov 17), the panic path:** "for a process panic, the uart will work for now." A panic report goes through the process's console connection (`uartproto`), not the kernel's debug print; the design makes that send as robust as it can (no allocation, a fixed buffer, the already-open connection) and says what is lost when it cannot be made. Later: a debug process that can introspect a crashed process and print its state even when that state is corrupt (filed separately).

**Lead: the design is up as doc `SO:sosmain-startup` (revision 1), for the owner's review and the reviewer's read before anything is built.** It recommends a new package `sosmain` (`rt/main/`) owning `_start`; the boot context lent from `_start`'s frame; an image-level `console = "PROC.RECORD"` giving every other process a client record under a reserved tag; `print` and panics over `uartproto` with a `Sync` at exit; a real thread entry; a runtime exit band above 255 (`0x140` panic and so on); migration package by package; and ten units. It notes for SO-138 that a `debug_print` without `Debug` is an `AccessDenied` fault, not a status. Thirteen open questions are at its end, each with a recommendation.
