## Description

**From the user, Nov 14:** "I would also like to kick off a design to support networking on the S3 board. We would need TCP/IP and BT stacks in addition to wrapping the binary blob provided by Espressif for the network devices."

**What this is.** A design, in two layers: an architecture for networking in sawos (which processes exist, what each holds, the protocols between them), and a feasibility study of the part that cannot be chosen freely, Espressif's closed radio libraries on the ESP32-S3. Nothing is built from it before the user and the reviewer have read it. It sits after the useless box (SO-72, due by Christmas) in the order of building, not of thinking.

**The lead's first thoughts, for the design to test.**

1. **Three pieces that can move apart.**
   - **A network stack and the interface a network device driver serves** (frames in, frames out, link state). Nothing about these is the S3's. They can be built and gated under the emulators the suite already uses, against a virtual network device on the `virt` boards, long before a radio works.
   - **The radio driver**: a userspace process that holds the radio's registers and interrupts, links Espressif's libraries, and gives them the operating-system services they expect. Board-only: the gate's emulator has no radio.
   - **Bluetooth**: the controller is another closed library that shares the radio, its calibration and a coexistence library with Wi-Fi, so it very likely lives in the same process; the host stack above it (BLE only on this part) is a separate choice.

2. **The radio libraries are the hard part, and one fact may decide a great deal: the calling convention.** sawos on the ESP32-S3 is built call0 (`hal/xtensa-esp32s3/ABI.md` §1a: the Saw compiler's objects are call0, and the C beside them is compiled to match). Espressif's toolchain defaults to the windowed convention for this core, and their prebuilt libraries are, as far as the lead knows, windowed. If so they cannot be linked into a call0 program: either the radio process is a windowed program (the kernel then has to handle window overflow and underflow exceptions and save register windows at a switch, and Saw code in that process needs a bridge), or every call across the boundary goes through thunks. The first thing the design does is look at the libraries themselves and say which it is.

3. **What the libraries expect of an operating system.** They are written against an adapter table (tasks, queues, semaphores, mutexes, timers, memory, critical sections, interrupt registration, an event loop, non-volatile storage for calibration), a C library, ROM functions, the PHY's initialisation, the clock tree with the PLL running, and memory in internal SRAM for anything the radio's hardware touches. Their interrupt handlers expect to run as interrupt handlers; in sawos an interrupt reaches a driver as a wake of a thread. Other systems have wrapped the same libraries outside Espressif's SDK (NuttX, Zephyr, the Rust `esp-radio` crates), which shows the surface is finite and gives three references for it.

4. **The stacks.** TCP/IP: port an existing C stack (lwIP is what Espressif's SDK uses) as a process, or write one in Saw (the user's standing preference for our own code), or the first as a way to the second. The same question for the BLE host (NimBLE is the permissively licensed one). The protocol between an application and the stack is ours to design either way.

5. **What the part's owner should know before any of it runs on the board.** The libraries are opaque: they read the eFuse block for the MAC address and calibration (reads, not writes; the design confirms from Espressif's sources what the libraries are documented to do, since their code cannot be read), they drive the RF front end, and on this flat tier nothing stops a fault in them from reaching the kernel's memory. Radio emissions are regulated; the module's certification covers Espressif's libraries used as shipped.

6. **Another board may be the easier first radio.** The user expects to get ESP32-C6 boards. Those are RISC-V, where Espressif's libraries use the ordinary calling convention and the windowed question does not arise. The design should say how much of the work is shared and whether the first radio bring-up belongs on the S3 at all.

**The design answers:** the architecture and its protocols; for the radio libraries, what they are (from the files: convention, size, undefined symbols, sections), what they need, what each need costs in sawos, and a go or no-go with the reasons; the stacks, each option priced; RAM (internal SRAM against PSRAM, with SO-102); clocks; what can be tested where; the order of work; and the questions for the user.

**Lead, Nov 14: the design is written and published as the tracker doc `SO:networking`** (a copy is at `.claude/lead/so103-design.md`). It changes nothing in the repository. The user and the reviewer read it before anything is built. Nothing of Espressif's was executed or linked into anything that ran; the libraries were inspected with tools only.

**Verdict: go, with conditions.** Nothing in Espressif's files rules out wrapping their Wi-Fi, PHY, coexistence and BLE controller libraries on the ESP32-S3. The conditions:
1. the kernel supports windowed threads on this core;
2. the priority scheduler of spec §7, which is specified and not built, exists, with preemption when a thread is woken;
3. the HAL raises the CPU to the PLL so the peripheral bus runs at 80 MHz;
4. the board reserves the RAM the ROM's radio code keeps its state in;
5. the radio has about 70 to 110 KB of internal SRAM, which in practice means SO-102 has moved other processes to PSRAM first.

**The calling convention is windowed,** on three pieces of evidence: all 362 objects for the S3 in the archives pinned by IDF v6.1 carry an attribute saying so; the disassembly has `entry` and `retw` throughout and no call0 return or call anywhere; Espressif publishes no call0 build, and every other integrator is windowed. The lead's worry about a bridge is answered more simply than expected: the pinned Saw compiler emits windowed code when asked (run), so the radio process can be one windowed program holding Saw and C. The kernel's part is the window overflow and underflow vectors, a larger trap frame (it fits the existing stride), windowed thread start, and floating-point and boolean-register state per thread, which one of the libraries uses.

**Facts that shape the plan.**
- **The libraries reach an operating system only through adapter tables** (119 entries for Wi-Fi, 18 for coexistence, 63 for Bluetooth) and use no privileged instruction. Part of the Wi-Fi MAC and most of the BLE link layer are in mask ROM, which keeps state in a fixed range at the top of internal RAM (0x3FCE_EE34 to 0x3FCF_0000). sawos hands that range to processes today and the suite's pool lies over it; a radio image's board description must reserve it.
- **Interrupt latency is the real unknown.** The Wi-Fi handler is a short top half that defers to a task, which fits an interrupt waking a thread; but no other integrator defers the handler itself to a thread, and in sawos today a woken thread waits for a yield, a block or the tick. Hence the scheduler condition, and a board stage that measures it.
- **No eFuse or flash write is needed.** The libraries name four eFuse addresses, all read registers, each used by a load; the write registers and the programming op codes appear nowhere in them. Full PHY calibration at every boot needs no stored data, and Wi-Fi's own use of storage is switched off by a flag. A scan of literals cannot rule out an address computed at run time, and the design says so.
- **Wi-Fi needs the peripheral bus at 80 MHz.**

**Stacks: both in Saw.** TCP/IP in Saw (about 7.5 to 9 thousand lines; UDP, DHCP and DNS before TCP), gated on the emulators, with lwIP as the named fallback (the version IDF pins compiles call0 for this core: checked). A BLE host in Saw, starting with advertising over raw HCI, then GATT, then pairing, with NimBLE as the fallback.

**What can be gated without a radio.** The suite's QEMU offers a virtio network device on both `virt` machines, and the runner can drive a scripted peer deterministically, so the stack and the device protocol are gated on riscv32 and arm64; Espressif's QEMU models an Ethernet device (not Wi-Fi) on the S3, so the same stack runs in the S3 smoke. Also gateable: the adapter against a fake library, a build-only check that the radio image links, and the windowed-thread cases. The rest is board stages, each one `write-flash 0x0` under the user's limit and only on their word.

**Order of work.** A stack track that needs none of the box's files (protocol packages, the IP layer, virtio-net with ping, DHCP and DNS, TCP, sockets, the S3's emulated Ethernet); a kernel track after SO-102 and SO-95 (windowed threads, FP state, the priority scheduler with its own design first, the clock, the board description); then the radio (a link check, the adapter, the PHY on the board, scan, WPA2, traffic); then BLE. In three months: ping, UDP and DHCP over a Saw stack on the emulators, windowed processes on the S3, and a radio image that links; nothing over the air, no finished TCP, no BLE.

**The ESP32-C6:** its libraries are RISC-V with the ordinary convention and the same adapter tables, so most of the work is shared; the designer still recommends the S3 for the first bring-up.

**Its ten questions for the user,** each with a recommendation: the radio as a windowed program with Saw allowed in it (yes); TCP/IP in Saw with lwIP as the fallback (yes); a BLE host in Saw starting with advertising (yes); the regulatory country (set the user's own explicitly); how Wi-Fi credentials reach the device (a git-ignored build input); whether to ask Espressif for call0 libraries (optional); the CPU on the PLL at 160 MHz for radio images (yes); the priority scheduler before the radio's board stages (yes); the S3's limits raised through SO-95 (yes); when the radio process dies, the image ends until a restart unit exists.

**Not verified:** whether a deferred handler meets the radio's timing; whether `ld.lld` treats the ROM's linker script as GNU ld does; whether the ROM's reserved RAM keeps its values once sawos boots; half the RAM figures; whether Blade can link archives and extra linker scripts; the certification wording for use outside Espressif's SDK.

**Lead, Nov 14: revision 2 of the design is published** (tracker doc `SO:networking`, revision 2; copy at `.claude/lead/so103-design.md`). All five threads are accepted, with one suggestion inside t3 disputed on evidence. No repository file changed.

**The verdict is still go with conditions, now six:** windowed processes and a gate for windowed code generation in sawlang; the priority scheduler with a ceiling; the clock switch done in the memory-SPI's order; SO-105 and a larger grant-row budget on the radio's board; kernel SRAM found by measuring and cutting the kernel's stack; and process SRAM at Espressif's minimum buffer configuration with the frame buffers in PSRAM.

**What the review changed.**
- **Interrupts and critical sections (t1).** The libraries' critical sections raise the interrupt level and their handlers preempt one another (Bluetooth's over Wi-Fi's). So the scheduler unit must give strict priority levels inside the radio process (a ceiling, the Bluetooth interrupt thread, the Wi-Fi interrupt thread, then the task threads in their own order: four levels at least, up to seven), preemption on a wake, and an immediate priority ceiling for critical sections. No radio traffic runs before that unit; only PHY calibration may.
- **The clock (t2).** On this part the memory-SPI clock is bound to the CPU's, and ESP-IDF brackets every switch with a speed-mode change and a cache freeze. The clock unit runs once at boot before `hal.memory_init()`, moves the console to the crystal first, sets the flash divider for the new clock before the switch, runs from IRAM with the cache frozen, and the kernel reads the clock back against the board description and stops on a mismatch. This agrees with SO-102's revision 2 (any switch runs first; a `[clock]` section checked at boot).
- **The radio's own numbers (t3),** counted item by item: 58 handles held and 60 at peak with both radios (43 and 45 for Wi-Fi alone); it declares handles 64, mappings 14, threads 6, events 6, Waiters 6, a Timer; 18 grant rows (15 for Wi-Fi alone). SO-95 as ruled gives the threads, events, Waiters, Timers, up to 12 mappings and the 15 rows a Wi-Fi-only image needs. A handle table past 32 for one process, a pool as its own RAM limit and rights narrowed to its declaration are stated as this design's three requirements on SO-105. A grant-row budget of 20 and an Interrupt slab of 8 are per-board raises. Disputed: putting the shared system registers behind a broker to save windows; the libraries write those registers by absolute address, so the windows stay.
- **RAM, with root in SRAM (t4).** Kernel SRAM: the box with Wi-Fi needs about 27 KiB of linked areas against 21.9 KiB of slack, and with a BLE host about 36 KiB; the answer is a new unit that measures the kernel's 64 KiB stack and cuts it. Process SRAM on the PSRAM board: about 99.6 KiB is left for the radio beside the box, which holds Wi-Fi at the minimum configuration (about 67 to 85 KiB) and holds both radios only if root's region is 64 KiB or less. On the plain board nothing fits beside the box. The ROM's reserved range is now a fact of the radio board's description, and the radio image's flash size is among what it asks of SO-95.
- **Shared rings and windowed Saw (t5).** A rule of the protocol packages: every field read from a shared ring is read once into private memory, checked, and only the copy used. A request to sawlang for a gate on windowed code generation before any windowed Saw is relied on.
- **Sizes, with their basis.** TCP is now four medium units, two to three months, measured against lwIP's TCP (8,263 lines). WPA2 is three units: ESP-IDF compiles 94 supplicant files unconditionally, and a WPA2-PSK-only subset of about 9,700 lines is a configuration it never builds alone. The socket protocol is one connection per application, since a pipe costs 3.5 KiB of kernel SRAM. **In three months: no frame over the air;** at most PHY calibration near the end.

**Fourteen questions for the user** (section 11), each with a recommendation. New: SO-105 and not a 64-entry table on every body (SO-105); the minimum buffer configuration with buffers in PSRAM, both radios beside the box only if root's region is 64 KiB or less (yes); measure and cut the kernel stack before moving the kernel's split (yes); one socket connection per application (yes). Changed: TCP in Saw at its honest size, UDP first (yes); 160 MHz at boot before PSRAM for every image on the PSRAM board (yes, after the stage that measures it); no radio traffic before the scheduler unit (yes); grant rows 20 and the networking slab totals on the PSRAM board (yes).

**Not verified:** deferred-handler latency and whether the libraries tolerate the ceiling; the task count and priorities the libraries ask for; the linker's treatment of the ROM's script; whether the WPA2 subset builds alone; the kernel stack's peak; the memory-SPI clock on the crystal; the certification wording.
