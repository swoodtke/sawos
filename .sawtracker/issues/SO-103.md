## Description

**From the user, Nov 14:** "I would also like to kick off a design to support networking on the S3 board. We would need TCP/IP and BT stacks in addition to wrapping the binary blob provided by Espressif for the network devices."

**What this is.** A design, in two layers: an architecture for networking in sawos (which processes exist, what each holds, the protocols between them), and a feasibility study of the part that cannot be chosen freely, Espressif's closed radio libraries on the ESP32-S3. Nothing is built from it before the user and the reviewer have read it. It sits after the useless box (SO-72, due by Christmas) in the order of building, not of thinking.

**The lead's first thoughts, for the design to test.**

1. **Three pieces that can move apart.**
   - **A network stack and the interface a network device driver serves** (frames in, frames out, link state). Nothing about these is the S3's. They can be built and gated under the emulators the suite already uses, against a virtual network device on the `virt` boards, long before a radio works.
   - **The radio driver**: a userspace process that holds the radio's registers and interrupts, links Espressif's libraries, and gives them the operating-system services they expect. Board-only: the gate's emulator has no radio.
   - **Bluetooth**: the controller is another closed library that shares the radio, its calibration and a coexistence library with Wi-Fi, so it very likely lives in the same process; the host stack above it (BLE only on this part) is a separate choice.

2. **The radio libraries are the hard part, and one fact may decide a great deal: the calling convention.** sawos on the ESP32-S3 is built call0 (`hal/xtensa-esp32s3/ABI.md` §1a: the Saw compiler's objects are call0, and the C beside them is compiled to match). Espressif's toolchain defaults to the windowed convention for this core, and their prebuilt libraries are, as far as the lead knows, windowed. If so they cannot be linked into a call0 program: either the radio process is a windowed program (the kernel then has to handle window overflow and underflow exceptions and save register windows at a switch, and Saw code in that process needs a bridge), or every call across the boundary goes through thunks. The first thing the design does is look at the libraries themselves and say which it is.

3. **What the libraries expect of an operating system.** They are written against an adapter table (tasks, queues, semaphores, mutexes, timers, memory, critical sections, interrupt registration, an event loop, non-volatile storage for calibration), a C library, ROM functions, the PHY's initialisation, the clock tree with the PLL running, and memory in internal SRAM for anything the radio's hardware touches. Their interrupt handlers expect to run as interrupt handlers; in sawos an interrupt reaches a driver as a wake of a thread. Other systems have wrapped the same libraries outside Espressif's SDK (NuttX, Zephyr, the Rust `esp-radio` crates), which shows the surface is finite and gives three references for it.

4. **The stacks.** TCP/IP: port an existing C stack (lwIP is what Espressif's SDK uses) as a process, or write one in Saw (the user's standing preference for our own code), or the first as a way to the second. The same question for the BLE host (NimBLE is the permissively licensed one). The protocol between an application and the stack is ours to design either way.

5. **What the part's owner should know before any of it runs on the board.** The libraries are opaque: they read the eFuse block for the MAC address and calibration (reads, not writes; the design confirms from Espressif's sources what the libraries are documented to do, since their code cannot be read), they drive the RF front end, and on this flat tier nothing stops a fault in them from reaching the kernel's memory. Radio emissions are regulated; the module's certification covers Espressif's libraries used as shipped.

6. **Another board may be the easier first radio.** The user expects to get ESP32-C6 boards. Those are RISC-V, where Espressif's libraries use the ordinary calling convention and the windowed question does not arise. The design should say how much of the work is shared and whether the first radio bring-up belongs on the S3 at all.

**The design answers:** the architecture and its protocols; for the radio libraries, what they are (from the files: convention, size, undefined symbols, sections), what they need, what each need costs in sawos, and a go or no-go with the reasons; the stacks, each option priced; RAM (internal SRAM against PSRAM, with SO-102); clocks; what can be tested where; the order of work; and the questions for the user.
