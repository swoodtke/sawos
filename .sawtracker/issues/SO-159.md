**On the part, a loop polling `Systimer.now()` for 100 µs took about 2.5 ms.** Find out why, before anything times or waits on SYSTIMER with interrupts masked.

**What was seen.** A PSRAM latency stage on the r8 part (rev v0.2) took a SYSTIMER count with `hal.psram_ticks()`. It read CCOUNT, polled until the count had advanced 1,600 ticks (100 µs at 16 MHz), then read CCOUNT again. Four runs:

| | pll80 | pll240 |
|---|---|---|
| polling `psram_ticks()`, which writes CONF on every call | 201,350 cycles | 605,358 cycles |
| CONF written once, then polling `now()` alone | 203,354 cycles | 609,374 cycles |
| expected | ~8,000 | ~24,000 |

- At each clock, the count is about 25.4× what 100 µs should take: about 2.54 ms either way.
- The pll80/pll240 ratio is 3.0, so the CPU clocks themselves agree with the clock line.
- `psram_cpu_passes`, which times CCOUNT against SYSTIMER over at least 80,000 ticks, reads the right clock (80.00 and 240.02 MHz). So the counter does advance at 16 MHz on average.

**The leading theory, unverified.** One `now()` takes about 2.5 ms on the part, so the loop exits after its first poll. `psram_cpu_passes` hides this, because both ends of each interval run the same instructions and the cost cancels. `now()` writes UNIT0_UPDATE and spins on VALUE_VALID (`hal/xtensa-esp32s3/kernel/lib.saw`). ESP-IDF v5.4.1's `systimer_hal_get_counter_value` does the same handshake. The emulator answers it at once.

**Why it matters.** The kernel's tick and timers read SYSTIMER. If a read takes milliseconds on silicon, every path that reads it with interrupts masked inherits that cost, and every timeout that polls it overshoots.

**To do.**
1. A read-only board stage that times, with CCOUNT:
   - one `now()`, and ten in a row;
   - the UPDATE-to-VALID spin alone;
   - a read of VALUE_LO/HI without the handshake;
   at `rom`, `pll80` and `pll240`. Print CONF and the UNIT0 op word before and after.
2. Find the cause: the clock gating in CONF, a missing clock enable, or the handshake as the chip does it. Check against the TRM's SYSTIMER chapter and IDF's `systimer_ll.h`.
3. If `now()` is slow, fix it and say in ABI.md what a read costs on the part. List every kernel path that reads SYSTIMER with interrupts masked, with its cost.

**Lead: SO-159.p1 lands the probe; the read is not slow.** The probe ran on the part at rom, pll80 and pll240 (f471–f473).
- **The counter:** SYSTIMER counts at 16 MHz at every key, about 16,000 ticks per CCOUNT millisecond.
- **The handshake:** the value registers hold the last snapshot until UPDATE, then turn valid within 1 to 3 polls.
- **A warm read:** about 120 cycles at 80 MHz and 170 at 240.
- **The largest round:** 16,468 cycles at pll240, about 69 µs. The harness prints only min and max, so it can't say which round that was.

So the issue's theory, a ~2.5 ms `now()`, is wrong.

**Still unexplained:** P9's calibration loop polling `psram_ticks()` took about 2.5 ms for 1,600 ticks. That loop is gone from SO-142.p9, and no kernel path does what it did.

**Left open on purpose:** the 69 µs worst read, which happens with interrupts masked. It is in ABI.md §6a. The flash-speed work (SO-147) and the scheduler's latency record are the places to watch it.

I'll close this issue when p1 merges.
