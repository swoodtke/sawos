**Networking K1: Pin and Unpin on memory objects, and a `contiguous` flag on Allocate.**

The design is `SO:virtio-net` revision 4, §3.4, with the owner's rulings of Nov 25 (Q15 is "no"). This unit is its K1 row:
- **The ops.** `MemoryOp.Pin` and `Unpin` on `MemoryRight.Physical`. Pin is the only way to learn an object's physical base and length.
- **The rights.** `PoolRight.Physical` carries the right for what a pool allocates. The three default rights sets change so that `physical` is off unless asked for.
- **Contiguous allocations.** `AllocateFlag.Contiguous`; Pin answers only for a contiguous object.
- **The quarantine.** A pinned object never returns to its pool.
- **Refusals.** `Extend` and `SlabDonate` refuse a pinned object.
- **The builder.** Its minimum for "off by default".
- **The rest.** The consumer sweep, and §3.4's cases.

**Lead: SO-162.p1 is K1: Pin, Unpin and the contiguous flag.** It is one commit on current main. Q15 is "no": Front's rights word is unchanged, and the Extend-while-pinned case is a named guard only.

**Numbers:**
- `MemoryOp.Pin` 2, `Unpin` 3;
- `MemoryRight.Physical` and `PoolRight.Physical`, both bit 12;
- `AllocateFlag.Contiguous`, bit 8;
- `MEMORY_PIN_RECORD_WORDS` 2.

The default rights words move from 1539 to 5635 and from 69123 to 73219.

**Kernel:**
- Pin answers in §3.4's order. Unpin answers AccessDenied, then BadState.
- `memory_release_if_idle` keeps a pinned object, and a teardown never unpins.
- SlabDonate of a pinned allocation is BadState.
- Unknown Allocate flags are BadArg, and boot allocations are contiguous.

**One reading to check:** a quarantined object stays charged to its creator while that process lives, and is disowned when it dies. Crediting the charge at release would let a process fill the Memory slab with quarantined objects without ever meeting its quota. The design's "charged to nobody" describes only the dead holder.

**Builder:**
- With no `[ceilings]`, a child gets Memory and Pool ceiling rows of every right but `physical`. A record with neither keeps the same word.
- `physical` named in a declaration is refused by name until B1 adds the image's grant.
- Spec §12's default sentences are updated alongside §2.5 and §2.8.

**Cases:** 15, on all three gate profiles. They include:
- `memory_pin_quarantine` steps 1 and 2;
- `memory_pin_copy_door`, which the design didn't list;
- `memory_unpin_denied`, split from `memory_pin_denied` because a fault ends the root;
- `stock_physical_default`.

**Mutants:** 23, all red. Two checks have no case:
- Unpin's release call is equivalent on the gate, because Unpin goes through a handle, so the object is never idle there;
- the Extend guard, as ruled.

**Runs:** `make sos-test` 1487 (45 new rows); S3 smoke 407. `MemorySlot` grows: `pinner` is a UInt64 pid.

Requested changes on patch SO-162.p1 (revision 2)

**Changes requested, revision 2.** r2 is r1 rebased, with identical lines. Pin and Unpin follow §3.4, and the builder's default holds. Three ordering rules and your flagged charge reading have no case, and on the S3 Pin can answer a flash address.

I ran with sawlang v0.24.3 on riscv32, against the 15 new cases plus `pool_ops`, `pool_cut_rights`, `pool_faults`, `pool_from_bad`, `slab_donate`, `handle_info`, `rights_ceiling_derived`, `memory_extend` and `memory_recycle`: 24 green. A control is red: with the pinned check removed, `memory_pin_twice` and `memory_pin_unmap_give` fail. The probes below are in f553. Together they are green on the patch (24 green), and each turns its own rounds red under its mutant.

## 1. Three ordering rules have no case
The order is dispatch.saw:3511-3518 and spec's Pin and Unpin bullets. Each mutant below survives all 24:
- **Pin's `Physical` check moved after the contiguous status.** `memory_pin_denied` pins an unpinned, contiguous page with a valid record, so `AccessDenied` comes back wherever the check sits.
- **Pin's `NoResource` decided before every fault.** `pool_physical_capped`'s page is contiguous.
- **Unpin's two checks swapped.** `memory_unpin_denied` pins first, so both orders answer `AccessDenied`.

**Asked:** three edits hold them.
- In `memory_pin_denied`, pin the page before the sibling's pin. The sibling then meets `BadState` unless the rights check comes first.
- In `pool_physical_capped`, allocate the capped page without `contiguous`.
- In `memory_unpin_denied`, never pin the page.

## 2. Your flagged reading has no case
The reading is that a quarantined object stays charged to its creator while that process lives. A mutant that credits the creator and disowns the slot at `memory_release_if_idle`'s pinned return (objects.saw:1730-1732) survives all 24. Two probes hold it:
- **In `memory_pin`:** root quarantines a page of its own and reads its Memory quota before and after. The mutant prints `quarantined, still charged: no`.
- **In `memory_pin_unmap_give`:** in design thread d06's shape, A allocates, then B pins the page and dies. The mutant prints `root still charged for the page: no (4 then 3)`.

**Asked:** land either probe as the rule's case.

## 3. On the S3, Pin answers a flash address
Every Ram boot row is marked `contiguous: true` (process.saw:1292-1305), and on the S3 an image row is flash used in place. Pin's only test of the region is `contiguous` (dispatch.saw:3534). Map refuses the same range through `hal.map_source_ok` (dispatch.saw:3452), and so does SlabDonate (1225). The S3 HAL says flash "is an image source and never a destination, a mapping or a slab donation".

**The probe.** With `memory_pin` added to the S3 smoke, root pins the child image row it holds: `the image row pinned: base=1008205824 len=10340`. That is 0x3C18_0000, in the flash data window, far from the internal DMA range (0x3FC88000 to 0x3FD00000 in IDF v5.4.1's soc.h). Root holds image rows with `memory_rights()`, which now carries `Physical`. On riscv32 the same row pins at 0x8002_3050, inside RAM, which is consistent.

**Asked:** have Pin answer `NoResource` for a range `hal.map_source_ok` refuses. That keeps the owner's ruling that every boot allocation is contiguous, and stops a driver being handed an address no device can reach. If the owner prefers that only rows the board can give a process be marked contiguous, that is the other fix.

## 4. The patch adds S3 artifacts that no S3 case builds
`tests/poolframes_xtensa.c` is used only by `tests/memory-pin/Saw.toml`, and the S3 smoke's process list has no pin case. With `memory_pin` added there, every pin line matches but one: the boot allocation pins `len=98304` against the expected 262144. On the r8 twin, the pool is PSRAM, so `at the pool's frames=no`.

**Asked:** either add `memory_pin` to the S3 smoke, with its boot length per board, the r8 twin handled, and the flash-row probe from finding 3 as a round; or drop the xtensa section.

## 5. Text
- **ops.saw:760-762 and spec.md:1023-1025:** Pin "is the only way to learn where an allocation is, so a process never holds the address of memory that could return to a pool". On riscv32 and the flat profile, a mapped allocation's pointer is its physical address, and `memory_pin` itself asserts `row_at == at.base` there. "Never" is also conditional, since another holder of `Physical` may unpin (thread d02). spec.md:1023's "a right no process holds unless its launcher grants it" overlooks root, which holds it from boot. This is the design's ruled wording, so the owner decides; the text should at least say "on a profile that translates".
- **spec.md:1442-1444:** "an allocation made without `AllocateFlag.Contiguous` is the `NoResource` status". A boot allocation is made without the flag, and pins.
- **floor.saw:928-929 and dispatch.saw:3552-3553:** an unpinned allocation "returns to its pool now" or "goes home now". Unpin goes through a handle, so nothing frees at the unpin; it goes home at the last handle's release.
- **dispatch.saw:3458-3464:** it lists Extend's answers "in spec §2.5's order", and leaves out the new `BadState` guard (3480-3487).

## Checked and found right
- **Pin's order** is §3.4's (dispatch.saw:3519-3549): rights, record capacity, the copy door, already pinned, not contiguous, then the write and the pin.
- **On riscv32 the 24 cases pass,** including the holder's death quarantining the object (`memory_pin_quarantine` against `memory_unpin_returns`) and a pinned SlabDonate's `BadState`.
- **Unpin's release call is equivalent on the gate,** as you say. Removing it survives all 24, because Unpin goes through a bound handle, so the object is never idle there.
