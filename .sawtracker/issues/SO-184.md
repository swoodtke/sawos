# Networking A6: `svc-net`, the stack as a server of `sockproto`, with echo applications

The networking design is `SO:networking`, mirrored in the scratchpad at
/private/tmp/claude-501/-Users-shawn-Projects-sawos/34c0d76b-723c-482d-939f-716d368f6e5c/scratchpad/networking.md.
Read §5.1 to §5.4 (the processes, the protocol packages and rule 5.2, the
copies, flow control and failure), §7.2 (rule 7.1) and §10's track A row
A6.

## What is there

- `drivers/sockproto`: the protocol, with its ops, statuses, slot layout
  and datagram headers, and hosted tests.
- `drivers/netstack`: Ethernet, ARP, IPv4, ICMP, UDP, the DHCP client, the
  DNS stub, and TCP (A5a and A5b on main; A5c, congestion control, is in
  review and changes only `tcpconn.saw`'s internals). The `Stack` API:
  - `configure`;
  - `udp_*`;
  - `tcp_secret`, `tcp_listen`, `tcp_accept`, `tcp_connect`, `tcp_write`,
    `tcp_read`, `tcp_close`, `tcp_abort`, `tcp_status`;
  - `poll(now)`.
- `drivers/svc-virtio-net`: the network driver serving `netdevproto` from a
  `pktring`.
- `tests/net-client`: a single process that today links `netstack` itself
  and talks `netdevproto` to the driver. Its scenarios (ping, DHCP, DNS,
  TCP echo) are the pattern for how a stack drives the device.
- `tools/netpeer`: the peer, with scripts for ARP, ICMP, DHCP, DNS,
  `tcp_echo` and A5c's `tcp_drop`.

## Build

1. **`drivers/svc-net`, a process** that is a `netdevproto` client of the
   network driver and a `sockproto` server for applications. It holds one
   `netstack.Stack`.
   - Its interface comes up by DHCP, or by a static configuration from
     its build input `netconfig`; say which is the default.
   - Its ISN secret comes from a source the image provides, or the build
     input; the stack refuses TCP without one. Say what you chose and why.
   - It serves every `sockproto` op:
     - `Attach`, `UdpOpen`, `TcpConnect`, `TcpListen`, `Accept`, `Send`,
       `Recv`, `Close`, `Resolve`, `IfStatus`;
     - the held calls for `TcpConnect`, `Accept` and `Recv`;
     - the status order the protocol states.
   - **Rule 5.2:** every field it reads from a client's ring is read once
     through `pktring`'s accessors and checked.
   - **Flow control (§5.4):**
     - a full ring holds (TCP) or drops and counts (UDP);
     - a slow client stops only itself;
     - a dead client's connection closes every socket it held;
     - a dead driver marks the interface down and closes its TCP
       connections.
   - One thread, or a serving thread and a timer, as `uartcore`'s model
     does. The stack's clock is `poll(now)` on a Timer.
   - Its `process.toml` says what a stock root gives it.
2. **Two applications in `tests/`:**
   - a UDP echo client;
   - a TCP echo client: it connects to the peer's `tcp_echo`, writes,
     reads back and closes.

   Each is a `sockproto` client only, with no `netstack` of its own.
3. **Gate cases** (riscv32, flat, arm64), each a stock-root image of the
   driver, `svc-net` and an application, against the peer:
   - `net_svc_udp`: a UDP echo through `svc-net`;
   - `net_svc_tcp`: the TCP echo through `svc-net`;
   - `net_svc_client_dies`: an application dies holding a TCP socket. Its
     connection closes and the peer sees the RST or FIN, whichever the
     stack sends; say which.
   - `net_svc_refusals`: the protocol's refusals through a real
     connection (a hosted test can cover the rest).

   Order everything by construction, and assert no time (rule 7.1).
4. **Hosted tests** of `svc-net`'s serving logic, where they can be split
   from the device: the op dispatch, the status order and rule 5.2. Use
   the shape of `uartcore`'s fake device.
5. **Docs:**
   - `svc-net`'s module doc;
   - CLAUDE.md's repo map;
   - `sockproto`'s doc wherever the server decides something the protocol
     leaves open.

**Out of scope:** `svc-openeth` and the S3 (A7), the radio, and the network
manager (`wlanproto`).
