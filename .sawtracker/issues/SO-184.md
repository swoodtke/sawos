# Networking A6: `svc-net`, the stack as a server of `sockproto`, with echo applications

The networking design is `SO:networking`, mirrored in the scratchpad at
/private/tmp/claude-501/-Users-shawn-Projects-sawos/34c0d76b-723c-482d-939f-716d368f6e5c/scratchpad/networking.md.
Read §5.1 to §5.4 (the processes, the protocol packages and rule 5.2, the
copies, flow control and failure), §7.2 (rule 7.1) and §10's track A row

## What is there

- `drivers/sockproto`: the protocol, with its ops, statuses, slot layout
  and datagram headers, and hosted tests.
- `drivers/netstack`: Ethernet, ARP, IPv4, ICMP, UDP, the DHCP client, the
  DNS stub, and TCP (A5a and A5b on main; A5c, congestion control, is in
  review and changes only `tcpconn.saw`'s internals). The `Stack` API:
  - `configure`;
  - `udp_*`;
  - `tcp_secret`, `tcp_listen`, `tcp_accept`, `tcp_connect`, `tcp_write`,
    `tcp_read`, `tcp_close`, `tcp_abort`, `tcp_status`;
  - `poll(now)`.
- `drivers/svc-virtio-net`: the network driver serving `netdevproto` from a
  `pktring`.
- `tests/net-client`: a single process that today links `netstack` itself
  and talks `netdevproto` to the driver. Its scenarios (ping, DHCP, DNS,
  TCP echo) are the pattern for how a stack drives the device.
- `tools/netpeer`: the peer, with scripts for ARP, ICMP, DHCP, DNS,
  `tcp_echo` and A5c's `tcp_drop`.

## Build

1. **`drivers/svc-net`, a process** that is a `netdevproto` client of the
   network driver and a `sockproto` server for applications. It holds one
   `netstack.Stack`.
   - Its interface comes up by DHCP, or by a static configuration from
     its build input `netconfig`; say which is the default.
   - Its ISN secret comes from a source the image provides, or the build
     input; the stack refuses TCP without one. Say what you chose and why.
   - It serves every `sockproto` op:
     - `Attach`, `UdpOpen`, `TcpConnect`, `TcpListen`, `Accept`, `Send`,
       `Recv`, `Close`, `Resolve`, `IfStatus`;
     - the held calls for `TcpConnect`, `Accept` and `Recv`;
     - the status order the protocol states.
   - **Rule 5.2:** every field it reads from a client's ring is read once
     through `pktring`'s accessors and checked.
   - **Flow control (§5.4):**
     - a full ring holds (TCP) or drops and counts (UDP);
     - a slow client stops only itself;
     - a dead client's connection closes every socket it held;
     - a dead driver marks the interface down and closes its TCP
       connections.
   - One thread, or a serving thread and a timer, as `uartcore`'s model
     does. The stack's clock is `poll(now)` on a Timer.
   - Its `process.toml` says what a stock root gives it.
2. **Two applications in `tests/`:**
   - a UDP echo client;
   - a TCP echo client: it connects to the peer's `tcp_echo`, writes,
     reads back and closes.

   Each is a `sockproto` client only, with no `netstack` of its own.
3. **Gate cases** (riscv32, flat, arm64), each a stock-root image of the
   driver, `svc-net` and an application, against the peer:
   - `net_svc_udp`: a UDP echo through `svc-net`;
   - `net_svc_tcp`: the TCP echo through `svc-net`;
   - `net_svc_client_dies`: an application dies holding a TCP socket. Its
     connection closes and the peer sees the RST or FIN, whichever the
     stack sends; say which.
   - `net_svc_refusals`: the protocol's refusals through a real
     connection (a hosted test can cover the rest).

   Order everything by construction, and assert no time (rule 7.1).
4. **Hosted tests** of `svc-net`'s serving logic, where they can be split
   from the device: the op dispatch, the status order and rule 5.2. Use
   the shape of `uartcore`'s fake device.
5. **Docs:**
   - `svc-net`'s module doc;
   - CLAUDE.md's repo map;
   - `sockproto`'s doc wherever the server decides something the protocol
     leaves open.

**Out of scope:** `svc-openeth` and the S3 (A7), the radio, and the network
manager (`wlanproto`).

**The implementer's note for SO-184.p1 (A6: `svc-net`, the stack as a `sockproto` server, with echo applications).**

**Structure.**
- **`drivers/netserve`, the hosted core** (in `uartcore`'s shape; no kernel calls):
  - `Link` is a trait (`tx`, `rx_return`, `next_event`), and `Setup` is DHCP or static;
  - `Server<M, L>` holds the `Stack`, its `Sink` (`Io`: the driver's ring, the UDP owner table, per-connection datagram backlogs, the DHCP and DNS inboxes), and each connection's ring, sockets and `Send`-named slots;
  - `request` answers `Now`, `Held(slot)` or `Attach`, and the process drains `next_answer` and `take_ended` after each event;
  - a fake ring and link, and a bench with a second netstack as the peer.
- **`drivers/svc-net`, the process:**
  - one worker thread, one Waiter, and the server boxed on the heap;
  - the driver's `Attach` is a blocking call;
  - `WaitEvent` is posted, with its claim on the Waiter;
  - client connections join the Waiter only once the interface is up;
  - two `serve` records (`sockets`, `sockets2`), so two applications per image.
- **`tests/sock-client`:** one package whose `sockcase` input picks `udp_echo`, `tcp_echo`, `tcp_dies` or `refusals`.

**Choices.**
- **DHCP is the default.** The gate uses static 10.0.2.15/24 except `net_svc_udp`, which uses DHCP, so both paths run.
- **The ISN secret** comes from the `netsecret` build input, with no default, so every image must name one. The kernel has no randomness, and a default in the tree would be one key for all. The key also draws the DHCP xid and DNS ids through SipHash.
- **One serving thread,** with a 100 ms periodic Timer for `stack.poll`.
- **At most 4 held calls per connection** (`MAX_HELD`); past that, `NoRoom`. The quota is 28 handles.

**Ops.**
- **The status order:** wire `BadOp`/`BadArg`, then `NotAttached`/`Attached`, then `Send`'s ring range, then `NoSocket`, `WrongKind`, `Busy`, then each op's own.
- **What the server settles** is written into `sockproto`'s new section "What the stack settles".
- **`Send`:**
  - answered at once;
  - its range must be the next unnamed published slots;
  - TCP slots go as the send buffer takes them, so a stalled TCP socket holds the ring behind it.
- **`Recv`:** UDP backlog 4 per connection, then drop and count.
- **`TcpConnect` and `Accept`:** held. An abandoned connect aborts and frees its id.
- **`Close`:** TCP data goes before its FIN, and the connection lingers.
- **`Resolve`:** held, up to 3 tries a second apart, then `TimedOut`. Any negative answer is `NotFound`.

**Flow control and failure.**
- **A full ring:** TCP holds, UDP drops and counts.
- **A slow client** stops only itself.
- **A dead client:** every socket closes, with TCP aborted by RST, held attachments removed and its ring unmapped.
- **A dead driver:** the address goes, TCP aborts, then `Down`.
- **Exit:** 0 once every connection has ended and the stack is idle.

**Gate cases (riscv32, arm64, flat), against the peer's new `svc` script:**
- `net_svc_udp` (DHCP, then a UDP echo);
- `net_svc_tcp` (connect, echo, close; the peer logs `tcp closed`);
- `net_svc_client_dies` (an app dies holding a connection, so the stack sends an **RST**, and the peer logs `tcp reset`);
- `net_svc_refusals` (13 refusals and outcomes, then a one-page ring ending that connection only).

**Rule 7.1:** only causally ordered lines are asserted, and the `svc` script answers a frame sent again exactly as the first time, without logging it. **A residual risk:** a datagram waiting on ARP is dropped after 3 s, so a 3 s stall of the peer during the UDP case would hang it. TCP recovers.

**Mutants:**
- **Hosted:** 31 of 33 killed; the 2 survivors are equivalent in the bench.
- **Gate:** 3 of 5 killed. The other 2 (two idle conditions) are killed by a new hosted `tcp.idle_waits`.

**Left for A7 and later:**
- `svc-openeth` and the S3;
- more than two applications per image;
- a gate case for a dead driver (hosted only);
- DHCP hosted.

**Totals:** gate 1817, S3 611; hosted `netserve` 5/5, `netpeer` 4/4, `sockproto` 1/1. The lead rebased it onto main with no conflicts.

Requested changes on patch SO-184.p1 (revision 2)

**Held for a revision.** The client-facing reads are sound:
- the ToServer head is read once and checked;
- each length word is read once, bounded, and copied before use;
- the "next unnamed published slots" rule holds, and `claims[]` can't overflow;
- teardown never touches an unmapped ring;
- `ConnId`'s generation stops cross-client aliasing;
- the build refuses an image without `netsecret`.

An Opus agent read it against `netstack`, `pktring`, the spec and the RFCs, and I checked each item below with a probe or by reading. On r1 (sawlang v0.24.6) the four cases are green on riscv32, arm64 and riscv32-flat, and each case is green 25 of 25 on riscv32 and on arm64.

**1. ✓ Counters that panic on overflow end the stack for every application** (by reading; the class U4 is held for).
- **The counters:** `Counts`' `slots_dropped`, `datagrams_unsent`, `datagrams_dropped`, `aborted` and `abandoned` are `UInt32` with `+ 1`. So is `draws` (`UInt32`), and `svc-net`'s `next_key` is a `UInt`, 32 bits on riscv32. `netstack` holds its own counters at the top (`count_up`).
- **A client can drive one:** `Send` of N slots to an id it never opened counts N `slots_dropped` each time, and a malformed `Resolve` counts a `draw` before its name is checked.
- **A remote host can drive one with no client involved:** a flood to a client's UDP port whose backlog is full counts `datagrams_dropped`.
- **Fix:** hold each count at its top, as `netstack` does, and wrap or widen `draws` and `next_key`.

**2. ✓ TIME-WAIT fills the TCP table for every client** (bench probe).
- A client made eight short exchanges, each closed by the client. Its ninth `TcpConnect` answered `NoRoom`, and another connection's `TcpConnect` five seconds later also answered `NoRoom`.
- The table has 8 slots (`tcpconn.saw`), `free_slot` skips TIME-WAIT, and TIME-WAIT lasts 240 s. So one application's ordinary traffic denies TCP to every application for four minutes.
- The same first-come capacity applies to the 16 UDP sockets, which `Resolve` also needs, and to the shared four-frame ARP queue.
- "A slow client stops only itself" holds for flow control only.
- **Fix:** recycle the oldest TIME-WAIT slot when the table is full, as stacks commonly do, and give each connection a share, or state the limits in `sockproto`'s "What the stack settles".

**3. ✓ The DHCP xid, the DNS ids and the DNS source ports repeat on every boot** (gate probe: the peer logging them, two boots of `net_svc_udp` and `net_svc_refusals` on riscv32).

| run | `xid` | DNS (id, port) pairs |
|---|---|---|
| boot 1 | 3838814822 | (43621, 49152), (43829, 49153) |
| boot 2 | 3838814822 | (43621, 49152), (43829, 49153) |

- `draw()` is SipHash(image key, `draws`) from 0, and the query socket takes the next ephemeral port. Within a boot that leaves 16 bits per query and none from the port.
- One observed boot gives an off-path forger the next boot's pairs. `dns.saw` checks only address, port 53, id and question.
- **Fix:** draw the query's source port too (RFC 5452 §9.2). With no randomness in the kernel, also state the cross-boot repetition, which the ISNs share (`isn.saw`: M counts from boot, F is per image), in the docs as a hazard until a source exists.

**4. ✓ Calls left unanswered once the driver is gone** (bench probe, and by reading).
- A UDP `Recv` held across `cut_link()`, or made after it, is still pending after 5 s of ticks. `recv()` has no `is_up` check, and `socket_status` has no `Down`. The module doc says every later operation answers `Down`.
- If the driver goes before the first link-up or lease, `serve_outlets` never runs: applications' `Attach` stay staged forever, and `svc-net` never sees their deaths or exits.

**5. `svc-net` exits on a refused delivery.** `serve` returns `failed("wait")` on any `wait()` error. The spec's rule is that a delivery whose mints are refused leaves the message staged and wakes the waiter with the status: "The server frees a slot and waits again". The process ending takes every application's networking with it. Survive it, or say why it can't arise.

**6. A held `TcpConnect` or `Accept` answered into a dropped claim leaves an orphaned connection.**
- `answer()` discards `reply()`'s `PeerClosed`, and the consumed request detaches its OneShot key, so `abandon()` never runs. The connection stays ESTABLISHED under an id the client never learned, holding a slot of item 2's table until the client's connection ends.
- Whether the Waiter can deliver the driver's event before the raised abandonment is the kernel's order: say which. If it can, treat a failed reply to a connect or an accept as the abandonment.

**7. The serving thread can block on the driver.** `tell()` falls back to a blocking `send` on `WouldBlock`/`QuotaExceeded`/`NoResource`, and each frame rings separately. A 256-datagram burst from one client can stall every client until the driver answers. State it, or keep the ring's doorbell non-blocking.

**8. Smaller:**
- `Resolve` refuses a malformed name with `BadArg` only after `Busy`, `NoRoom` and `Down`, and after a `draw`, while `sockproto` and the note put `BadArg` first.
- The module doc's "a socket the client closed first gets its FIN" is broken when the client dies with undrained slots: `close_all` sends RST (probably right; fix the doc).
- The peer's `svc` refusal branch logs before any `seen_before`, so a SYN resent after a ≥ 1 s stall logs "refused" twice: a red flake.
- The ARP 3 s risk is a stall of the whole host too, not only the peer's (`tick` receives, then polls, after a clock jump).
- `resolve sawos.test` turns `TimedOut` after two ≥ 1 s gaps with no answer.

**9. Rules with no red case** (my hosted mutants against `blade test` in `drivers/netserve`; each survives):

| mutant | result |
|---|---|
| `MAX_HELD` dropped from `TcpConnect` | survives |
| `MAX_HELD` dropped from `Accept` | survives |
| `MAX_HELD` dropped from `Resolve` | survives |
| the abandoned connect's `tcp_abort` removed | survives |

Also unpinned (the agent's list): abandonment of `Accept`, `Recv` and `Resolve`; TCP backpressure holding the ring; `Close` with undrained slots; `IndexOutOfOrder` through the server; items 1, 2, 4 and 5.
