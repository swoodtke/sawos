## The rule

A message's carried handles:
- **stay with the caller** on a transient refusal: `WouldBlock`, `NoResource`,
  `QuotaExceeded`. The typed tier hands them back in the error payload, in the
  shape `Waiter.give` and `Process.give` use (`kernel/sysapi/src/waiter.saw`,
  `kernel/sysapi/src/system.saw`). Copy that error-type pattern and its doc
  phrasing.
- **are consumed** by every other outcome. On success they travel, as today. On
  a terminal refusal (`PeerClosed`, and any other non-transient status the path
  can answer) **the kernel releases them**: each carried entry is unbound from
  the caller's table and its reference dropped through the ordinary release
  path, so an object whose last handle it was is freed (an Interrupt unbinds,
  a region is freed).
- A bad carried handle faults the caller, as today (`check_send`,
  `kernel/core/dispatch.saw` ~3013).

There is no new status. The fused call never answers a transient status (it
parks for room and mints no claim), so its `PeerClosed` is consumed whether or
not the message was staged.

**User ruling (Nov 9). This replaces the earlier lead ruling in this thread.**

**Transient refusals keep the handles; everything else consumes them.**
- **`WouldBlock`, `NoResource` and `QuotaExceeded`** (the "call again" refusals) leave the carried handles in the caller's table. The typed tier hands them back in the error, the same way as `Waiter.give` and `Process.give`.
- **Every other outcome consumes them:** success, `PeerClosed` and any other terminal refusal. On a terminal refusal the kernel releases the carried handles, so the caller can always assume they are cleaned up.
  - Releasing may destroy the object. An Interrupt unbinds its line, and a region whose last handle this was is freed.
- **A bad carried handle** still faults the caller.
- **No new status.** The fused send (`send_with`) never answers the transient statuses: it parks for room and mints no claim. So `PeerClosed` there is consumed, whether or not the message was staged.
- **Replies follow the same rule.** A reply to an abandoned request releases the replier's handles; before this ruling it left them with the replier.

**The unit:**
- **Kernel:** post, call and reply/reply_wait release the carried handles on their terminal refusals.
- **Typed tier:** `send_with`, `reply_with`, `reply_wait_with` (and post-with-handles) read the status first and hand back on a transient status.
- **Docs and spec:** drop the "not yet enforced" lines in §3 and §11.
- **Tests:**
  - handles sent to a dead outlet are released, and the object is freed where it was the last handle;
  - a `WouldBlock` post hands the handles back usable.

The unit is dispatched after SO-48 merges.

**Air: SO-39.p1, changes requested: the kernel is right; three text and API fixes, and two test gaps.**

The kernel side holds. I traced every status each op answers when the record carries handles:

| op | outcomes |
|---|---|
| post | `PeerClosed` releases; `WouldBlock`, `NoResource` and `QuotaExceeded` keep |
| call | `PeerClosed` at the call or while parked for room releases (including `resume_call_room`, which you found); later outcomes are consumed by delivery or at settle |
| reply, reply_wait | `PeerClosed` from abandoned, `Replied` or `Settled` releases; `Ok` stages |

No terminal status leaves the handles in the caller's table, and no transient one releases them. `release_carried` is `RELEASE_OP`'s unbind-then-unref, and a word repeated in a record is released once (its second lookup is stale). `resume_call_room` releases only after the thread is cleared, so a nested `notify_room` can't wake it twice. Nothing staged leaks: `pipe_drop_staged`, the settle path and the reap release it. The server gate passed.

1. **`kernel/sysapi/src/floor.saw:833-836` ✓ (stale, and it would mislead a C caller):** `sos_pipe_request_reply_wait` still says "a `Reply`-leg failure took none of them". The kernel now releases them on that `PeerClosed`, so a C caller following the doc keeps dead words, and its later release is a `BadHandle` fault.
2. **"The call never answers a transient status" is not true ✓.** That's floor.saw:797, dispatch.saw:3165, pipe.saw:792/967 and spec.md:1850, and pipe.saw:152-153 says "Only `post_with` can answer a transient status". But the call's wake path answers `mint_refusal(p)` (`NoResource`/`QuotaExceeded`) when the caller's table can't take the reply's handles (refs.saw ~1583), after the call's own carried handles were staged. The kernel comment there calls it "the one place a refusal is terminal". `reply_wait`'s `Wait` leg is the same after its reply landed. The kernel and typed tier are right, because those handles are consumed. But the ruling names the transient set by status, and floor.saw:787-788 gives `Call` "the same rule" as `Post`, whose `NoResource` keeps. Reword it as: transient means a refusal of the send itself; a fused op's `NoResource`/`QuotaExceeded` at the reply's delivery is terminal and consumes. **This touches the ruling's wording, so the user may want to confirm it.**
3. **`post_body`'s default runs the unsafe way (pipe.saw ~859-865):** `case PeerClosed -> handed_over(), case _ -> {}` keeps the carrier for every status except `PeerClosed`. The ruling closes the transient set, so the match should name `WouldBlock`, `NoResource` and `QuotaExceeded` to keep and send `_` to `handed_over()`. Nothing is live today, since `Post` answers only those four, but `checked` maps an unknown status to `Unknown`. Any future terminal status would leave stale words in the carrier, and dropping it would fault. A leak is the safe failure, a fault is not.
4. **Tests:**
   - Two of the three transient statuses have no arm: `post_with`'s `NoResource` and `QuotaExceeded` (dispatch.saw ~3109-3111). Root can provoke `NoResource` by filling its table with mints, posting with a carried handle, then freeing a row and retrying through the handed-back carrier.
   - `phase_parked` never asserts the ring was full: it discards `fill`'s result. If the ring weren't full, the call would stage and the close would release through the settle path, which already released before this patch. The arm would then pass on the old tree without reaching `resume_call_room`. Check the stop status as `phase_transient` does.
5. **Low:**
   - The Interrupt examples (refs.saw ~990, pipe.saw ~733, spec.md ~1846) can't happen yet: an Interrupt has no `Transfer` and no message kind.
   - "A region returns its slot" holds only with no grant row installed.
   - `send_args`'s docstring (dispatch.saw ~2987-2992) is garbled.
   - `tests/child-parked/Saw.toml:9-10` says the exit code is the verdict, but `main.saw:9` says it's the printed line.

**A pre-existing bug beside this code (not introduced here; please file it with a probe).** By code reading, a reply may carry its own obligation word.
- `check_send` never compares a carried word with the invoking handle.
- In `pipe_reply_status`'s `Ok` arm, `hold_staged` unbinds that word and stages a reference on the exchange's own obligation column.
- `consume_entry` then unbinds the same index again. `unbind_handle` doesn't check that it is bound, so the generation bumps twice and the handle quota is credited twice.
- It then unrefs a reference the handle no longer holds.
- The staged obligation is minted into the client, so a `PipeRequest` naming the exchange can outlive its settle.

The same mechanism applies to any op that consumes its invoking handle after staging (`reply_wait`). Refusing a carried word equal to the invoking one (`BadArg`) would close it. Your new `PeerClosed` arms consume before they release, so they are safe from this.
