## The rule

A message's carried handles:
- **stay with the caller** on a transient refusal: `WouldBlock`, `NoResource`,
  `QuotaExceeded`. The typed tier hands them back in the error payload, in the
  shape `Waiter.give` and `Process.give` use (`kernel/sysapi/src/waiter.saw`,
  `kernel/sysapi/src/system.saw`). Copy that error-type pattern and its doc
  phrasing.
- **are consumed** by every other outcome. On success they travel, as today. On
  a terminal refusal (`PeerClosed`, and any other non-transient status the path
  can answer) **the kernel releases them**: each carried entry is unbound from
  the caller's table and its reference dropped through the ordinary release
  path, so an object whose last handle it was is freed (an Interrupt unbinds,
  a region is freed).
- A bad carried handle faults the caller, as today (`check_send`,
  `kernel/core/dispatch.saw` ~3013).

There is no new status. The fused call never answers a transient status (it
parks for room and mints no claim), so its `PeerClosed` is consumed whether or
not the message was staged.

**User ruling (Nov 9). This replaces the earlier lead ruling in this thread.**

**Transient refusals keep the handles; everything else consumes them.**
- **`WouldBlock`, `NoResource` and `QuotaExceeded`** (the "call again" refusals) leave the carried handles in the caller's table. The typed tier hands them back in the error, the same way as `Waiter.give` and `Process.give`.
- **Every other outcome consumes them:** success, `PeerClosed` and any other terminal refusal. On a terminal refusal the kernel releases the carried handles, so the caller can always assume they are cleaned up.
  - Releasing may destroy the object. An Interrupt unbinds its line, and a region whose last handle this was is freed.
- **A bad carried handle** still faults the caller.
- **No new status.** The fused send (`send_with`) never answers the transient statuses: it parks for room and mints no claim. So `PeerClosed` there is consumed, whether or not the message was staged.
- **Replies follow the same rule.** A reply to an abandoned request releases the replier's handles; before this ruling it left them with the replier.

**The unit:**
- **Kernel:** post, call and reply/reply_wait release the carried handles on their terminal refusals.
- **Typed tier:** `send_with`, `reply_with`, `reply_wait_with` (and post-with-handles) read the status first and hand back on a transient status.
- **Docs and spec:** drop the "not yet enforced" lines in §3 and §11.
- **Tests:**
  - handles sent to a dead outlet are released, and the object is freed where it was the last handle;
  - a `WouldBlock` post hands the handles back usable.

The unit is dispatched after SO-48 merges.
