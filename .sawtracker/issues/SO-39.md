## Description

## Finding

Found by the SO-26 r2 implementer while rewriting `kernel/sysapi/src/pipe.saw`'s handle-transfer docs. The lead confirmed the code order; it has not been probed.

`call_body` (and, per the implementer, `reply_body` and `reply_wait_body`) calls `handles.handed_over()` **before** checking the kernel's status:

```
let raw = sos_pipe_inlet_call(handle, …)
handles.handed_over()      // disarms every carried wrapper
try checked(raw)           // then the status
```

When the kernel refuses with a status after taking nothing (for example `PeerClosed` because the outlet was gone before staging, or the client gone at reply), the carried entries are still bound in the caller's handle table, but no wrapper names them any more. They are stranded until the process exits. This is the same shape as SO-38 (`Process.give` on a status refusal).

## To decide

For each refusal path in `pipe_call`, `pipe_post`, `pipe_reply_status` and reply-wait (`kernel/core/dispatch.saw`, `refs.saw`), which statuses come back with the handles taken (staged, so disarming is right), and which with nothing taken (so the typed tier must hand the wrappers back, as `Waiter.give` does)?

## Acceptance

- [ ] A probe test: send handles on a connection whose outlet is gone. Today the sender can't name or release them afterwards.
- [ ] The fix: on a nothing-taken refusal, the typed tier returns the handles in the error payload (or never disarms them). The docs state the contract.
- [ ] Targeted pipe cases pass on all three profiles.

Lead ruling on the intended behaviour, applying the user's Sep 1 Waiter.give rule and SO-38's: on a refusal that took nothing, the typed tier hands the carried handles back to the caller (or never disarms them); it does not close them. On a reply to an abandoned request, the kernel takes nothing, so the replier keeps its handles. The spec (SO-31 r5) states this with a 'not yet enforced' marker until this issue lands.
