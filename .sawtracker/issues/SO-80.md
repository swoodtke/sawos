## Description

## Finding (from the ESP32-S3 HAL work, Nov 12; read, not probed)

On the ESP32-C3 board (`hal/riscv32-esp32c3/kernel/lib.saw`), `irq_mask`
routes the line's matrix source to CPU interrupt 0, and `irq_unmask` reads a
source routed to 0 as "unassigned" and allocates a fresh CPU interrupt number
for it. So every mask followed by an unmask of the same line consumes another
number, and the kernel masks a line at every delivery and unmasks it at the
driver's ack (spec §9). A driver that takes enough interrupts would exhaust
the board's CPU interrupt numbers.

The S3 HAL avoids the pattern: it routes each source once and masks with the
core's enable register.

## Acceptance

- [ ] A probe on the C3 smoke: a driver that takes more interrupts than the
      board has CPU interrupt numbers. Record what happens.
- [ ] If it fails: the mask keeps the line's assignment (mask through the
      CPU's enable bit, or remember the number), with the probe as its case.


## Comments

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":613,"created":"1794526069","id":"c1"} -->
**Lead, Nov 12:** the SO-75 review found the same mechanism on the ESP32-S3 (a CPU interrupt taken per line ever bound and never given back, so a process that binds and releases enough distinct lines stops the machine) and asked that the C3 get the same answer. The S3's fix, in SO-75.p1's revision: the HAL releases a line's CPU interrupt and route on every mask and takes one from a free set on every unmask, so the kernel's Interrupt slab bounds how many are in use at once. Apply the same shape here, with the reviewer's probe (bind and release more lines in turn than the HAL has CPU interrupts) as the case.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":901,"created":"1794532008","id":"c2"} -->
**Lead, Nov 12, from the approval of SO-75.p1 r2:** the S3's lazy take-back prefers a line that is masked and not pending, which is exactly a live line masked on fire with its device quiet, waiting for its driver's ack; it is taken ahead of lines whose Interrupts are long gone (the reviewer ran it: line 27 masked on fire, lines 1 to 8 bound and released, a ninth bind takes 27's CPU interrupt; nothing was lost, 27 fired again at its ack on another CPU interrupt). With `MAX_INTERRUPTS` at four and nine entries, five are always held by lines with no Interrupt, so a HAL told which lines are released would never touch a live one. **This unit is where that seam goes, for both boards:** the kernel tells the HAL when a line's Interrupt is destroyed (`destroy_interrupt`), the HAL frees that line's CPU interrupt then, and a take-back from a live line disappears. The identity HALs get an empty body.
