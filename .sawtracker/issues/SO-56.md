## The defect (a code reading; confirm it)

A `Gone` process slot is reclaimed when its `refs` reaches zero
(`reclaim_process_slot`), and `refs` counts Process handle entries and the
attachment. When a **live** process releases the last handle, the release path
reaches the Process arm of `free_object`, which reclaims. But when the last
handle sits in a process that **dies**, its teardown's close-all drops it with
`unref_teardown`, which counts without freeing, and the reap that follows
(`reap_unreferenced(p)`, `kernel/core/refs.saw`; it now takes the dying `p`
after SO-53) does not scan `PROCESSES`. So the slot stays `Gone` at `refs == 0`
for good, and process capacity shrinks by one. The same applies to an
attachment on that process dropped by the teardown's attachment sweep. Check
both.

Approved patch SO-56.p1 (revision 1)

**Air: SO-56.p1, approved.** The scan at the end of `reap_unreferenced(p)` calls `reclaim_process_slot(q)` for every `q != p`. That function frees only a slot that is `Gone` at zero references and returns at once for a live, `Created` or `Free` slot, so the scan can't disturb anything that still has a reader.
- **Placement:** it runs after both the close-all and the attachment sweep, so both forms of the last reference the dying process held on another process are counted.
- **The dying slot** is skipped and still waits for `end_process`'s final, `Gone`-guarded call, so the teardown keeps indexing it safely.
- **Safety of the reclaim:** reclaiming another finished slot writes only `state`, the property the SO-53 review established.
- **No nesting:** nothing else is mid-teardown, because the kernel is uniprocessor and `end_process` doesn't nest.

`gone_reclaim_teardown` covers the handle and attachment forms, and your unfixed probe showed `spare=1` against the fixed `spare=2`. Under the disown rule this was the last way a dead slot could outlive its handles and attachments.
