## Description

**Unit U1 of the image and packaging design (SO-95; tracker doc `SO:images-and-packaging`, revision 5, sections 1, 9, 10 and 14).** The user has agreed to the design's recommendations (Nov 14).

**What this unit is.** sawos's first tool written in Saw: `tools/sosimage/`, a hosted Blade package, takes over from `tools/sos_runner.py` the work of compiling a kernel, stitching a root image and child images into it, emitting the boot region table, and linking. The runner calls it. Nothing about any image changes: this unit moves code, in a new language, and proves the move by the images and the gate's report being the same.

**The shape (design rules 9.1 to 9.7).**
- The runner keeps its package phase (each Blade package built once, before any case), its case table, QEMU and the judging of consoles.
- Once per run, for each profile and each kernel entry the selected cases use, the runner calls `sosimage kernel`, writing to a path of its own (two compiles never write one output).
- Per case, the runner writes a JSON test image into the case's staging directory and calls `sosimage link`. The JSON is versioned and carries what a case states today: the kernel entry, the root image, the children, `asm` and `child_asm` payloads, explicit addresses, the region table's rows with their kinds and flags, and the ESP32-S3's fixtures. State its schema in the builder's source where it is read.
- In the builder: the boot-table stub, the `.incbin` stubs, `check_in_place` with today's message byte for byte, and the link.
- Stays in the runner: `_check_kernel_fp_free`, the ESP32-C3 smoke's whole path, `--emit-flash`'s final step if moving it is not needed for the above (say which way and why).
- No cache across runs.
- The runner builds `sosimage` right after it builds Blade, and writes the `<sawos>/.sawlang` link first so the package can depend on `libs/imgformat` by a relative path; `tools/toolchain.py` stays a verbatim copy of sawlang's.

**Acceptance.**
- For every case on every profile and both smokes, the linked image is byte for byte what the Python path produced. Keep the old path reachable behind a flag for this unit so the comparison can be run (and is run in the hand-back); where two builds of one input are not byte-identical even on main, show that and compare what is stable instead (sections and symbols).
- The gate's report is the same text as main's: rows, order, image sizes, totals (789 / 6 / 39), the package lines. The run is not slower by more than a small, stated amount; say how long the gate took before and after.
- `runner_dupkeys.py`: the same named cases, no duplicate key.
- A failure in the builder (a missing input, a refused image, a tool that exits non-zero) reaches the runner's report as the case's failure with the builder's message, never as a silent pass or a hang.
- The builder has tests of its own that run in the gate without an emulator: at least the JSON reader's refusals (an unknown key, a wrong version, a missing field) and the region table's bytes for a fixed input.

**Saw at the pinned compiler (v0.23.0): what to know before writing it.** Each is from the sawlang lead or from the design's probes (section 11):
- A raw-backed error-enum case returned bare from a function whose result is an integer payload beside an ERASED error (`Result<UInt, Box<any Error>>`) is `Ok(raw)`. Keep typed errors in the builder; where an erased error is unavoidable, bind the case first (`let w = Why.Bad; return w`).
- `TaskGroup`: a group whose owner sleeps or waits on a timer between spawning into it and dropping it can be read after the drop (SL-1109). Run child processes with `Command` and no group; if a group is needed, one long-lived group.
- In a generic body an array literal is accepted for `[T; N]` whatever N is; write a repeat literal.
- A `static_assert` that reads a size through a static is not checked; name `sizeof` in the assertion.
- `std.process.Command` has no working directory: run through `/bin/sh -c 'cd "$1" && exec ...'`. It has arguments, environment, exit status and collected output, which is all this unit needs.
- No `is_dir`: a path is a directory if `Directory.list` succeeds. No hex formatting: a small function. `Map.get` needs `Copy` values: for JSON, `var doc`, `borrow let top = doc.as_object()!`, `top.find(&key)`. No SHA-256: `shasum -a 256` through `Command` if a hash is needed.
- `blade build` ignores a flag it does not know and its build avoidance does not see a changed linker script: always `--force`, as the runner does.
- A gap that blocks the unit and has no workaround is reported to the lead with the smallest program that shows it and the exact error; it is not worked around by writing that piece in Python.

**Not in this unit:** the hand-written description formats and TOML (U3), per-board limits and linked slab areas (U2), generated link addresses (U4), anything a product repository needs (U7), the harness (U8).

**Lead: SO-104.p1 is up: `sosimage`, the image builder in Saw.** Gate on the lead's machine: 789 / 6 / 39, and the gate's report is byte for byte main's on all three targets. 305 named cases, none repeats a key.

**What moved.** `tools/sosimage/` is a hosted Blade package (ten source files, five test files). The runner builds it after Blade, having pointed a git-ignored `.sawlang` link at the resolved sawlang checkout so the package can depend on `libs/imgformat` by a relative path. Per profile the runner writes a profile description (JSON) and calls `sosimage native` (the HAL's native objects) and `sosimage kernel` once per kernel entry; per case it writes an image description and calls `sosimage link`. In the builder now: the kernel compile, the payload and hand-written child assembly, the root-image and region-table stubs (the stub `.incbin`s the package's image by its own path; no staging copy), the table's encoder, the link, and on the ESP32-S3 the flash image and `check_in_place` with today's messages. In the runner still: the package phase, the case table and which rows a case's table gets, QEMU, judging, `_check_kernel_fp_free`, the ESP32-C3's whole path, and `--emit-flash`'s last step (trim, hash, the esptool line). `SOS_IMAGE_BUILDER=python` keeps the old path, and both read the same row specs.

**The images.** Main's own builds are reproducible (the Python path's images match a second run of main byte for byte). Against them, every image the builder links (789 in the gate, 39 in the S3 smoke): program headers, every allocated section's address, size and bytes, and every symbol but one are identical; all 38 ESP32-S3 flash binaries are identical byte for byte; the C3's are identical (its path did not move). **The one difference** is the brief's own rule at work: the kernel is compiled once per entry, so the file symbol naming the kernel object changes from `<case>.o.ll` to `<entry>.o.ll`, and the string table's offsets shift with it. Nothing loaded differs.

**Time.** The full gate: 541 s on main, 392 s through the builder (one kernel compile per entry where there was one per case), 554 s through the kept Python path.

**A builder failure reads as the case's build error** with the builder's message: a missing child image, a description with no `kernel`, a tool exiting non-zero and a compile error were each produced on purpose and print `✗ <case> (build error)` and `error: ...`, a compiler's whole output included.

**The builder's own tests** run in a full `make sos-test` (`blade test` in the package, about three seconds, silent on a pass): the two description readers with every refusal checked against its message (an unknown key, a wrong version, a missing key, a wrong type), the region table's bytes for a fixed input at both word widths, each `check_in_place` message, and hex text.

**To weigh.**
1. The server's gate resolves the toolchain by fetch; the lead's runs name a checkout. The builder is built the way Blade is, from the resolved checkout, so it should build there the same; the server's run is the proof.
2. The S3's C natives get four flags twice (once from the board's arguments, once from the builder's rule for C); the objects are identical.
3. A tool killed by a signal reports 128 plus the signal where Python reported a negative code.
4. The flash-magic failure names the link script by absolute path now; it prints only on a red run.
5. `kernel/rootimg.S` is used only by the Python path.

**Saw gaps.** Two new, with the smallest program for each, being filed in sawlang's tracker: an optional chain with `??` on a call result whose payload owns a `String` fails the compile with an internal invariant (binding the optional first works); and `main -> Result<Void, E>` cuts an error's message at about 508 bytes, which would hide most of a compiler's output (the builder's `main` returns `Int` and prints the error itself). The known ones were met as section 11 of the design says, each with its workaround; no piece was written in Python for want of Saw.

Approved patch SO-104.p1 (revision 1)

**Approved (reviewer, Nov 14), revision 1.** The builder makes the images the runner made, fails loudly on everything I fed it, and its own tests have teeth. Three small things are below for a later unit; none is a reason to hold this one. Probes and logs: `.build/scratch/air-review/so104_p1/` on the Air.

**Checked.**

- **The images, my own comparison.** Fourteen cases chosen for their shapes (a payload, a root package, a hand-assembled child, pool blobs, pool destinations, off-grain rows, a device row, three children, the arm64-only and riscv32-only ones), on all three profiles, through `SOS_IMAGE_BUILDER=python` and through the builder: 35 images each way, every case passing both ways. For every pair the program headers and every allocated section's address, size and bytes are the same, and the symbol tables differ in exactly the one file symbol the note names (`<case>.o.ll` against `<entry>.o.ll`).
- **The ESP32-S3 smoke, which the server's gate does not run.** 39 cases pass through the Python path and 39 through the builder, and the 38 flash images each writes are identical byte for byte.
- **The builder's own tests are not vacuous.** Thirteen one-line changes to its source, `blade test` after each: eleven fail a test (a row's reserved bytes, the zero high half of a 32-bit linked field, the pool kind's value, boot flags past a byte, unknown keys, a negative address, a blob index past the children, the version check, `children` beside `child_asm`, a writable segment in flash, a segment linked off its bytes). The two that pass are below.
- **Descriptions it should refuse.** Twenty-three variants of a real image description through the built `sosimage link`. Twenty-one are refused with `error:` and a sentence naming the key or row, exit 1, and no ELF left behind: a wrong type, a wrong version, a missing key, an unknown key, flags of 256 and of -1, a base of 1.5, of 2^63 and of 2^64, a blob row with numbers, a blob index the image lacks, an unknown kind, `children` beside `child_asm`, a child image that is not there, a path with a quote in it, `rows` as an object, 256 rows, an empty file, an array, text after the object, and a repeated key whose last value is a wrong version (point 2). Two are accepted: a row of length 0, which is the kernel's to judge, and a base past 32 bits on riscv32 (point 3).
- **The source.** No result is discarded: the two `let _ =` are a directory test and a map insert. Every `?? ""` reads an index the loop has bounded. A tool's failure carries its exit code, command line and merged output. `incbin_operand` refuses a path the assembler would read differently.
- **The server's gate passed** with the toolchain fetched, which answers the note's first point.
- Not run by me: the full gate. That is the server's.

**1. Two lines nothing holds.**

- `flash_image`'s refusal of a flash image whose first byte is 0xE9: with the test removed from the source, `blade test` passes, and the S3 smoke is outside `make sos-test`. Its sibling, the direct-boot magic, is the same routine; the tests in `flash_check.saw` are `check_in_place`'s.
- The page a pool blob is placed on and padded to (`POOL_BLOB_ALIGN`): with 16 in place of 4096, `blade test` passes, and so do the gate's six cases that carry a pool blob, run through the builder on riscv32 (`pool_lifetime`, `pool_freed`, `pool_nodes_home`, `pool_boot`, `image_held`, `image_rows_held`; the generated stub showed `.balign 16`). I did not run arm64 or the flat profile with it. The Python path has the same alignment and the same lack, so nothing moved; a case that needs the whole blob as one run, or a test of the stub's text, would hold it.

**2. A repeated key is taken in silence.** `{..., "version": 1, ..., "version": 2}` is read as version 2: `std.json` keeps the last. `fields.saw` promises that a description the builder half-understood is refused, and this is the one way left to half-understand one. The runner cannot write it; a hand-written description (U3) can. It wants a `JsonValue.parse` that refuses a repeated key, which is sawlang's.

**3. A number the target cannot hold is the kernel's to refuse.** A numeric row whose base is past 32 bits on riscv32 links, and the kernel stops at boot on `fits_word`. The builder has `word_bytes` and could say so before anything is compiled. The same in the Python path, so nothing moved; for U3's refusals.

**On the note's points to weigh:** the duplicated C flags, the 128-plus-signal exit code, the absolute script path in the flash-magic message and `kernel/rootimg.S` staying for the Python path are all fine by me. `_run_sosimage` has no timeout, as `_run` never had one.
