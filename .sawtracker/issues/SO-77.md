## Description

## Scope

Userspace drivers for the two devices the box uses, each a process holding
only its own window.

- **Device rows:** the GPIO and LEDC windows in the board's region table, so
  they reach root as `IoMemory` and root hands each to its driver.
- **GPIO driver:** configure a pin as an input with a pull, read it, and wake
  on its edge through the GPIO interrupt line; configure a pin as an output.
- **PWM driver:** LEDC at a servo's 50 Hz frame with the pulse width as the
  request, one channel per servo.
- Each serves a pipe protocol, as `tests/svc-uart-ns16550` does for a UART.
- Register blocks are typed structs over the mapped window, with volatile
  accessors.

Under QEMU the GPIO driver is checked as far as the emulator models the
device, and the PWM driver as register writes only, because the emulator has
no LEDC. The real check is on the board.

## Needs the user

The pins: the switch, each servo's signal, and how the servos are powered.

## Acceptance

- [ ] a smoke case per driver under QEMU, to the limit above
- [ ] on the board: a servo moves to a commanded angle, and the switch's edge
      wakes its driver

## Implementation notes (lead, Nov 12)

**Model:** Sonnet, one dispatch per driver once SO-75 has merged.
**Rules:** `.sawtracker/docs/implementer-rules.md`.

### Needed from the user first

The pins: the switch's GPIO and whether it is wired to ground (pull-up) or to
3.3 V (pull-down); each servo's signal GPIO; how many servos.

### Read first

`tests/svc-uart-ns16550/src/main.saw` and the `uart_service` case: a driver
process that receives its window as an `IoMemory` and its line as an
Interrupt, maps the window, serves a pipe protocol, and holds a read until
the device has data. `tests/uartproto/` is how a protocol is shared between a
driver and its clients.

### Device rows

The board's region table gains a Device row for the GPIO block and one for
LEDC (addresses from `hal/xtensa-esp32s3/ABI.md`; the C3 board file's
console window is the model for offering a device window). Pin routing on
this family goes through the IO MUX and the GPIO matrix: say in the driver
which block each register lives in, and add a row for any block the two
drivers need beyond their own.

### The GPIO driver (`tests/svc-gpio-esp32s3/`, protocol in `tests/gpioproto/`)

- Requests: configure a pin as input with a pull, or as output; read a pin;
  write a pin; wait for an edge on a pin (held until the edge, as the UART
  driver holds a read).
- The edge arrives on the GPIO interrupt line, bound through
  `SystemOp.InterruptBind` by root and given to the driver. Read the status
  register before the ack (spec §9's release rule).
- Register blocks are structs over the mapped window with volatile accessors,
  as the UART drivers' `regs` are.

### The PWM driver (`tests/svc-pwm-esp32s3/`, protocol in `tests/pwmproto/`)

- LEDC: one timer at 50 Hz, one channel per servo, the duty set from a pulse
  width in microseconds. State the duty resolution and the clock source you
  chose and why they give a servo's 1 to 2 ms range enough steps.
- Requests: attach a channel to a pin; set a channel's pulse width; stop a
  channel.
- LEDC's clock gate and reset bits live in the system block, not in LEDC's
  own window. Say how the driver gets them: a row for that block, or the
  kernel's board code enabling the clock at boot. Ask the lead if neither is
  clearly right.

### Tests

- Under QEMU: GPIO as far as the emulator models it (`ABI.md` says how far).
  PWM as register writes read back, since the emulator has no LEDC; if a
  write to an unmodelled address faults there, the case is board-only and the
  report says so.
- On the board, through the lead and the user: a servo moves to three
  commanded positions; the switch's edge wakes a waiting client.

**Commits:** `drivers: GPIO for the ESP32-S3` and `drivers: LEDC PWM for the ESP32-S3`

## The wiring, as the user gave it (Nov 13), and a proposed pin plan

The user: "The board is a Freenove WROOM ESP32-S3. There will be 2 servos
and one switch. Power will come via USB." Pins "can be modified later
after I wire up the electronics", so the drivers take pin numbers as
configuration and nothing below is fixed.

**Pins to stay off** (from Freenove's GPIO notes and the module's facts;
the board's own probe showed 8 MB of embedded PSRAM):

| GPIO | why |
|---|---|
| 0, 3, 45, 46 | strapping pins, sampled at reset |
| 19, 20 | the native USB port |
| 43, 44 | UART0, the kernel's console |
| 35, 36, 37 | the module's octal PSRAM |
| 38, 39, 40 | the SD card slot |
| 48 | the onboard WS2812 LED |
| 4 to 13, 15 to 18 | the camera connector (free only with no camera fitted) |

**Left over and proposed:** GPIO 1, 2, 14, 21, 41, 42, 47.
- **Servo A: GPIO 41. Servo B: GPIO 42.** Neighbours on the header (if it
  follows the DevKitC-1 layout the board copies; to be checked against the
  silkscreen).
- **Switch: GPIO 21,** to ground, with the pad's internal pull-up, so it
  reads low when closed and needs no resistor.
- **Spares:** 47, 14, 1, 2 (2 may carry an onboard LED; unverified).

**For the drivers' design:** LEDC can route a PWM output to any GPIO, and
any GPIO can be an input with a pull-up and an edge interrupt, so the pin
choice costs the drivers nothing. A hobby servo wants a 50 Hz frame with a
pulse of about 1 to 2 ms; whether LEDC's timer can run from the crystal
while the CPU is still on the ROM's clock is to be settled in the spec.

**Power, which is the real risk.** The servos take 5 V from the board's
5 V pin (USB's supply), never the 3.3 V pin; the 3.3 V signal is enough
for the control wire; grounds are common. A micro servo draws a few
hundred milliamps moving and more than half an amp stalled, and a USB 2
port is specified for half an amp, so two servos starting together can
sag the supply and reset the board. Mitigations: a 470 to 1000 uF
capacitor across the servos' supply near them; a supply good for an amp
or more (a charger or powered hub rather than a laptop port); and the
motion sequence moving one servo at a time, which a useless box does
anyway (lid, then arm).

**From the Air, on the pin plan: one fact for the PWM driver.** The two pads proposed for the servos are the part's JTAG pads, and on them the IO MUX's function 0 is not GPIO.

From Espressif's register header for the ESP32-S3 (`soc/esp32s3/include/soc/io_mux_reg.h`, release v5.1), quoted:

```
#define PIN_FUNC_GPIO                               1
#define FUNC_MTDI_GPIO41                            1
#define FUNC_MTDI_MTDI                              0
#define FUNC_MTMS_GPIO42                            1
#define FUNC_MTMS_MTMS                              0
#define FUNC_GPIO21_GPIO21                          1
#define FUNC_GPIO21_GPIO21_0                        0
```

So GPIO 41 is `MTDI` and GPIO 42 is `MTMS` (39 and 40 are `MTCK` and `MTDO`), and GPIO is function 1 on every pad of this part. On GPIO 21 functions 0 and 1 are both GPIO, so a driver that leaves a pad's `MCU_SEL` at 0, or writes 0 meaning "plain GPIO", works for the switch and not for a servo on 41 or 42: LEDC's signal goes out through the GPIO matrix, which drives a pad only while the pad's IO MUX function is the GPIO one.

**What it asks of the drivers:** each selects function 1 (`MCU_SEL`, bits 14:12 of the pad's IO MUX register) for every pin it configures, whichever pin that is, and does not rely on the reset value. That keeps "the pin choice costs the drivers nothing" true.

**Why say it now:** the emulator's `esp32s3.iomux` will not show the difference, so this fails only on the board, and only on these pins. The smoke case can hold it as a register write: after a pin is configured, its IO MUX register reads function 1.

Not checked by me: the reset value of `MCU_SEL` on those four pads (the header gives the function numbers, not the reset state), and anything about the board's header layout. The plan's other rows agree with what I know of the module and I have no source to hold them to.
