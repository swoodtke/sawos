## Description

## Scope

Userspace drivers for the two devices the box uses, each a process holding
only its own window.

- **Device rows:** the GPIO and LEDC windows in the board's region table, so
  they reach root as `IoMemory` and root hands each to its driver.
- **GPIO driver:** configure a pin as an input with a pull, read it, and wake
  on its edge through the GPIO interrupt line; configure a pin as an output.
- **PWM driver:** LEDC at a servo's 50 Hz frame with the pulse width as the
  request, one channel per servo.
- Each serves a pipe protocol, as `tests/svc-uart-ns16550` does for a UART.
- Register blocks are typed structs over the mapped window, with volatile
  accessors.

Under QEMU the GPIO driver is checked as far as the emulator models the
device, and the PWM driver as register writes only, because the emulator has
no LEDC. The real check is on the board.

## Needs the user

The pins: the switch, each servo's signal, and how the servos are powered.

## Acceptance

- [ ] a smoke case per driver under QEMU, to the limit above
- [ ] on the board: a servo moves to a commanded angle, and the switch's edge
      wakes its driver

## Implementation notes (lead, Nov 12)

**Model:** Sonnet, one dispatch per driver once SO-75 has merged.
**Rules:** `.sawtracker/docs/implementer-rules.md`.

### Needed from the user first

The pins: the switch's GPIO and whether it is wired to ground (pull-up) or to
3.3 V (pull-down); each servo's signal GPIO; how many servos.

### Read first

`tests/svc-uart-ns16550/src/main.saw` and the `uart_service` case: a driver
process that receives its window as an `IoMemory` and its line as an
Interrupt, maps the window, serves a pipe protocol, and holds a read until
the device has data. `tests/uartproto/` is how a protocol is shared between a
driver and its clients.

### Device rows

The board's region table gains a Device row for the GPIO block and one for
LEDC (addresses from `hal/xtensa-esp32s3/ABI.md`; the C3 board file's
console window is the model for offering a device window). Pin routing on
this family goes through the IO MUX and the GPIO matrix: say in the driver
which block each register lives in, and add a row for any block the two
drivers need beyond their own.

### The GPIO driver (`tests/svc-gpio-esp32s3/`, protocol in `tests/gpioproto/`)

- Requests: configure a pin as input with a pull, or as output; read a pin;
  write a pin; wait for an edge on a pin (held until the edge, as the UART
  driver holds a read).
- The edge arrives on the GPIO interrupt line, bound through
  `SystemOp.InterruptBind` by root and given to the driver. Read the status
  register before the ack (spec §9's release rule).
- Register blocks are structs over the mapped window with volatile accessors,
  as the UART drivers' `regs` are.

### The PWM driver (`tests/svc-pwm-esp32s3/`, protocol in `tests/pwmproto/`)

- LEDC: one timer at 50 Hz, one channel per servo, the duty set from a pulse
  width in microseconds. State the duty resolution and the clock source you
  chose and why they give a servo's 1 to 2 ms range enough steps.
- Requests: attach a channel to a pin; set a channel's pulse width; stop a
  channel.
- LEDC's clock gate and reset bits live in the system block, not in LEDC's
  own window. Say how the driver gets them: a row for that block, or the
  kernel's board code enabling the clock at boot. Ask the lead if neither is
  clearly right.

### Tests

- Under QEMU: GPIO as far as the emulator models it (`ABI.md` says how far).
  PWM as register writes read back, since the emulator has no LEDC; if a
  write to an unmodelled address faults there, the case is board-only and the
  report says so.
- On the board, through the lead and the user: a servo moves to three
  commanded positions; the switch's edge wakes a waiting client.

**Commits:** `drivers: GPIO for the ESP32-S3` and `drivers: LEDC PWM for the ESP32-S3`

**Lead, Nov 12: what SO-73 found changes the test plan.** The emulator
models no GPIO beyond the strap register (an output write goes nowhere, an
input reads 0, no GPIO interrupt is raised) and has no LEDC device; writes
to LEDC's address are dropped and read back 0 (`ABI.md` §9).
- Neither driver can be checked against a device under QEMU. Each gets one
  smoke case that proves the process starts, maps its window and answers a
  request without faulting, and says in its header that the device is absent
  there.
- The real check for both is on the board (SO-76 first).
- LEDC is at 0x6001_9000 and GPIO at 0x6000_4000. The IO MUX (0x6000_9000)
  is hidden under the emulator, so pin routing is board-only too.
