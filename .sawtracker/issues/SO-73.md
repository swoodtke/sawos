## Description

## Scope

Establish, by probe, every board fact the Xtensa HAL will be written against,
and boot a bare stub on the emulated ESP32-S3. It needs no Saw compiler, so it
starts before sawlang's Xtensa target (SL-1063) exists.

`hal/riscv32-esp32c3/ABI.md` is the model: it records what the emulator does,
probe by probe, and marks where the emulator and the silicon disagree.

## To establish

- **Boot.** How the ROM in `qemu-system-xtensa -machine esp32s3` hands over
  control: the image it accepts (direct boot or the esptool image format), the
  entry address and state, what the ROM leaves configured, and what the same
  path is on silicon per the S3 technical reference.
- **The memory map** from the monitor's `info mtree`: RAM, the flash windows,
  the peripherals.
- **Exceptions and interrupts.** The vector layout and `VECBASE`, the
  interrupt levels, how `syscall` arrives, which special registers a trap
  frame must hold, and the cost of call0 against the windowed ABI for a
  kernel. `PS.UM` and what the S3 offers for privilege, to confirm that the
  first profile is `Flat`.
- **The timer.** SYSTIMER through the interrupt matrix, or the core's
  `CCOMPARE`: which one the emulator delivers, and whether `waiti` wakes.
- **The console.** UART0, and USB-Serial-JTAG as the alternative on boards
  that expose only the USB port.
- **Watchdogs** the ROM leaves running.
- **GPIO and LEDC,** as far as the emulator models them: what a GPIO write,
  a GPIO read and a GPIO interrupt do there, and that LEDC is absent.
- **The build spelling:** the Espressif clang's triple and `-mcpu`, the
  linker, and the helper library, for assembly and C.

## Deliverable

- `hal/xtensa-esp32s3/ABI.md`, each fact with the probe that produced it.
- A stub in assembly and C, built with the Espressif clang, that boots under
  QEMU, prints a banner, takes a timer interrupt and returns from a `syscall`
  exception. Its sources travel with the report for the HAL unit to adopt.
- Questions for the sawlang lead, posted by the lead.

## Why this unit exists

The user wants SOS on a real ESP32-S3 by Nov 19. The S3 is Xtensa LX7, a new
architecture for this kernel (today: riscv32 and arm64) and for the Saw
compiler, whose Xtensa target is being planned separately. This unit needs no
Saw compiler. It establishes every board fact the Xtensa HAL will be written
against, and proves them with a bare stub in assembly and C.

## Read first

- `CLAUDE.md`, section "Comments and docs": it governs the document you
  write.
- `hal/riscv32-esp32c3/ABI.md` and its `README.md`: the model. That file
  records what the emulator does, probe by probe, and marks where emulator and
  silicon disagree. Yours has the same shape and the same standard of
  evidence.
- `hal/riscv32-common/README.md` and `hal/riscv32-common/kernel/trap.S`: what

- `hal/riscv32-flat/kernel/lib.saw`: the flat tier, which the S3's first
  profile will be.

## What to establish, in this order

Work in this order, because each step needs the one before. If a probe
stalls, record what you tried and what you saw as an open question, and move
on: a complete map with marked unknowns is worth more than a perfect first
half.

1. **The build spelling.** The clang triple and `-mcpu` for the S3, the
   linker that links it, and what supplies integer helpers. How call0 is
   selected, and what the default ABI is.
2. **Boot.** How the ROM in the emulator hands over control: which image it
   accepts from the flash drive (direct boot, the esptool image format, or
   both), the entry address, the CPU state at entry, and what the ROM has
   already configured (the console, the flash mapping, the watchdogs). Read
   the ROM ELF where the behaviour isn't obvious, as the C3 file does.
3. **The memory map,** from the monitor's `info mtree`: RAM, the flash
   windows, each peripheral.
4. **The console.** UART0's registers as the emulator models them, enough to
   print. Note USB-Serial-JTAG as the alternative console.
5. **Exceptions.** `VECBASE` and the vector layout; how a `syscall`
   instruction arrives and how to return past it; `PS` (`UM`, `EXCM`,
   `INTLEVEL`) and what privilege separation the S3 has, to confirm or
   refute that the first profile must be `Flat`.
6. **Interrupts and the timer.** The interrupt matrix and the CPU's interrupt
   levels; a periodic timer from SYSTIMER through the matrix, or from the
   core's `CCOMPARE`, whichever the emulator delivers; whether `waiti`
   wakes on it.
7. **The trap frame.** Under call0, list every register a context switch must
   save: the general registers and each special register compiled code can
   change (`SAR`, `LBEG`/`LEND`/`LCOUNT`, `SCOMPARE1`, `THREADPTR`, the
   MAC16 and boolean registers, the FP coprocessor). For each, say whether
   the S3 has it and whether clang emits code using it at the flags you
   chose. State what the windowed ABI would add to the trap and switch paths.
8. **GPIO and LEDC** as the emulator models them: what a write to a GPIO
   output register, a read of the input register and a GPIO interrupt do
   there, and whether any PWM device exists.
9. **Silicon differences** you can establish from the ROM ELF or from
   Espressif's published technical reference: the watchdogs left running,
   the clock, anything the emulator forgives. Mark each as "not probed on
   silicon".

## The stub

Assembly and C only, built with the Espressif clang, in the scratch directory
with a script that builds and runs it. Under QEMU it must:
- boot from a flash image and print a banner on UART0;
- install vectors, execute a `syscall` from the main flow and return past
  it, printing from the handler;
- take a timer interrupt at least three times, printing each;
- end in a way the script can detect, with QEMU killed afterwards.

Keep it small and plain: the HAL unit will lift its vectors, its boot code and
its linker script.
