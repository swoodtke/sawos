## Description

## Ruling (user, Nov 12)

The code follows the spec: the teardown invalidates the dying process's bound
objects first and releases its handle table second.

## Finding

Every unit of epic SO-52 is merged, but the spec still says the lifecycle is
not enforced as written, in three places: the "Not yet enforced" paragraph
that ends §2.10's refund rule, the first entry of §11's known limits, and
§8's fault rule ("§2.10, which marks what of that order is not yet
enforced"). The epic cannot close while they stand.

§2.10 states the teardown order as:
1. invalidate every bound object the dying process owns (a Thread only if it
   has not exited);
2. release its handle table, each release an ordinary one that frees at zero;
3. disown what survives;
4. counters, domain, boot set, ledger, body.

`teardown_process` (`kernel/core/sched.saw`) runs a different order. It
releases the handle table first through `unref_teardown`, which counts without
freeing, and the sweeps after it invalidate or free the bound kinds. Part of
step 1 already runs ahead of the close-all: pending call claims are dropped,
the dying process's threads come off every list, and other processes' threads
parked on its Waiters are answered `Revoked`.

## What the reorder has to carry

- `unref_teardown` exists so the sweeps can count what they freed for the
  `SOS: process teardown` line. With ordinary releases the frees happen inside
  the close-all, so the line's fields need a new source or a new definition.
  §2.10 defines each field; keep the spec and the line in step, and name every
  transcript row that moves.
- The comments in `teardown_process` give a reason for each step's position
  (a notification must never find a thread of the dying process; a delivery
  must never mint into a table the close-all has passed). Each reason has to
  hold in the new order or be answered.
- Mutation checks: each step moved back to its old place fails a test.

## Acceptance

- [ ] `teardown_process` runs §2.10's order
- [ ] §2.10's "Not yet enforced" paragraph, §11's first known limit and §8's
      pointer to it are gone
- [ ] every teardown-line change is named, with the case that shows it
- [ ] the full suite on three profiles and the C3 smoke
- [ ] epic SO-52 closes

## Implementation notes (lead, Nov 12)

**Model:** Opus. Reordering a teardown is lifecycle work where each step's
position carries an invariant; the model split agreed with the user puts that
with Opus. **Rules:** `.sawtracker/docs/implementer-rules.md`.

### Read first

- Spec §2.10 whole, then §8's fault rule and §11's known limits.
- `teardown_process` in `kernel/core/sched.saw`: its doc comment and every
  comment inside the body. Each one states why its step sits where it does.
- `unref_teardown` and `unref_object` in `kernel/core/refs.saw`, and
  `invalidate_thread`, the Waiter and Timer sweeps, the Mapping sweep and
  `reap_unreferenced`.
- `report_teardown`, and §2.10's paragraph that defines each field of the
  `SOS: process teardown` line.

### The work

1. Write down, before changing code, the as-built order and the target order
   side by side, with the invariant each as-built step protects (from its
   comment) and how the target order keeps it. Put that table in your report.
2. Reorder to §2.10: invalidate the dying process's bound objects (a Thread
   only if it has not exited), then release the handle table with ordinary
   releases that free at zero, then disown, then counters, domain, boot set,
   ledger and body.
3. `unref_teardown` exists so that the sweeps, not the close-all, do the
   freeing and can count it. With ordinary releases the count has to come
   from the frees themselves. Keep each field's meaning as §2.10 defines it
   where you can; where a field must change meaning, change §2.10's
   definition with it and list every case whose teardown line moves.
4. Remove `unref_teardown` if nothing needs it afterwards.
5. Remove the three markers: §2.10's "Not yet enforced" paragraph, §11's
   first known limit and §8's "which marks what of that order is not yet
   enforced".

### Tests

- The full suite on three profiles and the C3 smoke; teardown touches most
  cases.
- Mutation checks: for each step you moved, move it back alone and show a
  case fails. If moving one back fails nothing, say so: that is a coverage
  gap to report, and a case to add if a program can observe the difference.

### Stop and ask if

An invariant in the as-built comments cannot hold in §2.10's order. Report
the conflict; the user ruled the order, so a conflict is a spec question.

**Lead review, SO-69.p1.**
- **The order.** `teardown_process` now runs §2.10's four steps, marked in
  the code: invalidate (pending calls dropped, the dying threads off every
  list, parked waiters answered `Revoked`, then Threads, Waiters with their
  attachments, Timers, and the Mapping rows); release the handle table with
  ordinary releases; disown (`disown_bound`, `disown_shared`); then the
  counters, domain, boot set, ledger and body. The lead read the function
  against the implementer's as-built and target table.
- **`unref_teardown` is gone.** The close-all frees at zero through
  `release_held`, which counts a free only when the object was the dying
  process's own. `exit_thread` uses `drop_reference` directly.
- **Refunds:** a Waiter or Timer is credited at invalidation, so
  `free_object` credits one only while it is `Live`.
- **Disown:** invalid and `Exited` bound objects keep their owner through the
  release, so it can count them, and lose it in step 3. That covers the note
  on epic SO-52.
- **The teardown line.** No `SOS: process teardown` line moved in any
  existing case on any profile: the implementer captured every console at
  main and at the patch and diffed them. §2.10's field paragraph is reworded
  to the new sources.
- **One value the new order changes:** a thread that has not exited and is
  named only by a staged message is invalidated first and then freed inside
  the close-all's cascade, uncounted. The new case `teardown_staged_thread`
  pins it.
- **The three markers are gone:** §2.10's "Not yet enforced" paragraph, §11's
  first known limit and §8's pointer.
- **Mutants, each moved back alone on riscv32:**
  - thread invalidation after the close-all: fails `teardown_staged_thread`;
  - Waiter invalidation after it: fails `mint_narrow_waiter`, whose last row
    now asserts the whole teardown line;
  - the disown moved into each invalidation: 44 cases fail;
  - the close-all made count-only: 25 cases fail;
  - **Timer invalidation after the close-all: fails nothing.** A program can
    see the difference (a thread of another process, parked on a Waiter whose
    last handle the dying process holds, with the dying process's Timer
    attached there), but the case needs a root at the floor API. The
    implementer is adding it as a revision;
  - the Mapping row cleared after the close-all: fails nothing, and the
    implementer argues nothing reads the row between the two positions.
- **Runs:** 600 across three profiles at the rebased commit, plus the C3
  smoke (5 cases).
