## Description

**Found while fixing SO-92.p4; older than it.**

`MemoryOp.Map` faults on a base off the grain and rounds the row's top **up** to the grain (§2.5 says "its top rounded up to the grain"). So an allocation whose length is not a whole number of grains is mapped with a row that reaches past its end, by up to a grain less one byte, into whatever lies beside it.

Only a boot allocation can have such a length: a pool serves whole grains, and a child's image blob is as long as its image, placed on a 16-byte boundary by the build.
- On the profiles whose grain is 4 bytes the tail is the build's padding.
- On arm64 the grain is a page. A blob that began on a page boundary and ended inside a page, with another blob after it in that page, would hand the process that maps it the next blob's first bytes, to read or to write as the access says. A blob that does not begin on a page cannot be mapped at all there (the base fault).
- No layout in the tree reaches it: of the arm64 builds the gate makes, the only blobs that begin on a page are whole pages.

**Lead's recommendation.** `map` refuses a `Memory` whose length is off the grain, with the answer it gives a base off the grain, as `process_create` now refuses such a destination (SO-92.p4). Then no row anywhere grants a byte outside its object. The spec sentence in §2.5 changes from rounding to refusing, so the user sees it first. The build should also stop making it possible: an image blob that is to be mapped (an image used in place on a paging board) is padded to the grain by the stitcher, which is the image builder's business (SO-95).

A case on arm64: a blob row on a page boundary and a page and a half long is refused where it is mapped; padded to two pages it maps.

**Lead: SO-100.p1 is up, and it carries SO-98 and SO-94 too** (the owner's Nov 14 rulings, one small kernel patch). On main. Gate on the implementer's machine: 1053 / 7 / 62 and 1 board-only.

**SO-100, map refuses a length off the grain.** The Map arm of `memory_op_decoded` answers a `Memory` whose length is off the grain with the `BadArg` fault it gives a base off the grain; the row's top is `base + len`, never rounded. Spec §2.5: the row covers exactly the allocation. Case `destination_off_grain` (every gate profile, not the issue's arm64-only sketch): its last step maps the build's allocation three bytes short of whole grains and now ends in root's `BadArg` fault. Left, as the recommendation said, for the builder (SO-95): padding a blob that is to be mapped to the grain.

**SO-98, a segment of no bytes loads and records no row.** `place_image` skips a segment whose `mem_len` is 0; `meets_row` loses its guard against an empty row and `record_grant` states the invariant that every row holds a byte; `segments_meet` keeps its guard (it compares segments). Spec §5.6: such a segment spends no grant row, still counts against the segment limit and is validated like any other. Case `empty_segment_no_row` (new, three profiles): root rewrites a child image in its blob with a zero-filled RW segment of two pages and an RX segment of no bytes at its second page; the child posts a body straddling that address (taken), and a second create makes a thread whose stack top sits half a word above it.

**SO-94, a release beside the frontier folds without a node.** `pool_return` checks the frontier first, lowering it with no node for a range that ends where it begins; the fold still runs on both paths. `MemorySlot.dropped`, write-only, is removed everywhere. Spec §5.9: the frontier is a free neighbour a range joins without a node; a range that finds no node is lost, seen as `available`'s total falling. `pool_nodes_home` gains three legs, two of them with the node slab full (`lost=0 bytes`). That case is riscv32 and flat only: a full node slab cannot be built at arm64's page grain, where `pool_first_fit` catches the inverted test, the partial updates and the missing fold but not the branch's removal.

**Mutants** (each alone, restored by hash): red for the length test dropped and inverted (three profiles), the empty-segment skip removed and inverted (three profiles), the frontier branch removed (riscv32, flat), inverted, its base or length update dropped, and the fold skipped on that path. Equivalent and not red: `align_up` put back on the top (the top is already on the grain once the length test passes) and `meets_row`'s empty-row guard put back (no empty row is recorded now).

**Text that moved:** `destination_off_grain` (its clean end becomes the fault, §2.5), `pool_nodes_home` (three lines added); `empty_segment_no_row` is new; nothing else.
