## Description

**Found while fixing SO-92.p4; older than it.**

`MemoryOp.Map` faults on a base off the grain and rounds the row's top **up** to the grain (§2.5 says "its top rounded up to the grain"). So an allocation whose length is not a whole number of grains is mapped with a row that reaches past its end, by up to a grain less one byte, into whatever lies beside it.

Only a boot allocation can have such a length: a pool serves whole grains, and a child's image blob is as long as its image, placed on a 16-byte boundary by the build.
- On the profiles whose grain is 4 bytes the tail is the build's padding.
- On arm64 the grain is a page. A blob that began on a page boundary and ended inside a page, with another blob after it in that page, would hand the process that maps it the next blob's first bytes, to read or to write as the access says. A blob that does not begin on a page cannot be mapped at all there (the base fault).
- No layout in the tree reaches it: of the arm64 builds the gate makes, the only blobs that begin on a page are whole pages.

**Lead's recommendation.** `map` refuses a `Memory` whose length is off the grain, with the answer it gives a base off the grain, as `process_create` now refuses such a destination (SO-92.p4). Then no row anywhere grants a byte outside its object. The spec sentence in §2.5 changes from rounding to refusing, so the user sees it first. The build should also stop making it possible: an image blob that is to be mapped (an image used in place on a paging board) is padded to the grain by the stitcher, which is the image builder's business (SO-95).

A case on arm64: a blob row on a page boundary and a page and a half long is refused where it is mapped; padded to two pages it maps.
