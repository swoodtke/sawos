## Description

## Ruled design (user, Nov 9)

**Pids.** Each process gets a pid at `ProcessCreate`: a 64-bit value from a
monotonic kernel counter, never reused for the machine's uptime, so a server's
pid-keyed table can never confuse a new process with an old one. A slot +
generation pair is not acceptable (generations wrap).

**No op accepts a pid** except `SystemOp.ProcessByPid` (the ProcessObserve
issue). A pid identifies; it grants nothing.

**Sender pid in message metadata.** Every pipe message carries the sending
process's pid, written by the kernel at send and copied out with the receive
record. It is unforgeable because the sender never writes it. "Sender" is the
immediate sender: a forwarding middle process is what the receiver sees.

**Reading a handle's pid.** Any Process handle can report the pid of the
process it names, so a server can match handles from other routes against its
table. Lead proposal, to settle in the brief: a `Stats` column, since the
observe set carries `Stats`.

**The sender handle.** An op on a received message mints a Process handle to
its sender carrying the **observe set** (`Wait | Stats`; capped by the
receiver's ceiling, SO-40). `Wait` lets a server evict a cached handle when the
sender dies (each cached handle pins a `Gone` slot, §2.10). A sender whose slot
is gone answers a status, not a fault. No System right is needed: having
received the message is the authority.

A spec-only patch to `spec.md`, modelled on how SO-40's spec landed. It
settles, with the ruled design in the description as given:
- **The pid:** a `UInt64` in the process **record** (`ProcessRecord`,
  `kernel/core/pslot.saw`), from a monotonic kernel counter, assigned where
  the record is taken (the boot door for root, `SystemOp.ProcessCreate` for a
  child). State root's pid.
- **The metadata field:** where the sender's pid sits in the message record
  (`PipeMsgMeta` and `PipeMsgRecord`, `kernel/abi/src/records.saw`), and that
  §2.2's copy-out record layout changes with it.
- **The pid query:** the lead's proposal is a column in the stats record
  (`ProcessOp.Stats`), since the observe set carries `Stats`.
- **The sender-handle op.** Open, and the reason this needs a spec: what the
  op is called on, and how the kernel knows the caller received a message
  from that sender. A message carries a pid, not a reference, and a reference
  per staged message would pin a `Gone` record per message. Candidates: an op
  on the obligation (`PipeRequest`) for calls only; or the take itself
  minting on request. A tell has no obligation, so say what a tell's receiver
  can do.
- The statuses: a sender whose record is gone answers a status. Name it.
- Ceilings (SO-40) cap the minted handle; the observe set is `Wait | Stats`.

### What it specifies

- **The pid:** a `UInt64` in the process record, from one counter that only
  increases. Root's pid is 1 and zero is never a pid.
- **The message field:** the kernel stamps the sender's pid at the op that
  sends (post, call, reply, reply-and-wait), and every door that hands a
  message over carries it: take, resolve, a call's reply and a wait delivery.
- **The pid read:** a fourth doubleword in the `ProcessOp.Stats` record and
  in each row of the stats region.
- **The sender handle:** `PipeRequestOp.Sender`, an op on the obligation,
  gated by a new `PipeRequestRight.Sender` in the default set. It mints a
  Process handle onto the request's sender with the observe set
  (`Wait | Stats`), capped by the caller's ceiling. It costs no reference per
  message: each exchange keeps the sender's pid and record index, and the op
  accepts the record only if it is live and still holds that pid.

### A correction to the notes

The notes said a tell has no obligation. In this kernel every take mints
one, a tell's included, so an op on the obligation covers tells. What it
does not cover is the reply direction.

### Decisions the user has not ruled

1. **The mechanism:** an op on the obligation. The alternative, minting at
   delivery, would need a flag on five doors and could not answer a dead
   sender with a status, because the delivery itself succeeds.
2. **Replies:** a client learns the replier's pid and gets no handle.
3. **A dead sender whose record another handle still pins:** the draft
   answers `Revoked`, as for a reclaimed one. The Nov 9 ruling says "a sender
   whose slot is gone answers a status", which can also be read as minting a
   handle onto a `Gone` record while it exists.
4. **The status:** `Revoked`, not a new word.
5. **The new right,** which a launcher can withhold through the server's
   `PipeRequest` ceiling.
6. **A forwarded obligation names the original client** to whoever holds it.
   A middle process cannot strip the right before forwarding.
7. **The pid read is gated by `ProcessRight.Stats`.**
8. **The pid is a column of the stats row itself,** which also closes §11's
   identity-column item.
9. **Root is pid 1; zero is reserved.**
10. **A counter that would wrap stops the machine.**
11. **Record placement:** the sender sits after the handles and before the
    body.
12. **No keep mask on the op.**
13. **A refused create assigns no pid.**

### Flagged for the implementer

On riscv32 the take record gains 4 bytes of alignment padding once it holds
a `UInt64`; the kernel must write them as zero. And a handle with the observe
set can already read the sender's rights ceilings, since that read is gated
by `Stats` too.

**Changes requested (rev 3, the server's rebase of the rev 2 I read: same `+/-` lines).** The text states all thirteen approved decisions and every point of the Nov 9 ruling, and its arithmetic for the wait, message and stats records holds on both word sizes. **1. "It is withdrawable" claims more than the ceiling rule gives** (§2.1, the sender handle): "an obligation is minted at the take, capped by the taker's ceiling for the `PipeRequest` kind (§2.7), so a launcher that narrows that ceiling stops a server naming its clients." §2.7's first exception says a handle a process receives "arrives with the rights its sender chose", and the same list in §2.1 says "a far process holding a forwarded obligation obtains the original client". **2. §12 still says "every Process handle comes from System"** (the `SystemOp.ProcessSelf` precedent sentence, unchanged). `PipeRequestOp.Sender` mints one from an obligation, "no System right is asked for".

**3. What an unoccupied stats row reads, two ways** (§2.7). "zero can stand for "no process" wherever a pid is read (an unoccupied stats row, below)", against, below: "A row for an unoccupied body reads whatever its last occupant left" and "A row whose process has died keeps its pid until a create reuses the body". Zero is a body no process has ever occupied.

**4. The observe set** (§2.7).
- "enough to learn that a process died and how, what it cost and what its pid is, and nothing that acts on it". `ProcessOp.Ceiling(kind)` is gated by `ProcessRight.Stats`, so every sender handle also reads its client's rights ceilings. The lead's note flags that for the implementer; the spec should say it where it says what the set is for.
- "where a process obtains a handle onto another by having heard from it … capped … by the receiving process's Process ceiling". §2.1 says the caller's ceiling, and a far process holding a forwarded obligation never heard from the client.

**5. The take record** (§2.1, a new sentence): "`Take` and `Resolve` answer through one copy-out record, laid out as §2.2's wait record lays out a message: the packed meta, the handle words, the sender's pid (below), then the body." `PipeTakeRecord` is `{ request, msg }`: the request word comes first, by its own doc comment. The lead's note has the padding; the spec, which is the C altitude's contract for this record, does not, nor that the kernel writes it as zero.

**6. Markers.** SO-40 marked each cross-reference inline, and this patch does so in six places. These read as built today and are not marked: the sender handle in §2.7's list of mints the ceilings cap, and §5.7's `Revoked` list ("and a sender handle asked of a dead sender, §2.1"). - "A dead sender is answered first" follows the `NoResource` and `QuotaExceeded` sentence but can be read as ahead of the `AccessDenied` fault too; §2.10 puts the rights fault first.
- "A lookup from a pid to a Process handle, if one is added": SO-50 rules one.

## Step 2 notes (lead, Nov 12): implement the pid spec

**Model:** Sonnet. **Rules:** `.sawtracker/docs/implementer-rules.md`.

### Read first

Search `spec.md` for "not yet enforced" and read every marked passage that
mentions the pid, the sender field, `Sender` or the observe set: §2 (the
object table), §2.1 (the sender's pid, the sender handle, the two records),

row), §2.10, §3, §5.7, §8, §11 and §12. Each marker you make true is removed
in this unit.

### The pid

- `kernel/core/pslot.saw`: `ProcessRecord` gains `pid: UInt64`. Say what it
  holds when the record is free.
- `kernel/core/process.saw`: one counter static that only increases. Root's
  pid is 1; zero is never a pid. If the counter would wrap, the kernel stops
  the machine.
- `kernel/core/dispatch.saw`, `process_create`: assign after the record is
  linked. A refused create assigns none.

### The stats record and row

- `kernel/abi/src/records.saw`: the stats record gains a fourth doubleword,
  `pid`, after the three counters, and the record-size function and its
  asserts follow. `StatsRow` gains the same column.
- `kernel/core/stats.saw`: the row width, the stamp when a process takes a
  body, and the region's version constant, which changes with the layout.
- `kernel/core/dispatch.saw`, `process_stats`.
- `kernel/sysapi/src/system.saw`: `ProcessStats.pid` and the region reader.

### The sender's pid in a message

- `kernel/core/objects.saw`: `Exchange` keeps the sender's pid and record
  index. It holds no reference.
- `kernel/core/dispatch.saw`: stamp at `pipe_post`, at `pipe_call` and its
  resume path (the caller, not whichever process is current when a parked
  call is staged), and at the reply paths. `pipe_take` and `pipe_resolve`
  write it.
- `kernel/abi/src/records.saw`: `PipeMsgRecord` and the wait buffer gain
  `sender: UInt64` after the handle words and before the body. On the 32-bit
  profile `PipeTakeRecord` then has four bytes of padding after its request
  word; the kernel writes every padding byte as zero. Add `static_assert`s
  for each record's size and body offset on both word sizes (the spec's
  review derived 160 and 176 bytes for the message record, 168 and 184 for
  the take record).
- `kernel/core/refs.saw`: the message, take and wait prefixes, `msg_prefix`,
  `deliver_take`, and `deliver_wait_record`, which must write the full prefix
  for a reply that carries an answer, an empty one included.
- `kernel/sysapi/src/pipe.saw`: `PipeMsg` exposes the sender's pid, and the
  decodes follow the new layout.

### The sender handle

- `kernel/abi/src/ops.saw`: `PipeRequestOp.Sender`. `rights.saw`:
  `PipeRequestRight.Sender` in the default set, and one definition of the
  observe set (`Wait | Stats`) for this op and the System lookup to come.
- `kernel/core/dispatch.saw`: the op. Its checks, in the spec's order: bad
  handle, missing right, a dead sender (`Revoked`: the record at the stored
  index is not live or no longer holds the stored pid), then the mint's
  quota and table. The mint is capped by the caller's Process ceiling,
  through the same capped mint the creation ops use. It does not consume the
  obligation.
- `kernel/sysapi/src/system.saw`: the typed op lives here, not in
  `sos.pipe`, which cannot name `Process`.

No case asserts a pid's numeric value beyond root's 1 and "differs from":

Requested changes on patch SO-49.p2 (revision 1)

**Changes requested (rev 1): the kernel side holds; one case does not check what its header says, and three comments still say "three".** Small revision; no kernel code needs to change.

**What I checked and found sound** (origin/main + rev 1, `SAWLANG_ROOT` at v0.21.0, three profiles):

- **Nothing of the kernel's leaves through padding.** A scratch root image filled each buffer with `0xA5` before a take, a resolve, a fused call's reply and a wait delivery, and printed the bytes after. Every padding byte reads 0 on riscv32, riscv32-flat and arm64 (take bytes 4-7 and 13-15 on the 32-bit profiles; the meta's tail on all), the sender doubleword reads the pid, and the bytes past the prefix are still `0xA5`. An empty message writes the whole prefix, sender included. The copy length is `sizeof` the prefix, which the `static_assert`s tie to the record.
- **`Sender` cannot name the wrong process.** The order is the spec's: the right (a fault), `sender_alive`, then the mint and its refusals, with `ref_object` only after a successful mint. Six mutants rerun on arm64 and riscv32-flat, all killed: each half of the liveness test (the pid half dies at "a reused record answers Revoked", so the case does reuse the record), the right check, the cap, a mint ahead of the liveness test, and the parked resume stamping `calling_process()`.
- **No second name can ask after the reply.** The exchange's sender fields become the replier's at the reply, so a request handle that outlived a reply would name the replier.
