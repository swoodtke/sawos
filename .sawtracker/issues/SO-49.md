## Description

## Ruled design (user, Nov 9)

**Pids.** Each process gets a pid at `ProcessCreate`: a 64-bit value from a
monotonic kernel counter, never reused for the machine's uptime, so a server's
pid-keyed table can never confuse a new process with an old one. A slot +
generation pair is not acceptable (generations wrap).

**No op accepts a pid** except `SystemOp.ProcessByPid` (the ProcessObserve
issue). A pid identifies; it grants nothing.

**Sender pid in message metadata.** Every pipe message carries the sending
process's pid, written by the kernel at send and copied out with the receive
record. It is unforgeable because the sender never writes it. "Sender" is the
immediate sender: a forwarding middle process is what the receiver sees.

**Reading a handle's pid.** Any Process handle can report the pid of the
process it names, so a server can match handles from other routes against its
table. Lead proposal, to settle in the brief: a `Stats` column, since the
observe set carries `Stats`.

**The sender handle.** An op on a received message mints a Process handle to
its sender carrying the **observe set** (`Wait | Stats`; capped by the
receiver's ceiling, SO-40). `Wait` lets a server evict a cached handle when the
sender dies (each cached handle pins a `Gone` slot, §2.10). A sender whose slot
is gone answers a status, not a fault. No System right is needed: having
received the message is the authority.

## Implementation notes (lead, Nov 12)

Two dispatches. **Rules:** `.sawtracker/docs/implementer-rules.md`.

### Step 1: the spec (Opus, or the lead; the user reviews before step 2)

A spec-only patch to `spec.md`, modelled on how SO-40's spec landed. It
settles, with the ruled design in the description as given:
- **The pid:** a `UInt64` in the process **record** (`ProcessRecord`,
  `kernel/core/pslot.saw`), from a monotonic kernel counter, assigned where
  the record is taken (the boot door for root, `SystemOp.ProcessCreate` for a
  child). State root's pid.
- **The metadata field:** where the sender's pid sits in the message record
  (`PipeMsgMeta` and `PipeMsgRecord`, `kernel/abi/src/records.saw`), and that
  §2.2's copy-out record layout changes with it.
- **The pid query:** the lead's proposal is a column in the stats record
  (`ProcessOp.Stats`), since the observe set carries `Stats`.
- **The sender-handle op.** Open, and the reason this needs a spec: what the
  op is called on, and how the kernel knows the caller received a message
  from that sender. A message carries a pid, not a reference, and a reference
  per staged message would pin a `Gone` record per message. Candidates: an op
  on the obligation (`PipeRequest`) for calls only; or the take itself
  minting on request. A tell has no obligation, so say what a tell's receiver
  can do.
- The statuses: a sender whose record is gone answers a status. Name it.
- Ceilings (SO-40) cap the minted handle; the observe set is `Wait | Stats`.

### Step 2: the implementation (Sonnet, from the merged spec)

The lead completes these notes when the spec merges. The places it touches:
- `kernel/core/pslot.saw` (the record), `kernel/core/process.saw` and the
  `ProcessCreate` arm of `kernel/core/dispatch.saw` (assignment);
- `kernel/abi/src/records.saw` (the message meta and the stats record) and
  the send and take paths in `kernel/core/dispatch.saw`;
- `kernel/abi/src/ops.saw` and `rights.saw` for the new op;
- `kernel/sysapi/src/pipe.saw` (`PipeMsg` exposes the sender's pid) and
  `system.saw` (`Process` exposes its pid and the new op's wrapper);
- tests as the description lists: two clients' pids differ and are stable
  across messages; the sender handle names the sender and carries exactly the
  observe set; a dead sender answers the status.
