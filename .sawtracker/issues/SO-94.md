## Description

**Found in the review of SO-92.p2; older than that patch.**

`pool_return` asks for a free-list node before it tries to fold the range
into the pool's unspent frontier. When the node slab (`SlabKind.FreeRanges`)
is full, a released range that touches the frontier is therefore dropped and
counted in `dropped`, though folding it back needs no node at all.

The reviewer's construction: 32 holes fill the node slab, 8192 bytes of
frontier remain; 1024 bytes are allocated from the frontier and released.
`available`'s `total` reads 19328 where 20352 stood before the allocation.
The probes are `probe_b_drop` and `agenta_nodes` (chat files f63 and f64).

**The question.** §5.9 says both "a free range that touches the pool's
unspent frontier folds back into it" and "a range needs a node only when it
touches no free neighbour". Is the frontier a neighbour?

**Lead's reading: yes.** The frontier is free memory, a range that touches
it can join it without a node, and "a pool whose every allocation has come
home is whole again" cannot hold otherwise. The change:
- `pool_return` (or `pool_insert_range`) lowers the frontier when the range
  ends where the frontier begins, before any node is asked for, and then
  runs the existing fold so list ranges that now touch the frontier follow;
- §5.9's sentence becomes "a range needs a node only when it touches neither
  a free neighbour nor the frontier";
- a case built as the probe is: the node slab full, a range beside the
  frontier released, `total` unchanged and `dropped` not raised.

A range that touches a free neighbour already coalesces without a node; the
case should hold that too with the slab full.

Depends on SO-92.p2 (the case reads `available`).
