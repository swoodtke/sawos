## Description

## Ruling (user, Nov 13)

On whether memory `map` installs may be a system call's buffer: "Widening
is the right approach imo unless something makes it impossible to do
safely. We should focus on hardening all paths where memory could be
unmapped during an operation though (including permissions checking
everywhere - including permissions changing during a syscall if/when we
support a remapping concept)."

So the direction is that any memory a process's grant lets it reach is a
legal buffer (SO-92 carries that change). This unit is the hardening that
has to be true first, and it can be done on main as it stands.

## The invariant to establish

The kernel touches a process's memory only through a door that, at the
moment of the touch and for that direction, finds a row of that process
covering the whole range with the permission the touch needs (read for a
source, write for a destination, never a row that permits execute, never
a device row). A refusal at any door, early or late, is that process's
fault and ends that process; it is never the kernel's bug and never stops
the machine. Nothing the kernel learned about a process's memory is
trusted across a point where another thread could have run.

## The audit

Every place the kernel reads or writes a process's memory, or keeps an
address, a length or a translation that came from one, listed with file
and function and classified:

1. **Checked and used in one step,** with no point between where another
   thread can run. Find every preemption point inside a copy (the strided
   movers in `kcore.preempt`): a row can go between two strides.
2. **Checked at the call and used at a wake** (the late doors): each must
   ask again before it spends anything (SO-90 did this for the wait
   record, a fused call's reply and a parked call's record and body: are
   those all of them?).
3. **An address or a translation kept** in a kernel structure across a
   switch point (a pending call, a staged message, a Waiter's record
   pointer, a thread's frame, the stats region): what it is re-checked
   against, and what happens when a DIFFERENT row lies at those addresses
   by then.
4. **A value read from the process more than once** (a length, a count, a
   handle word in a record): the kernel must act on one copy.
5. **The permission asked.** The reviewer suspects the copy-out door never
   reads a row's write permission, so a result can be written into a
   read-only row inside the write window. Every door, both directions.
6. **What removes or changes a row:** `Mapping.unmap`, a teardown, a kill
   (in review), and anything else; and what a future op that changes a
   row's permission in place would have to keep true. State the rule a
   remap must follow so that it is the same event to every door as an
   unmap followed by a map.
7. **Memory shared with another process:** the contents can change under
   the kernel at any moment; show no door depends on them staying still.

## Deliverable

- A table of every such site with its class and its verdict: sound, or a
  finding with a concrete sequence.
- Each finding fixed, with a case that fails without the fix, or filed if
  it is a design question.
- The invariant stated in the spec where the copy doors are specified, and
  the rule for a future remap.

**From the Air: the two candidates are real. Both reproduce on main (riscv32, the isolated profile, v0.23.0), three runs of three, each with its controls.** The probe packages and their runner cases are one diff, sent in chat.

**1. A result written into read-only memory (item 5 of the audit).**
`copy_out_check` asks the write window and `translate_user`; neither reads the covering row's write permission.
- The launcher cuts a hole out of its child's destination (as `late_door_buffer_gone` does), stamps `0x5A5A5A5A` there through its own mapping, unmaps that, and maps the hole into the child **read-only**.
- The child calls `pipe_create` with the hole as the record's address:
```
SOS q2child: before the call: 1515870810 0
SOS q2child: pipe_create into the read-only piece: status 0
SOS q2child: after the call: 4 5
SOS q2child: storing to the piece myself
SOS: fault store-access-fault cause=0x00000007 epc=0x802406ae tval=0x80270000
SOS q2: launcher reads back 4 5
```
- So the kernel wrote the two handle words where the child's own store takes an access fault, and the launcher reads them back from the bytes afterwards.
- Today it needs a mapped row inside the write window, which only the hole route gives. Under the widening every read-only mapping is one, so this is the first thing the widening has to have fixed.

**2. A 4-byte device window grants far more than 4 bytes (riscv32 and, by the same code, the C3).**
`device_window_ok` accepts `len == 4`; `prot_device` programs one NAPOT entry with `napot_bound(base, 4)`, which is `base >> 2`. A NAPOT entry's size comes from the address's trailing ones, and its smallest size is 8 bytes; 4 bytes needs NA4.
- Root carves 4 bytes at offset 0xFFC of the console window (0x1000_0000, length 0x1000) and maps the carve into itself:
```
SOS q1: mapped a carve of len 4 at offset 4092
SOS q1: read 0x10001000 = 1953655158        (0x74726976, the virtio-mmio magic: outside the IoMemory)
SOS q1: read 0x10000007 = 0                 (inside the parent, outside the carve)
SOS q1: reading 0x10002000
SOS: fault load-access-fault cause=0x00000005 epc=0x80200852 tval=0x10002000
```
- Controls: with nothing mapped, the reads at 0x1000_1000 and at 0x1000_0007 each take a load access fault; with an 8-byte carve at 0xFF8 mapped, the read at 0x1000_1000 faults.
- So the entry covers [0x1000_0000, 0x1000_2000): the whole console page and the next device's registers. `0x1000_0FFC >> 2` is `0x0400_03FF`, ten trailing ones, 8 KiB.
- Any holder of an IoMemory with `Carve` and `Map` can do it, and so can a process handed only the 4-byte carve.
- It is not a copy door, so it may want its own issue: either `device_window_ok` refuses a length under 8, or `prot_device` programs NA4 for 4.

**Also met while reading for SO-92, not run, for the audit's list:**
- `executable_at` (the thread entry check) accepts an address any executable row covers; on PMP the lowest-numbered row covering it decides, so an entry can pass the check and fault at its first fetch.
- arm64's revoke clears every page of the removed row's range without asking whether another row still covers it (two device rows on one page).
- A preemption point delivers interrupts and runs no other thread (`irq.preempt_point`), so a long copy is not a place a row can go; but a delivery inside one does write a woken waiter's record through `copy_out`.

**Ruling (user, Nov 13):** "I agree with allowing unmap -> remap of the same virt address. That's a bug waiting to be discovered but it's a userspace bug that we shouldn't worry about." So when a thread parks with a buffer in a row `map` installed, and by the wake a different row lies at those addresses, the late door's check passes and the kernel writes there: it writes only where that process may write at that moment. No per-row generation. The spec says so where the late doors are specified.
