## Scope

  `git ls-files tests | awk '$0 >= "tests/pipe-d"' | grep -E '\.(saw|S|c|h|ld)$' | grep -vE '^tests/taskdump(_empty)?\.saw$'`

## Unit-specific constraints

- **Test comments explain what the test proves.** A test's header should say what behaviour it checks and what the expected outcome is (pass, fault, refusal, exit status). A comment explaining why a step is needed to reach the case under test (ordering, a handle that must exist first, a deliberate bad argument) is how the test works; keep it. Drop design and unit provenance ("this case pins design 18's…"), and say what the case pins instead.
- **Hand-assembled payloads** (`.S` files) carry byte-layout comments: field names, offsets, magic values. Those are how the code works; keep them exact.
- **Don't change any string literal.** Tests print strings the runner matches, so a string edit changes behaviour. The equivalence checker enforces this.

## Verification cases

Run **every case whose sources you changed**, on `--arch riscv32` and `--arch arm64` (two runs; skip riscv32-flat, which builds the same test sources). To find them: each test directory has a `*_PKG` constant (or a `TESTS_DIR` path) in `tools/sos_runner.py`, and the `TEST_CASES` entries reference those. Map each changed file to the case names that use it, list that mapping in your report, and pass the names to `--case`. A case that runs on one arch only is simply skipped on the other.

## Goal

Comments in this tree narrate their own history: design numbers, unit
numbers, rulings, "this used to…", "that edit HAS LANDED", alternatives once
tried. That history lives in `designs/` and in git. Rewrite the comments so

future editor would get it wrong without it.

## The rules

**Change comments only. Do not change a single code token**, including
string literals (assertion messages, test expectations, help text, panic
messages: all code), whitespace inside code lines, and declaration order. If
a comment cannot be fixed without a code change, leave it and list it in your
report. Do not add, delete or rename files.

Remove:
- design and unit references: `design 32`, `sawos design 2 D-5/D-6`,
  `design 178 D2/D3`, `M5 unit 6a`, `sawlang#140`, `DF-232e`, `SL-26`,
  `K1`, `#39 As-built`, milestone names (M0 through M7), and the same
  references inside parentheses or brackets;
- history: "used to", "was", "now", "moved here", "HAS LANDED", "before
  this unit", "the old paragraph", dates, who ruled what, and accounts of
  how the code reached its current shape;
- rejected alternatives, unless a future editor would plausibly reach for
  the same alternative and break something. In that case keep one short
  sentence in the form "Don't do X: Y breaks."
- the ALL-CAPS emphasis style. Write in normal sentence case. Keep caps
  only for identifiers, constants and acronyms.

Keep, tightened where you can:
- invariants and preconditions;
- the conditions that make each `unsafe` block, or each raw pointer or
  register access, sound;
- ordering, locking and reentrancy rules, and anything that is load-bearing
  for alignment, layout, linking or the trap path;
- ownership and lifetime contracts, and what a function returns or refuses
  in each error case;
- the non-obvious "why" that prevents a real mistake;
- pointers to `spec.md` sections (`spec.md` §5.7), which count as how the
  code works;
- doc comments (`///`, `//!`, docstrings) on public items. Shorten them, but
  don't delete one outright unless it said nothing beyond history.

**Facts must be checked, not carried.** When a comment states a fact about
the code (a field, a constant's value, a caller count), and you can see that
it is false, fix or drop it and list it in your report. If you cannot tell
whether it is still true, check `spec.md`; if that doesn't settle it, keep it
and list it. A comment that points to another comment ("see X's doc") must
land on text that actually states the claim; if it doesn't, state the claim
in place.

Don't add new commentary except where removing history leaves a gap a
reader would trip on. Most comment blocks should get much shorter.

**Comment prose wraps at 80 columns.** Refill every comment line your change
touches so it ends at or before column 80, unless the comment's own
indentation leaves less than 40 columns of text. Don't rewrap comment lines
you otherwise left alone.

**Commits carry no attribution trailers** (repository rule).
