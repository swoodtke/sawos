## Description

**Slab areas get bounds of their own in each board script (user ruling, Nov 15: "I agree with all recommendations").**

SO-108 made the kernel accept a slab area anywhere inside its own zero-initialised memory, between the board script's `_bss_start` and `_arena_start`. The reviewer showed that a hand-made block can then place an area over the kernel's own statics (on riscv32, over `hal.IRQ_CLASSES`), which the boot zeroes; spec §12 now says plainly that the containment check does not catch this. The builder never does it: it gives each area a section of its own.

**The rule to build.** Each board's link script gathers the image's `.bss.sos_slab*` sections into one region with its own bounds (`_sos_slabs_start`, `_sos_slabs_end`), inside the kernel's zeroed memory and apart from every other static. The kernel's containment check tests an area against those bounds instead of `[_bss_start, _arena_start)`, through the same HAL seam (`kernel_bss_start`/`kernel_arena_start` become the slab region's bounds, or two new accessors beside them). §12's sentence about what the check does not catch is replaced by the rule. Every board script: riscv32 `virt` (and the flat profile through it), arm64 `virt`, the ESP32-C3 and the ESP32-S3.

**Acceptance**
- [ ] a case on each gate profile: an area over a kernel static is refused at boot, with the containment message
- [ ] an image with no slab areas links and boots byte for byte as before on every board (the S3's default images keep their hashes)
- [ ] the builder's sections land inside the region on every board (a link check or an assertion in each script)

**Approved (reviewer, Nov 15), revision 2 (the server's rebase of 1). The hole is closed on every board I could boot, and the check and its text are right. One board's script is held by nothing, and one comment is wrong; both are owed as a follow-up.**

## What holds

- **The area the SO-108 review placed over a kernel static is refused.** An area at `hal.IRQ_CLASSES` (`_bss_start + 0x4018` in this riscv32 build), which the old bounds took: "a slab area lies outside the kernel's slab region (0x8001f068)" (chat f167, `install_probes.py`).
- **The check:** `base < low || base > high || len > high - base`, with the bounds from the two new symbols. Two more probes: an area based at `_sos_slabs_end` is refused, and a zero-length area in an empty region is "a slab area has no length".
- **Every script gathers `*(.bss.sos_slab*)` first in `.bss`**, with `_sos_slabs_start` at `_bss_start` and nothing but that pattern between the two symbols (read in all four; `llvm-nm` on a riscv32 case gives both at 0x8001b050). Nothing in the kernel, the HALs, the runtime or root names a section the pattern would also take.
- **Mutants, the region's end put back at `_arena_start`:** riscv32 and riscv32-flat red on `slab_area_past_region`, `slab_area_over_static` and `slab_area_one_past_arena`; arm64 red on the same three.
- **The ESP32-S3, where the patch adds no case, on the emulator:** an area in a slab section of its own is taken; an area at `_sos_slabs_start` over reserved storage is taken; an area over an ordinary `.bss` static is refused (three probes). With the S3 script's gathering line removed, `image_limits` in the S3 smoke goes red, so that script is held.
- **The text:** spec §12 and the two ABI tables say what the code does; no file still names the old accessors or "zeroed memory".

## Owed, as a follow-up

**1. Nothing holds the ESP32-C3's script.** With `*(.bss.sos_slab*)` removed from `esp32c3.ld`, the C3 smoke passes, 6 of 6 (`script_mutant_c3.py`): none of its cases links an area. Each script's ASSERT holds the order of the symbols only, which an empty region satisfies, so the issue's third acceptance line ("the builder's sections land inside the region on every board") rests on a booted case, and the C3 has none. A C3 case with an area, as the S3's `image_limits`, or a check in the builder's link that each area's symbol lies between the two, would hold it.

**2. The runner's comment on `slab_area_below_region`** says an area below the region lies over "the kernel's own statics, which the old bounds took". The region starts at `_bss_start`, the old lower bound, so the old check refused such an area too. The bound that moved is the upper one; `slab_area_over_static` and `slab_area_past_region` are the cases that show it.

**Not run by me:** the suite and the smokes unchanged (the server's gate passed); the C3 on anything but its smoke; anything on the parts.
