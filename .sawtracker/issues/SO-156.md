**`rt/main` keeps one `BootSet` alive, not several.** Today the start-up of a program written with `main` holds several copies of its `BootSet` in `_start`'s frame for the process's whole life: the init's `Result`, `adopt`'s local, the `Boot` temporary and `start`. That frame was measured at 2560 bytes on riscv32. Raising `BOOT_SET_CAPACITY` from 32 to 64, as SO-105 needs, overflows the arm64 stock root's 16 KiB stack and riscv32's `main_start` thread stack (SO-105 U1's measurements).

Restructure so the set lives once, for example in a static the start-up fills in place, moved out of no temporary. Measure `_start`'s frame on riscv32, arm64 and the S3 before and after, and print it in a case where the runner can report it without asserting a host value. Then raise `BOOT_SET_CAPACITY` to 64 and show every gate case passes, including arm64's stock root and `main_start`. Saw has no inlining control, so check the frame on every profile. Every check needs a case that goes red when removed or inverted.

**Lead: SO-156.p1 is up.** The start-up of a program written with `main` drains its boot set in place, so `_start`'s lifelong frame holds no copy of it, and `BOOT_SET_CAPACITY` becomes 64. One commit, rebased onto current main. It conflicts with SO-105.p2 on one line of `kernel/abi/src/boot.saw`: that patch rewrites the comment above `BOOT_SET_CAPACITY`, and this one changes the value below it.

**`_start`'s frame** (bytes, from the disassembly):

| | main at 32 | new at 32 | new at 64 |
|---|---|---|---|
| riscv32 | 2560–2576 | 64 | 64 |
| arm64 | 4160–4176 | 112 | 112 |
| S3 | 2704–2720 | 64 | 64 |

**Peak stack** (the frame plus the deepest call chain, down to the panic path):

| | main at 32 | new at 32 | new at 64 | stack |
|---|---|---|---|---|
| stock root, riscv32 | 8752 | 6832 | 6832 | 16384 |
| stock root, arm64 | 13776 | 9200 | 10736 | 16384 |
| stock root, S3 | 8740 | 6952 | 6952 | 16384 |

**`main_start`'s entry leg,** against a 1024-word thread stack:

| | main | new | stack |
|---|---|---|---|
| riscv32 | 3792 | 1280 | 4096 |
| arm64 | 5536 | 1472 | 8192 |
| S3 | 3984 (already near the edge at 32) | 1328 | 4096 |

**What changed.**
- **`BootSet.drain_into(at:process:)`** builds the set in place: count 0, then an internal `fill`, which `init(process:)` uses too. `BOOT_SET_STORAGE_WORDS` is held to `sizeof` and `alignof` by `static_assert`s.
- **`rt/main`:**
  - The set lives in a static `SET_STORE`, and `take_set` moves it out.
  - `Boot` loses its `set: BootSet?` field.
  - `adopt` is `@export("sos_main_adopt")` with pointer parameters, so it isn't inlined into `_start`. Inlined, its panic buffers stayed in the lifelong frame: 1072 bytes on riscv32.
  - The public API is unchanged. The "boot set is missing" panic is gone, since it can no longer happen.
- **`BOOT_SET_CAPACITY` is 64.** Spec §12 gains a sentence on the in-place drain.
- **The runner.**
  - `_function_frames` reads frames for riscv, arm64 and Xtensa call0.
  - `_check_startup_frame` requires `_start`'s frame to be smaller than one boot set, (3 × capacity + 1) words, read from `boot.saw`. It runs on every process of the case that links `sosmain`, and refuses a case where none does.
  - It is set on the gate's `main_start` and `stock_root` and on the S3's `stock_root`, and prints `_start's frame N bytes, one boot set M` under the row.

**Mutants, at 64:**
- **A, `Boot` given its `BootSet?` field back:** red on riscv32, arm64, flat and the S3, for both cases (848 against 772; 1664 against 1544 on arm64). With the check switched off, A is green, so the check is what catches it.
- **C, `adopt` inlined:** red on riscv32, flat and the S3 (1072, 1056 and 1216 against 772). It is green on arm64 (1344 against 1544), where no set copy is involved and the set is larger.
- **Not caught:** a copy made only inside `sos_main_adopt`. It is transient, gone before `main` runs.

**`main`'s own frame** still holds the set it takes, plus `take_boot_set()`'s return temporary; at 64 that is 2992, 5168 and 3024. Removing it would change the public API.

**Totals at 64,** before the rebase:
- `make sos-test` 1349, including every arm64 case that overflowed before (`stock_root`, `stock_heap`, `stock_root_heap`, `stock_many`, the pl011 cases, `console_silent` and `main_start`).
- The S3 smoke: 224, with 5 board-only.

After the rebase, `main_start`, `stock_root` and `stock_heap` were rerun on three profiles, 9/9.
