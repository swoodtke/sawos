**Networking: strict ARP learning in `netstack`.** The owner ruled on Nov 24: "strict for arp". This follows the reviewer's point 5 on SO-151.p1.

**Today** the stack creates a cache entry from any ARP packet addressed to us, as RFC 826 allows. The reviewer showed three problems:
- an unsolicited reply re-points the gateway;
- a table's worth of unsolicited replies evicts it;
- it learns an off-subnet sender, 255.255.255.255, 224.0.0.1, a zero sender MAC, and our own MAC.

**Strict:**
- **Learning.** Create an entry only on a request whose target is our address, or on a reply to a request we sent (pending resolution for that address). Update an existing entry as RFC 826's merge does.
- **Refused senders, each a counted drop with its own reason:**
  - an IP that isn't a unicast host on our subnet (`ipv4.host_address`'s rules, plus on-subnet);
  - a sender MAC that is zero, broadcast, multicast (the I/G bit), or our own.
- **The gateway** can't be evicted by unsolicited replies, since none create entries.
- **The docs** state the rule, and that a host on the same link can still poison ARP, which nothing at this layer prevents.

Every check needs a case that goes red when it is removed or inverted. The reviewer's probes become tests. Small, hosted.
