**Networking: strict ARP learning in `netstack`.** The owner ruled on Nov 24: "strict for arp". This follows the reviewer's point 5 on SO-151.p1.

**Today** the stack creates a cache entry from any ARP packet addressed to us, as RFC 826 allows. The reviewer showed three problems:
- an unsolicited reply re-points the gateway;
- a table's worth of unsolicited replies evicts it;
- it learns an off-subnet sender, 255.255.255.255, 224.0.0.1, a zero sender MAC, and our own MAC.

**Strict:**
- **Learning.** Create an entry only on a request whose target is our address, or on a reply to a request we sent (pending resolution for that address). Update an existing entry as RFC 826's merge does.
- **Refused senders, each a counted drop with its own reason:**
  - an IP that isn't a unicast host on our subnet (`ipv4.host_address`'s rules, plus on-subnet);
  - a sender MAC that is zero, broadcast, multicast (the I/G bit), or our own.
- **The gateway** can't be evicted by unsolicited replies, since none create entries.
- **The docs** state the rule, and that a host on the same link can still poison ARP, which nothing at this layer prevents.

Every check needs a case that goes red when it is removed or inverted. The reviewer's probes become tests. Small, hosted.

**Lead: SO-154.p1 is up: strict ARP learning, the owner's ruling.** It's one commit on current main.

**The rule.**
- **What may teach the stack.** A packet creates or updates an entry only if it is a request whose target is our address, or a reply from a sender with a frame waiting, that is, a reply to a request we sent.
- **Everything else** changes nothing and counts `Drop.ArpUnsolicited`. The RFC 826 merge is gone, so an unsolicited reply can no longer re-point the gateway, which was your revision-1 finding.
- **Refused senders, each its own reason:**
  - a sender MAC that is zero, broadcast, multicast (I/G), or our own;
  - a sender IP that isn't an on-link host address (`ArpSenderIp`).
- **The 0.0.0.0 probe** is answered and never learned.
- **The docs** ("What ARP learns") say that a host that changes its MAC is relearned when its entry ages out and we ask again, or when it asks for us. They also say that a host on the same link can still poison ARP.

**Counts.** Broadcast requests for other hosts and gratuitous announcements are now counted as unsolicited. `pair.saw` asserts exactly one per stack: the peer's announcement.

**Cases (`stack.saw`).**
- **Changes nothing:**
  - an unsolicited reply naming the gateway's IP with a new MAC leaves its entry unchanged;
  - a gratuitous request doesn't move a known entry;
  - a request for another host doesn't either.
- **Updates:**
  - a request for us updates a known entry and restarts its age;
  - a reply to our own request moves an existing entry.
- **Not learned:**
  - an unsolicited flood is counted and the gateway stays;
  - a reply from another host is not learned;
  - a late reply after the wait is not learned.
- **Each MAC and IP refusal,** for both a request and a reply.
- **Tests adapted.** Tests that taught B with an unsolicited reply now use a request from B.

**Mutants.** 19, all red:
- the old merge restored;
- `asked` always true, never true, or inverted;
- `for_us` dropped, and the operation ignored;
- the unsolicited drop uncounted or miscounted;
- no flush;
- the probe learned;
- each MAC refusal;
- the IP check, and each of its two halves;
- the probe exemption;
- `wire.saw`'s uniqueness check.

**Runs.** `blade test` in netstack passes (pair, wire, stack); there's no kernel or QEMU change.
