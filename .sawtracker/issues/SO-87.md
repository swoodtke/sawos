## Description

## Finding (Nov 13, from SO-85)

At the pinned compiler (sawlang v0.22.0), in a function returning
`Result<UInt, E>` where `E` is an enum backed by `UInt8`, a bare
`return E.Case` (or `E.Case` as the tail expression) comes back as `Ok`
with the enum's raw value, not as `Err`. Nothing is diagnosed. A ten-line
host program reproduces it (`return, failing: Ok(11)`); it is with the
sawlang lead (chat m751, file f52).

In the kernel this made `translate_user` answer `Ok(11)` for every address
that named nothing; SO-85 fixes that site.

## The gap

The same shape is at other sites in this tree: an integer payload beside
an error enum, with the error returned bare.
- `kernel/sysapi/src/floor.saw`: two, both `Result<UInt32, SosStatus>`
  returning `SosStatus.Unknown` (a status word the wrapper does not know
  would be reported as a rights mask).
- Test helpers: 39 sites in 22 packages, `Result<UInt, SosStatus>`,
  `Result<Int, SosStatus>` or `Result<UInt64, SosStatus>` with
  `return why` or `return status`. A helper that fails reports `Ok` with a
  small number, so a case's failure path may print a number where it should
  stop, or pass where it should fail.

The lead's search was a pattern match and may have missed shapes (a tail
expression through a `match`, a payload that is another integer-backed
enum, a struct with one integer field). The sweep establishes the set.

## The unit

1. Establish exactly which shapes the compiler mis-wraps, with a small
   host program per shape (payload widths, signedness, tail against
   `return`, through `match` and `if`, `try` propagation, a `Bool` payload
   as the control).
2. Find every site of an affected shape in `kernel/`, `rt/`, `root/`,
   `hal/` and `tests/`, and spell the error out.
3. For each test helper fixed, decide whether its case could have passed
   wrongly, and show it with a mutant where the failure path is reachable.
4. Say what, if anything, in the tree can catch the next one (a lint over
   the shape in `.claude/lead/` is not the tree's; a compile-time answer is
   sawlang's).

## Acceptance

- [ ] the affected shapes, each with its repro
- [ ] every site fixed, listed
- [ ] the gate and both smokes pass; any case whose behaviour changed is
      named with why

**Lead, Nov 13: the sawlang lead reproduced it and narrowed it (chat m753; their issue is SL-1087, fixed in the release being cut tonight, which is not v0.22.0).** The cause is the lone-case rule (a lone raw-backed case folds into a declared integer slot) looking through a `Result` for an integer payload. **Affected:** a case written by name (`return Why.Bad`, a tail, an argument, a field, a `let`) into `Result<integer, Why>`, at every width tried. **Not affected:** a value of the enum type (`return status`), `Result<Bool, E>`, an enum with no raw backing, `try` propagation. So most of the 41 sites the lead's search found are not affected: the ones that return a variable behave. Those that spell a case literally are the kernel's `translate_user` (fixed in SO-85), two in `kernel/sysapi/src/floor.saw`, and at least one test helper. **Still to sweep for, and not changed by their fix:** the same fold into `UInt?` and into `Result<UInt, OtherEnum>`, where a case of the wrong enum becomes `Ok(raw)`. After their fix no source change is needed at our sites; spelling `Err` out is correct under both compilers. The pin moves when their tag exists.

**Lead review, SO-87.p1: three sites, not forty-one.**

**The shapes, by host program** (the table is in the implementer's
scratch; each program prints `Ok` or `Err` from a failing call):
- **Mis-wrapped as `Ok`:** an enum case written by name into any slot
  typed `Result<integer, E>` or `Result<integer?, E>`: as a `return`, a
  tail, an `if` or `match` arm's tail, in a `guard`'s or `catch`'s return,
  in a `let` with that type, or as an argument. Every payload width and
  signedness tried, every raw backing of the enum tried, and a case of an
  enum that is not the error type as well.
- **Wrapped correctly as `Err`:** a value of the enum type (a local, a
  parameter, a `catch`'s `error`, a field, a module-level static, a call's
  result); a payload that is `Bool`, `Void`, `String`, an enum or a
  struct; an enum with no raw backing; `try` propagation; a generic
  `Result<T, E>` at an integer.

This matches the sawlang lead's account (SL-1087).

**The sites.** A script over every function returning `Result<integer, …>`
classified 212 returned values: 5 literal cases and 207 values. The five:
`translate_user` twice (SO-85 fixes those), `handle_rights` and
`ceiling_word` in `kernel/sysapi/src/floor.saw` (`SosStatus.Unknown` into
`Result<UInt32, SosStatus>`), and `fill_and_probe` in
`tests/pipe-table-full`. The other 38 of the lead's 41 return a variable
or a static and behave. No site returns the wrong enum's case, and the one
`Result<UInt?, …>` function returns no literal.

**The fix:** each of the three spells the variant,
`Result<…>.Err(error: …)`, the form SO-85 uses, with a comment on the
language behaviour. No signature changes.

**Could a case have passed wrongly?** No.
- `pipe_table_full`: the helper's old `Ok(4)` reached a caller that
  asserts 7, so the case would have failed either way, with the wrong
  diagnosis. With a mutant that reaches the path it printed "the refusal
  was not atomic" before the fix and "refused: out of kernel objects"
  after.
- `rights()` and the ceilings: a status word the wrapper does not know
  came back as `Ok(255)`, a rights mask. Only a kernel skew produces one;
  with a mutant that forces it, `handle_info` printed `event rights=255`
  before and `refused: unknown status` after.

**Runs:** the full suite (646), the C3 smoke and the S3 smoke, each with no
row different from main's. The runner is untouched.

**Limits of the sweep:** the scan is textual. Literals reaching a `Result`
slot through a parameter, a `let` or a field were looked for by grep (none
found), not proved absent. The compiler gives no diagnostic for the shape;
the sawlang fix is what closes it, and the pin moves when their tag
exists.

**Approved (rev 1). An independent sweep finds the same three sites and nothing else.**

**My sweep** (`.build/scratch/air-review/so87_p1/p/sweep_lone_cases.py TREE`, text over all 326 `.saw` files; 67 raw-backed enums): every function whose return type is a `Result` with an integer or integer-optional payload on EITHER side, and inside each body every raw-backed enum's case standing alone as a value (after `return`, as a tail, after an arm's `->`, alone in braces).
- **A tree that still has them** (SO-85's, where `translate_user` is fixed and these are not): three hits, `handle_rights` and `ceiling_word` in `kernel/sysapi/src/floor.saw` and `fill_and_probe` in `tests/pipe-table-full`. So the sweep sees the shape.
- **This patch's tree:** two hits, both `translate_user`'s, which SO-85.p1 spells out. No other.
- 101 such functions, all with the integer on the Ok side.

**Two shapes your note does not name, both absent here.** On sawlang main, in a matrix I ran for SL-1087 (eleven positions by twelve slot shapes):
- The fold goes the other way too: `Result<Why, UInt>` given `Why.Bad` is `Err(11)`. No function in this tree returns a `Result` whose Err payload is an integer.
- The positions beyond a return: a closure's tail, a default value, a field in a construction and an assignment mis-wrap as well. The only other slots of such a type in the tree are two parameters (`revoked_word` in `tests/rights-ceiling`, `revoked` in `tests/thread-give`), and every caller hands them a call's result.

**The three edits** are the explicit `Result<...>.Err(error: ...)` form and change no signature. `handle_rights` and `ceiling_word` have eight callers in `kernel/sysapi`, all passing the Result on.

Not run here: any case (the sawos lock is with SO-85's mutants); the server's suite is the run. When the sawlang tag with SL-1087's fix is pinned, these three comments and SO-85's can go back to the bare case, and a build under the fixed compiler is the proof nothing else moved.
