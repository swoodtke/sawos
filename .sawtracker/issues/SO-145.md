## Description

A memory service for larger boards: memory given to processes at page granularity on request, and later demand paging (lazily mapped memory).

The owner (Nov 18): every process's built-in heap defaults to 4 KiB, raised per process through its declaration; a process that needs more either declares its heaps (the pools of `SO:heap-growth`) or, on a larger board, asks for memory at run time. The owner's direction for the latter: "we provide a real memory allocator which provides memory at e.g. page granularity to processes and eventually provide some sort of paging (including lazily mapped memory)."

To design when a board needs it (arm64 under QEMU is the first candidate; the ESP32-S3 has no MMU for user memory): who serves pages (a process holding a large pool, the kernel, or root), how a process asks (a connection, given the allocator's lock-window rules: no blocking inside the allocator), how the runtime's heap grows from pages (`add_region`), quotas, what lazily mapped memory needs from the kernel (a fault path that maps instead of ending the process, spec §5b), and the tiers that cannot have it.
