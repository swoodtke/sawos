## Description

**Unit U3 of the image and packaging design (SO-95): the description formats.** A board description (`hal/<board>/board.toml`), a process declaration (`process.toml` beside each package that is a process) and an image description (an image TOML), read by the image builder (`tools/sosimage`, in Saw) through sawlang's typed TOML reader, `libs/toml`, which is in v0.24.1, main's pin.

**What is built.** The design is authoritative for the formats (`SO:images-and-packaging` revision 6, the user's rulings recorded in its section 15; the lead's copy is `.claude/lead/so95-design.md`): section 3.0 (the rules every format follows), 3.1 (the board description, with devices by type and `[types.<type>] inputs`), 4 (a process's declaration), 5.1 and 5.3 to 5.5 (the image description and the worked examples). Section 14's U3 entry is the scope:
- `board.toml` for each board in the tree: riscv32 `virt` (and its flat profile), arm64 `virt`, the ESP32-C3 and the ESP32-S3, with devices by type. Each states what the board's HAL and the runner know today, from their sources; a fact the description states and the HAL also states must agree (say how that is checked).
- `process.toml` per section 4, for the packages that are processes today where the design's examples cover them (at least the UART service and its client, so that the worked example of 5.5 can be built from files).
- the image TOML per section 5;
- section 3.0 enforced by the builder's reader: unknown keys, suffixed sizes, bad names, reserved words, the reference grammar (`..` refused, `..=` inclusive) and every uniqueness rule, each refused by name with a test in `tools/sosimage/tests/`;
- `[types.<type>] inputs` and the board-input rules of section 4.6;
- `uart_service_ns16550` built from files and identical to the case the runner builds today (image bytes, or the transcript where the bytes legitimately differ: say which and why).

**Settled since the design, to build to:**
- A number the target's word cannot hold is refused by the builder by name (an address or length past `UInt32` on a 32-bit board).
- A repeated key, a table given twice and a redefinition are errors naming both places (`libs/toml` already makes them; the builder's message keeps the file, line and column it gives).
- A `part = true` window does not owe its device type's board inputs.
- Config names are consistent across formats: one name for one kind of thing (`len` for every length, `base` for every base); check every key you add against the others.
- `libs/toml`'s API at v0.24.1: `TomlDoc.parse(text)`, `root()`; required reads `string`, `integer`, `unsigned`, `boolean` (a `Missing` error naming the key, the table and its position) and `optional_*` reads for a key with a default; `table(key)` and `array(key)` as places with `expect` and `require`; `keys()` in file order (walk it to refuse an unknown key); `kind`, `position`, `path`, `defined_at`. Hexadecimal, octal and binary read up to `UInt64.max` through `unsigned`; decimal is `Int64`. One nesting limit for the whole tree, 32 by default. It refuses floats, date-times and multi-line strings by name. Read its `//!` at the top of `libs/toml/src/lib.saw` in the toolchain checkout.

**Not in this unit:** generated link addresses (U4; the builder still takes today's link scripts); root's boot plan and the stock root (U6); the per-board limit values (U2b); the runner reading these files for every case (the runner keeps its own case table; this unit proves the formats on the worked examples and its own tests).

- **Mutants:** 85, each red and restored (two needed a new test first).

**Differences from the design, for the reviewer and the user.**
1. Board facts are checked against a compiled HAL module, not the design's `sos_board_info` kernel export, which does not exist yet (this unit could not change the kernel); so `board.toml` restates the console window and the RAM ranges, and the check holds them to the HAL source.
2. Until regions are computed (U4), process `i` gets the `i`-th region above root's, each as long as root's: today's link-script layout, refused past the default process range. It would not fit the C3 (its child region is shorter than root's).
3. `hal` is a path from the tree's top (the design's example writes it so, against its own path rule); the builder checks it is the file's own directory.
4. Choices the design leaves open, made strict: a `[types.T]` with no device of type T is refused; every `[board]` key is required; `tick` is required; registers and array strides are 4-byte multiples; a slot range divides evenly and lies in the flash; an unbound pool and a row listed twice are refused; a declaration's `ram` accepts only `"fast"`.
5. The S3 file states today's HAL: a 32 MiB flash window (the design said 16 MiB, which is the PSRAM design's later layout), 4 MiB of flash, one child slot, UART0 only. No board has `[types]` or `[limits.default]` yet: nothing states them.
6. Not built: `sosimage build` reads, binds and prints a stock-root image and then refuses it (the stock root is U6), and refuses an image with pools (addresses are U4); the limit checks against board maxima wait for U2b. The in-tree `process.toml` files carry no `[quota]` (stating them needs an audit of each program).

**Found, not fixed:** the JSON test image and the TOML name the same limits differently (`slabs.process_records` and `quotas.event` against `records` and `events`), which breaks the one-name rule; the JSON is the runner's and is left for the unit that moves the runner to the files. The profile's compiler features (`+m,+a,+c`) have no `board.toml` key yet; U4 needs one.

## Asked

**1. The issue's settled list: "A number the target's word cannot hold is refused by the builder by name". `declaration.saw` reads `arena` against an 8-byte word and `check_against` has no word check.

**2. `sosimage board` passes board files the note says it refuses.** One value changed in a copy of the file, then `sosimage board` (`probe_board_mutants.py`):

| changed | result | the note |
|---|---|---|
| the kernel RAM range's base (riscv32) | passes | "the check holds them [the RAM ranges] to the HAL source" |
| the kernel range lengthened over root's region | passes | same |
| the process range lengthened past the HAL's `RAM_TOP` | passes | same |
| the S3's `[flash] base`, `root-slot`, `slots` base and count | pass | "refuses a ... flash layout that differs" |
| a module the profile maps, left out of `modules` (riscv32, S3) | passes | "refuses a ... module directory ... that differs" |
| `hal = "riscv32"` for `hal/riscv32` | passes | "checks it is the file's own directory" (it is a suffix test) |

  The console window, the root region, the triple, the cflags, a module mapped elsewhere and the flash's `len`, `ibus` and `dbus` are refused naming both values, as the note says. The RAM ranges matter beyond the file: `product.saw` bounds each process's region by the board's default range, so a range drawn past RAM lets `build` place a child past it. Hold these, or say in the note, in `CLAUDE.md` and in the runner's new comment ("a fact the file states that either says otherwise fails the profile here") which facts are held.

**3. Refusals with no test.** The design's U3: "each refused by name with a test". One-line mutants against the builder's tests, and for the board check also the three gate profiles' `board` runs: **24 of 38 reader mutants and 12 of 35 board mutants stay green** (the agents chose thin-looking branches, so the rate is not the note's; I re-ran 27 of the 36 survivors, every one named below, and two red ones, with the same results).
- **Unknown keys** are asserted in eight tables. With `only_keys` removed, nothing fails for the declaration's top level, `[[setup]]`, a register or array, `[[pool]]`, a flash span, or the image's top level (m42 to m47).
- **Bounds:** a negative `count` (m03), a count or stride of zero (m06), a flash span past the flash's end (m08), zero slots (m09), `root-slot` outside the flash (m14), a device window past the address space (m38), a pool length past the word (m40), a part smaller than the grain (m11; every test uses grain 4).

- The whole list with each mutant's line is in f162 (`mutants.out`, `mutants2.out`, `refusal_map.py`) and f163 (`logs/src_mutants_all.log`).

**4. Two refusals name the wrong thing.**
- A serve and a client under one name: "`gpio` names two client records, here and at line 18" where line 18 is the serve (D01; the other order says "two serve records"). `tests/process_declaration.saw` asserts that text.

**6. But no test and no runner path calls it, so the unit's last acceptance line is held by a run nobody repeats.

## Smaller

- **The S3 board file pins the default keys** (`s3clock=keys/clock-rom`, `s3stall=keys/stall-off`), so the smoke's own `boot_xtal40` profile is refused by it; the design's example has `modules = []`. No gate run checks the S3 file, so nothing fails today.

- The note's items 2 to 5 are as described but for the above; the process and image files match the programs and §5.5.

**Not run by me:** the suite and the smokes (the server's gate passed); `sosimage build` for the C3 or S3; most of the two agents' passing probes, which I read but did not repeat.
