## Description

## Goal (user, Nov 12)

A useless box running SOS on real hardware by the end of the week of Nov 12:
the kernel boots, a few simple tasks run, a switch is read, and servos are
driven through IoMemory windows so the box turns its own switch back off. The
user's board is an **ESP32-S3**.

It is the first step toward SO-1 (M6): the first time SOS runs on silicon and
the first userspace drivers for a device other than a UART.

## Where the tree stands

- SOS has run only under QEMU. The boards are riscv32 `virt`, arm64 `virt`
  and the ESP32-C3, and the C3 work ruled real hardware out of scope: it uses
  the ROM's direct boot, has no esptool image, and `hal/riscv32-esp32c3/ABI.md`
  records three places where the emulator and the silicon disagree.
- **The ESP32-S3 is an Xtensa LX7 part, not RISC-V.** It is a third CPU
  architecture for both the compiler and the kernel. None of the C3 board
  code carries over except as a model for the Espressif peripherals (UART,
  SYSTIMER, the interrupt matrix).
- The userspace driver pattern exists (`tests/svc-uart-ns16550`,
  `tests/driver-child`): a device window arrives as an `IoMemory`, the driver
  maps it, binds its line and serves a pipe. There is no GPIO or PWM driver.

## What the S3 needs, in dependency order

1. **sawlang: an Xtensa target.** sawc emits LLVM IR and drives clang, and its
   freestanding targets are `aarch64-unknown-none-elf` and
   `riscv32-unknown-none-elf` (`compiler/target/src/layout.saw`). It needs the
   Xtensa triple, data layout and calling convention, and Blade's sosimg needs
   the architecture tag. The Espressif clang installed on this machine
   (20.1.1) lists an Xtensa backend; whether the clang sawc drives today has
   one is not checked. This is sawlang-side work, then a release and a pin
   bump here.
2. **sawos: an Xtensa HAL.** Vectors and trap entry, the trap frame, the
   syscall stub, the context switch, the timer and the interrupt dispatch,
   with linker scripts for the kernel and for user images. For scale, the
   arm64 HAL and the riscv32 pair (`riscv32-common` plus a board) are each a
   few thousand lines. The call0 ABI avoids the register-window exceptions and
   is the lead's recommendation.
3. **The protection tier.** The S3 has no PMP. Its permission controller is a
   different mechanism, so the first S3 profile is `Flat`, as
   `hal/riscv32-flat` is for the virt board.
4. **An emulator smoke.** `qemu-system-xtensa -machine esp32s3` is installed
   here. Its memory tree shows the UARTs, GPIO, the timer groups, SYSTIMER,
   the interrupt matrix and USB-Serial-JTAG. It shows no LEDC (PWM) device,
   so a servo driver can be checked there only as register writes.
5. **Real silicon.** A flashable image the ROM or a second-stage loader
   accepts, the watchdogs the ROM leaves running, the clocks, and a console.
   The S3's built-in USB JTAG and the installed `openocd-esp32` give a
   debugger. This step needs the user at the board.
6. **The box itself.** Device rows for GPIO and LEDC in the region table, a
   GPIO driver (the switch, on its interrupt line), a PWM driver (the servos),
   and the root image that launches the tasks.

Steps 1 to 3 are a serial chain across two repositories before any hardware
is involved. Steps 4 to 6 can overlap.

## Decision for the user

- **S3 this week.** The architecture port is the critical path and the date
  is at risk. The port has lasting value, since the S3 is the board the user
  has.
- **A RISC-V Espressif board this week, the S3 after.** On a C3 the work is
  steps 5 and 6 only, because the HAL already boots under QEMU. It needs a
  board the user may not have.

Units are filed under this epic once the board is confirmed.
