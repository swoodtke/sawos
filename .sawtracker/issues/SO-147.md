**ESP32-S3: the flash at full speed.** Processes run in place from flash, and the flash is the part's slowest path. It runs at 20 MHz, single-line read, at every CPU speed. The memory-SPI core clock stays at 80 MHz, and SPI0 divides it by 4 (ABI.md §14c and §14h). The owner set the order on Nov 16: 160 MHz, then 240, then the flash. On Nov 24 they placed this right after the PSRAM.

**What it takes**, to settle in a short design (Opus) before any build:
- **The mode and the clock:**
  - which read mode the module's flash supports (DIO, QIO, or octal on an Octal-flash module) and how fast;
  - what ESP-IDF v5.4.1's bootloader and `spi_flash` / `mspi_timing` code write to get there (SPI0's clock and user registers, dummy cycles, the flash's QE bit);
  - which of those writes are non-volatile.
- **The flash's QE bit.** It lives in the flash's non-volatile status register. Writing it is a write to the flash chip, so the design must say whether we need to write it at all. If the ROM or the image header already leaves the module in QIO, we don't. If we do, the design says what the owner must approve.
- **Sharing with the PSRAM.** The flash and PSRAM share the memory-SPI core clock; only their chip selects and dividers differ (SO-102's design §3.3). A faster flash must not change the clock the PSRAM's divider was set against without saying so. ESP-IDF brackets such changes with its MSPI timing tuning. The design states whether 80 MHz needs that tuning on this module.
- **The image header.** The ESP-IDF image header carries the flash mode and frequency, and the ROM reads them at boot. The design says what `sosimage flash` writes there and what the ROM does with it.
- **The measure.** `kill_churn` at `pll240` against the same image at 20 MHz flash, as ABI.md §14h does for the CPU.

**Board stages.** Each needs a board run. The only write is `write-flash 0x0` of the image; no eFuse burn or write, no erase. Any write to the flash's status register needs the owner's word first.

**Lead: the design is written and published as the tracker doc `SO:flash-speed`, revision 1.** It changes nothing in the repository. The owner and the reviewer read it before anything is built.

**Verdict.**
- **The flash.** esptool's ID, 0x20 0x4017 (8 MB, quad, 3.3 V), is an XMC chip. ESP-IDF runs it through its generic driver at 20, 40 or 80 MHz in DIO or QIO.
- **The target.** QIO at 80 MHz, with DIO at 80 MHz first; DIO writes nothing to the flash chip. A 40 MHz image is built beside each 80 MHz stage and run only if 80 hangs.
- **The switch.** Every write is volatile: six SPI0 registers, plus pads 27 and 28 and two input selects for QIO. It runs from IRAM after the clock key, on a PLL key only.
- **No ROM read-mode routine is called.** Those routines set or clear the QE bit themselves, which is a non-volatile write. A new build check refuses any kernel that references them.
- **The core clock doesn't move.** Only SPI0's flash divider changes, from 4 to 1, so the PSRAM's clock contract (`SO:s3-psram` §3.3) holds. ESP-IDF tunes nothing at 80 MHz in this configuration.
- **No image header is involved.** The image direct-boots (byte 0 is 0xFF), so `sosimage flash` is unchanged.
- **The emulator.** It models SPI1's commands but not SPI0, and reads the image file directly through its cache. The smoke can check the stores, the decisions and the commands, but only the board shows whether 80 MHz works.
- **Board stages.**
  - F0: a read-only probe (JEDEC ID, status registers 1–3, SFDP, SPI0's state).
  - F1: DIO 80.
  - F2: QIO 80, only if the QE bit is already set.
  - F3: the measure, `kill_churn` at `pll240` with the flash at 20, DIO 80 and QIO 80.
  - F4: the QE write, only on the owner's word.
- **Preconditions.** The `pll240` board run passes, and PSRAM P2 at `pll80` reads 80 MHz.
- **Units.**
  - U1: read-only flash commands and the probe (Opus, M).
  - U2: the `s3flash` key and the switch (Opus, L).
  - U3: board runs (S).
  - U4: the QE-write harness (Opus, S), only if approved.

**Gaps the design names.** It hasn't read the XMC datasheet, JESD216 itself or the TRM. The part read SPI0's USER register back as `0x000000c0` after the ROM's wider store. Two failure modes survive a reset and need a power cycle: continuous-read mode, and ultra-deep power-down. §8 covers both.

**Owner's questions** (design §9.2):
1. If F0 finds the QE bit clear: measure DIO 80 first, then approve one non-volatile QE write as its own stage only if QIO's gain is wanted.
2. The flash key isn't on by default; products opt in with `[keys] flash = "dio80"|"qio80"`.
3. 40 MHz fallback images are built ahead.
4. No esptool read commands; F0 reads the same with our image.

**Lead: SO-147.p1 is up: U1, the flash's read-only commands and the F0 probe.** One commit, rebased onto current main. It takes ABI.md §17, because SO-102.p3 hasn't landed; whichever lands second renumbers. It will also conflict with SO-102.p3 in `mspi.c`'s header and `entry_ok`.

**The command layer.**
- **One primitive.** The PSRAM's S7 is now one command primitive, `link_start`/`link_finish`, which takes the chip select as a parameter. Before every start it compares `SPI_MEM_MISC(1)` [1:0] with that parameter; it never writes MISC(1). The PSRAM path's stores are unchanged, and every §16e case is green.
- **`sos_flash_read(record, op, addr)`** sends only 9Fh, 05h, 35h, 15h or 5Ah (`flash_read_bits`), the way IDF's `bootloader_flash_execute_command_common` does on the S3:
  - CTRL(1) holds WP alone;
  - USER1 is 0x5c000007 for SFDP, else 0, and USER2 is 0x70000000 | op;
  - ADDR is unshifted;
  - CACHE_FCTRL's 4-byte and line bits are cleared;
  - CMD(1) gets `SPI_MEM_USR` alone.
- **Checks, before any SPI1 store:**
  - 0x79, the record isn't in DRAM;
  - 0x7A, the opcode isn't one of the five reads;
  - 0x73, MISC(1) doesn't read 0b10;
  - 0x7B, DDR(1) isn't 0;
  - 0x74, SPI1 is busy.
- **Afterwards:** it saves the PSRAM path's 11 SPI1 words and writes back every one but MISC. 0x75, a command that never finishes, writes its line from IRAM.

**The probe and the harnesses.**
- **`tests/xtensa/s3_flash_probe.saw` (F0)** prints design §1.2's lines and decodes SFDP:
  - the header and the BFPT header;
  - DWORDs 1, 3, 4, 15 and 16;

  Every other register it reads goes through a `ReadOnly` view.
- **`flash_fault.saw`** is the fault build.
- **`rom_flash_reference.saw`** holds a ROM routine's address as data and never calls it.

- **`expect_spi1_stores`** checks the exact, ordered list of the kernel's SPI1 stores.
- **`check_rom_flash_references`** runs on every S3 image and covers 72 ROM routines (`Enable_QMode`, `Disable_QMode` and the write, erase and program routines), each by jump-table entry and by body address. Each address was checked against `esp32s3.rom.ld` and the ROM ELF.

So the emulator image's harness stores 0x2 first, while a board image's `sos_flash_case_setup` is a bare `ret`, checked by disassembly. Requested changes on patch SO-147.p2 (revision 4) (its test run was cancelled)

**Changes requested, revision 4.** r4 is r3 rebased, with identical change lines. r3 is r1's code plus 67 lines of ABI.md, the board results F1 to F3, so this review is of r1's code with r3's text.

I ran the S3 smoke with `BOARD=esp32s3` and sawlang v0.24.3. The patch's 50 cases are green. Turning a canary compare into `0` turns the three canary cases red. A note on reach: on QEMU, a shipping kernel at a flash key stops at W3's gate (0x73), because QEMU's MISC(1) reads 0. Only a board image stops at W2's 0x70. The harness cases reach W4 to W9.

## 1. A 0x7D stop leaves a cache frozen, and the boot goes on
- `cache_freeze` sets FREEZE_ENA (mspi.c:1737). When DONE never reads set, it returns 0 and leaves FREEZE_ENA set (mspi.c:1744-1745).
- `caches_freeze` answers 0x7D for the instruction cache with nothing undone (mspi.c:1769-1771).
- For the data cache, `caches_freeze` thaws the instruction cache and discards the answer: `(void)cache_thaw(r, ICACHE_FREEZE);` (mspi.c:1775). The data cache's FREEZE_ENA is never cleared.
- `flash_init_at` halts only on 0x75 and 0x7E (flash-common/lib.saw:192). After 0x7D the boot goes on.
- The two freeze cases pin this. `flash_switch_stop_freeze_icache` expects the stores `(0x600c4154,0x0),(0x600c4154,0x1)` and no clearing store, and the data-cache case expects the data cache's `0x1` with no clear after it.

A probe with two lies shows it: the data cache's freeze word read as 0 at step 0xE5, and the instruction cache's as 0x5 at 0xE7. The console:
```
SOS-S3: flash dio80 not taken: the data cache did not report its freeze done: EXTMEM's freeze word read 0x00000000 after 100000 polls; nothing was stored to SPI0
SOS flashswitch: starts=0x00000002 w0_reads=0x00000002 table_hits=0x00030d43
SOS flashswitch: SPI1 MISC=0x00000002 clock=0x00030103 after the reads, as before them
SOS-S3: halt fail code=0x0000007d
```
The instruction cache's thaw failed too: 200,003 hits, 100,001 of them on that thaw. Yet the stop is 0x7D, the IRAM line for an unfreeze that was not reported is never written, and the line says nothing of a cache left frozen. ABI.md:5324-5326 says the instruction cache is "unfrozen again", but nothing checks that it was.

The ROM's `Cache_Freeze_ICache_Enable` (0x4004e8a8) and `_Disable` (0x4004e8e8), and their DCache twins, poll with no bound. So the 100,000-read bound and its way out are this patch's own, and the way out owes the freeze it started an undo.

On the part I could not test this. A freeze that completes after the bound leaves the cache frozen, and its next miss would wait with nothing printed, since the not-taken line's code and strings are in flash.

**Asked:**
- On a freeze that is not reported, clear that cache's FREEZE_ENA and wait, bounded, for DONE to clear.
- Treat any thaw that is not reported as 0x7E: its IRAM line, then the halt. That includes the instruction cache's thaw on the data-cache path.
- Update both freeze cases' store lists.
- Add the probe above as a case. It should expect 0x7E.

## 2. No case reaches W7's freeze or thaw, and the fault table cannot
Each of these mutants survives all 50 cases:
- W7's thaw failure ignored;
- the put-back skipped when W7's freeze fails;
- W7 thawing although its freeze failed.

The table matches on (step, command, address) (mspi.c:803-816). W5's and W7's freezes both read at `STEP_W_FREEZE` (0xE5) and both thaws at `STEP_W_THAW` (0xE7), in the same command on the same two addresses. A lie meant for W7 is spent at W5 first: a thaw lie beside a canary lie stops at W5's thaw (0x7E) before any canary read.

The two paths also report less than they know:
- When W7's freeze fails, `switch_stop(r, STOP_SWITCH_CANARY, …)` overwrites its 0x7D record with 0x78 (mspi.c:1874, 1884-1885). The line says SPI0 was put back, not that it was put back unfrozen, and finding 1's FREEZE_ENA stays set.
- When W7's thaw fails, the stop is 0x7E (mspi.c:1876-1878), and the canary's mismatch is in neither the record nor the line.

**Asked:** give W7's freeze and thaw step numbers of their own. Add cases for W7's freeze not reported (each cache) and W7's thaw not reported, and say in each line what was left undone.

## 3. No case holds `flash_init_at`'s halt
Both of these survive all 50:
- `|| stop == STOP_THAW` dropped from flash-common/lib.saw:192;
- the halt never taken.

Without the halt, a 0x75 boot goes on with SPI1 possibly mid-command, and a 0x7E boot goes on with SPI0 switched and the canary unchecked. No case can reach it today, because the harness calls `flash_switch` itself (flash_switch.saw:149) and the shipping kernel stops at 0x73.

**Asked:** one way is a harness built at a flash key that stores MISC(1) and fills the lie table before `hal.clock_init()`, then boots with `quiet_halt` and an `expect_tail` ending at the not-taken line. Make one case with a lie at step 0x79 (0x75) and one at 0xE7 (0x7E). The same harness, one case per key, would also hold the keys' mode words in finding 5.

## 4. Survivors that a case green on the patch would hold
Each mutant below survives all 50 cases. Each probe case is green on the patch and turns red under its mutant alone; the other nine probes stay green:

## 5. Survivors with no case yet
- **The keys' mode words.** These survive: qio80 passing mode 0, qio40 without `MODE_HALF`, dio40 with mode 0, and dio80 with mode 1. The `boot_flash_*` cases stop at the gate before the mode matters, and the harness passes a mode of its own. F1 and F2 hold dio80 and qio80 on the part; nothing holds the 40 MHz keys. Finding 3's harness would hold all four.
- **W5.4's pad store** clearing only bit 12 of MCU_SEL. The pads read 0x1B00, whose MCU_SEL is 1, so a pad lie with MCU_SEL 7 would hold it.
- **The FREEZE_MODE clear's mask dropped** (mspi.c:1735). The freeze word reads 0, so a 0xE5 lie with bit 1 set on the first read would hold it.
- **W2's CORE_CLK_SEL mask dropped.** It is equivalent only if bits [31:2] read 0. Either cite that or add a lie that sets them. The PSRAM's S0.3 has the same mask.
- **W9's read-back removed.** The words after the switch read 0 either way, and no case lies at step 0xE9. F1 and F2 hold it on the part.
- **The runner's `firsts` skip dropped.** It is red only when `flash_key_dio80_at_rom_refused` runs alone, which fails at the shipping kernel's static assert, and it survives the full 50. The gate runs the full set, so nothing the gate runs holds it.

## 6. Text
- mspi.c:30 gives the switch's stops as "0x70 to 0x78". The switch also stops with 0x79, 0x7D and 0x7E.
- mspi.c:443 says "(W4, W6)", mspi.c:460 "(W6)" and mspi.c:476 "(W6's last store)", for stores §18e numbers W5.1, W5.5 to W5.8 and W5.9. W4 is the first timed read and W6 the canary.
- ABI.md:5436-5437 says the harness stores MISC(1) and then runs the clock key. The code does the reverse: `hal.clock_init()` at flash_switch.saw:125, then `sos_flash_case_setup()` at flash_switch.saw:144.
- The record's `stored` field is written (mspi.c:1810, mspi.c:1929) and declared (flash-common/lib.saw:108), and nothing reads it. Read it, in finding 1's line perhaps, or drop it.

## Checked and found right
- **Every stop has a red case.** Mutants of each of 0x70, 0x71, 0x72, 0x76, 0x77, 0x78, 0x79, 0x7D and 0x7E turn a case red. So do W3's read stops passed through, and the ID compare made after the SR2 read. Both poll bounds are held by the hit counts.
- **W5's stores are held exactly and in order,** including the clock going first and the freeze order. Keeping CTRL_KEEP or USER2's low bits is equivalent, because W2 compares CTRL and USER2 with the description exactly (mspi.c:1712-1721).
- **W7's put-back returns every word W5 stores, in order.** Each drop, wrong word and swap is red.
- **`check_iram` refuses each function or table taken out of IRAM.**
- **The owner's ruling holds:**
  - The one write to SPI_MEM_CMD(1) is mspi.c:1036.
  - The switch sends only RDID and RDSR2, through `flash_read_in`.
  - Sending SR2 as 0x01 stops at 0x7A.
  - No 01h, 31h, 11h, 50h or 06h appears anywhere.
  - p1's 35 flash-read cases are green after the split.
- **MISC(1), DDR(1) and SPI1's idle bit are checked before each command.**
- **Each key's static assert, the seam's order and the board description's true side have red cases.**
