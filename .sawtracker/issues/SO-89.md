## Description

## Finding (from the review of SO-85, Nov 13)

SO-85 makes executable memory unusable as a system call's buffer and
requires a thread's entry to be executable, and closes one way round both:
a second grant row over the same addresses. A process's rows may not
overlap.

That is an invariant on addresses. It says nothing about two addresses for
the same bytes:

- On arm64 a `map` takes addresses of its own. A launcher that keeps a
  child's destination `Memory` can map it into the child a second time, at
  another address, with other permissions: read-write over the bytes the
  child executes, or read-execute over its data.
- Through such a mapping a buffer in the child's code is a legal source
  (the row it lies in does not permit execute), and the child's code is
  writable to the child.
- Spec §2.5 says no row is both writable and executable. Two rows over the
  same bytes, one writable and one executable, are not one row.

Nothing has been probed. This is a reading of `map_place`, `map_target_ok`
and `record_grant`.

## To settle

- Whether the kernel should refuse a mapping whose storage a row of that
  process already covers with conflicting permissions, on every profile,
  and what that costs (a walk of the rows by physical range).
- Whether the launcher holding that power over its own child is a hole at
  all: a launcher already chooses the child's image.
- What the spec says either way.

## Acceptance

- [ ] a probe on arm64 that shows what happens today
- [ ] a ruling, and the spec sentence for it

## Where this stands after SO-92's rulings (Nov 13), and notes for the probe

**What the rulings since have settled.** The overlap rule is on user
addresses (the user: "the addresses in the hardware mapping are
disallowed"), so a second view of the same bytes at another address in
one process stays legitimate where the hardware gives a mapping its own
address, which is arm64. The buffer half of this finding is closed by the
spec's buffer rule once SO-92's widening step builds it: no byte of a
buffer may be granted by any row that permits execute, compared by the
bytes rows grant, so a read-write alias of a process's code is not a
buffer. What is left for a ruling is the other half: a launcher that
keeps a child's destination can give the child a writable view of the
child's own code, or an executable view of its data.

**The probe (acceptance item 1), for a Sonnet implementer. Nothing lands
in the repository: packages and a harness case in the scratchpad, and a
report.** On arm64, with a launcher holding its child's destination
`Memory` (and the rights it needs: say which), show what each of these
does on main today, with the console lines as evidence and a control
beside each:
1. `map` of the destination into the child a second time, read-write:
   the status, and the address the child is told.
2. Through that alias, the child stores to a word of its own code, then
   runs it: does the store land, and does the changed instruction execute
   (say what the test does about the instruction cache, and whether the
   emulator needs anything)?
3. A system call given a source buffer in the child's code through the
   alias (the same bytes at the code's own address are refused today):
   taken or refused?
4. A system call given a destination record in the child's code through
   the alias: does the kernel write into the child's code?
5. `map` of the destination read-execute (what it needs, and what a
   launcher without `MapExecute` gets), and a thread of the child started
   at an address in its data through that alias: does it run?
6. The same five on riscv32, expected to be refused at the `map` (the
   mapping meets the child's own rows): confirm, with the status.
Report a table of the six with what happened, and for each which
sentence of `spec.md` it agrees or disagrees with today (§2.2's execute
test, §2.5's "no row is both writable and executable", §2.7's entry
rule), and which the buffer rule's not-yet-built comparison by the bytes
rows grant would change. No kernel change, no spec change, no commit.

**Lead, Nov 13: the evidence the probe would have gathered is in SO-92.p3** (the widened copy doors), as its arm64 case `buffer_alias`. A launcher that keeps its child's destination can map it read-write into the child; on arm64 the map is taken, at a fresh address. Through that view the child's own code is no buffer at either copy door (the execute test compares the bytes granted, not the address), and its stack through the view is still a buffer. So the kernel never copies into a child's code through such a view. What the case does not show, and what is left for the user's ruling, is the other half: whether the child may store to its own code through the view with an ordinary store instruction, which the hardware allows as the row says. The converse is in the same patch: a read-execute view of the whole destination leaves the child with no buffer at all (`map_over_image_refused` on arm64).

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":1715,"created":"1794681521","id":"c4"} -->
**User ruling, Nov 14:** "We shouldn't allow writing to executable mapped memory generally. The launcher can do it because it's 'trusted' but nobody else should be able to do it."

So the answer to the open half is **no**: a child gets no writable view of its own code, whoever maps it. The rule is about bytes, not about one row: bytes a process can execute are writable only to the launcher that holds the memory they live in.

**The lead's reading, to be written as spec sentences and brought to the user before any build:**
1. No process holds both a writable and an executable view of the same bytes, compared by the bytes the rows grant (as the buffer rule compares), on every profile. A `map` that would make it so is refused, in either order (writable over executable, executable over writable).
2. A writable view, in another process, of bytes that some process executes is the launcher's power alone. What "the launcher" means to the kernel needs stating: the lead proposes it is the authority of the handle, so such a map needs the `Memory` handle to carry the execute right (`MapExecute`) as well as the write right; a launcher that passes the memory on without that right passes on no power over the code, and one that passes it on whole has delegated its trust on purpose.
3. What it costs: a walk at `map` of the rows that grant those bytes (the target's for 1; every holder's for 2, through the memory's mappings), and what `process_create` and the loader owe so an image's own rows are found by that walk.

**Open edge for the user:** whether 2's "the handle carries the execute right" is the right meaning of "the launcher", or whether a third process must be refused whatever handle it was given.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":1097,"created":"1794681609","id":"c5"} -->
**User ruling, Nov 14, which replaces the lead's reading above:** "I don't think we need to restrict it - it just falls out from only the launcher being able to map memory x. And there is no way to get a writable version of that memory without extra work (which we won't do)."

So **no new kernel rule and no check at `map`.** That only a launcher can store to bytes a process executes is a fact of capability flow, as "only root maps executable" already is (§2.5): the two views need a handle on the allocation, the executable one needs `MapExecute`, and a process holds neither for its own image unless its launcher gave it one. A launcher that makes a writable view of a child's code has done extra work on purpose; the launchers in this tree do not. The kernel never stores through such a view itself (the buffer rule, held by `buffer_alias` on arm64).

**SO-89.p1** is the spec sentences for it (§2.5, after the paragraph on two rows over the same bytes); no code changes. With it merged the acceptance is met: the run is `buffer_alias` and `map_over_image_refused`, the ruling is this one.

Requested changes on patch SO-89.p1 (revision 1) (its test run was cancelled)

**Changes requested (reviewer, Nov 14), revision 1: one clause says more than the rules give.** The paragraph is the ruling, and three of its four claims hold as written. Nothing here asks for a kernel rule.

**The clause.** "a launcher that makes one has chosen to, as it chose the image, and a process whose launcher made none cannot store to its own code." The two cases read as the only two, and there is a third the paragraph's own first sentence allows:

- The launcher makes no writable view, and gives the child a handle on its image's allocation carrying `Map` (no `MapExecute` is needed for a writable view).
- The child holds `ProcessRight.Map` on itself through `ProcessSelf`, so it maps that allocation writable into itself. On arm64 a second mapping takes an address of its own, and this bullet already says "a writable view and an executable view of one allocation are still expressible, as two rows", and "where both are in one process".
- `map` does not look (the sentence before), so the child now stores to its own code through a view its launcher did not make.

That is still the launcher's choice, which is the ruling's point: it gave the handle. But "a process whose launcher made none cannot" is false of it, and a reader will quote that clause. A wording that covers all three:

> a launcher that makes one, or gives the child the handle to make one, has chosen to, as it chose the image; a process given neither cannot store to its own code.

By reading the spec's own rules, not by a run: no case in the tree has a child map its own image, and I wrote none.

**The rest, checked against the spec on main.**

- "The two views need a handle on the allocation, and the executable one needs `MapExecute` besides": `Map` is the one op on a `Memory`, and an executable `map` through a handle without `MapExecute` is `AccessDenied` (§2.5).
- "a process holds neither for its own image unless its launcher gave it one": a create mints the child no handle on its image or its destination (I read `process_create` on main), and a child's table holds what its launcher gives it (§12).
- "The kernel never stores through such a view itself (§2.2)": the view meant is in the process that executes the bytes (the `map`'s target), and there "the writable view is no buffer", which `buffer_alias` holds on arm64. A writable view in the launcher's own address space is the launcher's buffer like any other, and that is the launcher storing.
