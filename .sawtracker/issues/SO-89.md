## Description

## Finding (from the review of SO-85, Nov 13)

SO-85 makes executable memory unusable as a system call's buffer and
requires a thread's entry to be executable, and closes one way round both:
a second grant row over the same addresses. A process's rows may not
overlap.

That is an invariant on addresses. It says nothing about two addresses for
the same bytes:

- On arm64 a `map` takes addresses of its own. A launcher that keeps a
  child's destination `Memory` can map it into the child a second time, at
  another address, with other permissions: read-write over the bytes the
  child executes, or read-execute over its data.
- Through such a mapping a buffer in the child's code is a legal source
  (the row it lies in does not permit execute), and the child's code is
  writable to the child.
- Spec §2.5 says no row is both writable and executable. Two rows over the
  same bytes, one writable and one executable, are not one row.

Nothing has been probed. This is a reading of `map_place`, `map_target_ok`
and `record_grant`.

## To settle

- Whether the kernel should refuse a mapping whose storage a row of that
  process already covers with conflicting permissions, on every profile,
  and what that costs (a walk of the rows by physical range).
- Whether the launcher holding that power over its own child is a hole at
  all: a launcher already chooses the child's image.
- What the spec says either way.

## Where this stands after SO-92's rulings (Nov 13), and notes for the probe

**What the rulings since have settled.** The overlap rule is on user
addresses (the user: "the addresses in the hardware mapping are
disallowed"), so a second view of the same bytes at another address in
one process stays legitimate where the hardware gives a mapping its own
address, which is arm64. The buffer half of this finding is closed by the
spec's buffer rule once SO-92's widening step builds it: no byte of a
buffer may be granted by any row that permits execute, compared by the
bytes rows grant, so a read-write alias of a process's code is not a
buffer. What is left for a ruling is the other half: a launcher that
keeps a child's destination can give the child a writable view of the
child's own code, or an executable view of its data.

**The probe (acceptance item 1), for a Sonnet implementer. Nothing lands
in the repository: packages and a harness case in the scratchpad, and a
report.** On arm64, with a launcher holding its child's destination
`Memory` (and the rights it needs: say which), show what each of these
does on main today, with the console lines as evidence and a control
beside each:
1. `map` of the destination into the child a second time, read-write:
   the status, and the address the child is told.
2. Through that alias, the child stores to a word of its own code, then
   runs it: does the store land, and does the changed instruction execute
   (say what the test does about the instruction cache, and whether the
   emulator needs anything)?
3. A system call given a source buffer in the child's code through the
   alias (the same bytes at the code's own address are refused today):
   taken or refused?
4. A system call given a destination record in the child's code through
   the alias: does the kernel write into the child's code?
5. `map` of the destination read-execute (what it needs, and what a
   launcher without `MapExecute` gets), and a thread of the child started
   at an address in its data through that alias: does it run?
6. The same five on riscv32, expected to be refused at the `map` (the
   mapping meets the child's own rows): confirm, with the status.
Report a table of the six with what happened, and for each which
sentence of `spec.md` it agrees or disagrees with today (§2.2's execute
test, §2.5's "no row is both writable and executable", §2.7's entry
rule), and which the buffer rule's not-yet-built comparison by the bytes
rows grant would change. No kernel change, no spec change, no commit.

**Lead, Nov 13: the evidence the probe would have gathered is in SO-92.p3** (the widened copy doors), as its arm64 case `buffer_alias`. A launcher that keeps its child's destination can map it read-write into the child; on arm64 the map is taken, at a fresh address. Through that view the child's own code is no buffer at either copy door (the execute test compares the bytes granted, not the address), and its stack through the view is still a buffer. So the kernel never copies into a child's code through such a view. What the case does not show, and what is left for the user's ruling, is the other half: whether the child may store to its own code through the view with an ordinary store instruction, which the hardware allows as the row says. The converse is in the same patch: a read-execute view of the whole destination leaves the child with no buffer at all (`map_over_image_refused` on arm64).
