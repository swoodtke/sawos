**riscv32: page-align `.text`'s end, the emulator's sub-page PMP cliff.**

On riscv32 a process's image rows are PMP TOR regions on the 4-byte grain. So root's `.text` row ends partway through a page that also holds `.rodata`, which is another row. Code fetched from a page a PMP rule covers only partly runs far slower under QEMU.

`arena_race` shows it: hot heap code on that page takes it from 0.04 s to 10 s. The case then times out at the default job count once v0.24.4's slightly larger `SpinLock` prologue pushes `highest_bit` across. sawlang's SL-1196 measured both directions; the table is in its last comment.

**The fix:** `. = ALIGN(4096)` before `_text_end` in `hal/riscv32/user/user.ld`, costing up to 4 KiB per process.

**Its consequence:** `arena_race` and `arena_churn` hold today only because the cliff made riscv32 slow, and their comments say the faster profiles "cannot fail". They need their contention made true by construction, not by slowness.

This blocks the v0.24.4 pin bump (SO-167).

Approved patch SO-169.p1 (revision 1)

**Approved.** I ran it on riscv32 with sawlang v0.24.3, on main at 9421d11c, since 2c46d60a is not on origin; the patch applied cleanly.

**The fix:** `_text_end` on a page boundary, so no page of code shares a PMP row boundary with `.rodata`. `arena_race` and `arena_churn` pass 5 of 5 each through the runner. Booted directly under `qemu-system-riscv32`, their ELFs finish in 0.034 s and 0.073 s (medians of 5).

**The data side, measured:** `.rodata` to `.data` is still a mid-page boundary, so I also aligned `.data` to a page and re-timed: 0.040 s and 0.061 s. That is within the noise, so these cases have no data-page cliff worth a second alignment. The script is `so169_p1/time_qemu.py`.

**Against v0.24.4:** not runnable here. Main's `tools/sosimage` does not compile under v0.24.4 (a `??` fallback typed `Byte` against `Int`, and an ambiguous call in `hex.saw`), which is SO-167's to fix, and SO-167 has no patch yet. The sawlang lead's direct experiment (m1692) confirmed the layout cause both ways, and SO-167's gate will run these cases under v0.24.4.

**Contention by construction:** with `arena_arrive` never counting, both cases loop until the harness times out (red, 2 of 2), as their comment says. `arena_churn`'s final `sos_arena_contended() == 0` check is then redundant, since the loop only ends once the count is above zero. It is harmless.

**An observation, not a hold:** `sos_arena_contended` and `sos_heap_contended` are exported from `rt/common`, so every process carries the two counters and an `is_locked` read before each acquisition, for the tests' sake. That is cheap, but it is runtime surface a test asked for. If you'd rather keep it out of shipping images, a test-only build input would do.
