## Description

**The ESP32-S3's read-only board probe: unit A of the PSRAM design (SO-102), with the reads of the driver design's stage 0 (SO-77).** The user answered yes to the PSRAM design's questions on Nov 14, among them that its read-only first stage is folded into the driver work's board probe.

**What is built.** One harness kernel, `s3_mem_probe`, whose `kmain` loads registers, prints them and halts. It is the PSRAM design's stage P0 (`.claude/lead/so102-design.md` in the lead's checkout, section 9, "P0", which lists every line it prints and what each decides; sections 1.1, 3.1 and 4.1 say where each word lives and why it matters), plus the words the driver design's stage 0 reads that P0 does not already (`.claude/lead/so77-design.md` section 8.3, "Stage 0", its first list only): `PERIP_CLK_EN0`, `PERIP_RST_EN0`, the IO MUX words of pins 14, 21, 41, 42 and 47, and `RTC_IO_RTC_PAD21` bit 19.

**The rule of this image: it reads, and writes nothing beyond what every image of this tree writes at `_start`.** No `intc_init`. SYSTIMER is neither started nor read (a read takes a write of its snapshot bit). No command on the memory-SPI bus, no MMU entry touched, no pad or GPIO register written, no interrupt routed, no peripheral clock turned on. The driver design's stage 0 goes on to write (the CCOUNT measurement against SYSTIMER, the source-16 check through `STATUS_W1TS`, LEDC's timer): **none of that is in this unit.** It is a second image, for later, on the user's separate word.

- Every address the probe loads is named by a constant with the source it comes from (the register's name in ESP-IDF's `soc` headers, or the ROM symbol), in one place, and each is checked against that source by you, not copied from the design: where the design's address or field differs from the header at ESP-IDF v5.4.1, say so and stop.
- A check that the image is what it says: the probe's object code contains no store to a peripheral address. Find the simplest thing that holds it (the harness kernel is small enough to read its disassembly in a test, or the probe goes through one `load`-only accessor and the build shows no other access), and say what you chose.
- The smoke case (`make sos-smoke-esp32s3`) asserts the emulator's values where the design says what they are (SPI0, IO MUX and cache words read 0, SPI1 as section 1.1, the eFuse word with the smoke's eFuse file if the runner has one; if it has none, assert what the emulator gives and say so) and ends at `SOS-S3: halt pass`. Values the emulator does not model the same way as the part are printed and not asserted.
- `hal/xtensa-esp32s3/ABI.md` gains a section that lists the probe's lines, what each word decides, and a table for the part's values, with the cells empty until the board run fills them: the unit does not guess them.
- The flashable image: `tools/sos_runner.py --board esp32s3 --emit-flash s3_mem_probe --out PATH` builds it. Report its SHA-256 and the expected text for the board request. Nothing is flashed by this unit.

**Not in this unit:** any write to the part beyond `_start`'s; the command layer (unit B); `[clock]` in a board description (it does not exist until the description formats do; the probe's values are what will fill it).

**Lead: SO-109.p1 is up.** A harness kernel, `tests/xtensa/s3_mem_probe.saw`, that loads the registers the PSRAM design's stage P0 and the driver design's stage-0 reads name, prints them and halts. Gate on the implementer's machine at v0.24.0: 806 / 6 / 42 (main's 41 S3 cases and this one) and 1 board-only not run.

**Read-only by construction.** Every peripheral access goes through one accessor whose view is `UnsafeMemory<Reg, Device>` with a `ReadOnly<UInt32>` field, so the compiler refuses a store through it (shown: a store in the accessor's body is refused with `memory.read-only`). A runner check (`check_read_only_probe`, case key `read_only_probe`) refuses the source before the build unless it holds exactly that one view, no `.write(` and no HAL call but `exit_pass` (shown red with a second view). Not shown red: the HAL-call rule. The probe calls no `intc_init` and starts no SYSTIMER; the console is the only other writer, as in every image.

**Every address checked by script against ESP-IDF v5.4.1's headers;** none differs from the designs. One word is not from a header and could not be checked: the ROM's dummy-cycle pointer at 0x3FCE_FFE4, which the probe follows only if it is a word-aligned SRAM address. The design's "cache words read 0" on the emulator is not quite right (`dcache_autoload` reads 0x8, its reset value); the smoke asserts what the emulator gives and prints, without asserting, what the part decides.

**Other images unchanged:** `boot`, `irq_takeback`, `kill_churn`, `root_server_boot` flash images keep their SHA-256.

**For the board** (after merge, on the user's word in the reviewer's session): `s3_mem_probe.bin`, 2,107,392 bytes, SHA-256 `ce5fe4cf88d14af9961b05a2b0c4ee3e26b8f8e15934cb207c9f2de82a9ed0eb` at v0.24.0; capture 10 s; the expected text with the part's values marked is in the patch's §15 of ABI.md. The clock words should agree with §14h.

**Not loaded, offered:** the eFuse's third PSRAM-capacity bit (`PSRAM_CAP_3`, bit 19 of `EFUSE_RD_MAC_SPI_SYS_5_REG`), which matters only for a 16 MiB part.
