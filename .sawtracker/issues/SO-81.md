## Description

## Ruling (user, Nov 12)

"Ideally, no test should check anything about run time or wall time. That
skews when the host machine is under load and so is inherently flaky."

No case asserts a value that depends on how long something took on the host:
an elapsed time, a count of timer fires or ticks that accumulated while the
program ran, or an order that only holds if one thing finishes before a clock
moves. The emulators' clocks follow host time, so each such assertion fails
when the host stalls.

## What prompted it

`timer_interval` failed once on the gate, on riscv32-flat, in the run of
SO-71.p1 r1, and passed on the retest of the same commit:

```
SOS interval: tick two fires=2 ackfree=1
SOS interval: coalesced=0          <- the case asserts coalesced=1
```

Its third phase spins until the kernel's clock has advanced several timer
periods, then waits and asserts the fire count is above one
(`tests/timer-interval/src/main.saw`). A stalled emulator jumps the clock,
ends the spin at once, and the wait can arrive before a second expiry was
serviced. That reading is the lead's and is not confirmed by a probe.

## Scope

1. **An inventory** of every asserted line whose value depends on host time.
   Known candidates, to confirm or clear:
   - `timer_interval`: `coalesced=1`;
   - `timer_oneshot`: `fires=1 slept=1` and `rearmed woke fires=1`;
   - the C3 smoke's `timer` case: five lines `tick N key=37 fires=1` and
     `slept=1`. A periodic Timer whose waiter is late by one period reads
     `fires=2`;
   - `thread_preempt`: the three asserted crossings need ticks to land while
     both workers still have work;
   - any case that compares two clock reads or bounds a wait by a deadline.
   CLAUDE.md already lists three cases with timing-dependent output that is
   printed and not asserted; the inventory checks that list is complete.
2. **For each, a replacement that asserts the property, not the timing.**
   What a Timer case can claim without a stopwatch: a wait returned at all
   (the wake happened); a count is at least one; a count is consumed by the
   wait (cancel, re-arm as a one-shot, wait: that count is exactly one,
   which the case's own last phase already does); a later reading is not
   below an earlier one. Where the property needs "more than one expiry
   accumulated", make the program wait on a second observable that says so
   before it reads the count, so it is true by construction.
3. **A kernel question the first item may raise:** whether a Timer's fire
   count is one per serviced expiry or one per elapsed period when delivery
   is late. Spec §2.6 says expiries coalesce into the count. If a late
   delivery can report fewer fires than periods elapsed, say which the spec
   means; that is a clarification for the user, not something to settle in a
   test.
4. **CLAUDE.md's Testing section states the rule,** and its paragraph on
   timing-dependent output is brought in line with what the inventory found.

## Acceptance

- [ ] the inventory, one row per assertion, with the property it should
      assert instead
- [ ] no asserted line in the suite or the C3 smoke depends on host time
- [ ] each changed case still fails under the mutant it failed under before;
      a case that guarded a property through its timing must guard it some
      other way, or the report says the property is no longer covered
- [ ] the rule in CLAUDE.md
