## Description

## Finding (the gate run of SO-71.p1 r1, Nov 12)

`timer_interval` failed once on the gate, on riscv32-flat, and nowhere else:

```
SOS interval: tick one fires=1
SOS interval: tick two fires=2 ackfree=1
SOS interval: coalesced=0          <- the case asserts coalesced=1
SOS interval: drained fires=1
SOS interval: done
```

The same commit passed the full suite on the lead's machine minutes earlier,
and the patch under test does not change this case's path (it boots
`kernel/main.saw` with the tick off, as before).

## What the case assumes

Its third phase spins in user mode until the kernel's clock has advanced by
`SPIN_NS`, several timer periods, and then waits, asserting the wait answers
with a fire count above one (`tests/timer-interval/src/main.saw`). CLAUDE.md
already lists this case's `fires=` values as timing-dependent and unasserted;
`coalesced=` is derived from the same count and is asserted.

The clock follows host time. If the emulator's CPU thread is stalled by the
host across that window, the clock jumps, the spin ends at once, and the wait
can arrive before more than one expiry has been serviced. That is the lead's
reading of the failure; it is not confirmed.

## To settle

- Whether a Timer's fire count is one per serviced expiry or one per elapsed
  period when delivery is late. Spec §2.6 says expiries coalesce into the
  count; if a late delivery can report fewer fires than periods elapsed, say
  which the spec means.
- Then make the assertion independent of the host: for example, spin until
  the count itself is known to exceed one by a second observable, or assert
  the property on a path that does not race the emulator.

## Acceptance

- [ ] The cause, shown by a probe (a deliberately stalled emulator, or the
      interrupt log of a failing boot).
- [ ] The case no longer depends on host timing, or the kernel is fixed if
      the count was wrong.
