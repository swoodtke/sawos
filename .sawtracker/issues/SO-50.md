## Description

## Ruled design (user, Nov 9)

A new `SystemRight.ProcessObserve` gates two System ops:
- `ProcessNext(cursor)`: iterate processes for a ps-style tool, answering one
  process's handle and the next cursor.
- `ProcessByPid(pid)`: the only op that accepts a pid (pid issue). A pid that
  no longer names a process answers a status.

Both mint the **observe set** (`Wait | Stats`), capped by the caller's ceiling
(SO-40), the same set as the sender handle. The lookup is the indexed form of
the walk, so it adds no authority beyond the iteration.

Ordinary servers identify clients through the sender handle without this right;
only system tools (ps, a debugger) hold it.

To settle in the brief: whether `Gone` processes appear in the iteration, and
the status for an unknown pid.

## Sequencing

After the pid issue. The brief is written at dispatch.

**Lead, Nov 12: the spec is drafted and held for the user's review.** One
commit that changes `spec.md` only (146 lines added, 39 removed), in the
lead's worktree, not uploaded.

### What it specifies

- **`SystemRight.ProcessObserve`,** in root's default System rights; the
  convention mask a launcher builds a child's System sibling with withholds
  it.
- **`SystemOp.ProcessNext(cursor)`:** the cursor is a pid, in a doubleword of
  caller memory. The op answers the process with the smallest pid above the
  cursor, writes that pid back and returns the handle. A walk starts at 0. At
  the end it answers `Drained` and writes nothing. The kernel keeps no walk
  state.
- **`SystemOp.ProcessByPid(pid)`:** answers what a walk would answer for that
  pid. A pid the record table does not hold (reclaimed, never assigned, or
  zero) answers `Revoked`.
- **Both mint the observe set** (`Wait | Stats`), capped by the caller's
  Process ceiling, with no keep mask.
- **What a walk guarantees:** every process whose record exists for the whole
  walk is answered exactly once, in increasing pid order; one created
  mid-walk is reached before `Drained`; it is not a snapshot.

### Decisions the user has not ruled

1. **The pid crosses the trap in memory,** a doubleword, as `Timer.Arm` and
   `Clock.Now` pass 64-bit values. Alternative: two registers.
2. **The cursor is a pid,** so no record index reaches a caller.
3. **`Drained` is the walk's end and is not final:** the same cursor later
   answers a process created since. Alternative: a new status.
4. **Dead processes still held by someone are answered,** as the lead
   proposed: they are what fill the record table. The sender-handle op
   answers `Revoked` for a dead sender; the spec says why the two differ.
   Alternative: live processes only.
5. **An unknown pid answers `Revoked`,** `Sender`'s word. Alternative: a new
   "no such process" status.
6. **Zero answers `Revoked`,** as data, since an empty stats row reads zero.
   Alternative: a `BadArg` fault.
7. **A created, never-started process is answered,** and a held observe
   handle keeps it alive. Alternative: started processes only.
8. **No keep mask** on either op.
9. **Root holds the right by default.**

### Flagged for the implementer

Each call scans the record table, so a full walk costs the table's capacity
per step; the spec states the cost and sets no limit. A ps cannot tell a
created process from a running one: the status word reads `Running` for both.

Requested changes on patch SO-50.p1 (revision 2)

**Changes requested (rev 2): wording only. No decision is misstated, and the walker's key rule is right.** Each item is a sentence an implementer could build the wrong thing from, or that says something the kernel does not do.

**What holds.** The nine decisions are each stated once and restated consistently. A refused mint writes nothing, so the cursor never passes a process the caller got no handle for, and `Drained` leaves the doubleword as it was. The walk's guarantees follow from the mechanism: the cursor only increases, a pid above every assigned pid goes to each create (`assign_pid`), and a second walker shares no state. The rebase kept every marker on what is unbuilt and none on what is built; the kernel has no `ProcessNext`, `ProcessByPid` or `ProcessObserve`.

**1. §2.8, "What they answer": "A record nothing names is reclaimed at once, so neither op ever answers one."** Not true of a running process: `reclaim_process_record` says "A running process is never reclaimed however far its count falls", and a started child whose launcher released its handle is exactly that. The bullet's first sentence does answer it ("a `Created` or running process"), but this one reads as a filter on names, and an implementer who scans for `refs > 0` gives a `ps` that misses every process nobody holds.
   - Say which records it is about: a `Gone` record is reclaimed when nothing names it and a `Created` process is torn down then (§2.7), so neither op answers either; a running process is answered whatever names it.
   - The same in the answers bullet: "asking again answers the same process if its record is still held" should be "if the table still holds it".

**2. §2.8, "What a tool reads through the handle": the ceilings of a dead process.** "With `Stats`, the pid and the trap counters, live or final (§2.7), and the rights ceilings (`ProcessOp.Ceiling`)", and a `ps` "shows each process's ... counters and its ceilings". §2.7 says `Ceiling` through a `Gone` process's handle answers `Revoked`, and the walk answers `Gone` processes. "and, while it lives, its rights ceilings."

**3. The doubleword's alignment.** "Then the doubleword: a misaligned address ... terminates the caller as every copy door does (§2.2)". After "doubleword" that reads as eight bytes; the copy doors ask for a word (`copy_out_check`, §2.2), which is what SO-49.p2's records now say in so many words. "an address that is not word-aligned". The two rows in §2.8's op table, `ProcessNext(cursor)` and `ProcessByPid(pid)`, also read as register arguments where decision 1 puts both in memory; "(address of ...)" or a word in the row.

**4. §2.7: "The one op that accepts a pid is `SystemOp.ProcessByPid`"**, two bullets above "as the cursor of a process walk", and §2.8's "The cursor is a pid". Both come from the approved design, so only the wording has to give: "the one op that answers the process a given pid names".

**5. A created process reads as running.** A `Created` record's status word is `Running` (`ProcessCreate` writes `exit_kind = Running`), so a tool cannot tell a process never started from one running. The lead's notes flag it for the implementer; the spec promises a `ps` "whether it has ended and how" and a reader will expect the other distinction too. One sentence beside it.

**6. §2.7, "The default set":** "(root's, `ProcessSelf`'s and `ProcessCreate`'s; the sender handle mints the observe set, below)" is the one list of observe-set minters the patch did not reach; the others name the walk and the lookup.

Low: "so today no op accepts a pid" carries a current-state word the marker already says.
