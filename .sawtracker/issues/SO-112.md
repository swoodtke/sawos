## Description

**Windowed threads on the ESP32-S3: the kernel stays call0 and learns to run windowed code beside it (the networking design's unit K1).** The user ruled on Nov 14: "build the windowed support now. then get the pll working." The radio libraries, the ROM and the ROM's libc are windowed; with this unit a process may be built windowed, and the kernel itself may call a windowed ROM function through a small stub with real window handlers under it.

**Design first (user ruling, Nov 14: "get the air to review the windowed mode design before implementing").** A design document for this unit is written, published as a tracker doc and reviewed by the reviewer before any of it is built. What follows is the unit's scope, which the design fills in: the trap entry and restore instruction by instruction, the thread start state, the handlers, the double-exception rule, the stub by which the call0 kernel calls a windowed ROM function, what was run on the emulator to check each, and an attack on itself.

**Where it starts.** `SO:networking` (in the lead's checkout: `.claude/lead/so103-design.md`), sections 3.1 (option (a), "What the kernel needs", its six items), 3.2 and 3.3; and `hal/xtensa-esp32s3/ABI.md` §5a (the six window vectors, fatal today), §7c (the trap frame), §7d (what the windowed ABI adds) and §7f (interrupts are masked in the kernel).

**What is built**, all in the S3's HAL; nothing in `kernel/core` knows about windows:
1. **The six window vectors** (overflow and underflow at 4, 8 and 12) become the spill and fill handlers the Xtensa ISA defines, and the Alloca exception (cause 5, `movsp`) is handled. They run in the faulting thread's own context with EXCM set and make no kernel entry. **Written here from the ISA reference** (each is a fixed handful of loads or stores to the frame's base save area followed by `rfwo`/`rfwu`), with the reference cited in ABI.md; not copied from another kernel's source.
2. **The trap frame carries the whole register file**: the current window as today, the other 48 physical registers, `WINDOWBASE`, `WINDOWSTART`, and PS's window fields. The kernel never writes a user's stack. The frame stays inside `THREAD_FRAME_STRIDE`; say what it grows to.
3. **Every S3 thread takes the 64-register path**, call0 or windowed: one trap entry, one restore, one switch. A thread starts in a state both conventions can run from (`PS.WOE`, `CALLINC`, one `WINDOWSTART` bit, a base save area under its stack top): a call0 entry never rotates the window, and a windowed entry's `entry` finds what it needs. If that cannot be one state, stop and say what a process would have to declare.
4. **A double exception whose `DEPC` lies in the window vectors** (a windowed thread whose stack is not mapped where a spill writes) is that process's fault with the reason the spec gives a bad access, not a kernel stop.
5. **The kernel is still call0 and still never takes a window exception itself.** Trap entry leaves the user's window state saved and runs the kernel on one window, as today. State how the entry gets from an arbitrary `WINDOWBASE` to the kernel's call0 world and back without a window exception firing before the frame is safe.

**Cases, in the S3 smoke** (windowed C built with the Espressif clang's windowed option; a package's `[sos.xtensa-esp-unknown-elf] target-features = "+windowed"` is believed to build one whole: confirm):
- overflow and underflow forced at each call size (4, 8, 12), to a depth past the register file, the values checked on the way back out;
- alloca (`movsp`) in a frame whose caller has been spilled;
- the tick taken inside a deep windowed chain, and the chain's values intact after it;
- two windowed threads switching, each deep in its own chain;
- a windowed process and a call0 process side by side, and a call0 process's transcript unchanged from main for every existing smoke case;
- a windowed thread whose spill faults (its stack unmapped or read-only below the frame): the process is faulted, the machine goes on;
- a system call made from deep in a windowed chain, through a windowed stub, with its arguments and result right.
Each line of the new trap path is shown to hold by a mutant where one can be made (a register of the 48 not saved, one not restored, `WINDOWSTART` or `WINDOWBASE` not restored, a handler storing to the wrong slot at each call size).

**Windowed Saw is not part of this unit.** The design's rule stands: no Saw is compiled windowed for a process until sawlang's freestanding suite has a windowed Xtensa row (asked of the sawlang lead on Nov 14). The cases here are C; say in the hand-back what a windowed Saw case will need once that lands.

**What it costs.** Every S3 thread switch and trap now saves and restores 64 registers. Measure it on the emulator in instructions where that means something, and build `kill_churn_profile` for the board at `rom` and `xtal40` so the cost can be read against the numbers on SO-110 (a flash needs the user's word in the reviewer's session; nothing is flashed by this unit).

**Not in this unit:** FP and `BR` state per thread (K2); the PLL (it follows, and calls the ROM's windowed `rom_i2c_writeReg*` through a stub that relies on these handlers); anything in the radio process.

**Lead: the design is published as `SO:windowed-threads` (revision 1) and with the reviewer**, on the user's word that it is reviewed before anything is built. The prototype diff is chat file f105 and in the lead's scratchpad (`SO-112/prototype.diff`); a copy of the document is `.claude/lead/so112-design.md`.

The designer's verdict: the approach works on the emulator and the scope stands. One start state serves both conventions; the trap path saves all 64 registers (87 to 213 instructions a round trip, the frame 104 to 304 bytes inside the 512-byte stride); a fault inside a window handler is the process's; the kernel can call a windowed ROM function through a stub. The S3 smoke on the prototype is 46 cases, five new, and thirteen mutants were all red after two tests were strengthened. The ISA manual could not be fetched, so the rules it states are from memory and each one relied on is confirmed by a run: the reviewer is asked to check them against a real copy.

Six questions for the user (section 15), each with a recommendation; the one that reaches past this unit is where the ROM's phy function table lives (inside a pool a case can give to processes), which decides when the kernel may call the ROM.
