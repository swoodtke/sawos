## Description

**From the user, Nov 14, in three messages while reading the image and packaging design (SO-95):**
- "Can we override the process handle table size per-process? So large processes can have more and smaller processes can use the smaller default limit?"
- "We could have other per-process limits, e.g. the amount of RAM it can allocate, etc."
- "And maybe each process's default rights? All of this can be later since it's not strictly needed for the useless box but will be as we scale the images, e.g. support networking."

**So this is deferred, not dropped: it is wanted before images grow past the box, and networking (SO-103) is the first that needs it.** The box runs on SO-95 as ruled: a 32-entry handle table on every board, quota defaults per board, one pool.

**What it covers,** with the lead's first reading of each (written up on SO-95 the same day; none of it ruled or reviewed):

1. **The handle table's size per process.** Today the table is two arrays in every process body, both `MAX_HANDLES` long, so every process pays for the largest. Proposed: sixteen entries stay in the body, and a process whose `Handle` allowance is set higher gets an extension block from a kernel slab (its storage one of the image's linked-in areas), attached when the launcher raises the allowance through the quota door, so a machine with no block left answers at setup. The radio process of SO-103 needs over fifty handles; this is what keeps every other process from paying for fifty.

2. **Counted limits per process.** Every process has a quota row per kind, all at the board's default. `ProcessOp.QuotaSet` (SO-95's unit U5) is the door that sets them per process. What is left for this issue is the image side at scale: a driver's declaration stating its needs, the image overriding, the builder summing them against the board.

3. **How much RAM a process may allocate.** Not a counter: a process allocates only from a pool it holds, so its limit is the size of the pool it is given. For an image that is a `pool` key per process, a boot row of kind `Pool` per process, and the stock root handing each to its process alone; no kernel change. For a launcher that makes children at run time it is the sub-pool (`Pool` ops 2 and 3, reserved in spec §2.5 with revoke), which this issue should decide whether to build.

4. **Each process's default rights.** The kernel already has rights ceilings per kind per process, which a launcher narrows before a child starts (`Process.restrict_rights`), and SO-95's image format has a place for them (`ceilings`). What is missing is a considered default: today a child's ceilings are whatever its launcher leaves. Proposed for the design: a process's declaration states the rights it needs per kind, the stock root narrows every ceiling to that before start, and an image may narrow further but not widen past what the declaration asks.

5. **Also in reach, to be placed by the design:** a per-process stack length (one length per board today), and whatever the priority scheduler (spec §7, needed by SO-103) wants stated per process.

**Shape of the work.** A short design first (it changes the kernel's contract in 1 and possibly 3, and the image formats in all), to the user and the reviewer; then units. It follows SO-95's units U5 (the quota door) and U6 (declarations and the stock root), and comes before SO-103's radio process.
