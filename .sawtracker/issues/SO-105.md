## Description

**From the user, Nov 14, in three messages while reading the image and packaging design (SO-95):**
- "Can we override the process handle table size per-process? So large processes can have more and smaller processes can use the smaller default limit?"
- "We could have other per-process limits, e.g. the amount of RAM it can allocate, etc."
- "And maybe each process's default rights? All of this can be later since it's not strictly needed for the useless box but will be as we scale the images, e.g. support networking."

**So this is deferred, not dropped: it is wanted before images grow past the box, and networking (SO-103) is the first that needs it.** The box runs on SO-95 as ruled: a 32-entry handle table on every board, quota defaults per board, one pool.

**What it covers,** with the lead's first reading of each (written up on SO-95 the same day; none of it ruled or reviewed):

1. **The handle table's size per process.** Today the table is two arrays in every process body, both `MAX_HANDLES` long, so every process pays for the largest. Proposed: sixteen entries stay in the body, and a process whose `Handle` allowance is set higher gets an extension block from a kernel slab (its storage one of the image's linked-in areas), attached when the launcher raises the allowance through the quota door, so a machine with no block left answers at setup. The radio process of SO-103 needs over fifty handles; this is what keeps every other process from paying for fifty.

2. **Counted limits per process.** Every process has a quota row per kind, all at the board's default. `ProcessOp.QuotaSet` (SO-95's unit U5) is the door that sets them per process. What is left for this issue is the image side at scale: a driver's declaration stating its needs, the image overriding, the builder summing them against the board.

3. **How much RAM a process may allocate.** Not a counter: a process allocates only from a pool it holds, so its limit is the size of the pool it is given. For an image that is a `pool` key per process, a boot row of kind `Pool` per process, and the stock root handing each to its process alone; no kernel change. For a launcher that makes children at run time it is the sub-pool (`Pool` ops 2 and 3, reserved in spec §2.5 with revoke), which this issue should decide whether to build.

4. **Each process's default rights.** The kernel already has rights ceilings per kind per process, which a launcher narrows before a child starts (`Process.restrict_rights`), and SO-95's image format has a place for them (`ceilings`). What is missing is a considered default: today a child's ceilings are whatever its launcher leaves. Proposed for the design: a process's declaration states the rights it needs per kind, the stock root narrows every ceiling to that before start, and an image may narrow further but not widen past what the declaration asks.

5. **Also in reach, to be placed by the design:** a per-process stack length (one length per board today), and whatever the priority scheduler (spec §7, needed by SO-103) wants stated per process.

**Shape of the work.** A short design first (it changes the kernel's contract in 1 and possibly 3, and the image formats in all), to the user and the reviewer; then units. It follows SO-95's units U5 (the quota door) and U6 (declarations and the stock root), and comes before SO-103's radio process.

**Lead: the design is written and published as the tracker doc `SO:process-limits`, revision 1** (against main 6ca48b20). It changes nothing in the repository. The owner and the reviewer read it before anything is built.

**Verdict.**
- **What is built:**
  - a pool per process as its RAM limit, through heaps;
  - the quota door and declared rows;
  - a declaration's System rights.
- **What is not built:**
  - **Per-kind rights ceilings from a declaration.** The kernel has `RestrictRights`, but the stock root never calls it. Windows, lines and outlets go out with every right root holds.
  - **Children's declared rows summed against the image's slabs.** `check_plan` counts only root's own objects.
- **The handle table.** The 32-entry table stays in each process body. A process whose `Handle` row is set higher gets 16-entry blocks from a new slab, `SlabKind.HandleBlocks` with floor 0:
  - at most 6 blocks, so the longest table is 128;
  - `QuotaSet(Handle)` on a `Created` child attaches them, or answers `NoResource` and changes nothing;
  - blocks stay until teardown;
  - lookups below 32 run today's code.

  Root gets its blocks from the image: the slab block's reserved word, and region table version 6. The boot set grows with the table (`BOOT_SET_CAPACITY` 32 → 64).
- **Rejected alternatives.**
  - A larger `MAX_HANDLES` would cost 1 KiB per S3 body, so 8–9 KiB for a networking image; BLE wouldn't fit at all.
  - A variable table chosen at create would need a run allocator, copies and an indirection on every lookup.
- **Costs.** Blocks cost the networking image about 1.75 KiB and the box 224 bytes.
- **The builder** derives the block total and root's table size. The radio writes only `handles = 64`.
- **Ceilings.** An optional `[ceilings]` table in `process.toml`, complete when present. Records stay within it, and the stock root calls `restrict_rights` before its first give.
- **Placed elsewhere.**
  - A per-process stack length becomes its own issue; it needs sawlang's `imgformat`.
  - The priority map goes to SO-148, with a `Created`-only op recommended there.
  - Sub-pools stay with SO-146.
- **Units.**
  - U1: handle blocks for children (L, Opus).
  - U2: root's blocks and version 6 (M, Opus).
  - U3: builder derivations (M).
  - U4: ceilings (M), which can run beside U1.
  - U5: summed rows (S).

**Owner's questions** (§ questions), with the design's recommendations:
1. Handle blocks, or a larger `MAX_HANDLES`? Blocks, on every board.
2. A longest table of 128? Yes.
3. Should the boot set grow to 64 (384 B more start-up stack per `main` program)? Yes.
4. Keep blocks until teardown when the row is set lower? Yes.
5. May an image narrow ceilings past the declaration? Declaration only for now.
6. Summed rows: derive the slab totals, or refuse a short image? Derive.
7. File the per-process stack length now, to build after U1–U5? Yes.
8. Lower the S3's 32-entry body table later? Not now.

**Lead: U1 found the design's `BOOT_SET_CAPACITY` cost was wrong.** The design said 384 more bytes in `_start`'s frame.
- **Measured:** the start-up keeps several copies of the `BootSet` alive (the init's `Result`, `adopt`'s local, the `Boot` temporary, and `start`), all in one frame that lives as long as the process. - **The failures:** at 64, nine gate cases overflow their stacks. On arm64 they are `stock_root`, `stock_heap`, `stock_root_heap`, `stock_many`, the two pl011 UART cases, `console_silent` and `main_start`. On riscv32 it is `main_start`'s second-thread leg.
- **At 32,** with everything else in place, all nine pass.

**Plan:** U1 lands at 32, and the raise to 64 waits for a small unit that restructures `rt/main` so only one `BootSet` stays alive, for example in a static. That unit runs before U2 and U3 need the raise. The owner ruled 64 on the old figure and is being told.

- **What would pin them:** `stock_record_rights` (or a sibling image) giving one record of each shape with a narrowed `rights`, the child printing each handle's rights. A setup-write window, a sibling, a carve, a line, a serve and a client would do.

**2. A heap needs `boot-handles` whether or not the program is written with `main`.** `check_runtime` asks `boot-handles` only under `main`.
- **Why it's needed:** a heap's pool is adopted only inside `BootSet`'s drain (`kernel/sysapi/src/bootset.saw`, `adopt_heaps`, called from `BootSet.init`). The kernel faults a drain without `BootHandles` `AccessDenied` (`dispatch.saw`, `BootHandleNext`).
- **What passes today:** a program with `_start`, a `[heap.default]`, and a `[ceilings]` whose `process` lacks `boot-handles` passes the builder, then ends at its first drain.
- **The builder allows that shape:** it lets a program not written with `main` declare a heap. The tree's three heap programs all use `main`, so no case meets it yet.
- **The fix:** move the `boot-handles` need into the heap branch as well, with a refusal case.

**3. The new spec text claims more than §2.7 allows.**
- **The claim:** §12's "Ceilings and record rights" says "so a process holds no more of a kind than its declaration says, whether it mints the handle or is given it". `declaration.saw`'s doc says `[ceilings]` "narrows the rights the process may hold".
- **What §2.7 says:** "A ceiling therefore bounds what a process can obtain from the kernel, not what it can be given". A handle carried in a pipe message lands uncapped (`refs.saw`, `mint_staged` → `mint_handle`).
- **So:** a process with `event = ["receive", "wait"]` can hold a `Signal` Event a peer sends it. What holds is narrower: the launcher's gives are within the declaration, and so is every handle the process mints. Saying that, and pointing at §2.7 for the rest, would make the text true. The radio's rights table becomes `[ceilings]`, so a reader of §12 will lean on this sentence.

**Checked and holding:**
- **Every give arm uses `r.keep`**, and `check_record_rights` keeps an explicit `rights` inside the ceiling. `keep_word` falls back to the ceiling under `[ceilings]`.
- **The heap's pool** goes with `HEAP_POOL_KEEP`, which the runtime check forces inside the `pool` ceiling.
- **The System sibling** stays outside the table, by design.
- **`waiter_create`** appears in `rt/main` only in a doc example. The runtime spends nothing beyond the list but (2).
- **Under a hand-written root**, a child's declaration is never read, `[ceilings]` included. That matches `[quota]` and the records, and the spec's "userspace convention" label.
