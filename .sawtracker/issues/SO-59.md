## The change

0. **Threads become givable in this unit** (a scope addition recorded on
   SO-59), so no Thread handle outlives its owner without the invalid state.
   Follow SO-58's Event pattern exactly (merged; read its diff in `git log`):
   - `thread_rights()` gains `Transfer`;
   - `BootHandleKind.Thread`, plus `boot_kind_of`/`msg_kind_of`;
   - the typed tier: a `PipeHandle` case, the carrier, `decode_handle`,
     `Process.give(thread:, tag:, keep:)` with the status hand-back, and the
     `BootHandle` accessor;
   - the spec markers for Thread's givability.
1. **Thread slots are counted.**
   - Every Thread handle entry, and any other counted reference to a Thread (an
     attachment or a staged message, once Threads are givable; that unit,
     SO-58, may land before or after you), holds a reference.
   - Wire `ObjType.Thread` into `ref_object`/`unref_object`/`free_object`
     (`kernel/core/refs.saw`) like the other counted kinds.
2. **Freeing.**
   - A thread that has not exited is never freed by losing its last handle (its
     slot is what it runs in).
   - A thread whose count reached zero while it ran is freed when it exits or is
     invalidated.
   - An `Exited` thread is freed when its count reaches zero.
3. **`Exited` wins.**
   - A thread that exited normally keeps its exit code in its slot. A late
     `Join` through any handle reads it, even after its process is `Gone`, and
     the slot is held while a handle names it.
   - Today the teardown frees every thread slot of the process whatever names it
     (`kernel/core/sched.saw` `end_process`'s thread sweep). Change it to keep
     an `Exited` slot that is still referenced.
4. **Invalidation at process death.**
   - A thread that has not exited when its process dies is **invalid**: it is
     unscheduled, and its slot keeps nothing for `Join`.
   - `Join` on it answers `SosStatus.Revoked`, as do the other thread ops (§2.10
     "What every op covers": rights and argument checks fault first, and
     `Release` works).
   - A thread parked in `Join` on a thread that becomes invalid is woken with
     `Revoked`.
   - If Threads are waitable (attachments), an attachment fires as an
     invalidated waitable does, a terminal level. Check whether they are today.
   - The invalid slot is freed when its count reaches zero, or at the teardown
     if nothing names it.
5. **Disown.**
   - At the teardown, every Thread that survives the death (an `Exited` one, or
     an invalid one still named elsewhere) gets `process = NO_PROCESS`, so a
     reused record's teardown sweep cannot match it.
   - Check every reader of `ThreadSlot.process` (scheduling, `calling_process`,
     the ready queue, the copy doors) and make sure none acts on a disowned or
     invalid thread.
6. **The `CURRENT_THREAD` comment and stranding** (sched.saw ~359,
   "This assumes the dying process is the caller"): make sure the new sweep
   keeps the running thread's handling correct. If a path still ends another
   process while a caller runs, say what happens.
7. **Quota:** a Thread's charge (`QuotaKind.Thread`) is refunded at
   invalidation or exit per §2.10's refund rule for bound kinds: at
   invalidation, while the ledger is still live or being cleared. Check what
   today's code does at exit, and keep the books balanced.
8. **Spec:** remove the markers this satisfies, in §2's Thread row and §2.10's
   not-yet list (the thread parts). Edit mixed markers down to what is still
   unbuilt. No issue numbers; 80 columns.

## Tests (probe first)

Model them on the `thread_*` and `death_*` cases. Each states its observable.
1. **Late join reads `Exited`.** A child's worker exits with a code, and the
   child gives (or sends) the worker's handle to root. The child then dies, and
   root joins and reads the code.
0. **Give and send.** A Thread handle given at boot and one carried in a
   message are both usable (`Join`), and a refused give hands the handle back.
2. **Invalid thread.** A thread still running or parked when its process dies:
   a held handle's `Join` answers `Revoked`.
3. **Freed at zero.** Thread slot capacity comes back after the handles go
   (count creates until refused, as other slab tests do).
4. **A running thread whose last handle is released** keeps running, and its
   slot frees at exit.

**Lead review, SO-59.p1: threads are givable and counted, survive their process `Exited` or invalid, and are freed at zero.**

**Mechanism.**
- **Counting:** `ThreadSlot.refs`, with Thread arms in `ref_object`/`drop_reference`/`free_object`. `ThreadSelf` refs the slot. Joiners are not references.
- **Freeing:** a thread that has not exited is never freed by losing its last handle. An `Exited` or `Invalid` thread is freed at zero, by a release or by the teardown sweep.
- **The invalid state:** a new `ThreadState.Invalid`. `invalidate_thread` wakes joiners with `Revoked`, refunds the quota and disowns the thread. `Join` and `Start` on an invalid thread answer `Revoked` after the dispatch checks. `Exit` and `Yield` stay `NotSelf`, the same rule as the §2.10 `Gone` self-only ops.
- **Teardown hygiene:** the dying process's threads come off the ready queue, every joiner list (`unjoin_process`) and its own Waiters' blocked lists before they are invalidated. Survivors are disowned.
- **Quota:** the thread row is now credited at exit or at invalidation; previously it waited for `quota_clear`. Spec §2.10 says so.
- **Givable:** `Transfer`, `BootHandleKind.Thread`, and the typed give/carry/decode/accessor in SO-58's shape.

**Implementer findings to note.**
- **"Freed when it exits" can't happen.** `Exit` names the thread through a handle, which is a reference, so an exited slot frees when that handle is released. In the typed API that is at process teardown, since `Thread.exit` never returns. It is documented on `Thread.exit`. Making it reachable would need `Exit` to consume its handle, which is an API/spec choice for the user.
- **`CURRENT_THREAD`:** the stranded-caller case for creation ops faulting a named process is unchanged, and the comment at the site now says so. SO-41 closes it.

**Probe (old kernel).** `give(thread:)` faults, and released exited threads keep their slots (`first=7 again=0`).

**Tests.**
- `thread_give`: a boot give, and an exited plus a parked worker sent back. Root's parked join is woken with `Revoked` at the child's death, the exited worker still joins as 82, and the invalid one answers `Revoked`.
- `thread_give_returns`.
- `thread_slots`: `first=7 again=7`.
- No existing `threads=` assertion changed. The field's meaning is written into §2.10.

**Runs.** The full suite passes locally (469 runs), plus the C3 smoke.

**Lead edit:** I wrapped one 81-column test comment line.

Requested changes on patch SO-59.p1 (revision 1)

**Air: SO-59.p1, changes requested: the exit leak now escapes the Thread quota (with a ruling pending), a false spec sentence, and a suspected late-mint path at teardown.** I found no use-after-free, double free or bad index in the new thread code. Every structure that can name a thread slot was enumerated (the table is at the end), and the counting is exact on every mint/release/give/send/refusal/close-all path.

**1. Exited workers keep their slots, and since the quota refund moved to exit, a child is no longer bounded by its Thread quota.** The `Exit` mechanism needs a user ruling.
- `Exit` resolves through a handle naming the caller (dispatch.saw:1614-1621). That handle is a counted reference (refs.saw:190), and `exit_thread` doesn't consume it (sched.saw:210-213).
- `Thread.exit(&self)` never returns, so its wrapper never releases it (thread.saw:69-72). Falling off the entry faults the process (system.saw:566-568), so there's no other exit.
- So every typed worker (`thread_self` then `exit`) holds one slot and one or two handle entries until its process dies, as your note says.
- **This patch makes it worse.** `exit_thread` now credits the Thread row (sched.saw:222), and limits.saw:402-409 accepts an uncharged `Exited` slot. Before, the row wasn't credited, so a child's thread-slab footprint was capped by `DEFAULT_QUOTA_THREADS` (4). Now it's capped only by `DEFAULT_QUOTA_HANDLES` (12): about 4-5 slots per child with the test idiom, about 9-10 with a lean worker.
- `MAX_THREADS` is 8 machine-wide, about 6 free once root and a child's main run. **One child can fill the slab, after which root's `thread_create`/`process_start` answer `NoResource`.**
- Whatever the user rules on `Exit`, credit the Thread row when the slot is FREED, not at exit, so a child's slab footprint is bounded by its Thread quota again.
- The ruling options: (a) `Exit` consumes the handle it names (`Thread.exit(move self)`); (b) `Exit` needs no handle; (c) the status quo, with the credit at free. For (a)/(b): the freed slot is still `CURRENT_THREAD` until the switch (`pick_next`'s deadlock arm, sched.saw:165, reads its `process`), and `exit_thread` reads `process` at :238 after the wake, so the free must be deferred past the switch, or `p` captured first.

**2. spec.md:77 and :1553 are false and unmarked: "a thread whose count reached zero while it ran is freed when it exits".** `Exit` needs a handle naming the thread, so its count is ≥ 1 at exit, and the slot is freed only when that handle goes. The patch removed the row's "not yet enforced" marker. ops.saw's wording ("frees once it has exited or been invalidated and nothing names it") is the true one.

**3. Suspected, pre-existing, at the site this patch edits: a mint into the dying table after the close-all has passed.** Please confirm or refute it with a trace or a case.
- The teardown removes the dying process's threads from the ready queue, the joiner lists and its own Waiters only AFTER the handle close-all (sched.saw:422-435). That contradicts sched.saw:372-375 ("a notification must never find a thread of the process being torn down").
- The candidate path: inside the close-all, `release_staged` of a staged one-shot handle, then `settle_exchange`, `notify_room`, `resume_call_room` (which stages a message), then `notify_ready(PipeOutlet)`. If the dying process serves that outlet's completion queue with a thread parked on its own Waiter, `deliver_take` mints handles into its table at indices the close-all already passed.
- Since SO-54 the body is then freed with those entries bound, and `process_create` relies on a reused body's table starting empty (dispatch.saw:1018-1026). **The next process in that body would inherit capabilities it was never given**, and a Thread handle can now be one of them.
- Suggested: move the three clears to just after `release_pending_calls`, and have the body free check (or clear) that every entry is unbound before the body goes back.

**4. Tests that would miss a regression:**
- No case uses a child's Thread quota (root's is unlimited), so the credit at exit and the credit at invalidation are unpinned. A double credit or a missing credit is caught by nothing.
- The ready-queue removal: no case kills a child with a runnable thread. Without the removal, an `Invalid` thread could run, reaching `load_domain(NO_PROCESS)`.
- The disown: no case reuses a record after a thread outlived its process.
- A dying process's thread parked JOINING another process's thread (the use-after-free direction for `unjoin_process`): in `thread_give` the child's join completes before the child dies.
- Free paths not run: `free_object` freeing an `Invalid` thread on release, the teardown sweep freeing another process's `Exited`/`Invalid` thread at zero, and `Start` on an invalid thread → `Revoked`.

**5. Nits:**
- refs.saw:223-226 says the zero test is "not defensive"; for the Thread arm (:374-378) it is, since it can only hide an undercount.
- sched.saw:484-486: on the last-thread `Exit` path the running thread is `Exited`, not "invalidated".
- dispatch.saw:553 says "a second reference"; for a child's main thread it's the first.
- spec ~1625-1628 (`threads=`) doesn't exclude a process's own thread freed inside the close-all, as `events=` does.
- sched.saw:41 is 81 columns.

**The structures checked** (all safe as written):
- the ready queue (cleared before invalidation);
- its own Waiters' blocked lists (another process's Waiter is unreachable: `waiter_rights()` has no `Transfer`, and `Wait` resolves in the caller's table);
- joiner lists (`unjoin_process` plus the waking of other processes' joiners);
- `Exchange.caller`/`call_pipe`/`call_claim` (`release_pending_calls` runs first, and `invalidate_thread` zeroes them);
- `CURRENT_THREAD`, trap frames, staged messages and handle tables (counted).
Index safety: nothing reads `ThreadSlot.process` as an index after the disown. The mutants that skip `unjoin_process` or skip waking joiners are caught by `thread_give`.

**Air: SO-59.p1 revision 2, approved.** Two text fixes are to be carried in the `Exit` follow-up, below.
- **The late-mint capability leak is fixed** (thanks for confirming the path). The clears now run right after `release_pending_calls`, before the close-all.
  - **The body-free check can't fire from userspace.** I had every way a handle can land in p's table after the close-all starts enumerated:
    - any syscall, a give, or `queue_boot_handle`: nothing runs during a teardown (no preemption point, interrupts only from user mode);
    - `wake_one_waiter`'s deliveries: they mint only into the woken thread's own process, and p's blocked lists are emptied first; another process's Waiter is unreachable, since Waiter rights lack `Transfer` and `Wait` resolves in the caller's table;
    - `wake_call_reply`/`resume_call_room`: cleared by `release_pending_calls`;
    - join wakes: mint nothing;
    - the top notify's cascades: run before the close-all, which then closes from index 0;
    - the later sweeps: reach only other processes' threads;
    - a rerun teardown: `body == NO_BODY`, so it's skipped.
  - `teardown_mint` reproduces the old order: under the check the machine halts, without it root's call hangs.
- **The new `drop_reference` Thread halt at zero is unreachable.** Every add and drop site was listed: mint/`ThreadSelf`/`MINT_OP`/move/stage add first, `release_carried` re-resolves the entry, and exit and invalidation don't touch `refs`.
- **Credit at free is exactly once on every path:**
  - an `Exited` thread freed by release credits its owner, or nobody once disowned;
  - one freed by the sweep credits a live ledger;
  - an `Invalid` thread is credited at invalidation only;
  - `exit_thread` no longer credits.
  - A live child's exited-but-named threads stay charged, so its slab share is bounded by its Thread quota, which closes r1's one-child-starves-the-machine problem.
- **The tests catch the mutants they claim:**
  - `thread_quota` catches a credit at exit, a missing credit, a double credit and a skipped disown;
  - `thread_hang` catches a skipped ready-queue removal and a skipped cross-process unjoin;
  - `thread_give` adds `Start` → `Revoked` and three free paths.
  - The one changed runner assertion (`handles=` 5 → 7) is explained by child-thread keeping two more handles.

**Carry into the `Exit` follow-up (text only):**
1. spec ~1611-1612 is now false: "only the shared kinds' frees test for no owner, a Thread's free crediting nothing". An `Exited` Thread's free credits through `credit_shared`; an invalid Thread's credits nothing.
2. `free_object`'s docstring (refs.saw ~505) says "`Mapping`, `Process` and `Thread` have no credit here", and `credit_shared`'s docstring still calls it the shared kinds' door only.

**For the user's `Exit` ruling:** with credit at free, a typed worker (`Thread.self()` + `Thread.exit()`) keeps its slot AND its Thread-quota row until the process dies, so a child can run at most 3 typed workers in its whole lifetime (quota 4, less its main thread). This is bounded, so the machine is safe, but it's a hard functional limit.
