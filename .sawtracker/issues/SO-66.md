## Description

## Proposal (Nov 10, discussed with the user)

Give the HAL a `zero_range(addr, len)` that the kernel's large clears call. The main one today is `long_zero` in `slab_donate`. Each architecture uses its cache-block zeroing instruction where it can.

**arm64: `DC ZVA, Xt`.**
- It zeroes one aligned block with no read-for-ownership.
- The block size comes from `DCZID_EL0.BS`, read at run time; never assume 64.
- If `DCZID_EL0.DZP` is set, fall back to stores.
- It works on Normal memory only; Device memory, or the MMU off, raises an alignment fault. The kernel's linear map is Normal, so the kernel can use it. EL0 use would need `SCTLR_EL1.DZE` and is not in scope.
- The unaligned head and tail are cleared with plain stores.

**riscv32: `cbo.zero` (Zicboz).**
- None of our targets has it today: the ESP32-C3 lacks it, and QEMU `virt` has it only with `-cpu rv32,zicboz=true` and `+zicboz` in the target features.
- So the riscv32 `zero_range` is the store loop for now, with a note on where Zicboz would plug in.

**Neither instruction uses FP/SIMD state,** so this keeps the kernel FP-free (see SO-4).

## Acceptance
- [ ] HAL `zero_range` on arm64 (`DC ZVA` with `DCZID_EL0` handling and a store fallback) and on riscv32 (store loop).
- [ ] `long_zero` and any other large kernel clears route through it. Keep the preemption points `long_zero` takes today.
- [ ] A test that donates a region with non-zero contents (unaligned start and length) and shows every byte of the installed slots reads as zero. Also force the `DZP` fallback on arm64, with a test hook or a mutation.
- [ ] The full suite and the C3 smoke pass.

Low priority. It is a performance improvement for large donations.
