**Using the ESP32-S3's second core: a design.**

The kernel is uniprocessor on every profile (spec §7), and the S3's core 1 is held in reset. The owner has projects that need both cores (Nov 26) and wants the design now.

**The design compares:**
- full SMP;
- an asymmetric second core for pinned real-time work;
- SMP with core affinity.

**It covers:** locking, the scheduler across cores, interrupts and IPIs, memory and the caches (including the flash switch's cache freeze), core 1's bring-up, the panic rule (stop the other core first), the API and image side, a two-core gate profile under QEMU, tests, and units.

Opus, design first; nothing is built before the owner and the reviewer read it.


<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":286,"created":"1795733822","id":"c2"} -->
**Design revision 1 is published as `SO:smp`.** It recommends SMP with process affinity: one kernel image under a big ticket lock, with per-core ready lists, tick, idle and reschedule IPI. A launcher places each process on a core, and a process never moves. Owner questions are pending.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":721,"created":"1795733902","id":"c3"} -->
**The owner's answers on design revision 1 (Nov 26):**
1. The projects need separate programs on separate cores (process affinity); one process spanning cores is not needed.
2. One big kernel lock, with the cross-core waiting measured on the board rather than designed away.
3. Timers are per core: a timer fires on the core of the process that owns it.
4. riscv32 runs every gate case on two harts, riscv32-flat stays on one, and arm64 SMP comes later.
The design's other questions take its recommendations unless the owner says otherwise: placement on `ProcessRight.BandMap`, the second stack sized from the stack-depth measurement, stall then reset on stop, arm64 later, and unplaced children on their launcher's core.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":140,"created":"1795733978","id":"c4"} -->
**Owner revision (Nov 26):** for the first stage, core 0 may handle all Timers, as revision 1 proposed. Per-core timers become a later unit.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":433,"created":"1795734329","id":"c5"} -->
**Owner proposal (Nov 26):** with one big lock, use one full kernel stack, shared and used only by the lock holder. Each core gets a small entry stack, used to save the user context and spin for the lock, before switching to the full stack; idle and the stop handler run on the small stack. Revision 3 evaluates it against the code: no frames live across a lock release, the waits for the other core, panic, and the entry-stack size.
