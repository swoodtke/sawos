## Description

## What this unit is

The memory model becomes pools and allocations. The design, its attack and
the reviewer's findings are the tracker doc `SO:split-and-slice`; **section
11, "The minimum build", is the brief**, and where it disagrees with
sections 1 to 10 it wins (the superseded passages are marked).

It replaces the model on main, where one `Memory` kind is both a pool and a
region, `split` works on a region in use, and grant rows follow the piece
that covers them (SO-91).

## The model (user rulings, Nov 13)

- **Hierarchical pools are the model.** A pool is what memory is allocated
  from; an allocation is what is mapped, holds a process, or is given. A
  pool will later be splittable into smaller pools, and revocable. "Both
  pool splitting and revocation can be added later. Let's do the minimum
  pool implementation now."
- **Built now:** the `Pool` kind with one op, `allocate`; `Memory` is an
  allocation and has no `split`; boot rows are typed in the region table
  (a child's image blob and destination are allocations, the pool row is a
  pool). No `slice`.
- **Reserved, not built:** `Pool.split` and a revoke: their op numbers and
  rights, and on a pool slot the `parent`, the lent range and the `depth`.
  Every allocation records its pool. Section 11.7 lists the invariants the
  minimum must keep so both follow without rework.
- **Any memory a process's grant lets it reach is a legal system-call
  buffer,** by a row the loader recorded or a row `map` installed, on every
  profile, judged by the row and its permission (section 11.9, answer c:
  W1 to W5). "Widening is the right approach imo unless something makes it
  impossible to do safely." The hardening it stands on is SO-93.
- **A different row at the same address at a wake is the program's bug:**
  the late door checks the row that is there and writes. No generation.
- **An overlap:** a `map` that meets any row its target already holds is
  refused (`NoResource`). The same bytes seen twice then takes two
  processes, or arm64's second address.
- **An allocation's rights** come from the pool handle it was allocated
  through.
- **Names:** `Pool`, `Memory`, `allocate`.

## Order of work (section 11.6)

1. **The spec,** one patch: what is built now stated as built, what is
   reserved stated as reserved; the user reads it before any code.
2. The kinds and the typed boot rows, with every package's type edits.
3. The overlap rule.
4. The widened copy doors, after SO-93 has merged; the late-door cases
   rebuilt on an allocation, on every profile.
5. The removal of an allocation's split, with the cases that used it
   rewritten (section 11.5 names each).

The gate is green at every step.

**From the Air: review of `SO:split-and-slice`, sections 1 to 9.** The addendum and the pool/allocation forms get their own pass when the doc is republished.

**Verdict.** The core holds. I found no sequence of ops that frees, donates, zeroes or re-grants bytes a live row or a live slice names. Two things need a decision before it is built: what the design keeps reachable through R18 (Q6), and what an overlap between two rows of one process means (R6). The rest is small.

**What was checked, and how**
- **§2, today's model:** every claim checked against main at the file and function it names. None is false. Imprecise: riscv32's row budget is 8 (`GRANT_ROW_BUDGET`), so the scan's bound is 256 x 8, not 256 x 9; `slab_donate`'s first test also covers a wrapping region; R12's "the donor could have checked" is the comment above `slab_donate`, not spec §2.8, which says only that the kernel never shares slab backing.
- **§7, the cases:** run, not read. With `split` answering a status for any region with `maps != 0`, the whole suite fails exactly the cases listed and nothing else:

| profile | failing |
|---|---|
| riscv32, riscv32-flat | `split_live_bytes`, `split_mapped_bytes`, `split_rows_held`, `image_split`, `late_door_buffer_gone` |
| arm64 | `split_live_bytes`, `split_mapped_bytes`, `split_rows_held` |
| ESP32-S3 smoke | `image_split_flash` |
| ESP32-C3 smoke | none |

  One more joins when SO-70.p2 merges: its `kill_late_door` cuts `front` and `hole` off the child's destination after the create, as `late_door_buffer_gone` does.
- **The rules, by reading:** the only place that treats "one handle and no rows" as sole access is `slab_donate` (every test of `refs`, `maps` and `out_bytes` in the kernel listed), so R12 is the whole list. A Memory handle is minted in two places only (boot, `Split`), so R3's assertion cannot be reached. `install_row` and `place_image` already take the range and the counted region as separate arguments, so R9 can be built as written. Process bodies are capped at 256 and rows at 9, so `maps` cannot overflow by the concentration R9 causes. The teardown order (close-all, disown, clear the domain) is right for R10 and R13.

**1. Q6 is the question that decides the shape, and the data says "no".**
- With R2 alone, no mapped row can lie inside a process's copy windows on any profile. On arm64 none can today: a mapping is placed at or above `region_top` (`free_user_va`), outside both windows. So the late doors of SO-90 would be unreachable everywhere.
- R18 re-opens the route (a slice of a process's own destination, mapped into it), and the reason given is that the doors stay testable.
- Run: with `install_row` refusing a mapping that meets the target's region window or read-only window, the whole suite and both smokes fail one case: `late_door_buffer_gone`, on the two riscv32 profiles. Nothing uses a mapped row as a system-call buffer except the case that checks the kernel survives its removal.
- The route also carries a likely hole on main today: `copy_out_check` and `translate_user` never read a row's write permission, so a result is written into a read-only row that lies inside the write window. Read, not yet run; a probe is running and I will report it on its own.
- **My view:** refuse a mapping that meets the target's copy windows (`meets_image_row` widened to the windows). Every buffer is then an image row, which nothing removes, on every profile; the late re-checks become assertions; and a read-only mapped row can no longer be where the kernel writes. It costs the one test route, and it is the user's to rule since it takes back what SO-90 made safe.

**2. R6: a partial overlap is new, and on the PMP profiles it is not the double map.**
- Today two mapping rows of one process over RAM are identical or disjoint (nested in one corner: a pool root mapped, grown by a returning piece, mapped again). `Map` takes no range and pieces are disjoint. Slices make partial overlap ordinary.
- On riscv32 and the C3, row `i` is PMP region `i` in record order (`load_domain`), and the lowest-numbered matching entry decides. So the overlap has the first-mapped row's permissions, never the union, and an access that runs from the overlap into the later row's own bytes faults.
- The kernel's own questions disagree with the hardware there: `translate_user` takes the first covering row and refuses a buffer that runs past its top, so the same buffer is accepted or refused by mapping order; `executable_at` accepts an entry the first fetch then faults on.
- This is already so for identical ranges: an RW row then an RX row over one region in one process gives no execute on PMP while the RW row stands. `map_wx_refused` maps both and never fetches. (Reading plus the PMP rule; not run.) So §2.5's "JIT-shaped pattern in full" holds across two processes and on arm64, not in one process on a filter profile.
- All of it fails closed. But R6's "buys nothing a holder cannot do anyway" is not right, and the design should say what an overlap means: either "the first-mapped row decides, on a filter profile" in the spec, or a map that partly overlaps another row of the same target is refused.

**3. Smaller**
- **R5** needs `Map`'s `region_wraps` test: `m.base + offset` panics the kernel (overflow checks are always on) for a boot region whose base plus length wraps, which nothing refuses at boot.
- **R5's alignment is relative to the source's base.** A slice is mappable only if that base is grain-aligned; a child image blob on arm64 is 16-aligned, so no slice of it can be mapped, as the blob cannot. And a slice cannot reach the last partial grain of a region whose length is not a grain multiple, which is every blob.
- **R12's reason** ("it cut the slices") is not true of a region that came from another process, which may have cut one first; nothing lets a holder read `slices`. Same shape as `maps != 0` today, so no new exposure, but R2 answers the same unknowable condition with a status and R12 with a fault.
- **New cases** the list lacks: R11 (a slice charged, the limit met, the refund, the disown) and N6 (a sub-slice of a slice without `MapExecute` cannot map executable).

**Views on the questions**
- **Q1:** a new status word. `WouldBlock`'s doc promises a peer whose act changes the answer and names poll loops; a row leaked by a dropped Mapping (N13) may never clear, and nothing can be waited on. `NoResource`'s text is false here.
- **Q2:** the new bit. Bit 11 is free, and a keep mask written as a list of bits excludes it.
- **Q3:** refuse it; the user's pool/allocation split is the clean form. A pool root's range is "not yet allocated", its offsets move when someone else's piece comes home, and one stray slice stops the system's allocator.
- **Q4:** `slice`.
- **Q5:** accept and document. Pinning is what a sibling handle already does; the freeze is the only new power, and a program confines it by slicing a piece, never what it allocates from. With `kill` built, a holder that will not let go can be ended.
- **Q6:** no (finding 1).
- **§6:** the trade is fair. What goes is a scan of every body's rows with no preemption point, and the attribution of a row to a piece by physical range. Answering Q6 "no" lets more go.

**On your question, whether a boot region is used directly as a region:** yes, by how the boot table is built. `_region_rows` writes three roles under one kind (`RAM`): a blob per child (passed straight to `process_create` as the image), a destination per child (passed straight as the memory), and the pool (split). Under the two-concept form, blobs and destinations have to be minted as allocations at boot (a kind in the table) or cut whole first. I will check the addendum's count by running it, as for §7.

**Found on the way**
- **`Map`'s round-up:** `mint_boot_regions` checks no alignment and blob lengths are arbitrary, so the kernel does not prevent it. In the tree's layouts it is harmless: on arm64 a blob's base is 16-aligned and in practice not page-aligned, so `Map` faults, and a tail that does round up lands in the padding before `.bss`'s page alignment.
- **`refs` as `UInt16`:** not worked through.
- **Two candidates met while reading, both outside this design, both read and not yet run:** the write permission above, and a 4-byte device window on riscv32 that is programmed as a NAPOT entry (`napot_bound(base, 4)` is `base >> 2`, so the entry's size comes from the address's trailing ones). Probes are running; each gets its own report.

**From the Air: sections 10 and 11 of `SO:split-and-slice` (revision 2).** The rulings are taken as given; this is what they did not have in front of them, and what I ran.

**Verdict.** I found nothing that makes the widening impossible to do safely. The minimum (pools, allocations, the overlap refusal, the widened doors, no `slice`) holds together. Three things for the spec author, then the checks.

**1. "A process's rows never overlap" is not true yet: the loader records rows too.**
- The ruled refusal is on `map`. `validate_image` checks each segment alone (`check_segment` in a loop) and nothing compares two segments, so an image with two segments over the same addresses loads, and its rows overlap. (Read, not run. On PMP the first row decides; arm64 writes one descriptor per page, so the last does.)
- 11.9 rests on one covering row per address (its closing sentence, and W1's "one row"). So the spec needs the loader's half: two segments of one image whose ranges meet are `BadImage`. It is a small pairwise test, bounded by the row budget.
- A single segment may still be both writable and executable (§2.5 leaves that to the linker script), so W1's execute test stays needed for image rows whatever is done about overlap.

**2. One consideration on the overlap ruling, said once.** As ruled, arm64's second address is the one place left where two rows of one process name the same bytes. If the refusal compared physical ranges on every profile instead:
- W2 (the execute test by physical range) would not be needed, since no byte would have a second row;
- SO-89 would close by construction: a launcher could no longer map a child's destination into it at a fresh address and so give it a writable view of its own code, which the identity profiles already refuse through `meets_image_row`;
- all four profiles would agree.
What it costs is the in-process double map on arm64. Census below: the cases that map one region twice into one process are four plus the late-door trials, and each is rewritten for riscv32 anyway. If arm64's second address is wanted (a JIT in one process), the ruling stands as it is and W2 carries it.

**3. 11.7's second invariant is off by donated bytes.** A donated allocation leaves its length in its pool's `out_bytes` for good (`memory_retire_donated`), so `out_bytes` is outstanding allocations plus bytes given to the kernel, and such a pool never frees. Sub-pools and revoke should be designed knowing a pool can hold a range that never returns.

**What I checked for "impossible to do safely"**
- **A row cannot go in the middle of a copy.** A preemption point (`irq.preempt_point`) delivers interrupts and runs no other thread; a reschedule waits for the return to user mode. What a delivery does do is write a woken waiter's record through `copy_out`, so that door needs W3 like any other, and it has it by being the same door.
- **W4, the stack:** `frame_init` on riscv32, arm64 and the S3 writes only the kernel's frame slot, and riscv32's trap entry swaps `sp` with `mscratch` before its first store. So nothing in those writes a user stack. The S3's and arm64's trap entries I did not read; SO-93's audit should list the assembly.
- **W3** is the hole now shown on main (SO-93, run).
- **WH3** is ruled. The rest is SO-93's list: every late door asking again, and no kept translation.

**11.5's lists, run rather than counted**
- **The pool model.** On main, with a boot region allowed one role (split from, or used directly as an image, a destination or a mapping) and a piece never split, the suite fails exactly these, which is the "rewritten" list: `split_live_bytes`, `split_mapped_bytes`, `split_rows_held`, `split_keeps_rights`, `split_keeps_rights_twice`, `donate_empty` on riscv32 and arm64; `image_split` and `late_door_buffer_gone` on riscv32; `image_split_flash` on the S3 smoke. Every other case passes, so `image_held`, `flash_region`, `process_donate`, `memory_split` and `memory_recycle` need a typed row or a renamed call and no change of logic, as the section says. (10.3's P4 lists five; `split-mapped-bytes` cuts a piece too.)
- **`kill_late_door`** (SO-70.p2, unread in the section) does build the same row: it cuts `front` and `hole` off the child's destination after the create. It joins `late_door_buffer_gone` in whatever that case becomes.
- **The overlap refusal.** With `install_row` refusing a range that meets any row the target holds, riscv32 and riscv32-flat fail five: `map_basics`, `map_exec_gated`, `map_wx_refused`, `late_door_buffer_gone`, and **`quota_vs_wall`, which the section's list does not have** (it reaches the row wall by mapping one region again and again; it needs an allocation per row). arm64, the S3 smoke and the C3 smoke pass whole, arm64 because a second map there gets a fresh address.

**Agreed without more to say:** typed boot rows rather than a cut at run time (a launcher cannot read a blob's length); rights handed down from the pool handle; no `slice` in the minimum; the order of work in 11.6 with the widening before the split of an allocation goes.
