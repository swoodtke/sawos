## Description

## Proposal (user, Nov 13)

"What's the use case for splitting an already mapped region? It seems to me
that we could refuse to split mapped regions entirely? And then add another
operation to slice an existing region into 2 or more regions and these
slices work the way I mentioned earlier which is that they are regions
which hold a reference to their parent."

## The shape

- **`split` is the allocator and nothing else.** It carves an independent
  piece from memory nothing uses; each piece returns to its pool by itself.
  A region with any row counted on it is refused.
- **`slice` makes views.** A slice is a region over part of an existing
  one and holds a reference on its parent; the parent's bytes go back to
  the pool only when its handles, its rows and its slices are all gone.

It replaces what SO-91 built (a split carries a region's rows to the piece
that covers them, and refuses a cut through a row), which is correct and
tested and stays until this is designed.

## What the lead found when asked

- **No strong use for splitting a region in use.** In the tree only tests
  do it, all written on Nov 12 and 13. In principle: reclaiming the unused
  middle of an over-sized child region, or handing on part of a shared
  buffer; both avoidable by sizing regions first.
- **Refusing the split alone removes the only route to code just fixed.**
  A mapped row inside a process's copy windows could be made only by
  cutting a piece from a child's destination after its creation. Without
  that: SO-90's late copy doors are unreachable through the syscall path
  and its case cannot be written; the trial that holds SO-85's
  any-covering-row rule loses its route; SO-84's and SO-91's split cases
  become refusals.
- **`slice` restores the route:** a slice of a child's destination, mapped
  and unmapped while the child is parked, reaches the same doors. So the
  two changes belong together.

## For the design pass (spec first, Opus)

- Whether `slice` should mirror `IoMemory`'s carve, and how carve handles
  lifetime today.
- Who is charged for a slice; whether a slice can be sliced; what a
  slice's rights are against its parent's; what a row on a slice counts
  on.
- A parent whose owner dies; a parent donated to the slabs; a slice of an
  image a process runs from in place; a slice given to another process.
- Whether a region with slices can be split (the lead expects not).
- Each case that splits a region in use today, and what it becomes.

## Sequencing

After the box (SO-84, SO-77, SO-78), unless the user says sooner. It
changes no behaviour a program on main relies on and closes no hole.

## Acceptance

- [ ] design and spec text reviewed by the user
- [ ] `split` refuses a region with rows; `slice` exists

**Follow-up from the user (Nov 13), on the design's N11 and Q3:** "Does it make sense to have 2 concepts of memory - allocated (split from the pool) and unallocated (in the pool). Then a slice operation on unallocated memory would fail so the issue of holding the root memory pool by creating a slice is impossible." The design had recommended against refusing a slice of a pool root because a program handed a `Memory` cannot tell a pool root from a piece. Making the two different on purpose removes that objection. The designer is writing an addendum that evaluates three strengths of it: (A) one kind, `slice` refuses a pool root, with something that lets a holder tell; (B) two concepts with disjoint ops: a pool can only be split, an allocation can be mapped, be a destination or an image, be sliced and given, and can never be split, so `split` never meets a region that can have rows; (C) anything between. For B it counts what uses a boot region directly today and what would have to allocate first. The lead republishes the doc when the addendum is in.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":1139,"created":"1794577578","id":"c4"} -->
**A further refinement from the user (Nov 13):** "I think it might be useful have 2 operations on a pool - allocate and split. Allocate creates a memory region which can be slice and mapped. Split creates a smaller pool which can be allocated and split. This allows a memory manager process to split its pool into smaller pools for use by either another memory manager or by an individual process e.g. a process can own its memory for allocating provided at process creation." So three roles: a pool (`allocate`, `split` into a smaller pool), an allocation (mapped, a destination or image, sliced, given; never split), and a slice (a view holding its allocation). The designer adds it to the addendum as form D and settles: what a sub-pool is to its parent and when its range returns; the bound on the release cascade up a chain of pools; where a pool's free list lives; pinning one level up; that a pool handed to a process is a byte budget, which the object-counting quota is not; how a child gets a pool at creation; whether reclaiming a sub-pool needs a revoke or `kill` is enough; rights and kinds; boot; and the new holes it creates.
