## Description

## Rulings (user, Nov 13)

- "We should refuse to send any data which is marked as executable - even
  strings embedded in the code probably shouldn't be sent."
- "Yes - only executable memory can be provided as the entry points."
- On where read-only data then goes: "a third segment where possible
  sounds like the right decision."

## The unit

On every board, a system call's buffer may not lie in memory the process
may execute, and a thread's entry must lie in such memory. This is the
first half of SO-84's design, split out because it needs no board: the
gate's three profiles and the two smokes show all of it. SO-84 (processes
on the ESP32-S3 run from flash) builds on the linker scripts this unit
changes.

The spec text is in SO-84's spec patch (§2.2, §2.7, §11).

## What changes

1. **The copy doors** (`kernel/core/process.saw`, `translate_user`): a
   grant row whose permissions include execute is not a candidate, so a
   buffer there is `BadBuffer` at copy-in and copy-out, a row that is both
   writable and executable included.
2. **`thread_create`** (`kernel/core/dispatch.saw`): the entry must lie in
   a non-device row that permits execute, or it is `BadEntry`. The stack
   check is unchanged.
3. **Every board's user linker script gives read-only data a segment of
   its own,** readable and neither writable nor executable, between `.text`
   and `.data`: `hal/riscv32/user/root.ld`, `child.ld`, `child2.ld`,
   `child3.ld`; `hal/riscv32-esp32c3/user/root.ld`, `child.ld`;
   `hal/arm64/user/user.ld` (page-aligned at both ends); the S3's two.
   Every board can afford the extra grant row (the design pass's table is
   on SO-84), so no board folds read-only data into the writable segment.
4. **`kernel/core/limits.saw`:** `IMAGE_GRANT_ROWS` becomes 4 (three
   loadable segments and the stack); its `static_assert` still holds.
5. **The S3's three link scripts** interleave literals with code,
   `*(.literal .literal.* .text .text.*)`, keeping the vectors' literals
   where the trap path needs them. Listing every literal pool first stops
   linking past about 256 KiB of code, since `l32r` reaches 262,141 bytes
   backwards.

## What moves in the transcript

`root image ok segments={two}` becomes `{three}` on riscv32 and arm64, in
seven case rows. No hand-written payload or fixture needs a change: a
harness kernel's payload has no grant rows, and the fixtures use no copy
door except the two that already assert a refusal.

## Cases

- `copy_from_code_refused`, all three profiles: a program passes the
  address of one of its own functions as a pipe-send body and is ended
  with `BadBuffer`. Mutant: drop the execute test; the send succeeds.
- `thread_entry_not_exec`, all three: an entry at a writable static is
  `BadEntry`. Mutant: accept any row.
- A string literal still goes through a system call on every profile
  (every existing case that prints is that case): say which rows show it.
- Mutant for the scripts: put `.rodata` back into `.text` on one board and
  show which cases fail and how.

## Acceptance

- [ ] kernel: the two checks
- [ ] every user linker script: three loadable segments
- [ ] the gate, the C3 smoke and the S3 smoke pass; every moved row named
- [ ] spec: the markers on these two rules removed, and only those

**Lead review, SO-85.p1: executable memory is not a buffer; a thread's
entry must be executable; read-only data in a segment of its own.**

**First, a kernel bug this unit found and fixes, which was on main.**
`translate_user` returns `Result<UInt, FaultReason>`, and its failure was a
bare `FaultReason.BadBuffer`. The compiler wraps that as `Ok` with the
enum's raw value, so every address that named nothing answered `Ok(11)`.
The "address must also resolve" checks in both copy doors were dead code,
and a buffer in a hole of the caller's own region made the kernel load from
address 11. The implementer met it as a machine that died with no fault
line and found it by disassembly. Both variants are now spelled out. The
lead reproduced the compiler behaviour in a ten-line host program at the
v0.22.0 pin and has reported it to the sawlang lead; the same shape at
other sites in this tree is SO-87.
- What shows the fix: `copy_from_code_refused` is the first case to reach
  that failure path; with the bare return it stops the machine with exit
  status 5 and no fault line.

**The unit:**
- `translate_user` skips a row whose permissions include execute, so a
  buffer there is `BadBuffer` at both doors. `thread_create` requires its
  entry in a non-device row that permits execute (`executable_at`), else
  `BadEntry`; the stack check is unchanged.
- Every user link script has three loads: code (R+X), read-only data (R),
  data (RW). `llvm-readelf -l` on one image per board is in the
  implementer's report; no script needed explicit `PHDRS`. arm64's
  read-only segment is page-aligned at both ends.
- `IMAGE_GRANT_ROWS` is 4.
- The S3's three scripts interleave literals with code.
- Spec: the markers on the two rules are removed. Left marked in the same
  paragraphs: the copy-in window over in-place segments, and an entry in an
  in-place code segment outside the region.

**Cases, on all three profiles:**
- `copy_from_code_refused`: a pipe-send body in the child's code ends it
  with `BadBuffer`; controls with the body in a string literal and in
  writable data are sent. With the execute test dropped, the first send
  succeeds and the case fails.
- `thread_entry_not_exec`: an entry in writable data, and one in a string
  literal, are `BadEntry`; one in code succeeds. With the region-only check
  restored, the case fails.
- With `.rodata` put back into the code segment in one script, three cases
  fail (`process_walk_gate`, and the two new ones) and nothing else does.

**Where the issue was wrong, and what changed for it:**
- No existing case passed a string literal's address through a copy door:
  `debug_print` sends a byte per call in a register. The new controls and
  `process_walk_gate` are what show a literal is a legal source.
- One fixture did use a code address as a read-only source
  (`child-walk-fault`, the pid read from read-only memory). It now uses a
  string literal's address: the fixture changed, not the rule.
- A copy-out twin is not expressible: a code destination is refused by the
  writable window before `translate_user` is reached, and no image or
  `map` yields a writable and executable row.

**Rows that moved:** `root image ok segments={two}` is `{three}` in seven
case rows; nothing else in an existing entry changed. Sizes, printed only:
the C3's two images grow 32 bytes and the S3's between 128 and 288.

**Runs:** the full suite (652; the row diff is the six new rows), the C3
smoke, the S3 smoke (23), the new cases 10 of 10 on each profile.

**Not shown by any case:** that a program on an isolated profile cannot
write its own constants (the rows are read-only; nothing stores to one),
and the 256 KiB literal range (the pattern links and runs at today's
sizes). `BadEntry`'s text still reads "thread entry outside the process",
which an existing case asserts; it now also covers an entry that is not
executable.

**Changes requested (rev 1): on the two riscv32 profiles a launcher can switch both rules off for a child with one `map`. The rest is as you describe, and the `translate_user` fix is real.** Two agents ran the probes and mutants below; I checked each finding against the code and their logs.

**1. A second row over the child's own region defeats both checks (riscv32, riscv32-flat).**
- A launcher keeps the destination `Memory` after `process_create`. `child.map(memory: &ram, access: ...)` installs a row at the same addresses as the image's rows: `map_place` answers `pa` on the identity profiles, `map_target_ok` asks only for RAM, and `record_grant` appends with no look at the rows already there.
- `translate_user` skips an executable row and keeps looking, so it finds the new row; `executable_at` is satisfied by any executable row.
- Probe (`probe-exec-overlap`, a root that launches this patch's `child-exec-fault`; the child's status word):

| | no map | its own region mapped |
|---|---|---|
| a send whose body is in the child's code, riscv32 and riscv32-flat | 131083 (`BadBuffer`) | mapped RW: **65543, sent** |
| a thread entry in the child's writable data, riscv32 and riscv32-flat | 131078 (`BadEntry`) | mapped RX: **65543, the thread is made** |
| both, arm64 | refused | refused (a `map` there gets its own addresses) |

**Lead, SO-85.p1: review accepted; the implementer is revising.** (1) **The overlap:** the lead chooses the invariant. A process's grant rows do not overlap: a row that would cover an address a row of that process already covers is refused where it is installed, so a second row over a child's own region cannot be made, and neither check can be switched off by one. Which answer the refused `map` gives is settled by the fault rule and `map`'s other refusals, stated in the spec, with a case on the two riscv32 profiles (the reviewer's probe) and what arm64 does said beside it. (2) The three texts are fixed, with the S3's entry address removed where it was written as fixed. Taken from the rest: the copy-out side pinned with a writable and executable segment (the reviewer's probe as a case); `executable_at`'s dead device test removed and its upper bound held by a case; the comment in `translate_user` reworded so it does not give a compiler defect as the language's rule. **Corrections to the lead's note:** the S3's flash images grow 120 to 304 bytes, not 128 to 288; and on arm64 the old bug did not stop the machine: the send succeeded after the kernel read 8 bytes at physical address 0xB. **Not addressed here, filed separately:** on arm64 a launcher can map a child's region a second time at another address with other permissions, which is two names for the same bytes and not an overlap of rows.

**Lead, SO-85.p1: the fix for the overlap is changed before it is built; the general invariant in the comment above is withdrawn.** The implementer stopped on it, rightly: spec §2.5 sanctions the double map ("an RW row here and an RX row there over one region"), on the identity profiles both rows are at the region's own address, and `map_basics` asserts a second mapping of one chunk. A rule that no two rows of a process overlap would contradict both. **What is built instead, in two parts:** (1) a mapping may not cover a row the loader recorded for the target (a segment of its image, or its stack grant); the `map` answers `NoResource`, a status, and installs nothing, and mapped rows may still overlap each other. That closes the reviewer's second attack (a read-execute row laid over a child's data to satisfy the entry rule) and means an image's rows are never unmapped. (2) For buffers, any covering row: an address is refused if ANY row covering it permits execute, which is the user's ruling read literally and makes the answer independent of the order rows were recorded in. That closes the first attack by itself. Its consequence is stated in the spec: on the identity profiles a region mapped both read-write and read-execute is one range of addresses and so is not a buffer; on arm64 its two mappings are two ranges. `map_basics` passes unchanged. **Filed separately:** the late copy doors treating a refusal as a kernel bug when a mapped buffer's row goes while a thread is parked, which is older than this unit; and SO-89, arm64's two names for the same bytes.
