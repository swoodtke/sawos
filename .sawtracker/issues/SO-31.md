# Docs unit 7: `spec.md` (epic SO-24)

You are rewriting `spec.md`, the authoritative specification of the SOS
microkernel (about 285 KB, 3,456 lines). The lead wrote this brief. **If it is
wrong, contradicts what you find, or leaves a decision you can't make from

## Goal

The spec narrates its own history: "(ratified Jul 29)", "BUILT M3 unit 4
(sawos design 6)", "RE-RULED Sep 2", "superseding this row's earlier…",
struck-through resolved questions, "(user ruling, lead review Sep 1)".
That history lives in `designs/` and git. The rewritten spec states **what
the system is and how it behaves**: the object model, rights, ops, errors,
invariants, the protocols, and why a design choice was made when the reason
is interesting or guards against a plausible mistake. A reader should be able
to learn the system from it without archaeology.

**The meaning of every normative statement must survive.** This is a
rewrite of the presentation, not of the design. You may not add, remove,
weaken or strengthen a requirement, a right, an error case, an invariant or a
guarantee. If you find the spec contradicting itself or the code, **report
it and leave the normative text as it is** (strip only its provenance). Don't
resolve it. That is a decision for the lead and the user.

## Rules

Remove:
- dates, "ratified", "DECIDED (user, Jul 31)", "user ruling", "lead review",
  and every design, unit, issue or milestone reference used as provenance
  (`design 178 D3`, `sawos design 6`, `M4 unit 4.5`, `designs/010 ruling
  12(b)`, `SL-16`, `DF-232e`, `sawlang#140`);
- narration of how the design got here: "superseding the earlier…", "used
  to", "was re-ruled", "unit 1 said it would", accounts of what an earlier
  slice did or did not build, and struck-through text;
- rejected alternatives, unless a future designer would plausibly propose the
  same thing. In that case keep one or two sentences saying why it doesn't
  work;
- ALL-CAPS emphasis, outside identifiers and acronyms;
- measurement anecdotes ("measured: 10 traps against 18") unless the number
  is a design property the spec relies on.

Keep, tightened:
- every normative statement: what an op does, which right it spends, what
  it returns or faults with in each case, what a kind's lifetime is, what
  counts against which quota, what the kernel guarantees;
- rationale that explains a non-obvious design, briefly;
- **implementation status where it matters to a reader, in the present
  tense**: "Not implemented: virtual clocks." Drop *when* and *in which unit*
  something was built. Where a status claim is easy to check against the tree
  (an op exists in `kernel/abi/src/ops.saw`, a right in `rights.saw`), check
  it. Report any status that is false and leave it as it is.
- forward-looking plans (M6, M7) as plans, under a clearly labelled section.
  Milestone names may name *future* work, not provenance.

**Lead's ruling on the implementer's clarification request.** The brief contradicted itself on false status claims: "report and leave" in Rules, versus "verified stale-status corrections allowed" in Verification. Verification is the intended rule:

- **Status claims:** a claim about what EXISTS in the tree (an op, right, type, API or package; its name; where something lives; what a default set contains; how many overloads) is corrected when it has been verified against the tree. Each correction gets a normative-ledger entry quoting old and new.
- **Behaviour claims:** a claim about how the system BEHAVES or what it guarantees is never changed. A contradiction is reported, unless the spec itself records which statement superseded the other ("amended", "superseding"). In that case only the current statement is kept, and the report quotes the supersession record.
- **Stale API reference:** `Process.start(donating:)` doesn't exist. The disarm site is stated only if it can be verified from the tree; otherwise it is reported as an open question.
- **§5.7 / §5.4:** `### 5.7` is the Syscall ABI (all 76 citations mean it). Waiter attach semantics folds into `### 5.4`.
