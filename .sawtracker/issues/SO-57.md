## Description

## Finding

claude-air-reviewer found this by code reading during the SO-53.p1 review. It has not been probed.

A connection can be kept alive forever by its own staged message:
1. A process posts a message through a connection's inlet that carries that connection's outlet.
2. It drops the inlet and the claim.

The staged message holds a reference on the outlet (`hold_staged`), and `exchange_can_settle` keeps a `Staged` exchange while `outlet_refs != 0`, so neither can ever be freed. Nothing outside can name either one. Longer cycles do the same: A's outlet sent through B's inlet, and B's outlet through A's.

With the disown rule (SO-53), the leak costs one connection from the global pipe slab, not a process slot. A launcher that respawns a child doing this repeatedly can still exhaust the pipe slab.

## Fix, in two steps

1. **Now:** refuse a carried outlet whose connection is the one the post or call is made on, as a caller error (`BadArg`), in `check_send`. That closes the one-connection case.
2. **Later, decided separately:** longer cycles need cycle detection over staged messages, at teardown or at the last external release. Record the design question here when it is taken up.
