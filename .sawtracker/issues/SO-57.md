## Description

## Finding

claude-air-reviewer found this by code reading during the SO-53.p1 review. It has not been probed.

A connection can be kept alive forever by its own staged message:
1. A process posts a message through a connection's inlet that carries that connection's outlet.
2. It drops the inlet and the claim.

The staged message holds a reference on the outlet (`hold_staged`), and `exchange_can_settle` keeps a `Staged` exchange while `outlet_refs != 0`, so neither can ever be freed. Nothing outside can name either one. Longer cycles do the same: A's outlet sent through B's inlet, and B's outlet through A's.

With the disown rule (SO-53), the leak costs one connection from the global pipe slab, not a process slot. A launcher that respawns a child doing this repeatedly can still exhaust the pipe slab.

## Fix, in two steps

1. **Now:** refuse a carried outlet whose connection is the one the post or call is made on, as a caller error (`BadArg`), in `check_send`. That closes the one-connection case.
2. **Later, decided separately:** longer cycles need cycle detection over staged messages, at teardown or at the last external release. Record the design question here when it is taken up.

## The defect (a code reading; confirm it)

Posting (`PipeInletOp.Post`) or calling (`Call`) through a connection's inlet
with that same connection's outlet among the carried handles stages a reference
on the outlet (`hold_staged`, `kernel/core/refs.saw`). `exchange_can_settle`
keeps a `Staged` exchange while `outlet_refs != 0`. Once the sender drops its
inlet and claim, nothing outside can reach the connection, and it never frees.

## Probe first

Add a runner case, for example `pipe_self_outlet`, modelled on the `pipe_*`
cases in `tools/sos_runner.py`: a child posts a connection's outlet through its
own inlet, drops the inlet and the claim, and exits. **Before the fix**, show
the leak: the pipe slab stays occupied (for example a later `pipe_create` in
root fails sooner than it should, or the child's teardown line shows the
connection was not freed). Record it in `<scratchpad>/SO-57/probe-before.txt`.
If you can't make it observable, record what you saw and ask.

## Fix

In `check_send` (`kernel/core/dispatch.saw`; it now takes an `invoking` word
from SO-55, so read its current shape first): when the op is a post or call on
a connection, a carried handle that is an outlet **of that same connection** is
a `BadArg` fault on the caller, raised before anything is staged. That means a
`PipeOutlet` entry whose target is the inlet's connection slot. Pass whatever
`check_send` needs to know the connection; keep the reply paths unaffected,
since a reply carries handles back to the client, not into the request's own
ring. Doc the rule at `check_send`, at the post and call docs, and in the
typed tier's `post_with`/`send_with` docs (`kernel/sysapi/src/pipe.saw`).

**Spec:** §3's handle-transfer passage (beside SO-55's rule that a reply cannot
carry its own request handle) states this rule. §11's known limits gains one
line: a longer cycle of connections, each carrying the next's outlet in a staged
message, is never freed.

After the fix the case asserts the `BadArg` fault.
