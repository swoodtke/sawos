**A server can't learn the length of a Memory it was given, so a short shared ring can fault it.** The networking packages (`pktring`, SO-149) map a ring Memory the client allocates and gives at `Attach`. The server computes the ring's size from the layout, but nothing tells it how long the received Memory is: `MemoryOp` has only `Map`, `Extend` and the rest, and `Mapping` has only `base()`. On a protected board, a client that gives a Memory shorter than the layout makes the server fault on its first access past the end. Rule 5.2.4 of the networking design (`SO:networking` §5.2) says a bad value must end the connection with a counted error, never fault the receiver.

**Wanted:** a way for the receiver to check the Memory's length before it maps or uses it. Two shapes to weigh, with spec text and cases:
- `MemoryOp.Len`, an answer to "how many bytes is this Memory?", gated by a right;
- `Map` taking a minimum length and refusing a shorter Memory by name.

Every check needs a case that goes red when removed or inverted. Small kernel unit, design note first (Opus).


<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":1587,"created":"1795545154","id":"c2"} -->
**Lead: the design note is published as `SO:mapping-len`, revision 1.** It recommends `MappingOp.Len = 3`, which answers how many bytes a Mapping's row grants.
- **Why the Mapping:** accesses are held to the row, not to the allocation, and the two differ after an `Extend` with no `Grow`. Asking the Mapping also keeps §2.5's "no op on a pool or allocation reads its bounds".
- **The gate:** it spends `MappingRight.Base` and gives `Base`'s answers in `Base`'s order, so no keep mask needs auditing. The wrapper is `Mapping.len()`.
- **Rejected:** `MemoryOp.Len` (it answers the allocation, and has no good gate); `Map` with a minimum length (its argument registers are full, and the receiver still learns nothing); the server allocating the ring (that breaks creator-pays); and a length carried in `Attach` (the client's own claim).
- **pktring:** `RingError.ShortMemory`, `FaultCounts.short_memory`, and a checked `SharedWindow.init(at:len:layout:)`.
- **Cases:** `mapping_len`, two `grow_faults` roles, a `Revoked` line in `mapping_grow_gone`, hosted pktring tests, and an end-to-end `ring_short`.
- **Size:** one small unit (Sonnet), about 550 lines, two-thirds of them tests.
- **Profiles:** on riscv32-flat and the S3 a short ring doesn't fault at all; it's a silent overrun, which is worse.

Owner's questions: (1) check the length after the map rather than before, since the map touches nothing; (2) a follow-up issue so `map` answers a status, not a fault, for an off-grain or in-flash Memory; (3) a short ring at `Attach` answers `BadArg`, is counted, and ends the connection.

<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":384,"created":"1795545309","id":"c3"} -->
**Owner's rulings, Nov 24:** "yes on all 3 recommendations".
1. The length is checked after the map and before the first access.
2. A follow-up issue makes `map` answer a status, not a fault, for an off-grain or in-flash Memory.
3. A short ring at `Attach` answers `BadArg`, is counted in `ring_faults`, and ends the connection.

The build follows (Sonnet), as the design note's unit.

**Lead: SO-150.p1 is up: `MappingOp.Len`, and pktring's short-ring check.** One commit, dd721056, on current main. It follows the design note `SO:mapping-len` and the owner's rulings.

**The kernel.**
- `MappingOp.Len = 3` answers `g.top - g.base` for the row.
- A shared helper, `mapping_row_asked` (dispatch.saw), holds the prologue that `Base` and `Len` share: the `AccessDenied` fault, the freed-slot and `NO_ROW` `BadState` faults, and `ROW_TARGET_DIED` → `Revoked`. `Base` now uses it.
- `Mapping.len()` reaches it through `call_value`, with no floor export.
- Every spec edit the note quotes is applied: §2's row, §2.5, the four-ops bullet, `Len`'s text, `Grow`'s `NoMemory` clause, "bound to its target", §5.6 and §12.

**pktring.**
- `RingError.ShortMemory(len)` is fatal; `FaultCounts.short_memory` is recorded and summed.
- A checked `SharedWindow.init(at:len:layout:)` makes the window at the layout's length.
- The module doc has an "Attaching a ring" recipe and a rule 0. Per your t1, it says that `map` itself still ends the receiver for a zero-length, off-grain or flash-backed Memory, which is SO-153.

**The protocols.**
- netdevproto and hciproto: `Attach`'s `BadArg` adds "one given without `MemoryRight.Map`, or one shorter than the ring".
- sockproto: its list gains "a ring shorter than its layout".
- All three: such an `Attach` is counted in `ring_faults`, answered `BadArg`, and ends the connection (owner's ruling 3). Each also notes the faults SO-153 will remove.

**`net_fields_sealed`.** With two inits, the forged `SharedWindow(base:…)` is now refused with a candidate list rather than "no parameter is labeled `base`". The expected text is updated; the compile still refuses it.

**Cases.**
- `mapping_len`: 8192, still 8192 after an `Extend`, 12288 after the `Grow`.
- `grow_faults`, two new roles: `len` without `Base` gives `status=131075`; on an unmapped Mapping, `status=131077`.
- `mapping_grow_gone`: a `Revoked` line.
- `ring_short`: root as the client and a child server, end to end.
- Hosted: pktring's `short_memory`.

On riscv32, arm64 and riscv32-flat, 12 of 12 pass, and the four process cases pass on the S3 too.

**Mutants.** All red.
- **Kernel:**
  - `Len` answers base, top or zero (red at `mapping_len` and `ring_short`);
  - the right check removed or inverted (`grow_faults`; `mapping_len`);
  - `NO_ROW` removed (`grow_faults`, a kernel panic);
  - `ROW_TARGET_DIED` removed (`mapping_grow_gone`).
- **Hosted pktring:**
  - the check removed;
  - `<` changed to `<=`;
  - the window at the row's length;
  - `record`'s arm dropped;
  - `total` omitting `short_memory`;
  - `ShortMemory` not fatal.
- **End to end:** with pktring's check removed, `ring_short` is red on all three profiles. On riscv32 and arm64 the child takes a store fault; on flat the refusal line is missing.

**Gate.** `make sos-test` ran 1346 passed and 3 failed before the `net_fields_sealed` text fix; the 3 were that case on each profile. After the fix it passed on all three profiles. The full gate wasn't rerun after a final comment-only rewrap, and the S3 smoke ran only the four cases. The server's run is the gate.
