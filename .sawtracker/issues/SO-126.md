## Description

**Windowed Saw processes on the ESP32-S3** (the windowed-threads design's U5, `SO:windowed-threads`). The kernel runs windowed processes beside call0 ones (window handlers, Alloca, the 64-register frame, one start state); every windowed case today is hand-assembled. The pin is now sawlang v0.24.2, which compiles Saw for the windowed ABI.

Build what the design's U5 lists: an S3 process package compiled windowed (the `[sos.xtensa-esp-unknown-elf]` section's way of choosing the ABI, or what sawlang provides), its runtime (`sosrt`, the syscall stub, `_start`) in that ABI, and cases that run a real Saw program windowed in the S3 smoke: deep recursion that overflows and underflows the window file across a preemption, a windowed and a call0 process side by side, and a windowed process's fault reported as its own. Read the design for the rules a windowed entry must keep (the start state, `retw` from the first frame). If sawlang lacks something this needs, stop and say what, for the sawlang lead.

**Lead: SO-126.p1 is up: windowed Saw processes on the ESP32-S3.** Rebased by the lead onto main with SO-125 (it applied with nothing to resolve). Gate on the implementer's machine (before SO-125): 1047 / 7 / 64 and 1 board-only. No kernel change.

**How a package is built windowed:** `target-features = "+windowed"` in its `[sos.xtensa-esp-unknown-elf]` section; Blade passes it to sawc (`--target-features +windowed`) and to each native unit after the triple's `-windowed`, so the whole module graph (the program, `sos`, `sosrt` and its panic path, `syscall.c`, `support.c`) is windowed. In the linked root every function opens with `entry`, `_start` and the syscall stubs among them; sawc emits only `callx8`.

**Cases (S3 smoke):**
- `windowed_saw_threads` (windowed root, tick on): "windowed code" (WINDOWSTART read through a probe: call0 code reads one bit, windowed at least two); a system call from 100 frames down; the 100-frame chain's answer printed beside a loop's (`3644919033, expected 3644919033`), each frame keeping a2 to a7 live across its call; two threads 64 frames down that spin at the bottom on each other's progress for four rounds, every round crossing by tick with both chains live; their answers printed beside the loop's; a clean exit.
- `windowed_saw_child`: a call0 Saw root launches a windowed Saw child that answers from 100 frames down and exits 5; the root wakes with its status.
- `windowed_saw_fault`: a windowed child loads from 0x1000_0000 100 frames down; the kernel reports `load-access-fault` with the child's own epc and tval, tears down process 1, and the root wakes with Faulted.

The answers are asserted as printed numbers, not as a verdict the program computes: the first mutant run had Overflow8's a6 store removed corrupt the very register holding a thread's verdict, and the case still passed.

**Mutants** (each alone, restored by hash): red for `+windowed` removed from each package, the probe inverted, each printed answer off by one, the verdict inverted, `expected` changed, the bottom marker dropped, the fault address made readable, the tick removed (a hang to the deadline), Overflow4's a1 store, all nine lines of Overflow8 and of Underflow8, all twelve SAVE12 and LOAD12 lines of the trap path, the WINDOWSTART and WINDOWBASE restores, the start state's a6 and CALLINC. Green and expected: Overflow4's a0, a2, a3 stores and the four Underflow4 loads (the only call4 frame in a Saw process is the start state's stand-in caller, spilled once and never filled; the C cases hold these), Overflow12 and Underflow12 (sawc emits no call12; the C cases hold them).

**Docs:** ABI.md §7d says how a windowed Saw process is built (it said none was) and lists the cases; the HAL README says the kernel is call0 and a process may be windowed.

**For the sawlang lead:** nothing missing; sawc uses only call8 here, and a frame over 32,760 bytes still prologues with `movsp` (noted on SL-1133), which the kernel's Alloca handling covers and no case reaches.

Requested changes on patch SO-126.p1 (revision 1)

**Changes requested, one thing: `windowed_saw_fault`'s chain runs 3,696 bytes past the bottom of its stack before it faults.** Everything else I checked holds, and is below.

**1. The fault child needs 20,080 bytes of a 16,384-byte stack.**

- **Measured, with the child's image as the patch builds it** (chat f184 `fault_sp.py`: the kernel's fault report prints the frame's a1 where it prints `cause`): at the faulting load a1 is `0x3fcdb190`. The stack is `0x3FCD_C000` to `0x3FCE_0000` (`user/child.ld`).
- **Why:** `descend`'s instance over `Fault` opens with `entry a1, 192`, where the instance over `Report` has 80: the bottom's two prints are inlined into the one function, so every frame of the chain carries their scratch. `_start` is 688, and 688 + 101 × 192 = 20,080, to the byte.
- **What it lands on:** the image's writable segment ends at `0x3fcd4010` (`_arena_end`), so the 3,696 bytes, and the spills and the print's own frames below them, are in memory that is neither the stack nor a segment. Nothing stops the stores on this board, so the case passes; the load fault it shows is real, but it is reached from outside the stack.
- **The other chains fit:** the root's 1,008 + 101 × 80 = 9,088 of 16,384; a thread's 1,008 + 65 × 32 = 3,088 of 8,192; the child's 752 + 101 × 80 = 8,832 of 16,384.
- **A way out, yours to choose:** a depth the stack holds (64 frames come to 13,168, leaving about 3 KiB for what the prints call), or 100 frames with the prints where they do not widen each frame. Since the frame's size follows whatever the bottom inlines, a line in the package saying what was measured would keep the next edit honest.

**What holds.**

- **The images are what the note says** (f185 `elf_abi.py`, each function's own range, pools left out). In the three windowed ELFs every function opens with `entry` (59 of 59, 44 of 44, 43 of 43; `_start`, the system-call stubs and the panic path among them), every call is `callx8`, every return `retw.n`, and there is no `movsp`. `death-notify`'s root beside them has 84 functions and no `entry`. So the two "green and expected" groups rest on what the images hold: no call4 and no call12 anywhere in them.
- **The asserted numbers are the rule's, not only the compiler's.** Computed in Python from `tests/winsaw/src/lib.saw`'s arithmetic: 3644919033, 685981353, 1275536650 and 393937586, as the cases state. Each package built without its `+windowed` prints `call0 code` and its case is red on that line; the root and the child still answer the same numbers.
- **My own mutants of `boot.S`, each alone against the three cases (f186 `mutants_126.py`): 30 of 39 red, the nine left the ones you name.** Each of Overflow8's nine lines and of Underflow8's nine, a4 and a5 stored at each other's slots, Overflow4's a1 store, each of the four `SAVE12` and four `LOAD12`, WINDOWSTART not saved and not restored: red. Overflow4's a0, a2 and a3 stores, the four Underflow4 loads, and one line each of Overflow12 and Underflow12: green.
- **Repetition:** the three cases sixty times, then `windowed_saw_threads` 140 more: every run green. The crossing does not lean on timing, since each thread leaves its spin only on the other's progress.
- **Smaller:** the start state (`WINDOWSTART` 1, `CALLINC` 1, `a4` the return that faults) is what `window.c`'s comment and §7d's new sentences say; the probe's bytes disassemble as `rsr a2, windowstart`; the builds leave the three new `Saw.lock` files as committed.

**One line of the note, for the record:** "each frame keeping a2 to a7 live across its call" is true of the thread chains. The 100-frame chains keep five of them and use a6 only for the bottom's print, which is why a6's spill and fill are red in `windowed_saw_threads` alone. Nothing follows from it.
