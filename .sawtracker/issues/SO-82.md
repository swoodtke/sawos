## Description

## Ruling (user, Nov 12)

"If we encounter a deadlock, I think for now we just panic the kernel. No
recovery at all. Initially, these will be small embedded systems so a
deadlock is a system design problem. We can reevaluate if/when necessary."

A deadlock stops the machine. The kernel ends no process for it.

## What a deadlock is

Unchanged: no thread is runnable and nothing outside the thread set can wake
one, which means no bound interrupt line and no armed Timer
(`has_external_wake_source`, `kernel/core/irq.saw`). A system with a driver
bound to a line, or any armed Timer, idles and is never in this state.

## What changes

- **Before:** `pick_next` ended the process whose thread left the processor
  last, and the machine carried on; `resume_after_death` ended root, which
  stopped the machine. Under the tick, which process blocked last depends on
  timing (the finding that opened this issue).
- **Now:** both paths report the deadlock and stop the machine. The outcome
  no longer depends on which thread blocked last, so it is the same with and
  without the tick.

## What it costs

A process that blocks forever while its supervisor waits on it with no
timeout, in a system with no bound line and no armed Timer, now stops the
machine, where the kernel used to end that process and let the supervisor
continue. A supervisor that wants to survive a stuck child arms a Timer
(which also makes the state not a deadlock) and ends the child itself with
`kill` (SO-70).

A process that is stuck while others can still run is not a deadlock and is
not touched: it holds what it holds until something ends it.

## Acceptance

- [ ] spec: §7 (the idle rule and who a deadlock ends), §8, §9 and §11's
      known limit on the victim
- [ ] kernel: both deadlock paths stop the machine with one report
- [ ] cases: the existing deadlock cases assert the new report; a case with

## Implementation notes (lead, Nov 12)

**Model:** Sonnet. **Rules:** `.sawtracker/docs/implementer-rules.md`.

### Kernel

1. `kernel/core/sched.saw` has the two paths: `pick_next` calls
   `fault_process(THREADS[cur].process, FaultReason.Deadlock)` and
   `resume_after_death` calls `fault_process(ROOT_PROCESS, …)`. Both become
   one function that reports the deadlock on the console and stops the
   machine through the HAL's failing exit. No process is torn down.
2. **The report is one line that names no process.** Which thread blocked
   last depends on timing under the tick, and a line a case asserts may not
   carry it. Suggested: `SOS: deadlock: every thread is blocked and nothing
   can wake one`. Choose the exit status the way the existing stops choose
   theirs (`ExitCode` in the kernel); give deadlock its own value so a
   harness tells it from a process fault.
3. `FaultReason.Deadlock` (`kernel/abi/src/status.saw`) can no longer be a
   process's reason. If it is the last case, remove it and its `describe`
   arm. If cases follow it, leave its number unused and say so in a comment:
   do not renumber the others. Search the sysapi and the tests for its
   number (a status word of 131079 is `Faulted` with reason 7).
4. Leave `has_external_wake_source` and the idle path as they are.

### Cases

- `wait_deadlock` and `timer_deadlock`: root deadlocks. They assert
  `SOS: process fault: every thread blocked` and a process-fault status
  today; they assert the new line and the new status.
- `thread_exit`: its stalled phase has a child whose threads have all gone
  while root waits on it, and expects the child to be ended and root to
  carry on. That no longer happens. Read the case's header for what each
  phase proves; keep the phases that do not depend on the old rule, and move
  the stalled phase into a case of its own that ends at the deadlock stop,
  or end `thread_exit` there if it is the last phase. Say which in your
  report, and what property, if any, is no longer covered.
- `child_churn` and every other test that mentions a deadlock or the number
  131079: check each (the list is short; several are comments) and fix what
  the change makes false.
- **New:** one deadlock case with `"tick": True`, asserting the same report
  and status as its untimed twin, run 20 times on each profile. This is the
  property the ruling buys: the outcome does not depend on timing.
- Mutation checks: make the predicate count the tick as a wake source, and
  show the deadlock cases hang into the harness timeout; restore the old
  "end a process" behaviour in `pick_next` and show the new case fails.

### Spec

- §7: the idle rule keeps its predicate; "Who a deadlock ends" becomes "A
  deadlock stops the machine", with the reason in one sentence.
- §8 and §9 wherever they say a deadlock ends a process, and the process
  status word's list of fault reasons.
- §11: remove the known limit about which process a deadlock ends; add that
  a deadlock is not recovered from, and that a process stuck while others
  run is not a deadlock.

### Runs

Every deadlock case and `thread_exit` 20 times on each profile; the full
suite, the C3 smoke and the S3 smoke (`--board esp32s3`).

**Lead review, SO-82.p1: a deadlock stops the machine (user ruling, in the
description).**

- **Kernel:** `pick_next` and `resume_after_death` both call
  `fatal_deadlock` (`kernel/core/diag.saw`), which prints
  `SOS: deadlock: every thread is blocked and nothing can wake one` and
  stops with `ExitCode.Deadlock`, a value of its own. Nothing is ended or
  torn down, and the line names no process. `FaultReason.Deadlock` is
  removed; its number stays unused and the others keep theirs.
  `has_external_wake_source` and the idle path are untouched.
- **Spec:** §7's "Who a deadlock ends" is now "A deadlock stops the
  machine"; §8 says a deadlock is not a fault tag; §11's limit about the
  victim is replaced by "not recovered from", with what that costs a
  supervisor.
- **Cases changed, because the ruling changes what they asserted:**
  - `wait_deadlock`, `timer_deadlock`: the new line and status; no teardown
    line, since no teardown happens.
  - `thread_exit`: its last phase expected the stalled child to be ended and
    root to carry on. It now ends at the stop.
- **Cases added:**
  - `deadlock_after_death`: root waits on an Event nobody signals while a
    child exits, so the deadlock is found in `resume_after_death`, a path
    no case reached before. With that arm alone made to fault root, this
    case fails and `wait_deadlock` still passes.
  - `deadlock_after_death_tick`: the same with the tick armed, where either
    path may find the deadlock. The transcript is fixed by construction
    (root prints before it starts the child and nothing after) and nothing
    asserts which path ran. On riscv32 the twin failed under the mutant
    above too, so on that run the tick did not move the deadlock to the
    other path; the lead has no run showing it found by `pick_next` in this
    case.
  - `wait_deadlock_tick`: the tick is not a wake source. With
    `has_external_wake_source` answering true, all the deadlock cases hang
    into the harness timeout.
- **No longer asserted:** the old last phase of `thread_exit` held that an
  exited thread's slot outlives the drop of its last reference until the
  switch, because the deadlock report read the slot's process. The report
  reads nothing now. The deferred free still runs in the case's churn
  phases, but no line fails if that one shape frees early.
- **Runs:** the six deadlock cases on every profile; the two new
  after-death cases 21 times each per profile and the first four 20 times;
  the full suite (631) and the C3 smoke. The row diff against main is nine
  added rows and nothing else.
- **Against SO-75.p1** (in revision): the S3 smoke has no deadlock case, so
  the two do not meet.

Requested changes on patch SO-82.p1 (revision 1)

**Changes requested (rev 1): the two paths the patch changes are right; a third way to reach a deadlock still hangs without a word, and four comments still describe the old rule.**

**What holds** (origin/main + rev 1, a checkout at the v0.22.0 pin, riscv32, arm64, riscv32-flat):

- **Both paths stop, and neither stops early.** `pick_next` and `resume_after_death` call `fatal_deadlock` and end no process. In `resume_after_death` the test comes after every wake the teardown makes, and each of those is synchronous (they end in `ready_push`). Eighteen existing teardown-wake cases, each also with the tick armed, and a new one where root is parked in a fused call whose outlet only a dying child holds: 38 of 38 on every profile, none stopped at the deadlock line.
- **Nothing was quietly weakened.** The only expectations that change are the three cases the ruling changes. The fourteen cases that accept any failing exit each end in an asserted fault or abort line, so none can pass by reaching the stop instead.
- **`FaultReason`:** the numbers on either side of the removed one are unchanged, its `describe` arm is gone, and nothing indexes by reason. No hit for 131079 or "every thread blocked" outside the diff.
- **Mutants, on arm64 and riscv32-flat:** `resume_after_death` faulting root is killed by both after-death cases; `pick_next` ending the last process by `wait_deadlock`, its tick twin, `timer_deadlock` and `thread_exit`; the predicate answering true hangs all six; the predicate counting only the tick hangs exactly the two tick cases.
- **Reliability:** the six cases 20 of 20 on each profile quiet and 10 of 10 with the host loaded.

**1. A deadlock that arises while the kernel idles is never reported.** `idle_until_runnable` loops on the ready queue and asks `has_external_wake_source` never again. So when the last wake source goes without waking anybody, the state is the ruling's own (nothing runnable, no line bound, no Timer armed) and the machine sleeps for good:

```saw
try waiter.add(&event, KEY)            // an Event nobody signals
try timer.arm(after_ns: 2_000_000)     // a one-shot, attached to nothing
let _ = waiter.wait()
```

   - Run as a root image: `QEMU hung (> 10s)` on riscv32, arm64 and riscv32-flat, with no `SOS: deadlock:` line. The idle was right when it began, since a Timer was armed; after the fire nothing is.
   - It is older than this patch, and the notes say to leave the idle path alone. But the ruling is that a deadlock stops the machine, and §7 as patched says "The kernel idles iff something outside the thread set can still wake somebody", which is false from that fire on. It is also the same mistake the ruling calls a system design problem, the one a report helps and a hang hides.
   - Either the loop asks again each time a delivery leaves the queue empty, with a case like the one above, or §7 and §11 say this deadlock is not detected.

**2. Comments that still say the kernel ends a process:**
   - `tests/wait-deadlock/src/main.saw`, above the wait: "so the kernel terminates the process rather than waiting for a wake that cannot come". The patch changed the file's header and not this.
   - `tests/timer-deadlock/src/main.saw`, above the wait: "and the kernel terminates the process rather than idling forever".
   - `kernel/abi/src/status.saw`, `Revoked`: "never a strand for the deadlock report to name later". The report names nothing now.
   - `kernel/core/threads.saw`, `PENDING_FREE`: the edit left the paragraph ragged ("so the slot / is freed there, after the choice of the / next thread"), and its reason is the weaker half. A freed slot's state takes the same branch as an exited one's; what needs the slot alive is `fp_switch_out`, which writes into its frame, as `pick_next`'s own comment says.

**Low, no change needed unless you want it:**
- **Nothing fails if the exited slot is freed early,** as the note says: with `free_object` moved to the exit, all sixteen thread and FP cases pass on the three profiles. One `fatal_kernel` in `pick_next` when the outgoing slot reads `Free` would hold it without a case.
- **`ExitCode.Deadlock` is its own among `ExitCode`s, not among machine statuses:** a kernel fault exits with the raw cause, and 7 is a store fault on riscv32 and the FP exception class on arm64; root's `shutdown(7)` is 7 too. The runner matches the line as well, so nothing is misread today, and the same is true of the other codes.
- **`deadlock_after_death_tick` finds its deadlock in `resume_after_death` every time** (70 runs of 70 with a marker in the other arm). That is fine: `wait_deadlock_tick` is the case that reaches `pick_next` under the tick, so the two tick cases cover the two paths between them. The runner's comment that either path may find it is true in principle and not in practice.
