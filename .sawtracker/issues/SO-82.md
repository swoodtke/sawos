## Description

## Finding (the review of SO-71.p1, Nov 12)

When every thread is blocked and nothing outside the thread set can wake one,
the kernel ends a process (spec §7, §9). The process it ends is the one whose
thread blocked last: `pick_next` faults the caller of the block that emptied
the ready queue. The spec says when a deadlock is reported; it does not say
who is ended.

Without a tick that order is fixed by the program. With the tick it is not.
In `thread_exit`'s stalled phase a child's last thread exits while root is
about to wait on the child. If root is preempted and blocks after that, root
is the last to block: the report reads `every thread blocked process=0`, root
is ended and the machine stops, where the case expects the child to be ended
and root to carry on. The reviewer saw it in 4 of 20 riscv32 runs under a
1 ms stress tick and 0 of 80 boots at the shipping 10 ms.

SO-71 states the behaviour as it is. This issue is the question of whether
it should be otherwise.

## Options, for the user

- **Leave it.** The victim is the last to block. A supervisor that waits on a
  child which then stalls can be the one ended.
- **A rule that does not depend on order.** For example: among the processes
  with every thread blocked, end the youngest (highest pid) first and root
  last, so a launcher outlives what it launched; repeat while the deadlock
  stands. Or: end the process others are waiting on, when the wait graph has
  one. Each needs a spec passage and a case that holds under the tick.
