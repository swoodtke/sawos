## Description

**Found while building the overlap rule (SO-92.p4).**

The loader accepts a segment with `mem_len` 0 (`check_segment` has no lower bound; §5.6 does not exclude one) and `place_image` records a row `[a, a)` for it. No profile programs anything for that row, but it sits in the grant record, counts against the row budget, and every range test has to remember it:
- `meets_row` and `segments_meet` skip it explicitly since SO-92.p4;
- `grants_execute` does not: an executable row of no bytes at X makes `translate_user` refuse any buffer that strictly straddles X, and `stack_top_ok` a stack top just above it. It is reachable (an image with an executable segment of no bytes inside its data segment loads) and it fails closed: a legal buffer is refused, nothing illegal is taken.
- `meets_row`'s guard is held today by a leg built with `Memory.split`, which is going away.

**The question.** What should a segment of no bytes be?

**Lead's recommendation: it loads and records no row.** It grants nothing, so there is nothing to record; the grant record then never holds an empty row, and the guards in `meets_row`, `segments_meet` and the one `grants_execute` lacks are not needed (keep them or drop them, with the invariant stated once where rows are recorded). An image with such a segment spends one row fewer. The alternative is to refuse it as malformed (`BadImage`), which is stricter than anything the toolchain is known to emit and would need checking against what Blade writes.

Either way it is one sentence in §5.6, a few lines in `loader.saw`, and a leg: an image whose data segment holds an executable segment of no bytes runs, and a buffer and a stack top across that address are taken.

Best done with or just after the removal of `Memory.split`, which removes the only leg `meets_row`'s guard has.
