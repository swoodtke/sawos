## Description

**Two cases for `process.kill()` from the review's probes.** When SO-70 merged, the reviewer's probe packages were kept, and two were named as candidates for the suite because they hold something no case does.

**`kill_churn`** (from `probe_kill_churn`): create, start, kill and release a child, over and over, with the scheduler tick on. Each round the child is in one of four states when it is killed: spinning, parked on an Event, asleep on a Timer, parked in a call on a pipe made for the round. Every create, pipe and give of every round must succeed, so a body, record, thread, Waiter, Timer, Event, pipe or handle that a teardown failed to return runs a slab dry within a few rounds and the case goes red. It ends by launching one more child that runs to its exit.

**`kill_runnable`** (from `probe_kill_runnable`): a kill that lands on a child that is runnable and not running, and on one that is running when the tick takes the processor from it. Read the probe for what it asserts and keep exactly that.

**The work.**
- The probes are a diff over main as it was at SO-70's merge (`e3d6192e`), in `.claude/lead/probes/so70-kill-probes.diff` in the lead's checkout. They are the construction to read, not text to apply: memory now comes from a `Pool` (`allocate`), boot rows are typed, and packages that cut a pool row with `split` were rewritten when pools landed. Port the two cases and the victim package they share to main as it is.
- Names: packages `tests/kill-churn`, `tests/kill-runnable` and `tests/child-kill-victim` (or an existing child package if one already plays a role, which is better); cases `kill_churn` and `kill_runnable`. Nothing named `probe` lands, and no comment says where a case came from.
- **No case asserts a value that depends on host time** (CLAUDE.md has the rule). The probe waits for a child to reach its state by watching the child's system-call count hold still; check that this is an observable and not a clock, and that a stalled host can only make it wait longer. The number of rounds is a constant of the case; nothing printed counts ticks.
- Profiles: every profile the case can run on, the ESP32 smokes included where the packages can carry a section for them and the board's layout holds the children. Say which and why not the rest.
- Show each case holds something: for `kill_churn`, make one teardown path leak (skip one release in the kernel's teardown, alone), see the case go red, restore. For `kill_runnable`, the same with the line it is there to hold. Report the mutants and the console line that moved.

**Acceptance.** The gate green (`make sos-test sos-smoke-esp32c3 sos-smoke-esp32s3`) with the totals reported; each case run twenty times in a row on each profile with no red; the two mutants; `runner_dupkeys.py` clean.
