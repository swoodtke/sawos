## Description

# Brief: comment cleanup, unit 1 — `kernel/core/`

You are implementing one unit of a comment cleanup in the sawos repository (a
capability microkernel written in Saw). The lead wrote this brief. **If this
brief is wrong, contradicts what you find in the tree, or leaves a decision
you cannot make from it, STOP and end your turn with a message that begins
`CLARIFICATION REQUEST:` and states the exact question. Do not guess, and do
not work around the problem.** The lead will answer and you will continue.

## Goal

Comments in this tree narrate their own history: design numbers, unit numbers,
rulings, "this used to…", "that edit HAS LANDED", alternatives once tried.
That history lives in `designs/` and in git. In the source it goes stale and
costs every reader time. Rewrite the comments so that each one tells a reader
**how the code works and what must stay true**, and nothing else. Explain
*why* only when the reason is non-obvious and a future editor would get it
wrong without it.

## Scope

- **In scope:** every `.saw` file directly in `kernel/core/` (19 files, about
  16K lines, and over half of that is comments).
- **Out of scope:** everything else, including `kernel/main.saw`,
  `kernel/abi/`, `kernel/sysapi/`, `hal/`, `rt/`, `root/`, `tests/`,
  `tools/`, `spec.md`, `CLAUDE.md`, and `designs/`. Later units cover the
  rest of the tree.
- **One exception inside scope:** in `kernel/core/slab.saw`, leave the
  signature of `Slab`'s `[]` accessor and the doc comment directly above it
  byte-for-byte unchanged. A pending patch (SO-21) edits exactly those lines,
  and touching them would make it conflict. Every other comment in
  `slab.saw` is in scope.

## The rules

**Change comments only. Do not change a single code token.** That includes
whitespace inside code lines, blank lines between code items, and the order
of declarations. If a comment cannot be fixed without a code change, leave it
and list it in your report.

Remove:
- design and unit references: `design 32`, `sawos design 2 D-5/D-6`,
  `design 178 D2/D3`, `M5 unit 6a`, `sawlang#140`, `DF-232e`, `SL-26`,
  `K1`, `#39 As-built`, milestone names (M0 through M7), and the same
  references inside parentheses or brackets;
- history: "used to", "was", "now", "moved here", "HAS LANDED", "before
  this unit", "the old paragraph", dates, who ruled what, and accounts of
  how the code reached its current shape;
- rejected alternatives, unless a future editor would plausibly reach for
  the same alternative and break something. In that case keep one short
  sentence in the form "Don't do X: Y breaks."
- the ALL-CAPS emphasis style. Write in normal sentence case. Keep caps
  only for identifiers, constants and acronyms.

Keep, tightened where you can:
- invariants and preconditions ("slot `i`'s frame and storage are located
  by the same `locate` call, so they always name the same extent");
- the conditions that make each `unsafe` block sound;
- ordering, locking and reentrancy rules, and anything that is load-bearing
  for alignment, layout or the trap path;
- ownership and lifetime contracts, and what a function returns or refuses
  in each error case;
- the non-obvious "why" that prevents a real mistake (an import cycle that
  forces a function's placement, for example);
- pointers to `spec.md` sections (`spec.md` §5.7) where the spec defines
  the behavior the code implements. These count as how the code works.
- doc comments (`///`, `//!`) on public and `public(package)` items. Shorten
  them, but don't delete one outright unless it said nothing beyond history.

Don't add new commentary except where removing history leaves a gap a
reader would trip on. Expect most comment blocks to get much shorter; a
module header of 60 lines will often become 5 to 15.

## Hard constraints

1. **The arch-free check.** `tools/sos_runner.py` (`_check_arch_free`) fails
   the gate if any line under `kernel/core/` contains an architecture word,
   and **comments count**. The list is `ARCH_WORDS` near line 981 of the
   runner. Removing such words is fine. Never introduce one (no `riscv`,
   `arm64`, `mepc`, `el0`, `pmp`, `csr`, `svc`, `ttbr` and so on, even in
   prose).
2. **No test reads a `kernel/core` line number**, so shifting lines is safe
   here. (Some test sources' line numbers are asserted, and those are out of
   scope.)
3. **Commits carry no attribution trailers.** That's a repository rule.

## Worked example

Before (`kernel/core/sched.saw` module header, abridged):

```
//! THE SWITCH POINT (design 178 D2/D3) AND THE END OF A PROCESS (sawos design
//! 2 D-5/D-6) — because with more than one process those are the same subject.
//! ...
//! # WHY THE TEARDOWN MOVED UP HERE (sawos design 2's structural finding)
//!
//! `end_process` used to live in `kcore.process`, beside the slot it clears.
//! That worked while ending a process ENDED THE MACHINE: ... So a teardown
//! written in `process` would be `process` importing `irq` from above it: the
//! import cycle DF-232e diagnoses, and exactly the shape design 1 met ...
```

After:

```
//! The switch point, and process teardown.
//!
//! This module sits above `threads`, `objects`, `time` and `waitables` and
//! below `dispatch`. Choosing nothing to run parks the core in the idle poll
//! (`irq`); retiring the last thread of a process ends the process.
//!
//! `end_process` lives here rather than in `process` because ending a process
//! can reschedule, rescheduling can idle, and idle delivery reaches back into
//! `process.copy_out`. Placing it in `process` would create an import cycle.
//! Consequence: `process`'s copy routines report a bad buffer instead of
//! terminating, and the callers above the switch point terminate on it.
```

## Verification (all required, in this order)

1. **Code-equivalence check.** Write a small Python script in your
   scratchpad (not in the repo) that, for every changed file, compares
   `git show HEAD:<file>` against the working copy with comments removed:
   strip `//` to end of line (when the `//` is not inside a string
   literal), strip `/* … */` blocks if any exist (check first; a match on
   `/*` inside a `//` comment, such as `tests/*.saw`, is not a block
   comment), drop lines that are then blank, and strip trailing whitespace.
   The two results must be identical for every file. Report the script's
   output. If any file differs, fix it before going on.
2. **Arch-word check.** Run the same scan as `_check_arch_free` over
   `kernel/core/` (import the runner's `ARCH_WORDS` and
   `_is_english_embedding`, or copy them) and confirm zero hits.
3. **Build and boot, targeted.** Comment-only edits can't change behavior,
   but they can still break the build (an orphaned doc comment, for
   example). Run:

   ```
   python3 tools/sos_runner.py --case no_root_image,thread_basics,pipe_basics,slab_donate,process_lifecycle
   ```

   from your worktree root, with no `SAWLANG_ROOT` set. That uses the pinned
   fetch path (it cold-clones sawlang at the `sawlang.pin` sha into
   `~/.cache/saw-toolchain/` the first time, which takes a while). This runs
   all three profiles. Follow the **suite lock** protocol: before running,
   take the lock with `mkdir /private/tmp/claude-501/sawos-suite-lock`. If
   it already exists, another run holds it. Wait for it with a foreground
   loop that retries every 30 seconds; never delete it unless you've verified
   its holder is dead. Run the cases in the foreground, then
   `rmdir /private/tmp/claude-501/sawos-suite-lock`. Release the lock even
   if the run fails. If the toolchain fetch or the build fails for a reason
   unrelated to your edits, stop and send a clarification request with the
   error text.
4. Every case must pass on every profile it runs on. Image sizes may move
   slightly, because a panic location string's line number can change
   length. Report any size change you see, but it isn't a failure.
