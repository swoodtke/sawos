## Description

## Ruling (user, Nov 12)

Processes get a kill. Threads do not.

## Gap (lead review, Nov 12)

This is a kill for **processes**. There is no thread kill and none is
proposed: §8 rules it out ("No thread kill"), and a thread ends by its own
`Exit` or with its process.

A supervisor cannot stop a child. Spec §8 specifies `process.kill()`, gated on
a kill right and process-granular, and marks it not built. §11 lists it under
"Not built" and in the plan. In the tree, `ProcessStatusKind.Killed` is
declared and unreachable, and there is no op and no right
(`kernel/abi/src/ops.saw`, `rights.saw`, `status.saw`). No issue tracked it.

Today a launcher can only wait for a child to exit or fault. A child parked
forever in a wait holds its process slot, its quota and everything it was
given until the machine stops. A shell (SO-1) needs kill to stop a program,
and the observe set (SO-49, SO-50) is defined partly by not carrying it.

§8 names what kill was waiting on: the kernel had no way to tear down a
process other than the one making the syscall. Two things have changed since
that was written:
- `teardown_process` already tears down a process that is not the caller
  (`is_caller == false`), for a process that never ran (`end_unstarted`).
- The kernel is uniprocessor, so during the caller's syscall no thread of the
  target is running: each is ready, blocked or parked.

## To settle in the spec (user review)

- The right: its name, whether `ProcessCreate` mints it to the creator by
  default, and that the observe set never carries it. Ceilings (SO-40) cap it
  like any other right.
- The status word: `Killed`, and whether the killer supplies the code.
- The edges: kill through a handle naming the caller, a `Created` process, a
  `Gone` process and root. By the fault and status rule, a `Gone` target is a
  status, since the caller could not have checked.
- What a killed process's parked calls and waits leave behind. The fault
  teardown is the precedent.

## Sequencing

After SO-50. Spec first.

## Implementation notes (lead, Nov 12)

Two dispatches, after SO-50 merges. **Rules:**

### Step 1: the spec (Opus, or the lead; the user reviews before step 2)

A spec-only patch to §8, §2.7 and §11, settling the points listed in the
description. Lead proposals for the user to rule on:
- `ProcessRight.Kill`, in the set `ProcessCreate` mints to the creator,
  absent from the observe set, capped by ceilings like any right.
- `ProcessOp.Kill(code)`: the status word reads `Killed` with the killer's
  code.
- Through a handle naming the caller: a `NotSelf` fault, as `Exit` through
  another process's handle is today. A process ends itself with `Exit`.
- A `Gone` target: a status, since the caller could not have checked. A
  `Created` target: torn down as `end_unstarted` does, with `Killed`.
- Root cannot be killed by a child unless a launcher gave it root's handle
  with the right; then the machine stops as it does when root exits.
- A killed process's parked calls and waits are abandoned exactly as the
  fault teardown abandons them.

### Step 2: the implementation (Sonnet, from the merged spec)

- `kernel/abi/src/rights.saw` and `ops.saw`: the right and the op. Their
  comments say today that neither exists; rewrite them.

- `kernel/core/dispatch.saw`, the Process arm beside `Exit` and `GetStatus`.
- The teardown: `teardown_process(p, kind, code, is_caller)` in
  `kernel/core/sched.saw` already serves a process that is not the caller

**Lead, Nov 12: the spec is drafted and held for the user's review.** One
commit touching `spec.md` only (`.claude/lead/so70-spec.diff`). Nothing is
uploaded. The whole specification is a new "Kill" block at the end of §8,
marked not yet enforced; every other section points to it.

### What it specifies

- **The right:** `ProcessRight.Kill`, in the one Process default set, so a
  launcher's handle from `ProcessCreate` carries it, as do root's own and
  the one `ProcessSelf` mints. The observe set never carries it. Ceilings
  cap it like any right.
- **The op:** `ProcessOp.Kill(code)`. The status word reads `Killed` with
  the killer's code. It answers `Ok`.
- **It is synchronous and total:** complete when the call returns. No
  thread of the target is running (one processor, and a kill through a
  handle onto the caller is a fault), the teardown has no preemption point,
  and waiters on the death are notified once the status word is written. It
  is not a signal: the target is not told and runs no code after it.
- **The edges:** no right, `AccessDenied`; the caller's own process, a
  `NotSelf` fault, as `Exit` through another's handle is; a `Gone` target,
  `Revoked` with its recorded death unchanged; a `Created` target is torn
  down and reads `Killed`; root ends as on its own exit and the machine
  stops.
- **What it leaves:** calls into and out of the target end as the fault
  teardown ends them (`PeerClosed` on both sides); the target's objects,
  quota and memory go by §2.10's order. Children are not touched: the
  kernel has no parent and child relation, so a supervisor kills each
  process of a subtree.
- **Cost:** one teardown inside the caller's call, bounded by the slabs
  and `MAX_HANDLES`, and interrupt latency for the machine for its length.
- §7 and §11 name kill as what a supervisor does about a child that never
  finishes, once the Timer fires.

### Where the lead's proposals did not hold

- **Killing a never-started child breaks a built justification.** Start
  and Give on a `Gone` child are a `BadState` fault because "a `Gone` child
  was always started and its launcher knows". Once someone else can kill a
  child before its launcher starts it, the launcher cannot know. The draft
  answers `Revoked` for a child killed before it was started and keeps the
  fault for one that had been started. That needs one bit in the record.
- **"The machine stops as on root's exit" left the exit status open.** On
  root's exit the code is the machine's status, so a kill of root with code
  0 would read as a pass. The draft gives it a failing status of the
  kernel's own.

### Decisions for the user

1. **Start or Give on a child killed before it was started:** `Revoked`
   (recommended), or keep the `BadState` fault. The fault punishes a
   launcher for a kill it could not see coming.
2. **The machine's exit status when root is killed:** the kernel's own
   failing status (recommended), or the killer's code.
3. **A process killing itself through its own handle:** a `NotSelf` fault
   (recommended, as `Exit` is), or treated as an exit that reads `Killed`.
4. **Does the handle a process gets onto itself carry the kill right:**
   yes (recommended; one default set, and a process can hand a watchdog the
   means to stop it), or no.
5. **Does the killer supply the code:** yes (recommended), or a fixed one.

### Found on the way, to file separately

Two stale sentences, in spec §9 and in `process_rights`' doc, say a
launcher cannot narrow the handle its child derives; ceilings let it.

## Rulings (user, Nov 13)

1. "It should be an error to kill an unstarted process (it should just be
   released since there is nothing running so nothing to kill)."
2. Root killed: a distinct failing status.
3. A process killing itself through its own handle: a fault.
4. The handle a process gets onto itself carries the kill right: yes.
5. The killer supplies the code: yes.

### What ruling 1 changes in the draft

- A kill of a `Created` process is refused and changes nothing. A process
  that was never started is ended by releasing every handle onto it, as
  now.
- So nothing can end a child between its creation and its start except
  its handles going, and the draft's exception falls away: Start and Give
  on a `Gone` child stay the `BadState` fault they are today, with no
  `Revoked` case and no "was started" bit in the record.
- Whether the refusal is a fault or a status is for the spec to settle by
  the usual rule (could the caller have checked?), and the lead will say
  which it chose and why when the revised text goes up.

The spec is revised to these and then uploaded for review.

**Lead, SO-70.p1: the spec, uploaded on the user's rulings (Nov 13, above).**
`spec.md` only; everything new is marked not yet enforced. The
specification is the "Kill" block at the end of §8; §2.7, §2.8, §5.3,
§5.7, §7, §11 and §12 point to it.

The five rulings as specified:
1. **A kill naming a `Created` process is refused and changes nothing.** A
   never-started process is ended by its handles being released, as now.
   So Start and Give on a `Gone` child stay the `BadState` fault they are,
   and §2.10's Process row and §3's Give list read as on main.
2. **Root killed:** its teardown runs and the machine stops with a failing
   status of the kernel's own, distinct from a fault's and a deadlock's.
3. **A kill through a handle naming the caller** is a `NotSelf` fault, as
   `Exit` through another's handle is.
4. **`ProcessRight.Kill` is in the one Process default set,** so
   `ProcessSelf`'s handle carries it; the observe set never does.
5. **`Kill(code)`:** the status word reads `Killed` with the killer's code.

**One choice the rulings left to the spec, for the reviewer and the user
to weigh:** ruling 1's refusal is the status `WouldBlock`, not a fault. The
author's reasons: a launcher knows whether it started its child, but a
holder handed a kill-carrying handle before the start cannot (a `Created`
process's status word reads `Running`), so by the fault rule it is a
status; and `WouldBlock`'s stated meaning (§2.1) is an object not yet in a
state to serve the call, whose answer changes when another party acts,
here the launcher's `Start`. `Revoked` would be false, since the process
can still start. The alternatives are a `BadState` fault, with the advice
that a kill-carrying handle is handed out only after the start, or a new
status nothing else would use.

**Sweeps:** every mention of kill, `Killed` and the right is marked or
inside a marked block; nothing built lost a statement or gained a marker.

**Not this patch:** two stale sentences (§9 and `process_rights`' doc) say
a launcher cannot narrow the handle its child derives; ceilings let it.

**Changes requested (rev 1): one sentence says more than the kernel does, and the choice you put to the reviewer and the user needs the user's word before it merges.** The other four rulings are specified as ruled, and the block's "as at any death" statements match §2.1, §2.7, §2.10 and the kernel wherever I and an agent could read them (eighteen claims checked against the patched spec and `kernel/core`; I reread the three that did not simply agree).

**1. The sentence to fix.** "An outlet whose last handle the target held goes too, so the messages staged there are abandoned and every caller parked on that connection, for a reply or for room, is answered `PeerClosed`."
- The outlet column reaching zero drops what is STAGED (§2.1: "The outlet column reaching zero drops what is staged"; `pipe_drop_staged`: "The rest stay, holding the answer their claims are owed").
- A caller whose message was already taken is parked for a reply on an obligation, and a one-shot is transferable ("the delegation primitive"). If the target took the message and handed the obligation to another process, that caller stays parked until that process replies or drops it; the target's death does not answer it.
- So: every caller whose message is still staged there, and every caller parked for room. The callers whose obligations the target still holds are the previous sentence's.

**2. Ruling 1's refusal: `WouldBlock` or a fault. My weight is on a `BadState` fault; it is the user's to say.**
- Your fact is right: a `Created` process's status word reads `Running` (§2.8, "It cannot tell a process that was never started from a running one"), so a holder cannot check.
- But who can be that holder? Today a Process handle does not travel in a message (§2.1: "`Process` and `System` are refused at the sender", a scope line with a named follow-up), so a kill-carrying handle onto a child reaches a third process only through `Give` into that process's boot set while it is `Created`. The one case is a launcher that starts the watchdog before it starts the child: an ordering inside one launcher's code. Once messages carry Process handles, whoever sends one still chooses when.
- The user ruled on that shape on SO-58 (Nov 9), keeping `waiter_add`'s `BadState` fault where the second process could not see the first's attachment: "the fault indicates a program error - which this is ... enforce that however you want in your code". A contract between cooperating programs is still the programs'.
- It is also what the neighbours do: `Start` and `Give` on a child in the wrong state are `BadState` faults in the same paragraph, for the reason that "the launcher that started it knows".
- And `WouldBlock` has no general meaning to lean on. Every use in the spec is a pipe's ring (§2.1, §5.7, §11), and `status.saw` defines it as "a `Post` whose ring is full, and a `Take` whose ring is empty", which "says call again". The ruling's own advice for an unstarted process is to release it, not to call again.
- If the user keeps the status: §2.1 and `SosStatus.WouldBlock`'s doc need the general definition the block cites, since neither has it.

**Smaller, same revision:**
- **The code is 16 bits where a watcher reads it.** `process_status_word` keeps `code & 0xFFFF`. "The op takes one argument word ... every word is a valid code" is true of what is accepted, and the watcher gets the low 16 bits; say so (the spec is silent on an exit code's width too).
