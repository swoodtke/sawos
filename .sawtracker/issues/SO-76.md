## Description

## Scope

The first run on silicon: the S3 smoke's boot case on a real ESP32-S3 board.

- A flashable image the ROM or a second-stage loader accepts, and the flash
  recipe (`esptool`, or OpenOCD over the built-in USB JTAG).
- Whatever silicon needs that the emulator forgave: the watchdogs, the clock
  setup, the console (UART0 or USB-Serial-JTAG, by board).
- Each difference goes into `hal/xtensa-esp32s3/ABI.md` beside the emulator's
  answer.

The probe unit's bare stub can be flashed first, before the kernel boots under
QEMU, to prove the boot path early.

## Needs the user

The user flashes the board and returns the serial log. The lead supplies the
image and the exact commands. Needed from the user: which S3 board (the module
and whether it exposes UART0, the USB port or both).

## Acceptance

- [ ] the banner and the handover line on a real board's console
- [ ] a Timer fire reaches a process on the board
- [ ] the recipe is in the HAL's README

## Implementation notes (lead, Nov 12)

**Rules:** `.sawtracker/docs/implementer-rules.md`. **Blocked on:** SO-73 for
step 1, SO-75 for the rest. This unit alternates between an agent and the
user at the board; the lead relays.

### Needed from the user first

- The board: its name and module, and which ports it exposes (UART0 through a
  USB bridge, the native USB port, or both).
- That the board is connected to this machine, and the serial device's path.

### Step 1: the bare stub on silicon (Sonnet prepares; the user flashes)

1. Wrap SO-73's stub in whatever image the real ROM accepts (`ABI.md`'s boot
   section says which; the emulator may accept more than silicon does).
2. Write the exact flash and monitor commands, using the `esptool` in the
   ESP-IDF Python environment under `~/.espressif/python_env/`, into the
   HAL's README.
3. The user flashes and returns the serial log. Expected: the banner, the
   `syscall` line and three timer lines, as under QEMU.
4. Each thing silicon needed that the emulator did not (a watchdog to
   disable or feed, clock setup, the console's real divisor) goes into
   `ABI.md` beside the emulator's answer, marked as probed on silicon.

### Step 2: the kernel on silicon

The same recipe with the S3 smoke's boot image, then the Timer case. If the
board hangs with no output, use OpenOCD over the built-in USB JTAG
(`~/.espressif/tools/openocd-esp32/`) and report the PC and the exception
cause registers.

### Acceptance check

The serial log from the board, pasted into the issue by the lead.

**Lead, Nov 12: step 1 is unblocked.** SO-73's stub boots under QEMU, so it
can go onto a real board as soon as the user names the board and connects
it. What `ABI.md` §11 says to expect on silicon, in the order to check:
1. **Direct boot may be fused off.** Read the eFuses first
   (`espefuse.py summary`): the ROM skips direct boot if secure boot is on or
   the legacy SPI boot mode bit is set (§2a).
2. **Watchdogs.** Expect the RTC watchdog, TIMG0's watchdog and the super
   watchdog to be live. The stub needs a disable step before it prints its
   banner; the registers and the unlock key are in §11 and §2c.
3. **The console.** UART0 through a USB bridge works as under QEMU. A board
   that exposes only the native USB port needs the USB-Serial-JTAG registers,
   which the emulator does not model (§4).
4. **Loads through the flash instruction window** (`l32r` and `.rodata`),
   unaligned access and the SRAM alias (§3a, §3c). ESP-IDF links literals
   into its flash text, so `l32r` is expected to work; `.rodata` moves to the
   data-bus window if it does not.


<!-- sawtracker:comment {"author":"agent:claude-sawos","body_bytes":2642,"created":"1794522349","id":"c3"} -->
**Lead, Nov 12: prepared for the first flash.** A new commit on top of
SO-75's two, in the lead's worktree; it is uploaded once SO-75 merges, since
it depends on it. Nothing has run on silicon. The lead reran the S3 smoke
with it (20 of 20) and built the five staged board images
(`.claude/lead/s3-flash/`: `boot`, `umode_syscall`, `timer_tick`,
`bus_probe`, `root_server_boot`, each about 115 KiB).

- **Watchdogs:** `_start` disables the RTC watchdog and TIMG0's, and sets
  the super watchdog to auto-feed, right after leaving the ROM's register
  window. Every register, key and bit is cited to esptool's S3 target or the
  ROM ELF on this machine (`ABI.md` §2e). The emulator's watchdogs never run,
  so no mutant can show this works.
- **The image:** `tools/sos_runner.py --board esp32s3 --emit-flash CASE
  --out PATH` writes a trimmed binary for flash offset 0, checks the
  direct-boot magic at 0x400 and that byte 0 is not 0xE9, and prints the
  `write-flash` command. The linker script places flash as one contiguous
  run so the image is short.
- **No `simcall` on a board image:** it is linked with
  `_sos_semihosting = 0`, so every stop prints its line and then loops
  quietly.
- **A read-only eFuse check** comes first in the recipe: `DIS_DIRECT_BOOT`
  and `SECURE_BOOT_EN` decide whether the ROM will direct-boot at all. No
  command in the recipe writes an eFuse.
- **Console:** UART0 at the ROM's 115200 baud, through a board's
  USB-to-UART bridge. A board with only the native USB port needs
  USB-Serial-JTAG, which is a written plan (`ABI.md` §4a), not built.
- **`bus_probe`,** a new stage: it makes each kind of access the kernel
  relies on, naming each before it runs, so a part that refuses one says
  which.
- **The README's "First run on a board"** is the recipe: what to connect,
  the eFuse read, build, flash, monitor, the expected text per stage, and a
  table of predictable failures.

**The expected failure.** esptool's S3 memory map marks only DRAM addresses
as byte-accessible, and process memory sits at IRAM addresses. So the
implementer expects `bus_probe`'s byte store to process RAM to fault on a
part, and `root_server_boot` with it. The fix keeps process code at IRAM
addresses and moves writable segments, the arena and stacks to the DRAM
names of the same memory; the loader's checks for that live in
`kernel/core/`, so it is a design unit of its own, written up in `ABI.md`
§11 and not built. The board will say whether it is needed.

**Needed from the user:** the board's name and module, which ports it has,
the serial device path, then the eFuse summary and each stage's console
text.

**Silicon, the later stages (user, Nov 12).** Images from
`.claude/lead/s3-flash/`, built from the preparation commit.

**`timer_tick`: user mode and the timer interrupt work.**

```
SOS M2: timer bring-up on xtensa (ESP32-S3)
SOS M2: timer armed
SOS M2: entering U-mode
SOS: console handover
SOS: timer tick 0x00000001 at 0x42019680
SOS: timer tick 0x00000002 at 0x42019680
SOS: timer tick 0x00000003 at 0x42019686
SOS: timer tick 0x00000004 at 0x42019689
```

SYSTIMER, the interrupt matrix route, the level-1 vector in IRAM, the frame
save and restore, and execution in place from the flash instruction window
all hold on the part. The paste ends before `SOS-S3: halt pass`; the
payload's spin is counted in instructions and the part is far slower than
the emulator, so whether the line arrives later is still to be confirmed.

**`root_server_boot`: the expected failure, in the loader.**

```
SOS: root image ok segments=0x00000002 entry=0x403a043c prio=0x01010100
SOS-S3: kernel fault vector=0x00000300 exccause=0x00000003
  epc1=0x42011863 excvaddr=0x403a0000 depc=0x00000000
```

(one line on the console). `epc1` is `s8i a7, a11, 0` in
`kcore.mem.copy_bytes`, the first byte the loader stores into root's
region, and the cause is 3, `LoadStoreError`. The byte load from the image
in the data window, the instruction before it, succeeded. So **the part
refuses a byte store at an IRAM address**, as `ABI.md` §11 expected, and no
process can be loaded where the layout puts it.

**`bus_probe`: one more refusal, and two faults in the tooling.**

```
SOS probe: bus probe on xtensa (ESP32-S3)
SOS probe: word load, instruction window at 0x42018d20
SOS probe: ok 0x00f5a542
SOS probe: byte load, instruction window at 0x42018d21
SO ltcx0000 s0000302043ax21d1=0000ESP-ROM:esp32s3-20210327
```

- A word load through the flash instruction window works (every `l32r`
  does this). **A byte load through it is refused.** Nothing in the kernel
  makes one: images, `.rodata` and the region table are read through the
  data window.
- **The fault line is mangled** because `sink.c`'s `fault_str` and
  `fault_hex` store to the UART FIFO without waiting for room. The
  emulator's FIFO never fills; here it was full of the lines just printed.
  The fault path must wait as the console path does.
- **The probe stops at the first refusal,** so the data-window and
  process-RAM steps never ran. It should recover from a refused access and
  carry on, and gain a step for the alias itself (a word stored through a
  DRAM address read back through its IRAM name).
- **The board reset after the fault,** where the halt should spin. The
  reason is on the `rst:` line after the second banner, which the paste does
  not include. Asked of the user, with whether the other stages stay halted.

**What follows:** a process's writable memory and read-only data have to
sit at DRAM addresses, with its code at IRAM addresses. That is a new unit
(filed next), ahead of the box's drivers.
