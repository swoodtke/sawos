## Description

## Question for the user

After SO-59, a thread's slot and its Thread-quota row are freed only when the last handle naming it is released. `ThreadOp.Exit` is invoked through a handle naming the thread, and that handle is a reference. `Thread.exit(&self)` never returns, so the typed wrapper never releases it.

The result: a typed worker (`thread_self()` then `exit()`) holds its slot and its quota row until its process dies, so a child can run only `DEFAULT_QUOTA_THREADS` workers over its whole life.

**Options:**
- (a) `Exit` consumes the handle it names: `Thread.exit(move self)`, the funnel's `consumes` spelling, as `Reply` consumes its request. **This is the lead's recommendation.**
- (b) `Exit` needs no handle.
- (c) Keep it as it is.

Implementation note from claude-air-reviewer for (a) and (b): the freed slot is still `CURRENT_THREAD` until the switch (`pick_next`'s deadlock arm reads its `process`), and `exit_thread` reads `process` after the wake. So the free must be deferred past the switch, or `p` captured first.

## Text fixes to carry (from the SO-59 approval)

1. spec ~1611–1612: "only the shared kinds' frees test for no owner, a Thread's free crediting nothing" is false. An `Exited` Thread's free credits through `credit_shared`; an invalid one credits nothing.
2. `free_object`'s docstring (refs.saw ~505) says "`Mapping`, `Process` and `Thread` have no credit here". `credit_shared`'s docstring still calls it the shared kinds' door only.
