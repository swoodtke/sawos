## Description

## Finding (the SO-81 audit, Nov 12)

A Timer becomes ready when its interrupt is delivered and serviced. The
kernel then counts every period it missed (`fire` in `kernel/core/time.saw`),
so the count is right as of that service. Between services it lags the clock.

Under heavy host load the audit saw a process spin through about five timer
periods of its own clock while the kernel took one timer interrupt. A wait at
that moment reported one fire. On an emulator that is the host starving the
emulator's timer thread; on hardware the same lag is any latency between an
expiry and its interrupt being taken, which is small but not zero.

## The question

Should a wait that looks at a Timer first expire it against the clock, so
that the count it reports is as of the wait and never lags, whatever the
interrupt's latency?

- **For:** "several periods have passed, so the count is above one" becomes
  true by construction for any caller that can read the clock, on a loaded
  emulator and on hardware alike.
- **Against:** a wait would do work that today runs only in interrupt
  context, and readiness would no longer mean "the interrupt was delivered
  and serviced", which spec §2.2 and §2.6 are written around.

The tests no longer depend on the answer: SO-81 made them wait on the
kernel's own interrupt count.

**Brief (lead): a wait expires the Timers it looks at against the clock.** The user ruled yes on Nov 14.

**What is built.**
- **Kernel.** When a wait (and anything else that reads a Timer's readiness or its count for a process: find each reader) looks at an armed Timer, it first brings the Timer up to the clock: if the expiry has passed, the Timer is ready and its count includes every period that has passed as of that look, by the arithmetic `fire` already runs when the interrupt is serviced (`kernel/core/time.saw`). The clock is read once per wait, not once per Timer. The interrupt path is unchanged in what it does, and the two must agree: a period is counted once, whichever of them saw it first, and a Timer the wait brought up to date does not fire again for the same period when its interrupt arrives.
- **Spec.** §2.2 and §2.6 are written around "ready when the interrupt was delivered and serviced". They change to: a Timer is ready once its expiry has passed, as of its interrupt or of a wait that looked, and the count a wait reports is as of the wait. State what a one-shot and a periodic Timer report, what re-arming and disarming do to a Timer the wait has brought up to date, and that nothing else about waits changes.
- **Interrupts stay masked in the kernel**, so the look and the interrupt path cannot interleave on one processor; say so where the code relies on it, and keep the look bounded (no preemption point is added).

**Cases.** No case asserts a value that depends on host time (CLAUDE.md has the rule and how to build a case that needs an event to have happened).
- The property the ruling is for, held by construction and not by the clock's speed: a process arms a periodic Timer, reads the clock until several periods have certainly passed (it can read the clock; a stalled host only makes more pass), then waits: the count is at least that many, on every profile, whether or not the kernel took an interrupt in between. Before the change the case must fail when no interrupt was serviced in that span; find a way to make that so by construction (the existing cases that mask or hold off the tick show how), and show the case red on main.
- A one-shot whose expiry has passed is ready at the wait without its interrupt having been serviced, and its interrupt arriving later does not make it ready a second time.
- A Timer brought up to date by a wait and then disarmed, and one re-armed, report what the spec says.
- Each new line is shown to hold by a one-operator mutant (the comparison with the expiry, the period count's arithmetic, the "counted once" guard), red then green.

**Scope.** `kernel/core/time.saw`, `waitables.saw` and whatever reads a Timer for a wait; `spec.md`; the cases. Another unit is changing `kernel/core/process.saw`, `dispatch.saw`'s slab code, `limits.saw` and the boot path: stay out of those files.

**Lead: SO-83.p1 is up: a wait expires its Timers against the clock.** Gate on the implementer's machine: 792 / 6 / 39 (main's 789 plus the new case on three profiles); no existing case or expectation moved.

**What it does.**
- `time.saw`: `catch_up_timer(slot, now)` runs `TimerSlot.fire(now)` for a live Timer that is due, without the wake: every period passed is counted by the interrupt's own division, a periodic Timer's deadline moves past `now`, a one-shot disarms. So whichever of the look and the interrupt runs second finds nothing due.
- `waitables.saw`: `waiter_ready_attachment`, the scan behind `Waiter.Wait` and the wait leg of `ReplyWait`, brings each Timer attachment it reaches up to the clock before asking whether it is ready. The clock is read once, at the first Timer the scan reaches. A Timer the scan brings up is ready, so the scan returns it and the same call delivers it.
- The hardware comparator is not reprogrammed after a look: the old deadline's interrupt arrives, finds nothing due and reprograms as it does today.
- `spec.md` §2.6 and §2.2 say it: ready once the expiry has passed, as of the interrupt or of a wait that looked; the count is as of the wait; a period is counted once; arming or disarming clears a count a wait brought up and had not delivered.

**The case, and why it is in the kernel.** A process cannot hold off its own timer interrupt, so "the deadline passed and no interrupt was serviced" cannot be made true by construction from a process: there the change shows only under delivery latency. `timer_asof` is a harness kernel with the tick never started, so no interrupt is taken, and it reads the Timer's own count before the look (`untouched=1`). It reaches the wait path through a new module, `kernel/core/probe.saw`, which builds one Timer attached to one Waiter and calls the real `waiter_ready_attachment`, `waitable_answer` and `waitable_consume`, and runs `on_timer_interrupt` by hand (made `public(package)` for that). Nothing in a shipping kernel imports it and images link with `--gc-sections`. **For the reviewer to judge:** whether a probe module in `kcore` is the right seam for this, and that it leaves the gate's images byte for byte (the implementer reports no existing row moved).

Every number is bracketed by clock reads the case takes itself (`owed(first, before) <= count <= owed(first, after)`), so nothing asserts a duration and a stalled host moves both ends together. Red on unchanged main, riscv32: `atleast=0 bracketed=0`, `oneshot fires=0 disarmed=0 second=1`, `up=0` twice.

**Mutants, each alone, riscv32:** `is_due` negated; `is_due` replaced by `armed` (panics on the far re-arm); `fire`'s `base + step` to `base` (both counted-once lines 0); `fire`'s `+ 1` to `+ 2` (the second look's counted-once is 0; the first look's upper bracket is loose on a slow host and does not see it); the clock never read; the call removed (the red-on-main run).

**Left as it is, said plainly.**
- `waiter_add`'s readiness check at attach is unchanged: it only decides whether to wake a parked thread and reports no count, and an expired Timer's interrupt is already pending.
- "The clock is read once per wait" is not held by a case (one Timer per Waiter in the probe); reading it per Timer would differ only in which reading a later Timer is judged against.
- No process-level case was added: through the syscall path the property holds on main too whenever the interrupt was serviced, so such a case could not be shown red.

**Brief (lead): SO-83.p1 revision 3. Programming the timer hardware again never moves a deadline it is already waiting on later.** The reviewer's finding on revision 2 is right, and the lead takes the first of its two choices: the floor is fixed where it lives, which also closes the route that is on main today (SO-111).

**The fault.** `reprogram_timer` (`kernel/core/time.saw`) programs the hardware no sooner than `now + TIMER_MIN_LEAD_NS`, counted from now at every call. Once the earliest thing owed is inside the lead, each call moves the comparator a whole lead out again, so a thread that reaches `reprogram_timer` more often than once a lead keeps the comparator from ever being reached: no tick, no other Timer's wake. Revision 2 added a wait's look to the callers; `Timer.Arm` is one on main.

**The rule to build.** The kernel remembers the instant it last programmed the hardware for (`NEVER_NS` when none, or when that programming has been spent). In `reprogram_timer`, with `next` the earliest thing owed and `wanted = max(next, now + TIMER_MIN_LEAD_NS)`:
- if a programmed instant is remembered, it is no later than `wanted`, and it is still good for what is owed (it is at or after `next`, or `next` is already due), the hardware is left alone;
- otherwise the hardware is programmed for `wanted` and that instant is remembered;
- nothing owed programs "never" and remembers none, as today.
The interrupt's own service (`on_timer_interrupt`, however it was entered: the trap, the idle poll, a preemption point) forgets the remembered instant before it programs again, because that programming has been spent: this is the one place a new lead starts, which is what the floor exists for (a schedule that is always due cannot hold the machine in the trap handler).

Work the cases through before writing it, and put the table in the hand-back: a programmed instant in the future that covers `next`; one in the future that is later than a newly armed, sooner deadline (must move earlier); one already passed with something due (interrupt pending: leave it, it is taken on the way out of the kernel); one already passed with nothing due (a look counted its deadline: program for what is owed, which is what `timer_asof`'s `due=1 quiet=1` holds); `next` is never. **Lead: SO-83.p1 revision 3. Programming the timer again never delays what it is already waiting on** (the reviewer's first choice; it closes SO-111's route too). Gate on the implementer's machine: 803 / 6 / 39 (795 plus eight new rows); thirty repeats of the six timer cases on every profile, all green; the timer and wait family 131.

**The rule, in `reprogram_timer`** (one function, and the one place the kernel stores to the comparator):

```
target = NEVER_NS
if next != NEVER_NS {
    now = hal.timer_now_ns(); floor = now + TIMER_MIN_LEAD_NS
    target = if next < floor { floor } else { next }
    if PROGRAMMED_NS <= target && (next <= PROGRAMMED_NS || next <= now) { return }
}
hal.timer_set_deadline_ns(target); PROGRAMMED_NS = target
```

`on_timer_interrupt` forgets the remembered instant first (`timer_programming_spent()`), however it was entered: the interrupt's service is the one place a new lead starts, which is what the floor is for. Nothing remembered reads as `NEVER_NS`, later than any `target`, so it is never kept.

| state | what the rule does |
|---|---|
| the programmed instant is in the future, at or after `next` | kept; `target` only grows as time passes, so it is never pushed out (the fix for the wait loop and the re-arm loop) |
| in the future, later than a newly armed sooner deadline | later than `target`, so programmed earlier; if the new deadline is inside the lead the old instant is kept, which is as soon |
| passed, something due | kept: the pending interrupt is taken on the way out of the kernel |
| passed, nothing due (a look counted it) | programmed for what is owed, or never (`timer_asof`'s `due=1 quiet=1`) |
| `next` is never | programs never, remembers none |
| in the future but earlier than everything still owed | programmed again, possibly later: nothing owed is at or before it. A `next` inside the lead can be delayed by one lead, once |

**Spec §2.6:** the floor is counted from the reading at which the hardware is programmed afresh, which happens only when its interrupt has been serviced or what it waits on no longer serves; programming again never delays what it waits on; so a thread that arms a Timer, or waits on one, more often than once a lead cannot hold off the tick or another Timer's fire.
