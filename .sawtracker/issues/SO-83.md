## Description

## Finding (the SO-81 audit, Nov 12)

A Timer becomes ready when its interrupt is delivered and serviced. The
kernel then counts every period it missed (`fire` in `kernel/core/time.saw`),
so the count is right as of that service. Between services it lags the clock.

Under heavy host load the audit saw a process spin through about five timer
periods of its own clock while the kernel took one timer interrupt. A wait at
that moment reported one fire. On an emulator that is the host starving the
emulator's timer thread; on hardware the same lag is any latency between an
expiry and its interrupt being taken, which is small but not zero.

## The question

Should a wait that looks at a Timer first expire it against the clock, so
that the count it reports is as of the wait and never lags, whatever the
interrupt's latency?

- **For:** "several periods have passed, so the count is above one" becomes
  true by construction for any caller that can read the clock, on a loaded
  emulator and on hardware alike.
- **Against:** a wait would do work that today runs only in interrupt
  context, and readiness would no longer mean "the interrupt was delivered
  and serviced", which spec §2.2 and §2.6 are written around.

The tests no longer depend on the answer: SO-81 made them wait on the
kernel's own interrupt count.

**Scheduled by the user (Nov 13)** to run beside the memory work, on Sonnet. It still needs its ruling before any code: should a wait that looks at a Timer first expire it against the clock? The lead's recommendation is yes: the catch-up arithmetic already exists in `fire`, a wait would run it for the Timers it looks at with the clock read once, the count a wait reports is then as of the wait on every machine, and a wait on a Timer whose expiry has passed returns without the round trip through its interrupt. Readiness in §2.2 and §2.6 becomes "its expiry has passed, as of the interrupt or of a wait that looked".
