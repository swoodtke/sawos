# Design: a source of randomness for SOS

**The owner's ruling (Nov 29):** SOS provides a randomness generator.

**Why.** Today the kernel gives programs nothing random, so everything that
needs unpredictability derives it from a fixed per-image key and a boot
counter, and repeats from one boot of an image to the next:
- TCP ISNs (`drivers/netstack/src/isn.saw`);
- the DHCP transaction id;
- DNS query ids and source ports (`svc-net`'s `netsecret` input).

SO-184's review reproduced the repetition across two boots. Every future
secret (TLS, WPA2's supplicant in the networking design §6.3, stack
canaries, ASLR if it ever comes) needs the same thing.

## What to design (a design document, not code)

Write a design to `/Users/shawn/Projects/sawos/.leadwork/rng/design.md`, in
the house style of the other designs (read
`/Users/shawn/Projects/sawos/.leadwork/SO-165/design.md` for the shape:
decisions in one place, each claim sourced with **[read file:line]** or
**[probed]**, cases with their mutants, units sized). Cover:

1. **The sources, per board, with what each really gives:**
   - **ESP32-S3:** `RNG_DATA_REG`. When is it a true entropy source (RF
     running, SAR ADC on) and when only pseudo-random? Read the TRM text
     and ESP-IDF's `bootloader_random*` and `esp_random`.
   - **riscv32 and arm64 `virt` under QEMU:** `virtio-rng`, which needs a
     driver and a transport. Is arm64 `RNDR` (ARMv8.5) available on the
     suite's CPU model? Is there anything on riscv32 (Zkr's `seed` CSR)?
   - **The flat profile, and the C3.**

   Say what the emulators can and can't show, and what only a board can.
2. **Where the generator lives.** Kernel or userspace (a driver serving a
   protocol, as `uartproto` and `netdevproto` do), or a split: a kernel
   DRBG seeded by a userspace driver. Weigh the microkernel's habits (no
   device code in the kernel unless needed) against needing randomness
   before any process runs (root's own secrets, the loader) and the cost
   of a call per draw. Recommend one.
3. **The generator itself:** a standard DRBG (ChaCha20, or NIST SP 800-90A
   Hash/HMAC/CTR_DRBG). Its state, how it's seeded and reseeded, how much
   entropy is credited from each source, and what happens before enough
   entropy has arrived: block, refuse, or answer flagged. Say what a draw
   returns and what it promises.
4. **The API and its authority:**
   - which right or object grants randomness;
   - whether every process gets it by default;
   - the op or protocol shape;
   - `sos` wrappers and a std seam if sawlang has one (check sawlang's
     `runtime/ABI.md` for a random seam such as `__saw_rt_random`).
5. **The users, moved:**
   - netstack's ISN key;
   - the DHCP xid;
   - DNS ids and ports;
   - `svc-net`'s `netsecret` (dropped, or kept as a test override).
6. **Tests:**
   - no test asserts a random value's content;
   - an emulator case shows two boots differ;
   - a case shows the not-yet-seeded behaviour;
   - mutants for each check;
   - what the board stage checks.
7. **Units,** in order and sized, as SO-165's §11 does.
8. **Questions for the owner.**
