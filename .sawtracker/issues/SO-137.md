## Description

**A console driver: `uartproto` served over the kernel's console.** The owner's idea (Nov 17): a process that serves `uartproto` and writes what it is sent through its System handle's `debug_print` (the kernel console), so a product's processes print through a UART connection on every board. On a board with a real UART driver (`svc-uart-ns16550`, `svc-uart-pl011`, and an S3 one later) the image names that driver instead, and the clients do not change. The useless box (SO-78) is its first user: the S3 has no UART driver, and the kernel console is UART0.

**Build:** `drivers/svc-console/` (the name is the implementer's to propose), a declaration with a `system` record (the only process in an image that needs `SystemRight.Debug`, so clients can run without it) and one `serve` record on `uartproto`; it runs on every board (no device needs). `Write` goes to the console; `Sync` answers once every earlier write is out; `Mark` as the protocol says. `Read`: the kernel console has no input for a process; say what the driver answers (a reply of no bytes at once, or a refusal the protocol can carry) and state it in `uartproto` and the driver; a read must never park forever unanswered.

**Cases:** a described image on each gate board and the S3 (the stock root, the console driver, a client that writes, syncs, reads, and ends), the client's text appearing on the console in order; the same client image built against the board's real UART driver where one exists, printing the same text; every refusal and stop held (the review standard). Note the cost in the driver's doc: each write is a pipe round trip and then the kernel's synchronous console write (which, on the S3, stalls with interrupts masked while UART0's FIFO is full), so it suits a product that prints little.

**For the box:** the S3 has four child slots; with the GPIO driver, the PWM driver, the controller and this, they are full.
