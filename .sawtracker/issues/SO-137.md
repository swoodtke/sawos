## Description

**A console driver: `uartproto` served over the kernel's console.** The owner's idea (Nov 17): a process that serves `uartproto` and writes what it is sent through its System handle's `debug_print` (the kernel console), so a product's processes print through a UART connection on every board. On a board with a real UART driver (`svc-uart-ns16550`, `svc-uart-pl011`, and an S3 one later) the image names that driver instead, and the clients do not change. The useless box (SO-78) is its first user: the S3 has no UART driver, and the kernel console is UART0.

**Build:** `drivers/svc-console/` (the name is the implementer's to propose), a declaration with a `system` record (the only process in an image that needs `SystemRight.Debug`, so clients can run without it) and one `serve` record on `uartproto`; it runs on every board (no device needs). `Write` goes to the console; `Sync` answers once every earlier write is out; `Mark` as the protocol says. `Read`: the kernel console has no input for a process; say what the driver answers (a reply of no bytes at once, or a refusal the protocol can carry) and state it in `uartproto` and the driver; a read must never park forever unanswered.

**Cases:** a described image on each gate board and the S3 (the stock root, the console driver, a client that writes, syncs, reads, and ends), the client's text appearing on the console in order; the same client image built against the board's real UART driver where one exists, printing the same text; every refusal and stop held (the review standard). Note the cost in the driver's doc: each write is a pipe round trip and then the kernel's synchronous console write (which, on the S3, stalls with interrupts masked while UART0's FIFO is full), so it suits a product that prints little.

**For the box:** the S3 has four child slots; with the GPIO driver, the PWM driver, the controller and this, they are full.

Requested changes on patch SO-137.p1 (revision 1)

**Changes requested, sent now because a revision is coming: one fault in both real UART drivers, and smaller things for the revision to carry. I stopped the rest of the review of revision 1 when you said to hold; what was done is at the end.**

**1. Both real drivers lose a buffered input byte when a `Read` they can answer at once has had its claim dropped.** The `Read` arm pops the byte (`body.ok_byte(input.pop())`), `answer` takes the failed reply as discharged and waits again, and nothing puts the byte back or counts it. `answer_held` beside it unpushes on the same failure ("so the next reader gets it"), and `InBuf`'s doc says a lost byte is never silent. On main the driver ended on that path (`return BUG`); the patch makes it live.

Run here (chat f335), ns16550 on riscv32 and flat and pl011 on arm64, each the same: with the harness's four bytes handed over at once (`SERIAL_TYPE_DELAY_S = 0`; the unchanged client still passes) and `svc-client` posting one `Read` and dropping its claim after its first round, a two-round client echoes `q#` where without the dropped read it echoes `q7`, and the three-round client hangs on a byte that went to nobody. No gate case reaches the path because the harness types a byte every 0.15 s, so every read is held before its byte comes: it is your named survivor, and pl011's twin. Handing the input over at once for one case would hold it without a clock.

**2. A change the note's driver list does not name:** a `Read`, `Sync` or `Mark` carrying a payload was served by both real drivers (`op_of` read the op byte alone) and is answered `BadOp` now (`Frame.request()`).

**3. Three hosted mutants pass, each closed by one assertion** (f337; run here, green alone and red with its mutant):
- `count_up` saturating from halfway (`count > 0x7FFF_FFFF`): `decisions.saw` says "saturates at its top and nowhere below it" and has no sum that ends just below the top. `check(count_up(0xFFFF_FFFD, 1) == 0xFFFF_FFFE, …)`.
- `Tally.count`'s `Busy` arm counted as refused: `t.count(UartStatus.Busy, 0)`, then served 5, refused 1, unsupported 1.
- `UartStatus.describe` with a name changed: only the text client's failure line reads it.

**4. Statements.**
- **`answer`'s doc, all three drivers:** "the client dropped its claim, as every `Write`'s does". A `Write` sent as a call keeps its claim; the protocol says so and `uart-text-client` does it.
- **`uartproto`'s module doc:** "each package that sends or receives asserts that `BODY_BYTES` is the kernel's". `templates/product/hello` sends and has no such assert (the send's array type refuses a skew anyway).
- **`uart-text-client/process.toml`:** "It holds, at the most, its System, Process and inlet, the claims of the four reads it posts, and the four Events" is eleven; `handles = 7` passes `console_service` and `console_service_uart` on every board and 6 is red. The claims are gone before the Events are made, so the row of 12 is five above its floor.
- **`uart-text-client`'s doc** leaves out the driver that has input buffered: it answers the posted read `Ok` and a byte at once, and the client then stops with its mismatch.

**5. For the owner, not a request:** `Busy` is a fourth status; the ruling on this issue names three. Your note says so; I have told the owner.
