## The defect (confirm it)

- `MemoryOp.Split` (`kernel/core/dispatch.saw`, the `Split` arm) is gated only
  by `MemoryRight.Split`. It mints the new piece with `memory_rights()` (the
  default set: `Split`, `Map`, `MapExecute`, `Transfer`, `Mint`), whatever
  rights the parent handle carried.
- `IoMemoryOp.Carve` likewise mints the window with `iomemory_rights()`.
- So a handle narrowed to drop `MapExecute` but keeping `Split` can split off a
  piece and map it executable. That breaks §3's "attenuation is monotonic … no
  handle is ever wider on the far side" and defeats §2.5's `MapExecute`
  example. The same holds for `Transfer`, `Map` and the rest.

## The fix

- **A `Split` piece is minted with the parent handle's rights** (the entry the
  op was invoked through), not `memory_rights()`.
- **A `Carve` window is minted with the parent window handle's rights.**
- Check every other op that mints a new object of the same kind from a held
  handle for the same flaw. A mint that creates a *different* kind (`Map`'s
  Mapping, which has its own vocabulary) keeps its default set: rights don't
  carry across kinds. Report what you checked.
- **Spec:**
  - §2.5 and §3 state the rule: a piece, or a carved window, carries its
    parent handle's rights.
  - An open patch, SO-40 (spec only, in review), adds a "Not yet enforced: a
    `Split` piece is minted with `memory_rights()` …" marker to §2.5's
    `MapExecute` passage. If SO-40 has merged when you fetch, remove that
    marker. If not, state the rule in §2.5 in your own words; the lead
    resolves the overlap.
  - No issue numbers; 80 columns.

**Air: SO-67.p1 (revision 2), approved.** It closes the amplification I raised on SO-40.
- **The fix is at the mechanism.** `Split` and `Carve` mint with `obj.rights`, the handle the op went through, instead of `memory_rights()`/`iomemory_rights()`, which are now documented as the boot-root sets only. The audit is right: `Map` makes a different kind (its Mapping, which SO-40's ceilings will cap), and `MINT_OP` and `give` already intersect.

That placement is right: it's an enforced invariant, not a not-yet-enforced item.
- **The tests have controls.** `split_keeps_rights`, `split_keeps_rights_twice` (a piece of a piece) and `carve_keeps_rights` each first use the derived handle successfully (a read-write map), so the closing `access denied` fault means the missing bit, not a dead handle.
