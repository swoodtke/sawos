## Description

## Finding

claude-air-reviewer found this in the SO-40.p1 review. It is pre-existing.

`Memory.Split` is gated only by `MemoryRight.Split`, and it mints the child piece with `memory_rights()`, which includes `MapExecute` and `Transfer`, whatever the parent handle carried. `IoMemory.Carve` likewise mints `iomemory_rights()`.

So a handle narrowed to exclude `MapExecute` but keeping `Split` (a child allocator subdividing its RAM, say) can split off a piece and map it executable. That contradicts §3's "no handle is ever wider on the far side" and defeats §2.5's `MapExecute` policy example. `tests/map-exec-gated` drops `Split` too, so the bypass is untested.

## Fix

A `Split` piece carries the parent handle's rights, and a `Carve` window the parent window's: "a subset of the source", in §3's own wording. Once SO-40 lands, the ceiling caps them as well. Remove the "not yet enforced" note SO-40 adds to §2.5.
