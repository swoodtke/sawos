## The defect (the reviewer's code reading; confirm it)

A reply (`PipeRequestOp.Reply`, and `ReplyWait`'s reply leg) is invoked through
the `PipeRequest` handle that names the exchange, and it carries handles in its
send record. Nothing stops a carried word from being that same request handle:
- `check_send` (`kernel/core/dispatch.saw` ~3013) never compares a carried
  word with the invoking handle.
- In `pipe_reply_status`'s `Ok` arm, `hold_staged` (refs.saw) unbinds the word
  and stages a reference on the exchange's own obligation column.
- `consume_entry` (dispatch.saw ~3888) then unbinds the same index again.
  `unbind_handle` (`kernel/core/objects.saw` ~530) does not check that the
  index is bound, so the generation bumps twice and the `Handle` quota row is
  credited twice. Then it unrefs a reference the handle no longer holds.
- The staged obligation is minted into the client, so a `PipeRequest` naming
  the exchange outlives its settle.

## Fix

1. **Refuse it as a caller error.** In the reply paths (and any other op that
   consumes its invoking handle after staging carried handles: check every
   caller of `consume_entry` and every op whose invoking handle is consumed),
   a carried word equal to the invoking handle is a `BadArg` fault on the
   caller, raised before anything is staged or released. Put the check where
   one place covers every such op, if that is clean (`check_send` taking the
   invoking word, say); otherwise at each op. State the rule in each op's doc
   and in spec §3's handle-transfer passage.
2. **Harden `unbind_handle`:** a call on an index that is not bound is a kernel
   bug. Make it `fatal_kernel`, so a double unbind is a kernel stop rather than
   a silent double credit. Check every caller first: if any legitimately
   unbinds an unbound index, stop and ask.

After the fix the case asserts the `BadArg` fault.

**Air: SO-55.p1, approved.**
- **The fix closes the class.** `check_send` faults `BadArg` on a carried word equal to the invoking one, before any lookup or staging, and only `Reply` (`obj.handle`) and `ReplyWait` (`word`) pass one. Those are the ops that stage and then consume their own handle. `post` and `call` don't consume their inlet, and carrying it is an ordinary move. Comparing whole words is enough because a `PipeRequest` has no `Mint`, so its one word is its only name.
- **The hardening is safe.** I read all ten `unbind_handle` callers in the patched tree, and each reaches it with the index bound:
  - `release_handle` and `slab_donate` (through `memory_arg`) fault on `Unbound` first;
  - `give`'s `move_entry` runs after `give_faults`;
  - `waiter_add`'s consuming arm runs after the target lookup;
  - `pipe_create`'s rollback unbinds the inlet it just minted;
  - `park_resolve` and `consume_entry` run after their op's lookup, with the self-carry now refused;
  - `hold_staged` and `release_carried` look up each word and skip `Unbound`, so a word repeated in a record is stale the second time;
  - the teardown's close-all skips `Unbound`.
  
  So `fatal_kernel` is unreachable from userspace and catches only a kernel bug.
- **The tests** drive the raw floor for both `reply` and `reply_wait`. Your unfixed probe answered `Ok` with the twice-bumped word `0x208`, so both arms discriminate.
