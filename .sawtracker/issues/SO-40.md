## Description

## Ruled design (user, Nov 9)

This replaces the original "typed `Process.give(process:)`" proposal. Its
motivating case (a launcher withholding a child's own Process rights) is met by
ceilings; handing a supervisor a narrowed handle to a child waits for a real
debugger (see SO-7 for Process handles in messages).

**Per-process rights ceilings.**
- Each process carries one rights ceiling per object kind.
- Every handle the kernel **mints** into a process's table is capped by that
  table's ceiling for the handle's kind: getters (`ProcessSelf`, `ThreadSelf`,
  `ClockGet`, and every later one), the creation ops, the System-level
  interrupt bind, the sender handle and the observe ops (later units). The
  ceiling is the table the handle lands in, so a cross-process create (SO-41)
  is capped by the caller's.
- Handles a process **receives** (give, message) are not capped: their sender
  already chose their rights.
- `process_self`'s keep mask stays: rights = default & ceiling & keep.

**Narrowing.** A new `ProcessOp.RestrictRights(kind, mask)` sets the named
process's ceiling for `kind` to `old & mask`. It only narrows, so it is valid at
any time (it affects future mints, never existing handles). It is gated by a
new `ProcessRight.RestrictRights` on the handle used, and a process may apply
it to itself (a pledge-style privilege drop).

**Inheritance and the ceiling source.** `SystemOp.ProcessCreate` takes an
optional Process handle naming a ceiling source. The child's ceilings are the
creator's ceilings intersected with the source's, so naming a process can only
restrict; any handle naming the process suffices, whatever its rights. With no
source the child inherits the creator's. Root starts unrestricted.

**No parent/child relation in the kernel** (§5.3 stands). A spawn service
records parents itself, by pid (see the pid issue).

**Air: SO-40.p1, changes requested: the capped/uncapped line leaves four mint sites unclassified, and one of them already undoes attenuation today.** The spec checks I can do pass: lines ≤ 80, the markers are right since nothing is built, and it's consistent with SO-41 (a cross-process create lands in, and is capped by, the caller's table) and SO-54 (the ceilings live in the body, `Gone` → `Revoked`).

**1. "From nothing" is defined by provenance ("not derived from a handle the process already holds"), and four kernel mints don't fit either side.** Every `mint_handle` in dispatch.saw (at f0b2bb7) is:
- **named and capped:** the getters (377, 528, 568), the creation ops (1460 Event, 1542 Waiter, 1596 Thread, 1880 Timer), `InterruptBind` (1512), `PipeCreate` (3146-3147), the claim (3383) and the obligation (3603);
- **excluded, correctly:** the `MINT_OP` sibling (2504), whose result IS a subset of its source;
- **unclassified:**
  - `ProcessCreate`'s new Process handle (1025, a System op, not a creation op "through a Process handle");
  - `Memory.Map` → Mapping (2723, `mapping_rights()`);
  - `Memory.Split` (2791, `memory_rights()`);
  - `IoMemory.Carve` (2914, `iomemory_rights()`).
  Each "derives from a held handle", so by the text it's uncapped. Yet each mints a fresh default set that is not a subset of anything the process holds.

Suggested rule, stated by result rather than provenance: **every mint is capped by the ceiling for its kind except a `MINT_OP` sibling (already a subset of its source) and a received handle (the sender chose).** That puts `ProcessCreate`, `Map`, `Split` and `Carve` under the ceilings and leaves no fresh default set uncapped.

**2. Pre-existing and adjacent, but it's why item 1 matters: `Split`/`Carve` amplify today.**
- `Split` is gated only by `MemoryRight.Split` and mints the child piece with `memory_rights()`, which includes `MapExecute` (rights.saw), whatever the parent handle carried. `Carve` likewise mints `iomemory_rights()`, `Transfer` and `Map` included.
- So §2.5's own example, "a launcher writes 'this child may map its RAM and may never map it executable' with `Memory.mint(rights:)`", holds only if the mask ALSO drops `Split`. `tests/map-exec-gated` does drop it ("`Split` is absent too"), so the bypass is untested. A child that keeps `Split` to subdivide its RAM, an allocator say, splits off a piece and maps it executable.
- That also contradicts §3's "no handle is ever wider on the far side": a split piece is wider than the handle it came from.
- Two fixes, not exclusive:
  - (a) a split/carve child takes the PARENT handle's rights ("a subset of the source", §3's own wording), which closes it at the mechanism;
  - (b) item 1's rule, which bounds it by the ceiling.
  (a) belongs in a kernel issue of its own. Until then, §2.5's `MapExecute` example should say `Split` must go too.

**3. A ceiling that leaves no rights:** when `default ∩ ceiling ∩ keep` is empty, does a creation op still create the object (quota charged, a table slot used) and hand back a zero-rights handle, or is the mint refused? A launcher that sets a kind's ceiling to nothing most likely means "may not create this kind". Please say which, and with which answer (a fault or a status).

**4. The ceiling source, "any handle naming the source process serves, whatever its rights":** add the consequence for the client. A client should pass a `MINT_OP` sibling narrowed to no rights. A full-rights Process handle given to a spawn service also hands it `RestrictRights` (now in the default set), `Map`, `Give` and the rest over the client.

## The contract (spec.md §2.7 "Rights ceilings"; read it in full)

- **What a process carries:** one ceiling per handle kind, in the **body**.
  Root's are all-ones, and a new process inherits its creator's.
- **What is capped:** every handle the kernel mints into a table, by the
  ceiling for the handle's kind. The result is the op's own rights (default
  set or derived) ∩ ceiling ∩ keep mask.
- **The exceptions:** a `MINT_OP` sibling, and a received handle (a give, a
  message's carried handles, a boot record). Neither is capped.
- **An empty result:** the op still succeeds, with a no-rights handle.
- **`ProcessOp.RestrictRights(kind, mask)`:**
  - gated by `ProcessRight.RestrictRights` (in the Process default set);
  - narrows only, and works at any time;
  - through a `Gone` handle, answers `Revoked`;
  - an unknown kind is a `BadArg` fault.
- **`SystemOp.ProcessCreate`'s optional ceiling source,** a third argument: a
  Process handle word, or `NO_HANDLE` for none.
  - The child's ceilings are the creator's ∩ the source's.
  - Any rights on the source handle serve.
  - A source naming a `Gone` process answers `Revoked` with nothing created.
- **Scope addition (user, Nov 11; see the SO-40 comment): a read of a
  process's ceilings.**
  - A Process op, for example `ProcessOp.Ceiling(kind)`, answers the named
    process's ceiling for one kind.
  - Gate it with a right on the handle used. Add a `ProcessRight` for it, or
    reuse `Stats` if that reads more naturally; decide, say why, and add it to
    the spec.
  - A process reads its own; a supervisor reads its child's.
  - Through a `Gone` handle it answers `Revoked`.

**Kinds** use `HandleKind` from SO-68 (merged): the published, stable kind
numbers. `RestrictRights` and the ceiling read take a `HandleKind`.

## The mint sites (the lead's census of `mint_handle(` at today's main; re-check)

Every site goes through one helper that applies the ceiling. Don't sprinkle
the intersection by hand.
- **Capped:**
  - the getters (`ProcessSelf`, `ThreadSelf`, `ClockGet`);
  - the creation ops (Thread, Event, Waiter, Timer, Pipe: both ends);
  - `InterruptBind`;
  - `ProcessCreate`'s handle on the new process;
  - `Split` and `Carve` (whose rights are now the parent's, then capped);
  - `Map`'s Mapping;
  - the claim `Post` mints;
  - the obligation `Take` mints, and the obligation a resumed fused call mints
    (refs.saw ~1649).
- **Not capped:**
  - `MINT_OP` (dispatch ~2502);
  - `move_entry` (give, refs ~1173);
  - `mint_staged` (message receive, refs ~1330).
- **Boot:** root's bootstrap mints (process.saw ~910, ~926, ~1028–1035) run
  under root's all-ones ceiling. Say whether they go through the helper
  anyway.

## The change

1. **Storage:** a ceiling array in the process body, indexed by `HandleKind`.
   Initialise root's to all-ones. Initialise a created child's from the
   creator's (∩ the source's) at `ProcessCreate`.
2. **The capping helper,** used at every capped site.
3. **The ops:** `RestrictRights` and the ceiling read in `ProcessOp`;
   `ProcessCreate`'s third argument; the new right(s) in `ProcessRight` and the
   Process default set; `static_assert`s as the tables have.
4. **Typed tier:**
   - `Process.restrict_rights(…)` as **one labeled overload per kind**
     (`restrict_rights(event: mask)`, `restrict_rights(thread: mask)` and so
     on, as the `give` overloads are shaped), so no kind number reaches typed
     callers;
   - the same labeled shape for the ceiling read;
   - `System.process_create(…, ceiling_source: &Process?)`, or the existing
     method's natural extension. If an `Optional` parameter conflicts with
     CLAUDE.md's Optional discipline, use an overload instead; absence is a
     real domain value here, so an Optional argument may be fine. Decide and
     say why.
   - Floor: the raw ops.
5. **Spec:** remove the §2.7 "Not yet enforced" note for ceilings and the
   §2.8 `ProcessCreate` row's marker. State the ceiling-read op and its right.
   No issue numbers; 80 columns.

## Tests (use SO-68's `rights()` to observe capped rights)

1. **A child can't regain a withheld right.** A launcher restricts the child's
   Event ceiling, dropping `Signal`, before `start`. The child's
   `event_create` yields an Event whose `rights()` lacks `Signal`, and a
   signal on it faults `AccessDenied`.
2. **A process narrows itself.** A process restricts its own Thread ceiling,
   and a later `thread_create`'s handle reports the narrowed rights.
3. **Inheritance.** A child created by a restricted process inherits the
   restriction: its own mint reports it.
4. **The ceiling source.** A spawn-style create names a third process as the
   source, and the child gets the intersection.
5. **Exceptions:**
   - a handle **given** to a restricted child keeps the giver's rights
     (`rights()` on the child side);
   - a `MINT_OP` sibling of a received handle is not capped.
6. **Empty ceiling:** the op succeeds, with `rights() == 0`.
7. **Ceiling read:** a launcher reads its child's ceiling after restricting it;
   a child reads its own.
8. **`Gone`:** `RestrictRights`, the ceiling read and a `Gone` ceiling source
   each answer `Revoked`.
9. **`Split`/`Map`/`ProcessCreate` capped:** at least one of these
   derived-object sites shows the cap.

Mutation-check: bypass the helper at one capped site, skip inheritance, and
cap a received handle; each must fail a test.
