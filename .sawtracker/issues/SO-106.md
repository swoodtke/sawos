## Description

**The spec patch for the kernel-contract changes of the image and packaging design (SO-95; tracker doc `SO:images-and-packaging`, revision 6).** The user has ruled on the design (Nov 14). Its units U2 (per-board limits and linked slab areas) and U5 (the quota door) change what the kernel promises, so each begins here, in `spec.md`, which the user reads before either is built, as they read the pool spec.

**What changes in the spec, with the design's rule for each.**

1. **Limits are per board, and an image can raise them** (design section 6; rule 6.4 and its table).
   - Which numbers are a board's (set in its HAL: the grant-row budget, the handle table, the domain pool), which are a board's defaults that an image may raise (the slab floors and the quota defaults), and which are derived from those. The spec says what the relations are and that they hold, not today's values, which the code prints.
   - §2.8's sentence that donation makes "the compiled limits a floor and capacity policy, decided by the deployment rather than by the build" changes: the build decides the capacity a machine boots with, and donation still raises it at run time.
   - The grant-row budget is no longer one number sized by the smallest board (§5b's "tier-2 floor" paragraph and the `DEFAULT_QUOTA_MAPPINGS` sentences).

2. **Linked slab areas and the boot table at version 5** (design 6.1, 6.7; §12 of the spec).
   - After the region table's rows comes nothing, or one whole block naming, per slab kind raised, an area of the kernel's own memory; anything else stops the boot. An area's length is a whole number of that kind's slots or the boot stops; each area lies inside the kernel's own zeroed memory and no two meet, or the boot stops; each becomes one extent of its slab, before the first process exists.
   - What a process can observe: a kind's capacity at boot is its floor plus its area, and `available`-style readers and donation behave as they do after a donation.
   - The block also carries the children's quota defaults for the image.

3. **The quota door** (design section 7; rule 7.2 gives proposed text).
   - `ProcessOp.QuotaSet` and `QuotaGet` under a new process right: a launcher sets a quota row of a child that is created and not yet started; never above the launcher's own row for that kind; the `Mapping` row bounded by the board's budget less the image's rows (rule 7.4); the unlimited sentinel refused; the answer order beside the op's other refusals; what `QuotaGet` reports.
   - It is a per-process cap and not a budget shared with the launcher (the review's t3).
   - §2.9's and §11's "there is no per-create quota argument in v1" change to say what there is.

4. **Root's interfaces, where the kernel already does what the design says** (design 8.1): the order in which a process's boot set drains (records come out in the order queued; one a `Start` took is stepped over), which the reviewer checked against the kernel and the spec does not state. This is true today and carries no marker.

5. **Deferred, one sentence each, no design:** per-process limits beyond the quota door (a handle table sized per process, a pool per process, rights ceilings from a declaration) are SO-105; several devices per driver, and limits that can be lowered, are reserved.

**How it is written.** As the pool spec was: the text states the model as it will be, and every sentence the kernel does not yet do carries a marker, `(not yet enforced: limits)` for 1 and 2 and `(not yet enforced: quota-door)` for 3, with a transition note saying what the kernel does until each part lands. No sentence without a marker may be false of main.

**Not in this patch:** the description file formats, the builder, the stock root's plan (they are tools and userspace convention, not kernel contract, and the design keeps them out of `spec.md` except §12's boot record); anything of SO-102, SO-103 or SO-105.

**Lead: SO-106.p1 is up: the spec for per-board limits, linked slab areas and the quota door.** It changes `spec.md` only (nothing in the gate reads it). **The user reads it before U2 or U5 is built;** the diff is at `.claude/lead/so106-spec.diff` in the lead's checkout.

**What it states.**
- **§2.8, "The machine's limits":** which numbers a board sets in its HAL (the grant-row budget, the segment bound, the domain pool, and the handle table), which are slab floors with their compile-time relations, that an image raises what a machine boots with by linking an area per slab kind, that an image's totals keep the floors' relations, and that donation raises capacity from there. The old sentence that capacity is "decided by the deployment rather than by the build" now reads: the build decides the capacity a machine boots with, and donation raises it at run time.
- **§12, "After the rows, the image's slab areas":** the table is at version 5; after its rows comes nothing or one whole block (a magic word, the number of areas, a quota default for each kind, then an entry per area: a slab kind, a base, a length); anything else stops the boot. Each stop is listed: an unknown or repeated kind; a length that is not a whole, nonzero number of slots, or a misaligned base; an area not wholly inside the kernel's own zeroed memory, or meeting another; a capacity past the slab's ceiling; boot capacities that break a relation of §2.8; a quota default out of its bounds. Then each area is one more extent of its slab, before the first process exists; a kind raised by its image accepts one donation fewer; no handle names an area.
- **§2.7, "Quota rows":** `ProcessOp.QuotaSet(kind, limit)` under `ProcessRight.QuotaSet`, on a child that is created and not started; a row is a cap on one process and not a budget shared with the launcher; a limit is below the unlimited sentinel, at most the caller's own for every kind but `Mapping`, a `Handle` limit at most `MAX_HANDLES`, a `Mapping` limit bounded by the child's free grant rows, and never below what the child already holds; the answers in order (the dispatch's; the kind; the process's state; the limit; then `NoResource` for a `Mapping` limit past the child's rows). `ProcessOp.QuotaGet(kind)` under `Stats` answers the limit and the use in one word.
- **§2.9:** a child's rows replace "no per-create quota argument in v1"; the transition note for both markers is at the section's end.
- **§5b.1:** the grant-row budget is the board's. **§12:** the boot set's drain order, which is true today, stated unmarked. **§11:** the plan names the deferred items (per-process limits beyond the door, a per-process stack, several devices per driver, limits that can be lowered).
- Everything the kernel does not yet do carries `(not yet enforced: limits)` or `(not yet enforced: quota-door)`. The author checked each unmarked sentence against the code and lists where (in the hand-back; the lead has it).

**Choices the author made where the design left one, for the user and the reviewer.**
1. `QuotaSet`'s answer order: faults before the machine's status; the kind before the process's state, as `RestrictRights` does.
2. Through a `Gone` child's handle `QuotaSet` is the `BadState` fault, as `Start` and `Give` are, and not `Revoked`; §2.10's table gains it as an exception.
3. A `Handle` limit above `MAX_HANDLES` is a `BadArg` fault, though a process is not told that number. The author's reason: it is the number of the board the image was built for. To confirm.
4. "Never below what the child holds" covers every kind, not only `Handle`: a created child can already be charged threads, events, Waiters, pipes and mappings made through its handle.
5. `QuotaGet`: one word, the limit in bits 0 to 15 and the use in bits 16 to 31; `Revoked` through a `Gone` handle.
6. An image's quota defaults can only raise the compiled ones, as its slab areas only raise.
7. The kernel's boot refusals include the relations the design gave the builder, as its backstop.

**Where the design and the code disagree, found while writing** (the spec follows the code where it is about today):
- The design's derivation "the Mapping slab is four times the processes" does not hold at the compiled floors (8 against 12), and test images keep the floors; it is not among the kernel's boot refusals and is not in the spec. **This needs settling before U2: either the floor moves or the derivation is the builder's alone.**
- `QuotaKind` and the unlimited sentinel are kernel-internal today; the door needs both published in the ABI.
- The `Mapping` bound is the child's actual free rows after its image is placed, not the budget less a fixed four.

**Already false of the spec on main, found on the way and not fixed here except where a sentence was being rewritten:** §2.1's claim that a ring cannot fill stops holding once threads are donated past the floor (the new §2.8 text says it holds up to the floor); the removed §5b.1 paragraph said no in-tree target consumed the tier-2 price, which riscv32 and the C3 do.

Approved patch SO-106.p1 (revision 1)

**Approved (reviewer, Nov 14), revision 1.** Every sentence the patch states without a marker is true of the kernel at `4eee2aaf`, as far as I checked them below, and the marked text follows the design's revision 6 with the author's seven choices, each stated. Two of the points the note raises have an answer from me; both are for the user's reading and neither needs the patch held. Notes: `.build/scratch/air-review/so106_p1/` on the Air.

**Unmarked sentences, checked against the source.**

- **§2.8's floors and their relations** (`kernel/core/limits.saw`): records are `PROCESS_RECORDS_PER_BODY` × `MAX_PROCESSES` by definition; attachments are events + interrupts + timers + records; `MAX_PROCESSES <= hal.PROT_DOMAIN_SLOTS` is asserted; each of the nine quota defaults is asserted below its slab (the handle default below the table); `PIPE_INFLIGHT` is 2 × `MAX_THREADS`.
- **The board's numbers:** each of the three HALs sets `GRANT_ROW_BUDGET`, `MAX_ROOT_SEGMENTS` and `PROT_DOMAIN_SLOTS` (8, 7, 256 on the S3 and riscv32; 9, 8, 5 on arm64), and the build asserts the budget, and the segments plus a stack, each within the grant record's nine.
- **The transition note's "limits":** `MAX_HANDLES` is `kcore.limits`' 16; the mapping default is asserted against `MIN_GRANT_ROW_BUDGET` (8) and each board's budget against that minimum; the kernel accepts exactly its own table version.
- **§2.9's rows** (`install_quota_limits`): root's are the sentinel but for `Mapping`; a child's are the compiled defaults; both mapping rows are clamped to the free grant rows after the image. The sentinel is a `UInt16` 0xFFFF, so `QuotaGet`'s sixteen bits each for limit and use is the ledger's own width.
- **"Created or mapped through its handle ... is charged to it":** `ThreadCreate`, `EventCreate`, `WaiterCreate` and `PipeCreate` charge the named process and mint into the caller's table; a mapping charges its target.
- **§12's boot stops:** more rows than the two slabs together, a kind's slab running out, and "no handle table room for the boot regions" are each a `fatal_image`.
- **The drain:** the cursor steps over a record `start(boot_tag:)` took and answers the rest in queue order.
- **§2.8's ring sentence:** `Post` into a full ring answers `WouldBlock`; `Call` parks.

**One pointer for U2, not a fault of the text.** §2.9 now says root's mapping row is clamped "to the Mapping slab's capacity at boot", unmarked. That is true today only because the capacity at boot is the floor: the code clamps to the constant `MAX_MAPPINGS`, and the boot's row bound reads `MAX_MEMORIES + MAX_IOMEMORIES` the same way. When an area can raise a kind, both have to read the capacity (the design's t13 and t14), or these two sentences stop being true the day the marker comes off.

**On the author's choice 3, which asks to be confirmed: I would make it a status.** A `Handle` limit above `MAX_HANDLES` is a `BadArg` fault in the patch. The kernel's own rule for a fault on a number is that the maximum is published and the caller chose the number (`pipe_post`: "The maximum is published and the caller chose the number"). `MAX_HANDLES` is not readable by any op: `QuotaGet` on root answers the sentinel. The patch's reason for making a `Mapping` limit past the child's rows a status, "a fact ... the launcher never parses", holds here word for word. And SO-105 will make the table's size a per-process number, which moves the bound again. So: `NoResource`, as for `Mapping`; or publish the number on System and keep the fault. The other three `BadArg` cases are numbers the caller can read (its own limit, the child's use) or chose (the sentinel), and are right as faults.

**On "the Mapping slab is four times the processes", which the note says needs settling: it is the builder's alone.** Nothing in the kernel needs it: a process with no mapping runs, and a process that asks for one more than the slab holds is answered `NoResource` after its quota, which is §2.9's policy first. It is a default the builder derives so that an image's children can each spend their default, the same kind of number as the board's quota defaults, and it belongs where those are derived. The floors (8 against 12) then need no change, and the spec is right to leave it out of the boot refusals.

**The other six choices** (the answer order; `BadState` through a `Gone` child; "never below what the child holds" for every kind; `QuotaGet`'s one word and `Revoked`; defaults that only raise; the kernel's refusals as the builder's backstop) I agree with. Choice 4 is what the charging code requires, as checked above.
