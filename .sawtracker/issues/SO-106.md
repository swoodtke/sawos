## Description

**The spec patch for the kernel-contract changes of the image and packaging design (SO-95; tracker doc `SO:images-and-packaging`, revision 6).** The user has ruled on the design (Nov 14). Its units U2 (per-board limits and linked slab areas) and U5 (the quota door) change what the kernel promises, so each begins here, in `spec.md`, which the user reads before either is built, as they read the pool spec.

**What changes in the spec, with the design's rule for each.**

1. **Limits are per board, and an image can raise them** (design section 6; rule 6.4 and its table).
   - Which numbers are a board's (set in its HAL: the grant-row budget, the handle table, the domain pool), which are a board's defaults that an image may raise (the slab floors and the quota defaults), and which are derived from those. The spec says what the relations are and that they hold, not today's values, which the code prints.
   - §2.8's sentence that donation makes "the compiled limits a floor and capacity policy, decided by the deployment rather than by the build" changes: the build decides the capacity a machine boots with, and donation still raises it at run time.
   - The grant-row budget is no longer one number sized by the smallest board (§5b's "tier-2 floor" paragraph and the `DEFAULT_QUOTA_MAPPINGS` sentences).

2. **Linked slab areas and the boot table at version 5** (design 6.1, 6.7; §12 of the spec).
   - After the region table's rows comes nothing, or one whole block naming, per slab kind raised, an area of the kernel's own memory; anything else stops the boot. An area's length is a whole number of that kind's slots or the boot stops; each area lies inside the kernel's own zeroed memory and no two meet, or the boot stops; each becomes one extent of its slab, before the first process exists.
   - What a process can observe: a kind's capacity at boot is its floor plus its area, and `available`-style readers and donation behave as they do after a donation.
   - The block also carries the children's quota defaults for the image.

3. **The quota door** (design section 7; rule 7.2 gives proposed text).
   - `ProcessOp.QuotaSet` and `QuotaGet` under a new process right: a launcher sets a quota row of a child that is created and not yet started; never above the launcher's own row for that kind; the `Mapping` row bounded by the board's budget less the image's rows (rule 7.4); the unlimited sentinel refused; the answer order beside the op's other refusals; what `QuotaGet` reports.
   - It is a per-process cap and not a budget shared with the launcher (the review's t3).
   - §2.9's and §11's "there is no per-create quota argument in v1" change to say what there is.

4. **Root's interfaces, where the kernel already does what the design says** (design 8.1): the order in which a process's boot set drains (records come out in the order queued; one a `Start` took is stepped over), which the reviewer checked against the kernel and the spec does not state. This is true today and carries no marker.

5. **Deferred, one sentence each, no design:** per-process limits beyond the quota door (a handle table sized per process, a pool per process, rights ceilings from a declaration) are SO-105; several devices per driver, and limits that can be lowered, are reserved.

**How it is written.** As the pool spec was: the text states the model as it will be, and every sentence the kernel does not yet do carries a marker, `(not yet enforced: limits)` for 1 and 2 and `(not yet enforced: quota-door)` for 3, with a transition note saying what the kernel does until each part lands. No sentence without a marker may be false of main.

**Not in this patch:** the description file formats, the builder, the stock root's plan (they are tools and userspace convention, not kernel contract, and the design keeps them out of `spec.md` except §12's boot record); anything of SO-102, SO-103 or SO-105.
