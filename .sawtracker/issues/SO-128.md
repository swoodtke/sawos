## Description

**Unit U4 of the image and packaging design (SO-95): generated link addresses.** Today every board keeps hand-written link scripts for each resident image (riscv32's `root.ld`, `child.ld`, `child2.ld`, `child3.ld`; the S3's `root.ld`, `child.ld` and one child flash slot), and the builder gives process `i` the `i`-th region above root's, each as long as root's, refused past the default process range. That layout does not fit the box: the useless box needs four flash slots on the S3 (root, the GPIO driver, the PWM driver, the controller) and has one, and it does not fit the C3, whose child region is shorter than root's.

**Build what the design's §5.2 and §14's U4 list** (`SO:images-and-packaging` revision 6; the owner approved it Nov 14), for every board in the tree:
- **Computed regions and named ranges**, each process's RAM region placed by the builder from the board's ranges (`board.toml`) and the process's declared RAM, with each named range budgeted separately and an over-asked range refused by name (§5.2);
- **`ram = "fast"` enforced** (a declaration that asks for it gets the board's fast range, or the build is refused by name);
- **Artifacts named by instance** (rule 5.11: one process per instance, its ELF and objects named so);
- **Flash slots computed** on an in-place board: as many as the image's processes, each placed by the builder, with the S3's `.drom` moved behind the last slot (§5.2's note), and a generated `image_slots.ld` in place of the hand-kept `CHILD_IMAGE_SLOT`/`ROOT_IMAGE_SLOT` symbols; the board check's linker-script reader (`sosimage board`) follows;
- **The hand-kept per-image scripts gone**: one generated script per process, from the board's user script and the computed addresses; the runner builds every case through them;
- **Not in this unit:** the PSRAM range and the `-r8` board (SO-102's units C and D generate their script once this lands), the stock root (U6), lowering any limit.

**What must not move:** every case's console transcript and totals stay as they are; where an address a case prints moves, say which and why. Images the gate builds byte for byte today (`uart_service_ns16550` from its description) keep doing so unless an address legitimately moves, and then both sides move together.

**Cases:** an image with more processes than today's hand-kept slots on riscv32, arm64 and the S3 (four processes on the S3, each running); a region refused past its range, by name; a `ram = "fast"` refusal; two instances of one package named apart. The C3's smoke keeps passing on generated scripts. The review standard (the owner's ruling, Nov 15): every check and refusal has a case or builder test that goes red when it is removed or inverted; list the mutants.
