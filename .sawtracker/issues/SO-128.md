## Description

**Unit U4 of the image and packaging design (SO-95): generated link addresses.** Today every board keeps hand-written link scripts for each resident image (riscv32's `root.ld`, `child.ld`, `child2.ld`, `child3.ld`; the S3's `root.ld`, `child.ld` and one child flash slot), and the builder gives process `i` the `i`-th region above root's, each as long as root's, refused past the default process range. That layout does not fit the box: the useless box needs four flash slots on the S3 (root, the GPIO driver, the PWM driver, the controller) and has one, and it does not fit the C3, whose child region is shorter than root's.

**Build what the design's §5.2 and §14's U4 list** (`SO:images-and-packaging` revision 6; the owner approved it Nov 14), for every board in the tree:
- **Computed regions and named ranges**, each process's RAM region placed by the builder from the board's ranges (`board.toml`) and the process's declared RAM, with each named range budgeted separately and an over-asked range refused by name (§5.2);
- **`ram = "fast"` enforced** (a declaration that asks for it gets the board's fast range, or the build is refused by name);
- **Artifacts named by instance** (rule 5.11: one process per instance, its ELF and objects named so);
- **Flash slots computed** on an in-place board: as many as the image's processes, each placed by the builder, with the S3's `.drom` moved behind the last slot (§5.2's note), and a generated `image_slots.ld` in place of the hand-kept `CHILD_IMAGE_SLOT`/`ROOT_IMAGE_SLOT` symbols; the board check's linker-script reader (`sosimage board`) follows;
- **The hand-kept per-image scripts gone**: one generated script per process, from the board's user script and the computed addresses; the runner builds every case through them;
- **Not in this unit:** the PSRAM range and the `-r8` board (SO-102's units C and D generate their script once this lands), the stock root (U6), lowering any limit.

**What must not move:** every case's console transcript and totals stay as they are; where an address a case prints moves, say which and why. Images the gate builds byte for byte today (`uart_service_ns16550` from its description) keep doing so unless an address legitimately moves, and then both sides move together.

**Cases:** an image with more processes than today's hand-kept slots on riscv32, arm64 and the S3 (four processes on the S3, each running); a region refused past its range, by name; a `ram = "fast"` refusal; two instances of one package named apart. The C3's smoke keeps passing on generated scripts. The review standard (the owner's ruling, Nov 15): every check and refusal has a case or builder test that goes red when it is removed or inverted; list the mutants.

**Lead rulings on the implementer's clarification (Nov 15), within the approved design:** (1) S3 flash slots are fixed and equal, from `board.toml` (the design's §3.1: count 4 at 128 KiB each); an image's children take slots 0..n-1, more children than `count` is refused by name, `.drom` sits at the end of the slot range, root's slot is unchanged, so no S3 image moves. (2) A region is the span of every segment the loader places in RAM (all of them on copied and translated boards, the writable one on in-place boards), measured by a first link, rounded to max(grain, 16), plus the HAL's `ROOT_STACK_LEN`; packed from root's top in image order inside each range, each range budgeted; pools after the processes, and images with pools allowed. Rule 5.6's formula was the in-place case of this. (3) Test images keep runner-given addresses (rule 5.5) through generated scripts that reproduce today's; computed addresses come from descriptions through `sosimage build`, with new cases of root plus four children (three on the S3) including two instances of one package. One address-free template per board replaces the hand-kept per-image scripts.

**Lead: SO-128.p1 is up: generated link addresses** (the design's U4, with the lead's three rulings on this issue). On main; the lead rewrapped two prose lines. Gate on the implementer's machine, diffed against a baseline run of main under the same lock: 1053 / 7 / 65 and 1 board-only, against 1050 / 7 / 62. **No existing case's row or console transcript moved**, every S3 and C3 flash size is the same, and three riscv32 images built through the old and the generated scripts are identical byte for byte. Package lines now name `<pkg>/.build/<triple>/<role>.sosimg`. Both transcripts: scratchpad `SO-128/base-gate.txt`, `new-gate.txt` (on request).

**Ordering:** SO-126 (windowed Saw) is ahead in the merge queue and adds three packages naming `root.ld`/`child.ld`, which this patch removes; SO-100.p1 adds `tests/empty-segment` naming `root.ld`. Whichever merges second takes a one-line `linker-script` change per manifest; the lead will revise this patch when SO-126 lands.

**Scripts.** One address-free user script per board (`hal/<board>/user/user.ld`); for each process the builder writes a short script setting `SOS_REGION_BASE`, `SOS_REGION_LEN`, `SOS_STACK_LEN` (and `SOS_SLOT_BASE`, `SOS_SLOT_LEN` on the S3) and INCLUDE-ing the script the manifest names; `sosimage package PROFILE PROCESS` links it through Blade (`--linker-script`, `--out-dir`). Removed: riscv32's `root.ld`, `child.ld`, `child2.ld`, `child3.ld`, the S3's and the C3's `root.ld` and `child.ld`. 335 manifests change: 317 only in their `linker-script` lines, 18 with comments that named a child position.

**Regions** (computed only for images built from descriptions; test images keep the runner's addresses, rule 5.5): the span of the segments the loader places in RAM (all of them on copied and translated boards, the writable one on the S3), measured by a first link, plus the HAL's `ROOT_STACK_LEN` (HAL facts record version 3); packed in image order after root's region, each range budgeted, pools after the processes (images with pools are no longer refused), an overrun refused naming the process and the range; `ram = "fast"` takes a fast range or is refused by name. **One departure from the lead's ruling:** on a copied board a region is page-aligned, not aligned to max(grain, 16): at a base off the page, ld.lld loads the ELF headers into the page below as a fourth segment outside the region, which the loader refuses; `PHDRS` in the template avoids it but moves every riscv32 image by 12 bytes. `region_align` states it; the S3 stays at 16, arm64 at its page.

**Slots (S3):** `count = 4` equal 128 KiB slots of the board's range, child i in slot i, more children than slots refused; `esp32s3.ld` INCLUDEs a per-image `image_slots.ld` (`ROOT_IMAGE_SLOT`, its length, `DROM_FLASH` at the range's end, so `.drom` stays at 0x20_0000) and one `.childimg<i>` section per child with a fit ASSERT. `sosimage board` holds `board.toml`'s slots to the profile's; ABI.md §13 says what a slot is.

**`uart_service_ns16550`'s bytes move, not its transcript:** its description is built first and the case takes the builder's images and regions (driver 0x80240000 + 0x19000, client 0x80259000 + 0x16000); FROM_FILES compares the case's rows, limits and link with the description's.

**New cases:** `launch_all` (riscv32, arm64, flat: root, three instances of one package named apart, a fourth process, a pool; the S3: three instances in slots 0 to 2 and a pool), `too_many_processes` and `too_many_children` (S3). New builder tests `layout_plan`, `process_description`. **Mutants:** 35, each red (25 builder, 10 runner), table in the scratchpad.

**Not held by a case, stated:** a translated board skipping the relink (a saving, not a check); the slot of a test image's second child on the S3 (no S3 test image has two children: two 0x18000 regions do not fit below `RAM_TOP`; the described image covers slots 0 to 2); the Python image path's slot refusal (not in the gate; checked by hand).

**For U6:** the stock root still stops after binding; `build` does not yet set `ARENA_SIZE` from a declaration's `arena`; `imageplan` and `[[setup]]` untouched. **For SO-102 C and D:** the r8 board's PSRAM range needs only its `board.toml`; placement already handles a slow default range.
