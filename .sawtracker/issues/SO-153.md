**`MemoryOp.Map` faults the caller on two kinds of received Memory it can't check first.** Making it answer a status instead would close the gap. The two shapes:
- an allocation off the grain (a boot allocation);
- an allocation in flash (the S3's blob rows).

Both are `BadArg` faults today. A server that maps a client's Memory can't check for either before it calls `map`, so a hostile client can fault the server. `ProcessCreate` already answers the same shapes with a status, on the same reasoning.

Make `Map` answer a status for both, with spec text and cases; every check needs a case that goes red when removed or inverted. No client on the gate or the S3 holds such a Memory today. Found by the SO-150 design (`SO:mapping-len`).

**Lead: SO-153.p1 is up: `Map` answers a status for a region it can't map, not a fault of the caller.** One commit, rebased onto current main.

**The answers.**
- **Now `NoResource`:**
  - a zero-length region;
  - a region that wraps the address space;
  - a base or length off `PROT_GRAIN`;
  - a region `hal.map_source_ok` refuses (flash on the S3).

  Nothing is installed or charged.
- **Still faults:** the access word, the rights, the target handle, and `room` off the grain. `room` is the caller's own argument, so its check moved ahead of the region checks.
- **Order:** the region statuses come before `Revoked`, `QuotaExceeded` and `install_row`'s own `NoResource`.

**Why `NoResource` and not a new status.** `NoResource`'s doc already covers "the caller offers something else", and `BadImage` means "not a process image". One question for you: a retry-minded caller could read `NoResource` as transient. Would you rather have a dedicated status?

**Docs:**
- spec §2.5's `Map` answer order, the §8 status list, and the S3 blob-row note;
- `status.saw`'s `NoResource`;
- `Process.map` and `sos_memory_map`;
- pktring's attach recipe;
- netdevproto, hciproto and sockproto, which now say `map` refuses these shapes with `NoResource`, counted, ending the connection.

**Cases:**
- `map_base_off_grain` becomes `map_refused_regions`, which runs clean on riscv32, arm64 and riscv32-flat. Root maps a pool allocation, then four that each answer `NoResource`: length off the grain, base off the grain, past the end of the address space, and length zero. The runner flags `wrapping_region` and `empty_region` build the rows.
- On arm64 no wrapping row can be built (signed 64-bit lengths, 39-bit base), so the case prints that line instead.
- `destination_off_grain` drops its fault-ending map and exits clean.
- `flash_region` (S3) maps the flash allocation and gets `NoResource`, then ends as before.

**Mutants.**
- Red:
  - the wrap check removed (riscv32 and flat, a kernel overflow panic; arm64 can't build the shape);
  - the base-grain check removed, on all three profiles;
  - the length-grain check removed, on all three profiles;
  - the S3 flash answer turned back into a fault.
- **Survivors, equivalences:**
  - `len == 0` removed: every HAL's `map_source_ok` requires `base < top`, which refuses an empty region.
  - `map_source_ok` disabled on the S3: `install_row`'s `map_target_ok` refuses flash with the same `NoResource`.

  Both are kept as defence in depth. Say if you'd rather drop them and document the HALs as the contract.

**Totals:** `make sos-test` passed 1349, and the S3 smoke 224 with 5 board-only, `flash_region` green. After a final doc rewrap only the three touched cases were rerun.

Approved patch SO-153.p1 (revision 1)

**Approved.** `Map` now answers `NoResource` for every region shape a server handed a client's Memory couldn't have checked. `install_row` already answers only statuses, so after this no region shape faults the caller at `map`; only the caller's own arguments still do.

**My mutants** (main suite, every profile, and the S3 smoke for the flash row):

| mutant | red on |
|---|---|
| the grain answer turned back into a `BadArg` fault | `map_refused_regions` |
| the base half of the grain check removed | `map_refused_regions` |
| the length half removed | `map_refused_regions` |
| the empty-or-wrapping answer turned back into a fault | `map_refused_regions` ("past the end of the address space") |
| `map_source_ok`'s answer turned back into a fault | `flash_region` on the S3 |

The last survives the main suite because no gate board has a region `map_source_ok` refuses.

**Your two equivalences hold:**
- **`len == 0`:** every HAL's `map_source_ok` refuses an empty range. riscv32 (and the flat profile through it), arm64 and the C3 test `base < top`; the S3 and r8 go through `process_ram`, which returns false for `base >= top`.
- **The S3's `map_source_ok`:** `install_row` asks `hal.map_target_ok` over the placed range and answers `NoResource`. On the S3, which doesn't translate, that range is the flash region itself, and `process_ram` refuses it.

**Open, the owner's:** your question of a dedicated status in place of `NoResource`, since a retry-minded caller could read `NoResource` as transient.
