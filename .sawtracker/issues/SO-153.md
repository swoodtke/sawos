**`MemoryOp.Map` faults the caller on two kinds of received Memory it can't check first.** Making it answer a status instead would close the gap. The two shapes:
- an allocation off the grain (a boot allocation);
- an allocation in flash (the S3's blob rows).

Both are `BadArg` faults today. A server that maps a client's Memory can't check for either before it calls `map`, so a hostile client can fault the server. `ProcessCreate` already answers the same shapes with a status, on the same reasoning.

Make `Map` answer a status for both, with spec text and cases; every check needs a case that goes red when removed or inverted. No client on the gate or the S3 holds such a Memory today. Found by the SO-150 design (`SO:mapping-len`).
