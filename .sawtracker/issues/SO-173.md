## The reviewer's open comments on the design that land in this unit

These threads are still open on `SO:virtio-net`. Build to the corrected
version.

1. **MTU (t16).** §1.2's row takes `MTU` whenever it is offered, but then a
   device offering, say, 9000 is accepted, and a 2048-byte slot can't meet
   §5.1.4.2's MUST: enough receive buffer for one packet of size `mtu` plus
   the Ethernet header.
   - §3.1.1 lets a driver read the device configuration before accepting
     features, so read `mtu` first.
   - Take `MTU` only when a frame of `14 + mtu` fits a slot as the driver
     lays slots out. Otherwise decline it, and report `MTU_STACK` as when it
     isn't offered.
   - `drivers/virtio/src/transport.saw` reads `mtu` only after negotiation
     today (around l.373–392), so the change belongs there.
   - A fake-device hosted test offers an `mtu` too large for a slot. It
     expects `MTU` declined and a working device at 1500. It must go red
     when the fit check is removed.
2. **The pool record's rights (t21).** The driver mints the client's ring
   with `Map | Transfer` and sends it in the `Attach` reply (§5.2). An
   allocation inherits its pool handle's rights, `mint` needs `Mint`, and
   sending needs `Transfer`. So the driver's pool record, in the declaration
   and in `[ceilings]`, must keep `transfer` and `mint` beside `allocate`,
   `map` and `physical`. Drop §2.5's comment saying it is kept without them.
3. **The DMA sentence (t24).** Write §10's sentence with these corrections:
   - Pin is "the only op that answers an object's physical bounds", not "the
     only way to learn an object's physical address". On riscv32 and the
     flat profile, `Mapping.base()` already is the physical address.
   - Pin also answers for boot allocations, not only for allocations made
     contiguous.
   - Root holds `Physical` with no launcher granting it.
   Check every claim against `spec.md` as it stands after K1, K1s and B1.
4. **Every program ends by itself (t25).** Root stops the machine only once
   every child has ended, and with `on-exit = "report"` it stops with
   `EXIT_OK`.
   - `net-ping` needs an explicit end on every failure path, a refused
     `Attach` and `PeerClosed` included: print the status and exit nonzero.
   - In `net_legacy`, `net_wrong_device` and `net_no_device` the driver ends
     at start, so the pinger must end on its first refusal and not wait.
   - No case may reach the harness timeout. §7.1's and §7.3's text about
     root stopping on the driver's exit code is stale; follow root's actual
     behaviour (`root/`).
5. **`Attach`'s other answers (t31).** `Allocate` can also answer
   `QuotaExceeded` or `NoResource`, not only `NoMemory`. Answer each as a
   status, and keep the connection. Pin each mapping with a hosted test or
   a case where one can produce it; if none can, say why in your note.

**The five review comments on SO:virtio-net**
1. **t16 MTU.**
   - `transport.saw`'s `read_offered_mtu` reads `mtu` under `ConfigGeneration` before any feature is accepted, and refuses below 68 there.
   - `mtu_fits` holds `14 + mtu <= frame_bytes`, and `Lifecycle.begin(registers:frame_bytes:)` takes `MTU` only when it fits.
   - Hosted `mtu_past_a_slot` offers 9000: `MTU` is declined and the device reports 1500. It also checks that 2034 is taken and 2035 declined. Forcing `fits = true` turns it red.
   - A second hosted test holds that the mtu is read before `DriverFeatures` is written, and that 67 and a generation that never settles are refused.
   - `exp5.sh` with `host_mtu=1400` read mtu 1400 at config offset 10.
2. **t21.** The pool record and `[ceilings] pool` keep `allocate`, `map`, `physical`, `mint` and `transfer`. The memory ceiling is `transfer`, `mint`, `map`, `physical`.
3. **t24.** spec §2.5's DMA paragraph:
   - Pin is "the one op that answers an allocation's physical bounds", for contiguous and boot allocations.
   - Root holds `Physical` from boot; another process only when its launcher grants it.
4. **t25.**
   - Every pinger failure path prints and exits 1, `PeerClosed` included.
   - In `net_legacy`, `net_wrong_device` and `net_no_device` the driver exits 1 at start, the pinger's `Attach` answers `PeerClosed`, and root stops cleanly. No case reaches the timeout.
5. **t31.** `refusal()` turns `NoMemory`, `QuotaExceeded` or `NoResource` from the allocate, the map or the sibling's mint into the status `NoMemory`, and keeps the connection; any other status stops the driver.
   - There is no hosted test, because the driver depends on `sos`.
   - `NoMemory` is reachable by A3-5's `net_attach_too_large`.
   - `QuotaExceeded` is unreachable. The driver allocates at most two Memories (its declared row) and maps at most three. A second `Attach` is refused `Attached` before any allocation. An image's `quota` can only raise a row.
   - `NoResource` (a full slab or handle table) could come from an image `[limits]` that leaves the Memory slab exactly full at the ring's allocation. That case isn't built.

**Survivors:**
- **M07** (no RX buffers posted at `Attach`): the first TX-completion interrupt posts them, and no peer script speaks first.
- **M13** (`release_tx` removed from `send_tx`): `drain` still releases. It matters only for length-refused frames, which A3-5's `net_tx_length` pins.
- **M15** (`MTU` taken whatever its size): 1400 fits, so the gate can't see it. The hosted `mtu_past_a_slot` is red.

**Pinned elsewhere:**
- "No address before its pin" and "no unpin before a confirmed reset" are pinned by `drivers/virtio`'s hosted lifecycle tests (`early_unpins`, `stray_addresses`). The driver unpins only through `give_up`.
- The ring and range checks, the `NotAttached`/`Attached`/`Busy` order and the client sibling without `Physical` are A3-5's cases and pktring's hosted tests.

**Where the code and the design differ**
1. **`num_buffers`.** QEMU 11.1.3 leaves the field unwritten without `MRG_RXBUF`: a stored 0xABCD read back unchanged. So the design's `num_buffers == 1` check refused QEMU on the first receive.
   - The check is kept, and `post_rx` now stores 1 before posting. A silent device reads 1, and a device that writes 0 or 2 is still refused. A hosted test pins this.
   - The alternatives were to accept 0, or to negotiate `MRG_RXBUF`.
2. **Stack.** A process stack is 16 KiB, and the start-up's frames take about 7 KiB.
   - The driver prints through `Printable` wrappers and small functions, and only its loop waits: handlers answer with `reply`/`reply_with`, not `reply_wait`. Its peak is about 13 KiB.
   - The pinger's work frame (about 12.7 KiB, plus about 6 KiB on netstack's send path) runs on a worker thread with a static stack of 8192 words.
3. **The pipe-outlet ceiling** is `["wait"]`: the consuming attach checks only `PipeOutletRight.Wait`.
4. **`Attached` is `NoCopy`.** Otherwise a `match` over `Attached?` binds a copy, and the ring's cursors are lost.
5. **"Client gone" ordering.** The pinger calls `process().exit(code)` while still holding its end, so the kernel's exit line comes before the driver's `client gone`.
6. **`abandoned=N`.** The driver's last line adds it, for A3-5's `net_wait_abandoned`.

**What §7.2's transcript can't force**
- `root: ping ended status=65536` is left out. The kernel's `SOS: process exit: code=0 process=2` asserts the pinger's code instead.
- In the three refusal cases, the pinger's `PeerClosed` line and root's reports aren't ordered against each other, so the pinger's line is left out.
- Everything else is causal.

**Held for a revision.** The driver is careful, and the lifecycle order holds on every path I followed. Five things need changing first: an obligation two earlier approvals left for this unit, one real bug, two missing barriers and a double read. Each can be pinned now.

I applied the patch to ba75d53d and ran it with sawlang v0.24.5. An agent read the driver and library against §3.9 and §4–§5 of the design, and I rechecked each finding below against the code.

**1. arm64's rows 0, 8 and 16 are still unpinned** (owed from SO-168.p1's approval). I ran SO-168's mutants on `net_ping` and `net_mtu`:

| mutant | result |
|---|---|
| `row24_line73` | red |
| `row16_line63` | survives |
| `row0_base_page1` | survives |

Every arm64 net image names `VIRTIO24`, and `net_bus` is per profile (`"net_bus": 24`), so no case can put the device on another row. `virtio_probe_empty_arm64` names `VIRTIO0`, but its transport is empty, and so is the page the base mutant moves it to.
- Give a case its own bus (a case-level `net_bus` over the profile's).
- Spread the arm64 images over the rows, each on a case that takes interrupts, so a wrong line hangs it. For example `net_mtu` on `VIRTIO0`, `net_no_status` on `VIRTIO8`, `net_ping` on `VIRTIO16`, and one case kept on `VIRTIO24`.
- Then each row's base mutant and line mutant must go red.

**2. A `WaitEvent` answered at once loses its event when the reply doesn't land** (`main.saw`, `wait_event`'s `if let event = take_event(&var s)` arm).
- `take_event` clears the pending state, and `answer()` discards the reply's result. The held path puts the event back (`answer_held` → `restore_event`); this one doesn't.
- The spec makes it reachable: "a staged message is still owed to a live outlet whatever became of its claim" (the `PipeReply` row of the ledger). `answer`'s own comment names the tell's case.
- **Scenario:** the client attaches (`link_pending = true`), then tells a `WaitEvent` (posts it and drops the claim). The driver takes `LinkUp`, the reply answers `PeerClosed`, and the event is gone. The next `WaitEvent` is held until frames move, and with a stable link the client never learns the link's state. A lost `RxReady` or `TxDone` can be recovered from the ring's index words; a lost link event cannot.
- **Fix:** `restore_event` on a failed reply here too.
- **Case:** that scenario, deterministic: attach, tell a `WaitEvent`, then call `WaitEvent` and expect `LinkUp`. Under the bug it hangs.

**3. Two barriers are missing.** QEMU can't show either, but the fake device logs every barrier (`EVENT_BARRIER`), so a hosted test can pin each one.
- **Zeroing before the queues are given to the device.** `setup_queues` zeroes the plan with `store32`, then `program` writes the addresses and `QueueReady`, and `go_live` writes `DRIVER_OK`, with no barrier between. The library's only barriers are in `kick` and `pending`. A Normal-memory store is not ordered before a later Device-memory store as the device sees it, on arm64 or RISC-V (Linux's `writel` carries `__iowmb()` for this). The device may then read a stale `avail.idx` and stale descriptors from the pool's last use, outside any current pin, before the first `kick`'s barrier. That is the hazard the pin design exists to close.
  - **Fix:** `hardware.barrier()` after the zeroing loop, before the first `program`.
  - **Pin:** a hosted test that a barrier lies between the last zeroing store and the first `QueueReady` write.
- **The interrupt's status read before the used `idx`.** `interrupt()` calls `take_interrupt` (read `InterruptStatus`, write the ACK), then `drain` → `pending` loads the used `idx`. The only barrier follows that load. Nothing orders the Device read before the Normal load (Linux's `readl` has `__iormb()`), so the `idx` can be read stale after the status was taken and acknowledged, and the completion waits for unrelated traffic.
  - **Fix:** a barrier after `take_interrupt`.
  - **Pin:** a hosted test that the barrier lies between the status read and the `idx` load.
- The design's §4.3/§4.6 ordering paragraph lists only the kick and used-side barriers. It wants both added.

**4. `mtu` is read twice, and the value used is not the one checked.**
- `begin` reads it (`read_offered_mtu`) and applies `mtu_fits`. `read_config` reads it again and checks only `>= MTU_MIN`.
- That second value becomes `reported_mtu()`, which sets `Server.mtu`, the TX bound and `AttachInfo.mtu`.
- So a device that offers 1400 and shows 1500 at `read_config` gets frames sized for 1500. That breaks the library's own "read once, checked, then acted on" rule.
- **Fix:** carry the checked value in `Negotiated`, or refuse a second read that differs.
- **Pin:** a fake device that changes `mtu` between the reads.

**5. Pins to settle in this patch or name for A3-5:**
- **t31's `NoResource`:** the note says it is reachable through an image `[limits]` that leaves the Memory slab full at the ring's allocation, and that case isn't built. Make it A3-5's beside `net_attach_too_large`, or build it here. The `QuotaExceeded` argument holds: one Attach per driver life, two Memories, three Mappings, and `quota` only raises a row.
- **M07 (no receive buffers at `Attach`):** it survives because every peer frame answers a guest frame. `burst` answers a request too, so no script speaks first. A peer script that sends first, with a client that only listens, pins it deterministically: QEMU queues the frame until a buffer is posted, so under M07 the client hangs. Name it for A3-5, or add it.
- **`row7_len200`** (riscv32 and flat) survives. That looks like a real equivalent. The riscv32 transports sit 0x1000 apart, but each one's registers and configuration are 0x200 bytes (QEMU's virtio-mmio region, as arm64's row comment says), and nothing reads past them. Say so beside the row.
- **`peer_status_gone`** still survives. Each nonzero exit of the peer prints an `error:` line the log comparison sees, so only a crash after its last line is the status check's alone. Name that at `_check_peer`.

**What holds** (checked against the code):
- **t16:** the mtu is read before `DriverFeatures` and the fit is `14 + mtu <= SLOT_BYTES`, the posted length. 2034 is taken and 2035 declined.
- **t21:** the pool record and ceiling keep `mint` and `transfer`.
- **t24:** the spec's paragraph makes all three corrections, and its quarantine claim matches the Pin rules.
- **t25:** every pinger failure path prints and exits 1, and the refusal cases' `expect_clean_exit` forces the pinger's end.
- **`num_buffers` pre-store:**
  - The store comes before `kick`'s barrier.
  - A chain is re-posted only after its completion is taken.
  - A device writing 0 or 2 is still refused.
  - It masks only a device that writes nothing there.
- **Device checks:** the used `idx` advance, the element `id` and `len`, and the RX `len` bounds.
- **The client ring:** every index and length is read once.
- **Unpin and unmap** happen only from `give_up` after `reset_device` reads 0.
- **The SO-164 obligations:** row 7's line is red on riscv32 and flat.
- **The stacks**, summed from each linked image's prologues along the deepest call path (the flat ELFs are riscv32's byte for byte):

  | stack | riscv32 | arm64 |

  The driver's bound includes a panic inside a panic and a step that can't happen (an allocation from a fixed builder). Its failure-free peak is 8160 on riscv32 and 10320 on arm64. Your "about 13 KiB" is arm64's. The driver makes no indirect call, and the client's one (`run_thread` → `work`) has one target.
