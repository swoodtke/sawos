## Description

**Found in the review of SO-92.p4; older than that patch (main's kernel does the same).**

On arm64, `process_create` into a destination of 0x201000 bytes prints `grant outside the page-granular window: 0x0000000040400000` and the machine halts. The page-granular window a process's rows must lie in is 2 MiB, and a destination past it is caught only when the row is installed, by a kernel stop.

`process_create`'s own comments make a destination it will not use a status, and a process must not be able to stop the machine with an argument.

**The fix:** `process_create` refuses, before anything is recorded, a destination (and any segment or stack row placed in it) that the HAL cannot grant, with the status it already answers for an unusable destination; the HAL publishes the bound it needs for that (it already publishes `device_window_ok` for the device side). A case on arm64: the create is refused, nothing is left behind (the quota and the slabs read the same), and the next create works.

The reviewer's probe is `probe_b4_bigdest` in chat file f71 (`SO-92/step-overlap/reviewer-probes/probes_b.diff` in the lead's scratchpad).

**Lead: SO-99.p1 is up.** Gate on the implementer's machine: 792 / 6 / 39 (main's 789 plus the new case on three profiles).

**The fix is one question, asked earlier.** The HAL already publishes the bound as `map_target_ok` (a `map` asks it and answers `NoResource`). `process_create` now asks it of the linked range, `hal.map_target_ok(dest.link_base, dest.link_top())`, after `map_source_ok` and before the image is validated or anything is taken, and answers `BadImage` with the other refused destinations. No new status, op or HAL function.

**The routes to the stop, as found:** the stack row (any destination over 2 MiB on arm64: the window is the first 4 MiB of RAM and a child links 2 MiB into it), and a copied segment's row, which `check_segment` keeps below the stack, so the one check covers both. A region placed high is not a route on arm64 (the child's addresses do not depend on where the frames are). Segments used in place do not exist on arm64. `MemoryOp.Map`, the stats-region map and `IoMemoryOp.Map` already ask before they install. Root's image uses HAL constants, which is the stop's remaining use.

**Reproduced on main** (the new case, unfixed kernel, arm64): `SOS: grant outside the page-granular window: 0x0000000040400000` and the machine stops.

**Case `destination_past_window`** (three profiles, a 5 MiB pool). arm64: a destination of 2 MiB and a page is `BadImage`; the room for processes and for handles reads the same after it as before (root counts creates into a small destination and System siblings until each is refused, before and after; there is no op that reads a ledger row); exactly 2 MiB then loads. riscv32 and riscv32-flat: both destinations load, since those profiles have no translation window and `map_target_ok` there is `map_source_ok`'s question over the same range.

**Mutants, arm64, each alone:** the bound a grain high (the 2 MiB create refused) and a grain low (the stop); the check dropped (the stop); the check moved after the first record (`room for processes 2 then 1, for handles 7 then 6`); the HAL's `<=` to `<` (2 MiB refused).

**Spec:** §2.7 gains the sentence (a destination whose rows the profile cannot grant at the addresses the child would see them at is `BadImage` before a record or a body is taken) and §5b.1's arm64 row states the window. `hal/arm64/kernel/ABI.md`'s `map_target_ok` row said `BadArg` for a map; it says `NoResource` now, and `BadImage` for a create.

**Noticed by the implementer, for a later look:** the ESP32-S3's `prot_update` asserts `same_bytes` over a row's rounded length, the one other kernel-stopping assert on a row path; it found no way to reach it.
